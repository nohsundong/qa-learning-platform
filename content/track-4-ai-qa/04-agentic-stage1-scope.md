## 개념 설명

### Agentic Testing 이란

지금까지의 AI 활용은 **사람이 묻고 AI가 답하는** 방식이었다. Agentic Testing은 다르다. **AI가 스스로 판단하고 행동하는 루프**를 만든다.

```text
[기존] 사람: "이 요구사항으로 TC 만들어줘" → AI: TC 출력 → 사람: 검토·실행

[에이전트] 
   PR 이 올라옴
     ↓
   ① 에이전트가 diff 와 요구사항을 읽고 검증 범위를 판단
     ↓
   ② TC 를 생성하고 우선순위를 매김
     ↓
   ③ 실제로 앱을 조작하며 탐색, 엣지 케이스 발견
     ↓
   ④ 실패하면 원인을 분석하고 테스트를 스스로 수정
     ↓
   사람: 결과를 검토하고 승인/반려
```

**사람이 사라지는 게 아니라 사람의 역할이 이동한다.** 실행자에서 **검토자·설계자**로 옮겨간다.

이 트랙의 4~7편에서 네 단계를 하나씩 실습한다. 각 단계는 **독립적으로도 가치가 있으므로** 전부 구현하지 않아도 된다. 실제로 대부분의 팀은 ①②만으로도 큰 효과를 본다.

### 왜 1단계가 가장 중요한가

**"무엇을 테스트할 것인가"** 는 트랙 1에서 배운 회귀 범위 산정이다. 그리고 이게 QA 업무 중 **가장 시간이 많이 들고, 가장 자주 틀리는** 부분이다.

```text
개발자: "이번 PR 은 유틸 함수 하나만 고쳤어요. 간단합니다."
QA:    (그 유틸을 47곳에서 쓰고 있다는 걸 아무도 모름)
       → 회귀 범위를 좁게 잡음 → 운영 장애
```

**코드를 읽어야 알 수 있는 것**이라 QA가 놓치기 쉽다. 그래서 이 판단을 자동화하면 가치가 크다.

### 1단계 에이전트가 하는 일

```text
입력
  - PR diff (변경된 파일과 라인)
  - 요구사항 문서 / 티켓 설명
  - (있으면) 과거 장애 이력, 기존 TC 목록

처리
  1. 무엇이 바뀌었는지 파악 (기능 추가? 수정? 리팩터링?)
  2. 변경된 코드를 호출하는 곳을 역추적
  3. 영향 범위를 직접/간접으로 분류
  4. 리스크 점수 산정 (트랙 1의 발생가능성 × 영향도)
  5. 실행할 테스트 범위 제안

출력
  - 영향 범위 목록 (근거 포함)
  - 실행할 테스트 목록
  - 확인이 필요한 질문
```

### PR diff 에서 무엇을 읽어내는가

diff는 단순한 텍스트 변경이 아니다. **변경의 성격**에 따라 리스크가 완전히 다르다.

| 변경 유형 | 리스크 | 신호 |
|---|---|---|
| **공통 모듈·유틸 수정** | 매우 높음 | 호출처가 많다. 영향 범위 폭발 |
| **함수 시그니처 변경** | 높음 | 호출부를 다 고쳤는가? |
| 조건문 변경 (`>` → `>=`) | 높음 | **경계값 테스트 필수** (트랙 1) |
| DB 스키마 변경 | 매우 높음 | 롤백 불가. 마이그레이션 검증 |
| 의존성 버전 업 | 중~높음 | 변경 로그 확인 필요 |
| 설정값 변경 | 중간 | 환경별로 다르게 적용되는가 |
| 새 API 엔드포인트 추가 | 중간 | 기존 기능엔 영향 적음 |
| 주석·문서만 변경 | 없음 | 테스트 불필요 |
| 로그 추가 | 낮음 | 단, 개인정보가 로그에 찍히는지 확인 |

**조건문의 부등호 변경**을 자동으로 잡아내는 것만으로도 유용하다. `amount > 30000` 이 `amount >= 30000` 으로 바뀌었다면, 정확히 30,000원 케이스를 반드시 테스트해야 한다.

### 프롬프트 설계

```text
너는 QA 회귀 범위 분석 에이전트다.

## 입력
### PR 정보
제목: [PR 제목]
설명: [PR 설명]

### 변경된 파일 목록
[git diff --stat 결과]

### 변경 내용
[git diff 전문 또는 핵심 부분]

### 참고: 각 변경 함수의 호출처
[grep 결과를 함께 제공 — 이게 정확도를 크게 올린다]

## 분석 규칙
- 변경 유형을 먼저 분류하라 (기능추가 / 버그수정 / 리팩터링 / 설정 / 의존성).
- 조건문의 비교 연산자가 바뀌었으면 경계값 테스트를 반드시 제안하라.
- 공통 모듈이 바뀌었으면 호출처를 근거로 간접 영향을 나열하라.
- diff 에 없는 코드의 동작을 추측하지 마라. 필요하면 "확인 필요"로 남겨라.
- 영향 없음으로 판단한 것도 명시하고 이유를 적어라.

## 출력 (JSON)
{
  "change_type": "...",
  "summary": "이 PR이 무엇을 바꾸는가 (2문장)",
  "direct_impact": [
    { "area": "...", "reason": "...", "evidence": "파일:라인" }
  ],
  "indirect_impact": [
    { "area": "...", "reason": "...", "evidence": "호출처 경로" }
  ],
  "no_impact": [{ "area": "...", "reason": "..." }],
  "risk_score": { "likelihood": 1-5, "impact": 1-5, "reason": "..." },
  "required_tests": [
    { "test": "...", "priority": "High|Medium|Low", "why": "...", "technique": "경계값|상태전이|..." }
  ],
  "open_questions": ["요구사항이나 코드만으로 판단할 수 없는 것"]
}
```

**`"evidence"` 필드가 이 설계의 핵심이다.** 근거로 파일과 라인을 대라고 강제하면, **지어낸 영향 범위를 걸러낼 수 있다.** 근거를 확인해서 실제로 그 코드가 없으면 환각이다.

**`"no_impact"` 를 요구하는 것도 중요하다.** "영향 없음"을 명시적으로 판단하게 하면, 그냥 안 본 것과 보고 제외한 것이 구분된다. 트랙 1의 "테스트하지 않을 항목을 명시하라"와 같은 원리다.

### 호출처 정보를 함께 주는 것이 결정적이다

AI에게 diff만 주면 **"이 함수를 누가 쓰는지"를 모른다.** 그래서 간접 영향을 못 찾는다.

```bash
# 변경된 함수를 찾아 호출처를 수집한다
git diff origin/main...HEAD --name-only
git diff origin/main...HEAD | grep '^[+-].*function \|^[+-].*const .* = (' 

# 각 함수명으로 호출처 검색
grep -rn "calculateShipping" src/ --include="*.ts" --include="*.tsx"
```

이 결과를 프롬프트에 함께 넣으면 정확도가 크게 오른다. **에이전트에게 "도구"를 준 것**이고, 이게 에이전트 설계의 기본이다 — 스스로 검색할 수 있게 하거나, 검색 결과를 미리 넣어준다.

MCP를 쓸 수 있는 환경이면 AI가 직접 `grep` 을 실행하게 할 수도 있다 (3편).

### 실제 워크플로로 만들기

```yaml
# .github/workflows/qa-scope.yml
name: QA 회귀 범위 분석

on:
  pull_request:
    types: [opened, synchronize]

permissions:
  contents: read
  pull-requests: write        # PR 코멘트 작성 권한

jobs:
  analyze:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0      # diff 를 위해 전체 히스토리 필요

      - name: diff 와 호출처 수집
        run: |
          git diff origin/${{ github.base_ref }}...HEAD > /tmp/pr.diff
          git diff origin/${{ github.base_ref }}...HEAD --stat > /tmp/pr.stat
          node .github/scripts/collect-callers.mjs > /tmp/callers.json

      - name: AI 분석
        env:
          API_KEY: ${{ secrets.AI_API_KEY }}
        run: node .github/scripts/analyze-scope.mjs > /tmp/scope.json

      - name: PR 에 코멘트
        uses: actions/github-script@v7
        with:
          script: |
            const scope = require('/tmp/scope.json');
            const body = [
              '## 🤖 QA 회귀 범위 분석 (제안)',
              '',
              `**변경 유형**: ${scope.change_type}`,
              `**요약**: ${scope.summary}`,
              '',
              '### 직접 영향',
              ...scope.direct_impact.map(i => `- **${i.area}** — ${i.reason} \`${i.evidence}\``),
              '',
              '### 간접 영향',
              ...scope.indirect_impact.map(i => `- **${i.area}** — ${i.reason} \`${i.evidence}\``),
              '',
              '### 권장 테스트',
              ...scope.required_tests.map(t => `- [${t.priority}] ${t.test} _(${t.technique})_ — ${t.why}`),
              '',
              '### 확인 필요',
              ...scope.open_questions.map(q => `- ${q}`),
              '',
              '---',
              '_이 분석은 제안입니다. QA 검토 후 범위를 확정하세요._',
            ].join('\n');
            await github.rest.issues.createComment({
              ...context.repo, issue_number: context.issue.number, body,
            });
```

**`permissions` 를 최소로 지정한 것에 주목한다.** `contents: read` 와 `pull-requests: write` 만 준다. 기본 권한을 그대로 쓰면 에이전트가 저장소를 수정할 수 있게 된다.

### 이 단계에서 사람이 하는 일

에이전트 출력을 그대로 믿지 않는다. **검토 체크리스트**가 있다.

```text
□ evidence 로 제시한 파일:라인이 실제로 존재하는가 (환각 점검)
□ 간접 영향을 놓친 곳은 없는가 — 내가 아는 도메인 지식과 대조
□ no_impact 로 분류한 것이 정말 영향 없는가
□ 리스크 점수가 비즈니스 임팩트를 반영하는가 (AI 는 이걸 모른다)
□ open_questions 가 실제로 애매한 지점을 짚었는가
□ 과거 장애 이력이 있는 영역이 빠지지 않았는가   ← AI 는 이력을 모른다
```

**마지막 두 개가 사람의 고유 영역이다.** 에이전트는 코드는 읽지만 **"작년에 이 모듈에서 사고가 났다"** 는 걸 모른다. 그 정보를 프롬프트에 넣어주는 것도 방법이다 (10편에서 다룬다).

### 정확도를 측정하는 법

도입하고 끝내면 안 된다.

```text
매 릴리즈 후
  1. 운영에서 발견된 결함(탈출 결함)이 있었는가
  2. 그 결함의 영역을 에이전트가 영향 범위에 넣었는가
     - 넣었는데 테스트를 안 했다 → 사람의 판단 문제
     - 안 넣었다 → 에이전트 개선 필요 (프롬프트, 입력 정보)
  3. 반대로, 에이전트가 제안했는데 실제로는 불필요했던 범위는?
     → 과잉 제안이 많으면 아무도 안 읽게 된다
```

**과잉 제안도 문제다.** 모든 PR에 "전체 회귀 필요"라고 하면 신호가 아니라 소음이다. 트랙 3의 알림 피로와 같은 원리다.

## 왜 채용시장이 요구하는가

- **Agentic Testing 은 2026년 채용공고의 최신 키워드**다. 개념을 설명할 수 있고 일부라도 구현해 본 사람은 아직 드물다.
- **"PR diff 를 읽고 테스트 범위를 정한다"** 는 시니어 QA의 핵심 역량이고, 이걸 자동화하려 한다는 것 자체가 그 역량을 이해한다는 증거다.
- 면접에서 **"AI 에이전트에게 QA 업무를 얼마나 맡길 수 있다고 보세요?"** 라는 질문이 나온다. 단계별로 나눠서 답할 수 있으면 강하다.
- **`evidence` 강제, `no_impact` 명시, 권한 최소화** 같은 설계 디테일은 실제로 만들어 본 사람만 말할 수 있다.

## 실습 과제

### 과제 1 — 손으로 먼저 해보기 (15분)

**자동화하기 전에 사람이 어떻게 하는지 알아야 한다.**

오픈소스 프로젝트의 실제 PR을 하나 고른다. (GitHub에서 아무 프로젝트나)

1. diff를 읽고 변경 유형 분류
2. 직접 영향 / 간접 영향을 손으로 정리
3. 각 판단의 근거(파일:라인) 기록
4. 확인이 필요한 질문 3개 도출
5. 걸린 시간 기록

### 과제 2 — 같은 PR로 AI 분석 (15분)

이 레슨의 프롬프트로 같은 PR을 분석시킨다.

| 비교 항목 | 사람(과제 1) | AI |
|---|---|---|
| 직접 영향 개수 | | |
| 간접 영향 개수 | | |
| **AI만 찾은 것** | — | |
| **사람만 찾은 것** | | — |
| evidence 가 실제로 존재하는가 | — | |
| 걸린 시간 | | |

**"사람만 찾은 것"이 무엇인지 분석한다.** 대체로 도메인 지식이나 과거 이력에서 나온다. 그게 사람의 몫이다.

### 과제 3 — 호출처 정보의 효과 (12분)

같은 PR을 두 번 분석시킨다.

- A: diff만 제공
- B: diff + `grep` 으로 수집한 호출처 정보

**간접 영향을 찾는 능력이 얼마나 달라지는지** 측정한다. 이 차이가 "에이전트에게 도구를 준다"는 것의 의미다.

### 과제 4 — 부등호 변경 탐지 (10분)

작은 diff를 직접 만든다.

```diff
- if (amount > 30000) return 0;
+ if (amount >= 30000) return 0;
```

AI에게 분석시키고 확인한다.

| 확인 항목 | 결과 |
|---|---|
| 경계값 테스트를 제안했는가 | |
| **정확히 30000 케이스**를 명시했는가 | |
| 29999 / 30001 도 제안했는가 | |
| 이 함수를 호출하는 곳의 영향을 언급했는가 | |
| 적용 기법을 "경계값 분석"으로 표시했는가 | |

### 과제 5 — 워크플로 구현 (20분)

본인 연습 저장소에서 실제로 만든다.

1. `.github/scripts/analyze-scope.mjs` 작성 (Node 내장 `fetch` 만 사용, 의존성 0)
2. `.github/workflows/qa-scope.yml` 작성
3. `permissions` 를 최소로 설정
4. 테스트 PR을 열어 코멘트가 달리는지 확인
5. **주석만 바꾼 PR**을 열어보고, 에이전트가 "영향 없음"으로 판단하는지 확인

5번이 과잉 제안 여부를 보는 테스트다.

### 과제 6 — 과잉 제안 평가 (10분)

서로 성격이 다른 PR 5개(문서 수정, 스타일 변경, 버그 수정, 신규 기능, 공통 모듈 수정)를 분석시키고 제안 범위를 비교한다.

| PR 유형 | 제안 범위 | 적절한가 |
|---|---|---|
| 문서만 수정 | | |
| CSS 스타일 | | |
| 단일 버그 수정 | | |
| 신규 API 추가 | | |
| 공통 유틸 수정 | | |

**앞 두 개에 큰 범위를 제안한다면 프롬프트를 고쳐야 한다.** 어떻게 고칠지 적는다.

## 자가 체크리스트

- [ ] Agentic Testing 의 4단계를 나열하고 각 단계가 무엇을 하는지 설명할 수 있다
- [ ] 에이전트 도입이 사람의 역할을 실행자에서 검토자로 옮긴다는 것을 이해한다
- [ ] 4단계를 다 구현하지 않아도 ①②만으로 가치가 있다는 것을 안다
- [ ] 1단계(범위 판단)가 가장 가치 있는 이유를 설명할 수 있다
- [ ] PR diff 의 변경 유형별 리스크를 구분할 수 있다
- [ ] 부등호 변경(`>` → `>=`)이 경계값 테스트 신호임을 안다
- [ ] `evidence` 필드를 강제해 환각을 걸러내는 설계를 할 수 있다
- [ ] `no_impact` 를 명시하게 하는 이유(안 본 것과 제외한 것의 구분)를 안다
- [ ] 호출처 정보를 함께 주면 간접 영향 탐지가 크게 좋아진다는 것을 안다
- [ ] "에이전트에게 도구를 준다"는 것의 의미를 설명할 수 있다
- [ ] GitHub Actions 에서 `permissions` 를 최소로 지정할 수 있다
- [ ] 에이전트 출력 검토 체크리스트 6가지를 적용할 수 있다
- [ ] AI가 모르는 것(과거 장애 이력, 비즈니스 임팩트)을 사람이 보완해야 함을 안다
- [ ] 탈출 결함으로 에이전트 정확도를 측정할 수 있다
- [ ] 과잉 제안이 알림 피로를 만든다는 것을 알고 경계한다
