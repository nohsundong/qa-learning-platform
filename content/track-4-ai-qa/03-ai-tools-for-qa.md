## 개념 설명

### QA가 이 도구들을 쓰는 이유

Cursor·Claude Code·Copilot·Windsurf는 개발자용으로 만들어졌지만, **QA에게 더 큰 가치를 주는 지점**이 따로 있다.

| 용도 | 왜 QA에게 유용한가 |
|---|---|
| **코드베이스 질문** | "이 API 호출하는 곳 어디야?" → 회귀 범위 산정 (트랙 1) |
| **PR diff 이해** | 변경 내용을 읽고 무엇을 테스트할지 판단 (트랙 6) |
| 테스트 코드 작성·수정 | 반복 작업 단축 |
| 셀렉터 개선 | 취약한 로케이터 리팩터링 (트랙 3) |
| 로그·에러 분석 | 스택 트레이스에서 원인 좁히기 (트랙 2) |
| 테스트 데이터 생성 | 경계값 조합 데이터셋 |

**첫 두 개가 핵심이다.** 이건 코드를 쓰는 일이 아니라 **읽고 판단하는 일**이고, QA의 본업에 직결된다.

### 도구별 성격

| 도구 | 형태 | QA 관점 강점 | 비용 |
|---|---|---|---|
| **Claude Code** | 터미널 CLI / IDE 확장 / 웹 | 여러 파일을 읽고 작업을 끝까지 수행. 큰 코드베이스 탐색 | 구독 또는 API 종량 |
| **Cursor** | VS Code 기반 에디터 | 코드베이스 인덱싱 + 채팅. 에디터 통합이 매끄러움 | 무료 티어 + 유료 |
| **GitHub Copilot** | IDE 확장 | 인라인 자동완성이 강함. PR 요약 기능 | 유료 (학생·OSS 무료) |
| **Windsurf** | 에디터 | 에이전트형 흐름 | 무료 티어 + 유료 |

**비용 0원 제약 하에서는** Cursor·Windsurf의 무료 티어, Copilot의 학생/오픈소스 무료 자격, 또는 **이 플랫폼의 BYOK AI 패널 + Gemini 무료 티어** 조합으로 학습할 수 있다. 도구별 조작법보다 **컨텍스트 설계와 검증 습관**이 학습 목표이므로 어느 것으로 익혀도 전이된다.

### 컨텍스트가 결과의 90%다

같은 질문도 무엇을 함께 주느냐에 따라 답이 완전히 달라진다.

```text
[나쁨] 이 테스트 왜 실패해?

[좋음] 이 테스트가 CI 에서만 실패한다.
  - 테스트 코드: (파일 첨부)
  - 실패 로그: (Call log 포함)
  - CI 워크플로: (yml 첨부)
  - 로컬에선 100회 중 100회 통과, CI 에선 10회 중 3회 실패
  - 최근 변경: 이 PR 에서 상품 목록 API 에 페이징이 추가됨
  원인 후보를 3개 제시하고, 각각을 어떻게 확인할지 알려줘.
```

**"원인 후보 3개 + 확인 방법"** 형태로 요청하는 게 요령이다. 하나의 단정적 답을 요구하면 AI는 그럴듯한 하나를 만들어낸다. **여러 후보를 요구하면 불확실성이 드러난다.**

### 프로젝트 규칙 파일 — 반복 지시를 없앤다

대부분의 도구가 프로젝트 루트의 규칙 파일을 읽는다. (Claude Code는 `CLAUDE.md`, Cursor는 `.cursorrules` 또는 규칙 설정 등 도구마다 다르다)

QA 프로젝트라면 이런 내용을 넣는다.

```markdown
# 테스트 코드 작성 규칙

## 로케이터
- getByRole > getByLabel > getByTestId 순으로 사용한다.
- CSS 클래스 셀렉터는 금지. 자동 생성 클래스(css-xxx, sc-xxx)는 특히 금지.
- 목록에서 항목을 고를 때 nth() 대신 filter({ hasText }) 를 쓴다.

## 대기
- waitForTimeout 금지. 불가피하면 이유를 주석으로 남긴다.
- networkidle 대기 금지.
- 항상 await expect(locator) 형태를 쓴다. expect(await ...) 금지.

## 구조
- 페이지 오브젝트에 어서션을 넣지 않는다.
- 테스트 데이터는 테스트마다 고유하게 생성한다. 하드코딩 금지.
- try/catch 로 어서션을 감싸지 않는다.

## 검증
- 기대 결과는 실제 계산과 비교한다. 존재 여부만 확인하지 않는다.
- 새 테스트는 --repeat-each=5 로 검증한 뒤 커밋한다.
```

**이 파일 하나가 트랙 3의 안티패턴 대부분을 사전에 막는다.** 매번 "sleep 쓰지 마"라고 말할 필요가 없어진다.

그리고 이 파일은 **팀의 테스트 컨벤션 문서로도 기능한다.** 사람과 AI가 같은 규칙을 본다.

### MCP — 도구를 외부와 연결하기

MCP(Model Context Protocol)는 AI 도구가 외부 시스템에 접근하게 해주는 개방형 규격이다. QA 관점에서 유용한 조합이 있다.

| MCP 서버 | 무엇이 가능해지는가 |
|---|---|
| **Playwright MCP** | AI가 실제 브라우저를 조작하고 접근성 트리를 읽는다 → 자율 탐색 (6편) |
| 파일시스템 | 테스트 코드·로그 파일 직접 읽기 |
| GitHub | PR diff, 이슈 조회 → 회귀 범위 판단 (4편) |
| 데이터베이스 | 정합성 쿼리 실행 (트랙 2) |

**Playwright MCP가 특히 중요하다.** 스크린샷이 아니라 **접근성 트리(구조화된 텍스트)** 를 AI에게 주기 때문에, AI가 화면을 "읽고" 조작할 수 있다. 트랙 4 후반의 Agentic Testing이 이 위에서 돌아간다.

```bash
# Playwright MCP 서버 (오픈소스, 무료)
npx @playwright/mcp@latest
```

**주의**: MCP로 AI에게 DB 접근을 주면 **쓰기 권한은 절대 주지 않는다.** 트랙 2의 안전 수칙이 그대로 적용된다. 읽기 전용 계정만 연결한다.

### QA가 실제로 쓰는 요청 패턴

**1. 회귀 범위 산정**

```text
이 PR diff 를 읽고, 영향받을 수 있는 기능을 나열해줘.
각 항목에 대해:
- 직접 영향 / 간접 영향 구분
- 왜 그렇게 판단했는지 (어느 코드가 근거인지)
- 어떤 테스트를 돌려야 하는지
확실하지 않은 것은 "확인 필요"로 표시하고, 누구에게 무엇을 물어야 하는지 적어줘.
```

**2. 코드베이스 탐색**

```text
`calculateShipping` 함수를 호출하는 모든 곳을 찾고,
각 호출부에서 어떤 인자가 넘어가는지 정리해줘.
```

이건 QA가 **"이 로직이 어디서 쓰이는지"** 를 개발자에게 묻지 않고 스스로 확인하는 방법이다.

**3. 테스트 코드 리뷰**

```text
이 테스트 코드를 CLAUDE.md 의 규칙에 비추어 검토해줘.
위반 사항을 표로 정리하고, 각각 왜 문제인지 설명해줘.
코드를 고치지는 말고 지적만 해줘.
```

**"고치지 말고 지적만"** 이 유용하다. 바로 고치게 하면 무엇이 왜 바뀌었는지 놓친다. 학습 목적일 때 특히 그렇다.

**4. 로그 분석** (트랙 2)

```text
이 로그에서 무슨 일이 있었는지 시간순으로 정리해줘.
- 로그에 실제로 적힌 사실만 쓸 것
- 추론한 부분은 "추정"이라고 표시할 것
- 로그에 없어서 알 수 없는 것은 "확인 필요"로 남길 것
```

### 검증 습관 — 이게 없으면 도구가 위험해진다

AI 도구가 위험해지는 지점은 **자신 있게 틀릴 때**다.

```text
□ 코드를 수정했다면 → 실제로 실행해서 통과하는지 확인
□ API·메서드를 썼다면 → 공식 문서에서 존재 확인 (환각)
□ "이 함수는 X를 한다"고 설명했다면 → 코드를 직접 읽고 대조
□ 여러 파일을 고쳤다면 → git diff 로 전부 확인
□ "안전하게 고쳤습니다"라고 하면 → 무엇을 근거로 안전한지 되묻기
□ 테스트가 통과했다면 → 그 테스트가 실제로 무엇을 검증하는지 확인
```

**마지막 항목이 가장 중요하다.** AI에게 "테스트를 통과시켜줘"라고 하면, 제품을 고치는 대신 **테스트를 약하게 만들어서** 통과시키는 경우가 있다. 어서션을 지우거나, 기대값을 실제값으로 바꾸거나, `try/catch` 로 감싼다.

```typescript
// AI 가 "고친" 결과
- await expect(page.getByTestId('total')).toHaveText('9,000원');
+ await expect(page.getByTestId('total')).toBeVisible();   // ← 통과는 하지만 검증이 사라졌다
```

**초록불이 됐다고 해결된 게 아니다.** 반드시 diff를 읽는다.

### 도구를 쓸 때 하지 말아야 할 것

```text
✗ 사내 코드·로그·개인정보를 무단으로 외부 AI 에 붙여넣기
   → 회사 보안 정책 먼저 확인. 로컬 모델(Ollama) 이 대안
✗ API 키·비밀번호가 포함된 파일을 컨텍스트로 주기
   → .env, 인증서, storageState 파일 주의 (트랙 3)
✗ AI 가 만든 코드를 실행 없이 커밋
✗ "AI 가 그렇게 했다"를 근거로 쓰기
✗ 자동 승인 모드로 파일 수정 권한을 무제한 주기
```

**첫 항목은 실제로 사고가 자주 난다.** 고객 데이터가 든 로그를 그대로 붙여넣는 경우다. 마스킹하거나, 재현 가능한 최소 예시로 줄여서 준다.

## 왜 채용시장이 요구하는가

- 2026년 채용공고에 **"AI 코딩 도구 활용 경험(Cursor, Copilot 등)"** 이 명시되는 경우가 늘었다. 생산성 도구를 쓸 줄 아는지를 본다.
- 하지만 **변별력은 "검증 습관"에 있다.** 면접에서 "AI가 만든 코드를 어떻게 검증하세요?"라는 질문에 구체적인 절차를 말할 수 있어야 한다.
- **AI가 테스트를 약하게 만들어 통과시키는 패턴을 안다**고 말하면 실제로 써본 사람이라는 게 드러난다.
- **MCP로 도구를 연결해 본 경험**은 아직 드물어서 차별화된다. 특히 Playwright MCP는 Agentic Testing의 기반이라 흐름을 이해하고 있다는 신호가 된다.
- **보안 경계를 아는 것**도 평가 요소다. 사내 코드를 외부 AI에 붙여넣지 않는 판단은 신뢰의 문제다.

## 실습 과제

### 과제 1 — 도구 하나 골라 세팅 (15분)

무료로 시작할 수 있는 것을 고른다.

- Cursor 또는 Windsurf 무료 티어
- Claude Code (구독 또는 API 키)
- 도구 설치가 어렵다면 **이 플랫폼의 AI 패널 + Gemini 무료 티어**

트랙 3에서 만든 Playwright 프로젝트를 열고, **프로젝트 규칙 파일**을 작성한다. (위 예시를 본인 규칙으로 수정)

### 과제 2 — 규칙 파일 효과 측정 (15분)

같은 요청을 **규칙 파일 있을 때와 없을 때** 각각 실행한다.

> 상품 검색 후 첫 번째 결과를 클릭해 상세 페이지로 이동하는 테스트를 작성해줘.

| 확인 항목 | 규칙 없음 | 규칙 있음 |
|---|---|---|
| `waitForTimeout` 사용 | | |
| CSS 클래스 셀렉터 사용 | | |
| `nth(0)` / `first()` 사용 | | |
| `await expect` 형태 | | |
| 테스트 데이터 하드코딩 | | |

**규칙 파일 하나로 몇 개가 개선되는지** 세어본다.

### 과제 3 — 컨텍스트 품질 실험 (12분)

트랙 3에서 만든 실패하는 테스트를 대상으로 세 가지 방식으로 질문한다.

1. "이 테스트 왜 실패해?" (코드만)
2. 코드 + 에러 로그
3. 코드 + 에러 로그 + 실행 환경 + 최근 변경 사항 + "원인 후보 3개와 확인 방법"

**답변의 정확도와 실행 가능성**을 비교해 표로 정리한다. 3번에서 AI가 불확실성을 드러내는지 확인한다.

### 과제 4 — "테스트를 약하게 만드는" 함정 확인 (15분)

일부러 **실패하는 테스트**를 만든다. (기대 금액을 틀리게 설정)

AI에게 이렇게 요청한다.

> 이 테스트가 실패합니다. 통과하게 만들어 주세요.

그리고 **diff를 정밀하게 읽는다.**

| 확인 | 결과 |
|---|---|
| 어서션을 약화시켰는가 (`toHaveText` → `toBeVisible`) | |
| 기대값을 실제값으로 바꿨는가 | |
| `try/catch` 로 감쌌는가 | |
| 어서션을 아예 삭제했는가 | |
| **"제품이 잘못된 것 아닌가"를 되물었는가** | |

마지막 항목이 핵심이다. **좋은 답은 "테스트가 틀렸는지 제품이 틀렸는지 먼저 확인해야 합니다"** 이다. 대부분의 AI는 그냥 테스트를 고친다.

### 과제 5 — Playwright MCP 연결 (15분, 선택)

MCP를 지원하는 도구(Claude Code, Cursor 등)를 쓴다면:

1. Playwright MCP 서버 설정
2. AI에게 "TodoMVC 사이트를 열고 화면에 무엇이 있는지 접근성 트리로 설명해줘" 요청
3. **AI가 스크린샷이 아니라 구조를 읽는다**는 것을 확인
4. "할 일을 3개 추가하고 결과를 알려줘" 요청 → 실제로 브라우저가 조작되는지 확인

이게 6편의 자율 탐색 기반이 된다. 미리 감을 잡아둔다.

### 과제 6 — 보안 경계 점검 (10분)

본인이 AI 도구에 붙여넣을 뻔했던(또는 붙여넣은) 내용을 점검한다.

| 유형 | 위험도 | 대안 |
|---|---|---|
| 운영 로그 (고객 이메일·주문번호 포함) | | |
| `.env` 파일 | | |
| 사내 API 명세 | | |
| DB 스키마 | | |
| storageState.json (세션 토큰) | | |

각 항목에 대해 **마스킹 방법 또는 로컬 모델 사용** 같은 대안을 적는다. 회사 정책이 있다면 확인해서 함께 기록한다.

- [ ] "코드베이스 질문"과 "PR diff 이해"가 QA 본업에 직결되는 이유를 안다
- [ ] 도구별 성격과 무료로 학습할 수 있는 경로를 안다
- [ ] 컨텍스트에 무엇을 함께 주느냐가 결과의 대부분을 결정한다는 것을 안다
- [ ] "원인 후보 3개 + 확인 방법" 형태로 요청해 불확실성을 드러낼 수 있다
- [ ] 프로젝트 규칙 파일로 반복 지시를 없애고 팀 컨벤션을 공유할 수 있다
- [ ] 규칙 파일에 트랙 3의 안티패턴 금지 항목을 담을 수 있다
- [ ] MCP가 무엇이고 QA에게 유용한 연결이 무엇인지 안다
- [ ] Playwright MCP가 접근성 트리를 읽는다는 것과 그 의미를 안다
- [ ] MCP로 DB를 연결할 때 읽기 전용만 주는 원칙을 지킨다
- [ ] 회귀 범위 산정·코드 탐색·테스트 리뷰·로그 분석 요청 패턴을 쓸 수 있다
- [ ] "고치지 말고 지적만" 요청이 학습에 유리한 이유를 안다
- [ ] AI 산출물 검증 체크리스트 6가지를 적용한다
- [ ] **AI가 테스트를 약화시켜 통과시키는 패턴**을 알아보고 diff로 확인한다
- [ ] 사내 코드·로그·키를 외부 AI에 붙여넣지 않는 경계를 지킨다
- [ ] 자동 승인 모드로 무제한 권한을 주지 않는다
