## 개념 설명

### 9편까지 만든 것의 한계

파이프라인은 돌아간다. 그런데 에이전트는 여전히 **우리 팀에 대해 아무것도 모른다.**

```text
에이전트가 모르는 것
  - 작년 11월 결제 모듈에서 중복 결제 장애가 났다
  - 이 기능은 전체 사용자의 2%만 쓴다
  - 다음 주 대형 프로모션이 있다
  - 우리 도메인에선 금액을 원 단위로 절사한다
  - 이 화면은 규제 대상이라 반드시 검증해야 한다
  - 저 API 는 외부 팀 소유라 우리가 못 고친다
```

이런 정보 없이 매긴 우선순위는 **일반론에 불과하다.** 5편에서 확인한 한계다.

**10편의 목표는 조직의 지식을 에이전트의 입력으로 만드는 것**이다.

### 입력 소스 세 가지

```text
① 명세 (무엇이 옳은가)
   OpenAPI, 기획서, 도메인 규칙, TC 아카이브
   → 기대값의 근거. 이게 없으면 검증이 불가능하다 (6편)

② 변경 (무엇이 바뀌었는가)
   PR diff, 커밋 이력, 배포 이력, 의존성 변경
   → 범위 판단의 근거 (4편)

③ 이력 (무엇이 위험한가)
   장애 이력, 결함 이력, 플래키 이력, 사용 통계
   → 우선순위의 근거
```

**대부분의 팀이 ①②까지만 하고 ③을 빠뜨린다.** 그런데 ③이 우선순위 판단의 질을 가장 크게 바꾼다.

### ③ 이력을 데이터로 만들기

이력이 사람 머릿속에만 있으면 에이전트에게 줄 수 없다. **파일로 만든다.**

```yaml
# qa-knowledge/incident-history.yml
incidents:
  - date: 2025-11-14
    area: payment
    components: [PaymentService, OrderService]
    summary: 결제 응답 지연 시 재시도가 중복 주문을 생성
    root_cause: 멱등키 미적용
    escaped_because: 동시성 시나리오가 TC 에 없었음
    severity: Blocker
    recurrence_check: |
      결제 API 를 동일 멱등키로 2회 호출 시 주문이 1건만 생성되는가

  - date: 2026-03-02
    area: coupon
    components: [CouponService]
    summary: 정률 쿠폰 상한 미적용으로 과다 할인
    root_cause: 상한 검증 누락
    escaped_because: 경계값(상한 도달) TC 누락
    severity: Critical
    recurrence_check: |
      정률 쿠폰 적용 시 할인액이 상한을 넘지 않는가
```

**`escaped_because` 필드가 핵심이다.** 트랙 1의 결함 탈출 원인 분류를 여기에 기록한다. 이게 쌓이면 **우리 팀이 반복해서 놓치는 패턴**이 보인다.

```yaml
# qa-knowledge/domain-rules.yml
rules:
  - 모든 금액은 원 단위로 절사한다 (반올림 아님)
  - 쿠폰은 주문당 1장. 포인트와는 중복 사용 가능
  - 휴면 계정은 로그인은 되지만 결제는 불가
  - 도서산간 배송비는 기본 배송비와 별도로 가산된다

regulated_areas:
  - area: 개인정보 수정
    requirement: 본인인증 필수. 미인증 시 접근 차단 확인
  - area: 결제
    requirement: PG 사 연동 로그 보존 확인

external_owned:
  - api: /api/external/exchange-rate
    owner: 플랫폼팀
    note: 우리가 고칠 수 없음. 실패 시 폴백 동작만 검증
```

```yaml
# qa-knowledge/usage-stats.yml   (분석 도구에서 주기적으로 갱신)
areas:
  - name: checkout      traffic_share: 0.85   business_critical: true
  - name: search        traffic_share: 0.62   business_critical: true
  - name: wishlist      traffic_share: 0.08   business_critical: false
  - name: admin-report  traffic_share: 0.001  business_critical: false
```

**이 세 파일이 에이전트의 "우리 팀 지식"이다.** 저장소에 두면 버전 관리가 되고, PR로 리뷰할 수 있고, 무료다.

### 지식을 프롬프트에 주입하기

전부 넣으면 컨텍스트가 넘친다. **관련 있는 것만 골라 넣는다.**

```javascript
// lib/context.mjs
import { readFileSync } from 'node:fs';
import { parse } from './yaml-lite.mjs';   // 또는 JSON 으로 관리

export function buildContext(changedAreas) {
  const incidents = parse(readFileSync('qa-knowledge/incident-history.yml', 'utf8'));
  const domain    = parse(readFileSync('qa-knowledge/domain-rules.yml', 'utf8'));
  const usage     = parse(readFileSync('qa-knowledge/usage-stats.yml', 'utf8'));

  // 변경된 영역과 관련된 이력만 추린다
  const related = incidents.incidents.filter(i =>
    changedAreas.some(a => i.area === a || i.components.some(c => a.includes(c)))
  );

  return {
    related_incidents: related,
    domain_rules: domain.rules,
    regulated: domain.regulated_areas.filter(r => changedAreas.includes(r.area)),
    external: domain.external_owned,
    usage: usage.areas.filter(u => changedAreas.includes(u.name)),
  };
}
```

프롬프트에는 이렇게 들어간다.

```text
## 우리 팀의 맥락 (반드시 반영할 것)

### 이 영역의 과거 장애
- 2025-11-14 결제 응답 지연 시 재시도가 중복 주문 생성 (멱등키 미적용)
  놓친 이유: 동시성 시나리오가 TC 에 없었음
  → 재발 확인: 동일 멱등키 2회 호출 시 주문 1건인가

### 도메인 규칙
- 모든 금액은 원 단위로 절사 (반올림 아님)
- ...

### 사용 비중
- checkout: 트래픽 85%, 비즈니스 크리티컬

## 우선순위 규칙 (추가)
- 과거 장애가 있었던 영역의 재발 확인 항목은 무조건 High 로 분류하라.
- 트래픽 비중이 5% 미만이고 크리티컬하지 않으면 우선순위를 한 단계 낮춰라.
- 규제 대상 영역은 우선순위를 낮추지 마라.
```

**"과거 장애 재발 확인은 무조건 High"** 같은 규칙 하나가 우선순위의 질을 크게 바꾼다. 트랙 1에서 배운 "과거 결함이 잦았던 영역은 항상 포함"을 자동화한 것이다.

### 지식을 유지하는 루틴

**만들어 놓고 갱신 안 하면 곧 거짓말이 된다.** 트랙 2에서 배운 "틀린 문서는 없는 문서보다 나쁘다"가 여기에도 적용된다.

```text
장애 발생 시 (즉시)
  □ incident-history.yml 에 항목 추가
  □ escaped_because 를 반드시 채운다 (트랙 1의 탈출 원인 분류)
  □ recurrence_check 를 검증 가능한 문장으로 쓴다

릴리즈 회고 때 (릴리즈마다)
  □ 탈출 결함이 있었으면 이력에 추가
  □ 에이전트가 그 영역을 우선순위에 넣었는지 확인
  □ 안 넣었으면 왜 놓쳤는지 → 지식 파일 보완

분기마다
  □ usage-stats 갱신
  □ 1년 이상 지난 이력 중 코드가 완전히 바뀐 것은 아카이브
  □ domain-rules 가 현재 사양과 맞는지 확인
```

**`escaped_because` 를 채우는 것이 이 체계의 엔진이다.** 이 필드가 쌓이면 다음이 보인다.

```text
지난 2년 탈출 원인 집계
  경계값 TC 누락        7건  ← 우리 팀의 약점
  동시성 시나리오 누락   5건
  환경 차이             3건
  명세 불명확           3건
```

**"우리 팀은 경계값을 자주 놓친다"** 는 결론이 나오면, 그걸 프롬프트에 넣는다.

```text
## 우리 팀이 자주 놓치는 것 (특히 주의하라)
1. 경계값 — 특히 상한 도달 시점 (지난 2년 7건 탈출)
2. 동시성 — 중복 요청, 동시 수정 (5건)
```

이게 **조직 학습을 에이전트에 이식하는 것**이다.

### 신뢰 등급 — 무엇을 자동으로 믿을 것인가

체계가 커지면 "이 출력을 얼마나 믿을 것인가"를 정해야 한다.

| 등급 | 조건 | 처리 |
|---|---|---|
| **자동 반영** | 규칙 기반 결과 (안티패턴 검사, 컴파일) | 검토 없이 적용 |
| **자동 + 사후 샘플링** | AI 분류 신뢰도 ≥ 0.85, 과거 정확도 ≥ 90% | 적용하되 주간 20건 검토 |
| **사전 검토** | 신뢰도 0.6~0.85 | 사람이 승인 후 적용 |
| **참고만** | 신뢰도 < 0.6, 또는 제품 결함 분류 | 정보로만 제공 |
| **금지** | 릴리즈 판단, 결함 자동 종료, 우선순위 최종 확정 | 자동화하지 않음 |

**"자동 + 사후 샘플링"이 실무의 주력 구간이다.** 전수 검토는 비용이 안 맞고, 무검토는 위험하다. **샘플링으로 정확도를 상시 감시**하면서 자동으로 굴린다.

### 책임 소재 — 반드시 문서화한다

2편에서도 다뤘지만, 체계가 커질수록 중요해진다.

```text
누가 무엇에 책임지는가
  □ 에이전트 출력의 최종 승인: (담당자 지정)
  □ 프롬프트 변경 승인: (담당자 지정, PR 리뷰 필수)
  □ 지식 파일 유지: (담당자 지정)
  □ 정확도 측정과 보고: (담당자 지정, 주기)
  □ 파이프라인 중단 권한: (누구나 / 지정자)

사고가 났을 때
  □ "AI 가 그렇게 판단했다"는 사유가 되지 않는다
  □ 자동 반영된 결과도 팀의 결정으로 간주한다
  □ 사고 후 반드시 지식 파일과 프롬프트에 반영한다
```

**마지막 줄이 선순환을 만든다.** 사고 → 이력 기록 → 프롬프트 반영 → 다음엔 에이전트가 잡음.

### 전체 그림

```text
                  ┌─────────────────────────┐
   명세 ─────────>│                         │
   PR diff ──────>│   에이전트 파이프라인     │──> 범위 / TC / 실행 / 분류
   장애 이력 ────>│   (4~9편)               │
   도메인 규칙 ──>│                         │
   사용 통계 ────>└───────────┬─────────────┘
        ↑                     │
        │                     ↓
        │              ┌──────────────┐
        │              │  사람 검토    │
        │              └──────┬───────┘
        │                     │
        └─────────────────────┘
              피드백 (탈출 결함, 오분류, 새 이력)
```

**왼쪽 화살표(피드백 루프)가 이 체계의 핵심이다.** 이게 없으면 에이전트는 처음 수준에 머문다.

### 트랙 4를 마치며 — 무엇이 사람의 일로 남는가

10편을 관통하는 결론이다.

| AI가 가져간 것 | 사람에게 남는 것 |
|---|---|
| TC 초안 작성 | **무엇을 테스트하지 않을지 결정** |
| 조합 나열 | 리스크 기반 범위 축소 |
| 코드 생성 | 생성물이 진짜 검증하는지 판단 |
| 실패 분류 초안 | 제품 결함 여부 최종 판단 |
| 반복 탐색 | 도메인 직관에 기반한 의심 |
| 리포트 작성 | **릴리즈 Go/No-Go** |
| 셀렉터 복구 | 근본 원인 해결 요청 |

**오른쪽 열이 전부 "판단"이다.** 그리고 판단의 근거는 트랙 1의 기본기와 트랙 6의 검증 능력에서 나온다.

**AI를 잘 쓰는 QA가 되려면 역설적으로 QA 기본기가 더 필요하다.** 기법을 모르면 AI 출력에서 무엇이 빠졌는지 안 보이고, 코드를 못 읽으면 검증을 못 한다.

## 왜 채용시장이 요구하는가

- **"에이전트형 테스트 체계 구축"** 은 QA 리드·아키텍트 레벨의 요구사항이다. 개별 도구가 아니라 **체계를 설계할 수 있는 사람**을 찾는다.
- **조직 지식을 데이터로 만들어 주입한다**는 발상은 매우 드물다. 면접에서 이 이야기를 하면 확실히 기억에 남는다.
- **신뢰 등급과 책임 소재 설계**는 AI 도입을 실제로 주도해 본 사람의 언어다. 기술이 아니라 거버넌스 영역이고, 조직이 가장 걱정하는 부분이다.
- 면접 질문: **"AI가 QA를 대체할까요?"** — 위의 표로 답할 수 있다. **"판단이 남는다"** 와 **"그래서 기본기가 더 중요해졌다"** 는 성숙한 답이다.

## 실습 과제

### 과제 1 — 이력 파일 만들기 (18분)

본인이 겪었거나 들어본 장애·결함 **5건**을 `incident-history.yml` 형식으로 작성한다.

각 항목에 반드시 포함:
- `escaped_because` — 왜 테스트에서 못 잡았는가 (트랙 1의 6분류 활용)
- `recurrence_check` — 재발을 확인할 검증 가능한 문장

**`escaped_because` 를 5건 모두 채운 뒤 집계한다.** 어떤 유형이 반복되는가?

### 과제 2 — 도메인 규칙 정리 (12분)

본인 도메인의 `domain-rules.yml` 을 작성한다.

- 암묵적 규칙 5개 이상 (신입이 모를 만한 것)
- 규제/필수 검증 영역 2개 이상
- 외부 소유 API 1개 이상 (있다면)

**"암묵적 규칙"을 뽑는 게 어렵다.** 힌트: 신입 QA가 물어봤을 때 "아 그건 원래…"로 시작하는 답이 나오는 것들이다.

### 과제 3 — 컨텍스트 주입 효과 측정 (18분)

4편이나 5편에서 만든 프롬프트로 같은 PR을 두 번 분석한다.

- A: 컨텍스트 없음
- B: 과제 1·2의 지식 주입

| 비교 | A | B |
|---|---|---|
| 과거 장애 영역을 우선순위에 넣었는가 | | |
| 도메인 규칙(원 단위 절사 등)을 반영했는가 | | |
| 저트래픽 영역의 우선순위를 낮췄는가 | | |
| 규제 영역을 유지했는가 | | |
| 제안한 TC 개수 | | |

**차이가 크지 않다면** 프롬프트에서 컨텍스트를 실제로 쓰라고 지시했는지 확인한다. 그냥 붙여넣기만 하면 무시되는 경우가 있다.

### 과제 4 — 탈출 원인 집계와 프롬프트 반영 (15분)

과제 1의 `escaped_because` 를 집계해 **우리 팀의 약점 3가지**를 도출한다.

그걸 프롬프트에 반영한다.

```text
## 우리 팀이 자주 놓치는 것
1. ...  (지난 N년 M건 탈출)
2. ...
3. ...
이 관점을 TC 설계에 반드시 포함하라.
```

반영 전후로 생성 결과를 비교해 **약점 영역의 TC가 늘었는지** 확인한다.

### 과제 5 — 신뢰 등급 설계 (15분)

본인 팀에 맞는 신뢰 등급 표를 작성한다.

| 항목 | 등급 | 조건 | 검토 방법 |
|---|---|---|---|
| 안티패턴 검사 | | | |
| 범위 분석 | | | |
| TC 생성 | | | |
| 실패 분류 | | | |
| 셀프힐링 | | | |
| 결함 심각도 | | | |
| 우선순위 | | | |
| 릴리즈 판단 | | | |

각 등급의 **승급/강등 조건**도 정한다. 예: "4주 연속 정확도 90% 이상이면 사전 검토 → 자동+샘플링으로 승급".

### 과제 6 — 거버넌스 문서 (15분)

**1페이지 운영 규칙**을 완성한다. 이게 트랙 4의 최종 산출물이다.

```text
1. 입력 소스와 유지 담당
2. 신뢰 등급 표
3. 사람이 반드시 개입하는 지점
4. 절대 자동화하지 않는 것
5. 정확도 측정 방법과 주기
6. 파이프라인 중단 기준과 권한
7. 책임 소재
8. 사고 발생 시 절차 (지식 파일 반영 포함)
9. 비용 상한과 초과 시 조치
```

### 과제 7 — 트랙 4 종합 회고 (12분)

메모에 정리한다.

1. **AI에게 넘긴 것 / 내가 쥔 것** 을 각각 5개씩
2. 지금 당장 실무에 적용할 수 있는 것 3가지
3. **적용하지 않기로 한 것과 그 이유** 2가지
4. 트랙 1·2·3의 어떤 내용이 트랙 4의 전제가 되었는가

**3번을 진지하게 쓴다.** 모든 걸 도입하는 게 정답이 아니다. 트랙 3의 "자동화하지 않을 것"과 같은 판단이다.

## 자가 체크리스트

- [ ] 파이프라인만으로는 팀의 맥락을 모른다는 한계를 설명할 수 있다
- [ ] 입력 소스 세 가지(명세·변경·이력)와 각각의 역할을 구분할 수 있다
- [ ] 대부분의 팀이 ③이력을 빠뜨리고, 그게 우선순위 질을 좌우한다는 것을 안다
- [ ] 장애 이력을 `escaped_because`, `recurrence_check` 포함해 데이터로 만들 수 있다
- [ ] 도메인 규칙·규제 영역·외부 소유 API를 문서화할 수 있다
- [ ] 관련 있는 지식만 추려서 컨텍스트에 넣을 수 있다
- [ ] "과거 장애 영역은 무조건 High" 같은 규칙으로 우선순위를 강제할 수 있다
- [ ] 지식 파일 유지 루틴(장애 시·릴리즈마다·분기마다)을 설계할 수 있다
- [ ] `escaped_because` 집계로 팀의 반복 약점을 도출할 수 있다
- [ ] 도출한 약점을 프롬프트에 반영해 조직 학습을 이식할 수 있다
- [ ] 신뢰 등급 5단계를 설계하고 승급·강등 조건을 정할 수 있다
- [ ] "자동 + 사후 샘플링"이 실무 주력 구간인 이유를 안다
- [ ] 책임 소재를 문서화하고 "AI가 그랬다"가 사유가 안 됨을 명시한다
- [ ] 사고 후 지식 파일과 프롬프트에 반영하는 피드백 루프를 만든다
- [ ] AI가 가져간 것과 사람에게 남는 것을 각각 설명할 수 있다
- [ ] **AI를 잘 쓰려면 QA 기본기가 더 필요하다**는 역설을 설명할 수 있다
