## 개념 설명

### 1단계와 무엇이 다른가

```text
1단계 출력: "결제 금액 계산 로직이 바뀌었다. 경계값 테스트가 필요하다."
2단계 출력: 실제로 실행 가능한 Playwright 테스트 코드 + 실행 순서
```

**추상적인 범위를 구체적인 실행 단위로 바꾸는 것**이 2단계다. 그리고 여기서 두 가지를 결정한다.

1. **어느 계층에서 테스트할 것인가** (트랙 3의 테스트 피라미드)
2. **무엇을 먼저 실행할 것인가** (시간이 제한적일 때)

### 계층 선택 — 에이전트가 놓치는 지점

AI에게 "테스트를 만들어줘"라고 하면 **거의 항상 E2E를 만든다.** 트랙 3에서 배운 대로 이건 비싸다.

프롬프트에 명시적으로 계층 판단을 요구해야 한다.

```text
## 계층 선택 규칙
각 검증 항목에 대해 가장 낮은 계층을 선택하라.

Unit  — 순수 계산, 포맷 변환, 유효성 검사 로직
API   — 비즈니스 규칙, 권한, 데이터 정합성, 상태 전이
E2E   — 사용자 여정, 여러 화면에 걸친 흐름, 렌더링 결과

같은 규칙을 여러 계층에서 중복 검증하지 마라.
E2E 는 "화면에 올바르게 반영되는가" 1건으로 충분한 경우가 많다.

각 테스트에 왜 그 계층을 선택했는지 이유를 적어라.
```

**"같은 규칙을 여러 계층에서 중복 검증하지 마라"** 가 실전에서 효과가 크다. 이걸 안 넣으면 할인 계산을 Unit 12건 + API 12건 + E2E 12건으로 만든다.

### 우선순위 판정 — 제약을 주어야 작동한다

트랙 1에서 배운 대로, 제약이 없으면 전부 High가 된다. 에이전트에게는 **실행 예산**을 주는 게 효과적이다.

```text
## 우선순위 규칙
- PR 검증에 쓸 수 있는 시간은 총 10분이다.
- 각 테스트의 예상 실행 시간을 추정하고, 10분 안에 들어가는 조합을 골라라.
- 선택 기준 순서:
  1. 이번 변경으로 직접 깨질 수 있는가
  2. 깨졌을 때 비즈니스 임팩트가 큰가
  3. 과거에 이 영역에서 결함이 있었는가 (이력이 제공된 경우)
  4. 다른 테스트로 커버되지 않는 고유한 검증인가

- 10분 예산에 들어가지 못한 테스트는 "nightly" 로 분류하라.
- 선택하지 않은 이유도 적어라.
```

**"10분 예산"이라는 물리적 제약**이 우선순위를 강제한다. 트랙 3의 "PR 피드백 10분 원칙"과 연결된다.

### 출력 형식 — 바로 실행 가능해야 한다

```text
## 출력 (JSON)
{
  "test_plan": [
    {
      "id": "T1",
      "layer": "api",
      "layer_reason": "비즈니스 계산 규칙이므로 UI 불필요",
      "description": "3만원 정확히 주문 시 배송비 0원",
      "technique": "경계값 분석",
      "priority": "High",
      "estimated_seconds": 3,
      "bucket": "pr",
      "why": "이번 PR 에서 > 가 >= 로 바뀐 경계",
      "code": "...실행 가능한 코드..."
    }
  ],
  "excluded": [
    { "description": "...", "reason": "예산 초과, nightly 로 이관" }
  ],
  "total_estimated_seconds": 540,
  "assumptions": ["코드 생성 시 가정한 것 — 검증 대상"],
  "open_questions": ["명세로 판단 불가한 것"]
}
```

**`assumptions` 필드가 중요하다.** 코드를 생성하려면 AI가 뭔가를 가정해야 한다 — 엔드포인트 경로, 필드명, 테스트 계정, 셀렉터. 그 가정을 밖으로 꺼내게 하면 **검증할 것이 명확해진다.**

```json
"assumptions": [
  "주문 생성 엔드포인트가 POST /api/v1/orders 라고 가정",
  "응답의 배송비 필드명이 shippingFee 라고 가정",
  "테스트 계정 qa_user_01 이 존재한다고 가정",
  "장바구니 아이템에 data-testid='cart-item' 이 있다고 가정"
]
```

이 목록을 하나씩 확인하면 **생성된 코드가 왜 실패하는지 실행 전에 안다.**

### 생성 품질을 올리는 입력

트랙 4의 1편에서 다룬 것과 같은 원리다. **무엇을 함께 주느냐**가 결과를 결정한다.

| 입력 | 효과 |
|---|---|
| **기존 테스트 코드 2~3개** | 프로젝트의 구조·POM·헬퍼를 그대로 따른다 |
| 페이지 오브젝트 파일 | 존재하는 메서드만 쓴다 → 환각 감소 |
| OpenAPI 명세 | API 테스트의 경로·필드가 정확해진다 |
| 프로젝트 규칙 파일 | 안티패턴을 피한다 (3편) |
| **실제 DOM 스냅샷** | 셀렉터가 실제와 맞는다 |

**마지막이 결정적이다.** 셀렉터를 상상해서 만들면 거의 다 틀린다. Playwright MCP나 접근성 트리 덤프를 함께 주면 정확도가 크게 오른다 (6편에서 본격적으로 다룬다).

```bash
# 접근성 트리를 텍스트로 덤프해서 프롬프트에 넣는다
npx playwright codegen --target=javascript https://staging.example.com/cart
# 또는 페이지에서 직접
```

### 생성된 코드를 검증하는 루프

**에이전트가 만든 코드를 사람이 다 읽을 수는 없다.** 자동 검증 단계를 파이프라인에 넣는다.

```text
생성
  ↓
① 정적 검사 — 컴파일/린트가 통과하는가
  npx tsc --noEmit
  npx eslint tests/
  ↓
② 안티패턴 검사 — 규칙 위반이 있는가
  waitForTimeout / try-catch 어서션 / CSS 셀렉터 / expect(await ...)
  ↓
③ 실행 — 실제로 통과하는가
  npx playwright test --repeat-each=3
  ↓
④ 변이 검사 — 정말 검증하고 있는가   ← 가장 중요
  기대값을 일부러 틀리게 바꿔서 테스트가 실패하는지 확인
  ↓
사람 검토
```

**④ 변이 검사(mutation check)가 핵심이다.**

```typescript
// 생성된 테스트
await expect(page.getByTestId('shipping-fee')).toHaveText('0원');

// 변이: 기대값을 틀리게 바꾼다
await expect(page.getByTestId('shipping-fee')).toHaveText('9999원');
// → 이때도 통과한다면? 그 테스트는 아무것도 검증하지 않는 것이다.
```

간단한 스크립트로 자동화할 수 있다.

```javascript
// scripts/mutation-check.mjs (개념 코드)
// 각 테스트 파일의 toHaveText/toBe 기대값을 무작위 값으로 바꾸고 실행
// → 여전히 통과하는 테스트를 "의심" 목록으로 출력
```

**②의 안티패턴 검사**는 정규식으로도 꽤 잡힌다.

```javascript
const ANTIPATTERNS = [
  { re: /waitForTimeout\s*\(/,           msg: '고정 대기 사용' },
  { re: /waitForLoadState\(['"]networkidle/, msg: 'networkidle 대기' },
  { re: /expect\s*\(\s*await\s/,          msg: 'expect(await ...) — 재시도 안 됨' },
  { re: /catch\s*\([^)]*\)\s*{[^}]*}/s,   msg: 'try/catch — 어서션을 삼킬 수 있음' },
  { re: /page\.(click|fill)\s*\(\s*['"]\./, msg: 'CSS 클래스 셀렉터' },
  { re: /\.nth\(\d+\)|\.first\(\)/,       msg: '순서 의존 로케이터' },
];
```

이 검사는 **트랙 3의 실습 랩 "Playwright 스크립트 리뷰어"와 같은 로직**이다. AI 키 없이도 동작한다.

### 우선순위 판정의 한계 — 사람이 반드시 개입할 지점

에이전트가 우선순위를 잘못 매기는 전형적 경우들이다.

| 상황 | 왜 AI가 틀리나 |
|---|---|
| 다음 주 대형 프로모션이 있다 | 로드맵을 모른다 |
| 이 고객사가 계약 갱신 협상 중이다 | 비즈니스 맥락을 모른다 |
| 작년에 이 모듈에서 장애가 났다 | 이력을 안 주면 모른다 |
| 이 기능은 사용자의 2%만 쓴다 | 사용 통계를 모른다 |
| 규제 대상 기능이라 반드시 검증해야 한다 | 법무 요건을 모른다 |

**해법은 두 가지다.**

1. **컨텍스트를 주입한다** — 장애 이력, 사용 통계, 규제 항목을 프롬프트에 포함 (10편)
2. **최종 확정은 사람이 한다** — 에이전트 출력은 "제안"으로 표시

### 이 단계를 파이프라인에 붙이기

```yaml
      - name: 1단계 범위 분석
        run: node .github/scripts/analyze-scope.mjs > /tmp/scope.json

      - name: 2단계 테스트 생성
        run: node .github/scripts/generate-tests.mjs /tmp/scope.json > /tmp/plan.json

      - name: 생성 코드 정적 검증
        run: |
          node .github/scripts/write-tests.mjs /tmp/plan.json   # 파일로 저장
          npx tsc --noEmit
          node .github/scripts/antipattern-check.mjs tests/generated/

      - name: PR 예산 내 테스트만 실행
        run: npx playwright test tests/generated/ --grep @pr

      - name: 결과와 함께 PR 코멘트
        if: always()
        uses: actions/github-script@v7
        # ...
```

**생성된 테스트를 바로 저장소에 커밋하지 않는다.** 임시로 실행하고 결과만 보고한다. 사람이 검토한 뒤 가치 있는 것만 정식 테스트로 편입시킨다.

**이걸 안 지키면** 6개월 뒤 아무도 이해 못 하는 테스트 500개가 저장소에 쌓인다. 트랙 3의 "자동화 유지보수 비용" 문제가 그대로 재현된다.

## 왜 채용시장이 요구하는가

- **"AI 기반 테스트 자동 생성"** 은 2026년 공고의 핵심 키워드다. 단순히 써본 것과 **파이프라인으로 만들어 본 것**은 다르게 평가된다.
- **생성된 코드를 자동 검증하는 루프**를 설계할 수 있는 사람은 매우 드물다. 특히 변이 검사 개념은 강한 인상을 준다.
- 면접 질문: **"AI가 만든 테스트를 어떻게 신뢰하나요?"** — 정적 검사 → 안티패턴 → 실행 → 변이 검사의 4단계로 답할 수 있으면 된다.
- **생성 테스트를 바로 커밋하지 않는 판단**은 유지보수 비용을 이해한다는 신호다.

## 실습 과제

### 과제 1 — 계층 선택 강제하기 (15분)

같은 요구사항으로 두 번 생성한다.

```text
요구사항: 주문 금액 30,000원 이상 무료배송. VIP는 금액 무관 무료.
도서산간은 무료 대상이라도 추가 3,000원.
```

- A: "테스트를 만들어줘"
- B: 계층 선택 규칙을 넣은 프롬프트

| 비교 | A | B |
|---|---|---|
| E2E 테스트 개수 | | |
| API 테스트 개수 | | |
| Unit 테스트 개수 | | |
| 계층 선택 이유를 적었는가 | | |
| 예상 총 실행 시간 | | |

**A는 대체로 전부 E2E로 만든다.** 실행 시간 차이를 계산해 본다.

### 과제 2 — 예산 제약 실험 (12분)

과제 1의 B 결과에 예산 제약을 추가한다.

- 예산 10분 → 어떤 테스트가 선택되는가
- 예산 2분 → 무엇이 남는가
- 예산 30초 → 무엇이 남는가

**예산 30초일 때 남는 것이 진짜 핵심이다.** 그게 스모크 테스트다 (트랙 3의 1단계).

각 경우에 `excluded` 사유가 합리적인지 검토한다.

### 과제 3 — assumptions 검증 (12분)

실제 프로젝트(트랙 3에서 만든 것)를 대상으로 테스트를 생성시킨다.

`assumptions` 목록을 하나씩 확인한다.

| 가정 | 실제로 맞는가 | 틀렸다면 코드가 어떻게 실패할까 |
|---|---|---|
| | | |

**실행하기 전에 몇 개가 틀렸는지 예측**하고, 실행해서 맞는지 확인한다.

### 과제 4 — 안티패턴 검사기 만들기 (15분)

위의 정규식 목록으로 실제 검사 스크립트를 작성한다.

```bash
node scripts/antipattern-check.mjs tests/
```

요구사항:
- 파일별로 위반 항목과 라인 번호 출력
- 위반이 있으면 종료 코드 1 (CI에서 빌드 실패시킬 수 있게)
- 주석에 `// antipattern-ok: 이유` 가 있으면 예외 처리

**마지막 요구사항이 실무적이다.** 정당한 예외를 허용하되 이유를 남기게 한다 (트랙 3의 "주석 없는 waitForTimeout 금지").

이 스크립트를 AI가 생성한 코드에 돌려본다.

### 과제 5 — 변이 검사 (15분)

AI가 생성한 테스트 3개를 골라 수동으로 변이 검사를 한다.

| 테스트 | 기대값 변이 | 여전히 통과? | 판정 |
|---|---|---|---|
| T1 | `'0원'` → `'9999원'` | | |
| T2 | | | |
| T3 | | | |

**"여전히 통과"가 하나라도 나오면** 그 테스트는 가짜다. 왜 그런지 분석하고 고친다.

여유가 되면 이 과정을 스크립트로 자동화해 본다.

### 과제 6 — AI 우선순위의 한계 확인 (10분)

에이전트에게 우선순위를 매기게 한 뒤, **AI가 알 수 없는 정보**를 추가로 주고 다시 매기게 한다.

```text
추가 컨텍스트:
- 다음 주 월요일 대형 프로모션 시작 (쿠폰 트래픽 10배 예상)
- 작년 11월 결제 모듈에서 중복 결제 장애 발생
- 배송비 계산은 최근 6개월간 결함 0건
```

**순위가 어떻게 바뀌는지** 비교하고, 이 컨텍스트를 어떻게 상시로 주입할지 아이디어를 적는다. (10편의 예습)

## 자가 체크리스트

- [ ] 1단계(범위)와 2단계(생성·우선순위)의 차이를 설명할 수 있다
- [ ] AI가 기본적으로 모든 것을 E2E로 만들려 한다는 것을 알고 계층을 강제한다
- [ ] "같은 규칙을 여러 계층에서 중복 검증하지 마라" 지시의 효과를 안다
- [ ] 실행 시간 예산으로 우선순위를 강제할 수 있다
- [ ] `assumptions` 를 출력하게 해서 검증 대상을 명확히 할 수 있다
- [ ] 생성 품질을 올리는 입력 5가지를 안다
- [ ] 실제 DOM 스냅샷 없이 만든 셀렉터는 대부분 틀린다는 것을 안다
- [ ] 생성 코드 검증 4단계(정적·안티패턴·실행·변이)를 설명할 수 있다
- [ ] **변이 검사**로 "아무것도 검증하지 않는 테스트"를 찾아낼 수 있다
- [ ] 정규식 기반 안티패턴 검사기를 만들 수 있다
- [ ] 정당한 예외를 주석으로 허용하는 설계를 할 수 있다
- [ ] AI가 우선순위를 틀리는 5가지 상황을 안다
- [ ] 생성된 테스트를 바로 커밋하지 않는 이유를 설명할 수 있다
- [ ] 에이전트 출력을 "제안"으로 표시하고 최종 확정은 사람이 한다
