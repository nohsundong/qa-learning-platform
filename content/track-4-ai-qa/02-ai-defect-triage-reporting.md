## 개념 설명

### 어디까지 AI에게 넘길 수 있는가

결함 처리 흐름에서 AI가 유용한 지점과 위험한 지점이 명확히 갈린다.

| 단계 | AI 적합도 | 이유 |
|---|---|---|
| 리포트 초안 정리 (문장 다듬기) | **높음** | 형식 변환 작업 |
| 중복 결함 탐지 | **높음** | 의미 기반 유사도 비교를 잘한다 |
| 컴포넌트 자동 분류 | **높음** | 텍스트 분류는 잘하는 일 |
| 심각도(Severity) 1차 제안 | 중간 | 기준이 명확하면 가능. **검토 필수** |
| 우선순위(Priority) 판정 | **낮음** | 비즈니스 맥락이 필요 (트랙 1) |
| 근본 원인 추정 | 중간 | 로그가 있으면 도움. **지어내기 위험** |
| 릴리즈 Go/No-Go 판단 | **금지** | 책임 소재. 사람이 판단한다 |

**심각도와 우선순위의 적합도가 다르다는 게 핵심이다.** 심각도는 "시스템에 미치는 영향"이라 텍스트에서 어느 정도 추론 가능하지만, 우선순위는 "지금 고칠 것인가"라서 로드맵·마케팅 일정·계약 조건 같은 걸 알아야 한다. AI에겐 그 정보가 없다.

### 자동 분류를 실제로 쓰려면 — 구조화 출력

자유 텍스트로 받으면 사람이 다시 옮겨 적어야 해서 의미가 없다. **JSON으로 받아 그대로 처리**한다.

```text
너는 QA 결함 트리아지 담당이다. 아래 결함 리포트를 분류하라.

## 분류 기준
severity:
  Blocker  - 테스트 진행 불가, 핵심 기능 완전 불가, 데이터 유실, 금전 손실
  Critical - 핵심 기능이 우회 방법 없이 실패, 보안 취약점
  Major    - 주요 기능 실패하나 우회 가능
  Minor    - 부가 기능 실패, 사용성 불편
  Trivial  - 오타, 미세한 UI 어긋남

component: [Auth, Payment, Order, Product, Search, Notification, Admin, Unknown]

## 출력 (JSON 만, 다른 설명 없이)
{
  "severity": "...",
  "severity_reason": "한 문장",
  "confidence": 0.0~1.0,
  "component": "...",
  "duplicate_of": "기존 티켓 ID 또는 null",
  "missing_info": ["리포트에 없어서 추가로 확인해야 할 항목"],
  "suggested_title": "[영역] 조건에서 무엇이 어떻게"
}

## 규칙
- 판단 근거가 리포트에 없으면 confidence 를 0.5 미만으로 낮추고
  missing_info 에 무엇이 없는지 적어라.
- priority 는 판단하지 마라. 비즈니스 맥락이 필요하다.
- 추측으로 severity 를 올리거나 내리지 마라.

## 결함 리포트
[여기에 원문]
```

**`confidence` 필드가 이 설계의 핵심이다.** 이걸로 사람이 볼 것과 자동 처리할 것을 나눈다.

```text
confidence >= 0.8  →  자동 반영, 주간 샘플 검토
confidence 0.5~0.8 →  사람이 확인 후 반영
confidence < 0.5   →  사람이 직접 분류 + missing_info 를 리포터에게 회신
```

**`priority 는 판단하지 마라`** 를 명시적으로 넣는 이유: 안 막으면 AI가 알아서 매긴다. 그리고 그 값이 티켓에 들어가면 아무도 다시 안 본다.

### 중복 결함 탐지 — AI가 가장 잘하는 일

같은 결함을 다른 말로 쓴 티켓을 찾아내는 건 키워드 검색으로는 잘 안 된다.

```text
기존: "장바구니에서 수량 변경 시 총액이 갱신되지 않음"
신규: "상품 개수를 늘려도 결제금액이 그대로임"
```

키워드가 하나도 안 겹치지만 같은 결함이다. **의미 기반 비교는 AI가 확실히 잘한다.**

```text
아래 신규 결함이 기존 결함 목록 중 하나와 동일한 문제인지 판단하라.

## 신규 결함
[제목 + 재현 절차 + 증상]

## 기존 열린 결함 목록
[ID | 제목 | 증상 요약]  ← JQL 로 뽑아서 붙여넣는다 (트랙 2)

## 출력 (JSON)
{
  "is_duplicate": true/false,
  "duplicate_of": "PROJ-1234" 또는 null,
  "confidence": 0.0~1.0,
  "reasoning": "왜 같은/다른 문제라고 판단했는가",
  "related_but_different": ["관련은 있지만 별개인 티켓 ID"]
}

같은 화면에서 발생한다는 이유만으로 중복으로 판단하지 마라.
근본 원인이 같아 보여도 재현 경로가 다르면 related_but_different 에 넣어라.
```

마지막 지시가 중요하다. **AI는 중복을 과하게 판정하는 경향이 있다.** 같은 화면이면 같은 버그라고 묶어버린다. 그러면 실제로는 다른 두 결함 중 하나가 조용히 닫힌다.

### 품질 리포트 자동 생성

트랙 1의 지표를 AI에게 계산시킬 수 있다. **단, 계산은 반드시 검증한다.**

```text
아래 릴리즈 데이터로 QA 품질 리포트를 작성하라.

## 데이터
[TC 실행 현황, 결함 목록, 이전 릴리즈 지표]

## 계산 규칙 (반드시 이 정의를 따를 것)
- 실행률 = 실행 / 계획 × 100
- 통과율 = Pass / (Pass + Fail) × 100    ← Blocked 는 분모에서 제외
- 결함 탈출률 = 운영 발견 / (QA 발견 + 운영 발견) × 100

## 출력
1. 요약 3문장 (좋아진 것 / 우려되는 것 / 다음 액션)
2. 지표 표 — 이번 값, 이전 값, 증감
3. 잔여 결함 목록 (심각도순)
4. 리스크 3가지

## 금지
- 데이터에 없는 추세나 원인을 만들어내지 마라.
- 근거 없는 총평("품질이 개선되고 있습니다")을 붙이지 마라.
- 계산에 쓴 분자와 분모를 각 지표마다 명시하라.
```

**"분자와 분모를 명시하라"** 가 검증 장치다. 이게 있으면 계산이 맞는지 눈으로 30초 만에 확인된다. 없으면 숫자만 보고 넘어가게 된다.

**트랙 1에서 배운 대로, AI는 Blocked 처리에서 자주 틀린다.** 정의를 프롬프트에 박아두는 이유다.

### 자동화 파이프라인 — 무료로 구성하기

GitHub Actions + BYOK 로 구성할 수 있다. 서버가 필요 없다.

```yaml
# .github/workflows/triage.yml
name: 결함 자동 분류

on:
  issues:
    types: [opened]

jobs:
  triage:
    runs-on: ubuntu-latest
    steps:
      - name: AI 분류 요청
        id: classify
        env:
          API_KEY: ${{ secrets.AI_API_KEY }}
          ISSUE_BODY: ${{ github.event.issue.body }}
        run: |
          # 프롬프트 + 이슈 본문을 API 로 보내고 JSON 응답을 받는다
          # (전체 스크립트는 실습 과제에서 작성)
          node .github/scripts/triage.mjs > result.json

      - name: 라벨 자동 부착
        uses: actions/github-script@v7
        with:
          script: |
            const r = require('./result.json');
            const labels = [`severity:${r.severity}`, `component:${r.component}`];
            if (r.confidence < 0.8) labels.push('needs-human-review');
            await github.rest.issues.addLabels({
              ...context.repo,
              issue_number: context.issue.number,
              labels,
            });
            await github.rest.issues.createComment({
              ...context.repo,
              issue_number: context.issue.number,
              body: `🤖 자동 분류 (신뢰도 ${r.confidence})\n\n` +
                    `- 심각도: ${r.severity} — ${r.severity_reason}\n` +
                    `- 컴포넌트: ${r.component}\n` +
                    `- 추가 확인 필요: ${r.missing_info.join(', ') || '없음'}\n\n` +
                    `_이 분류는 제안입니다. QA 검토 후 확정하세요._`
```

**설계에서 지킨 두 가지**

1. **`needs-human-review` 라벨** — 신뢰도가 낮으면 사람이 봐야 한다는 표시가 남는다
2. **"이 분류는 제안입니다"** — 자동 판정이 최종 결정으로 오해되지 않게 한다

이 두 가지가 없으면 **AI가 매긴 심각도가 사실처럼 굳어진다.** 그리고 나중에 "왜 Critical 인데 아무도 안 봤죠?"가 된다.

### 신뢰 보정 — AI 분류를 계속 믿어도 되는가

도입하고 끝이 아니다. **정기적으로 정확도를 측정**해야 한다.

```text
주간 점검
  1. 지난주 자동 분류된 결함 중 20건 무작위 추출
  2. QA가 독립적으로 분류 (AI 결과를 보지 않고)
  3. 일치율 계산
     - severity 일치율
     - component 일치율
     - 중복 판정 정확도 (오탐/미탐)
  4. 일치율 90% 미만이면 프롬프트를 수정하거나 자동 반영을 중단
```

**2번의 "AI 결과를 보지 않고"가 중요하다.** AI 결과를 먼저 보면 사람도 거기에 끌려간다(앵커링). 그러면 측정 자체가 무의미해진다.

이 측정 자체가 QA의 산출물이 된다. **"AI 분류 도입 후 트리아지 시간 60% 감소, 분류 정확도 93%"** 는 트랙 1에서 배운 지표 언어다.

### 넘기면 안 되는 것 — 책임의 경계

```text
AI 가 하는 것: 제안, 분류, 요약, 초안
사람이 하는 것: 결정, 승인, 책임
```

특히 이 세 가지는 절대 자동화하지 않는다.

1. **결함을 자동으로 닫는 것** — "재현 불가"로 AI가 판단해 닫으면 진짜 결함이 사라진다
2. **우선순위 최종 확정** — 비즈니스 맥락 없이 매긴 값이 로드맵에 반영된다
3. **릴리즈 판단** — 트랙 1의 Go/No-Go. 책임 소재가 명확해야 한다

**"AI가 그렇게 판단했습니다"는 사고가 났을 때 통하지 않는 변명이다.**

## 왜 채용시장이 요구하는가

- 채용공고에 **"AI 기반 결함 분석·리포팅 자동화"** 가 등장하기 시작했다. 도입을 주도할 수 있는 사람을 찾는 것이다.
- 면접 질문: **"AI를 QA 프로세스에 도입한다면 어디에 쓰고 어디에 쓰지 않겠습니까?"** — 위의 적합도 표가 그대로 답이다. **"쓰지 않을 곳"을 말할 수 있는지**가 판별 기준이다.
- **신뢰도 기반 라우팅**(confidence로 사람 검토 여부를 가르는 설계)은 실무에서 매우 유용한데 아는 사람이 적다.
- **정확도를 측정하는 루틴**을 설계할 수 있으면 "AI를 써봤다"가 아니라 "AI를 운영해봤다"가 된다.

## 실습 과제

### 과제 1 — 분류 프롬프트 만들고 측정하기 (18분)

결함 리포트 10건을 준비한다. (트랙 1·2에서 쓴 것, 또는 오픈소스 프로젝트의 실제 이슈)

1. 이 레슨의 분류 프롬프트를 본인 도메인에 맞게 수정
2. **먼저 본인이 10건을 분류**한다 (severity, component)
3. 그다음 AI에게 분류시킨다
4. 일치율을 계산한다

| 항목 | 일치 / 전체 | 일치율 |
|---|---|---|
| severity | | |
| component | | |
| confidence 가 낮은 건이 실제로 애매했는가 | | |

**2번을 먼저 하는 순서가 중요하다.** AI 결과를 보고 나면 판단이 오염된다.

### 과제 2 — 중복 탐지 시험 (12분)

같은 결함을 **완전히 다른 표현으로** 3개 작성한다. 그리고 **비슷해 보이지만 실제로는 다른** 결함 2개를 섞는다.

AI에게 중복 판정을 시키고:

| 실제 | AI 판정 | 결과 |
|---|---|---|
| 중복 3건 | | 미탐(놓침) 몇 건? |
| 별개 2건 | | 오탐(잘못 묶음) 몇 건? |

**오탐이 미탐보다 위험하다.** 왜 그런지 메모에 적는다.

### 과제 3 — 품질 리포트 계산 검증 (15분)

트랙 1 과제의 릴리즈 데이터를 AI에 주고 리포트를 생성시킨다.

```text
계획 TC 120건 / 실행 108건 / Pass 99건 / Fail 9건 / Blocked 12건
QA 발견 결함: Blocker 0, Critical 2, Major 11, Minor 23
운영 발견 결함: Critical 1, Major 3, Minor 4
```

| 확인 항목 | 손계산 | AI | 일치 |
|---|---|---|---|
| 실행률 | | | |
| 통과율 (Blocked 제외) | | | |
| 결함 탈출률 | | | |
| 분자·분모를 명시했는가 | — | | |
| 근거 없는 총평을 붙였는가 | — | | |

**통과율에서 갈릴 가능성이 높다.** Blocked 12건을 분모에 넣었는지 확인한다.

### 과제 4 — GitHub Actions 자동 분류 구현 (20분)

본인의 연습용 저장소에서 실제로 만들어 본다. **무료로 동작한다.**

1. `.github/scripts/triage.mjs` 작성 — 이슈 본문을 받아 AI API 호출, JSON 출력
   (Gemini 무료 티어 또는 본인 키. Node 내장 `fetch` 만 쓰면 의존성 0)
2. `.github/workflows/triage.yml` 작성
3. Secrets 에 API 키 등록
4. 테스트 이슈를 열어 라벨이 자동으로 붙는지 확인
5. **일부러 정보가 부족한 이슈**를 열어 `needs-human-review` 가 붙는지 확인

5번이 이 과제의 핵심이다. 신뢰도 기반 라우팅이 실제로 동작하는지 본다.

### 과제 5 — 책임 경계 문서 작성 (10분)

본인 팀에 AI 트리아지를 도입한다고 가정하고 **1페이지 운영 규칙**을 쓴다.

```text
1. AI 가 하는 일 / 하지 않는 일
2. 신뢰도별 처리 경로
3. 사람이 반드시 검토하는 조건 (예: Critical 이상, 결제 컴포넌트)
4. 정확도 측정 주기와 방법
5. 자동 반영을 중단하는 기준
6. AI 분류가 틀려서 문제가 생겼을 때의 책임 소재
```

**6번을 적는 것이 이 과제의 목적이다.** 명시하지 않으면 사고가 났을 때 "AI가 그랬다"로 흐른다.

## 자가 체크리스트

- [ ] 결함 처리 단계별로 AI 적합도를 구분할 수 있다
- [ ] 심각도는 AI가 어느 정도 가능하지만 우선순위는 왜 어려운지 설명할 수 있다
- [ ] JSON 구조화 출력으로 받아야 실제로 자동화가 되는 이유를 안다
- [ ] `confidence` 필드로 사람 검토 여부를 라우팅하는 설계를 할 수 있다
- [ ] 프롬프트에 "priority는 판단하지 마라"를 명시하는 이유를 안다
- [ ] AI가 중복 결함을 과하게 판정하는 경향과 그 위험을 안다
- [ ] 오탐(잘못 묶음)이 미탐보다 위험한 이유를 설명할 수 있다
- [ ] 품질 리포트 프롬프트에 계산 정의를 박아 넣을 수 있다
- [ ] "분자와 분모를 명시하라"가 검증 장치가 되는 이유를 안다
- [ ] GitHub Actions + BYOK 로 서버 없이 자동 분류를 구성할 수 있다
- [ ] `needs-human-review` 라벨과 "제안입니다" 문구의 필요성을 안다
- [ ] 정확도를 주기적으로 측정하고, 측정 시 AI 결과를 먼저 보지 않는다
- [ ] AI에게 절대 넘기지 않을 3가지(자동 닫기, 우선순위 확정, 릴리즈 판단)를 안다
- [ ] AI 도입 성과를 지표 언어로 보고할 수 있다
