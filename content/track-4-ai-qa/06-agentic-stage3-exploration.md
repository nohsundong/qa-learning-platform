## 개념 설명

### 3단계가 앞 단계와 근본적으로 다른 점

1·2단계는 **사람이 정한 것을 대신 해주는** 일이었다. 3단계는 다르다.

```text
1·2단계: "이걸 테스트해" → 에이전트가 테스트를 만든다
3단계:   "여기를 탐색해봐" → 에이전트가 무엇을 테스트할지 스스로 찾는다
```

트랙 1의 **탐색적 테스트**를 에이전트가 수행하는 것이다. 그리고 트랙 1에서 "자동화가 대체하지 못하는 유일한 영역"이라고 했던 바로 그 영역이다.

**대체가 아니라 보완이다.** 에이전트는 사람이 지루해서 안 하는 것을 지치지 않고 한다.

| 사람이 잘하는 탐색 | 에이전트가 잘하는 탐색 |
|---|---|
| 도메인 직관에 기반한 의심 | 무차별 입력 조합 (긴 문자열, 이모지, 특수문자) |
| "이건 좀 이상한데" 감각 | 모든 링크·버튼을 빠짐없이 눌러보기 |
| 비즈니스 맥락 판단 | 같은 동작을 100번 반복 |
| 사용성 문제 발견 | 콘솔 에러·네트워크 실패 상시 감시 |

### 에이전트가 화면을 "보는" 방법

여기가 기술적 핵심이다. 두 가지 방식이 있고, 차이가 크다.

**방식 1: 스크린샷 (비전 모델)**
- 사람과 비슷하게 본다. 레이아웃 문제를 인식할 수 있다
- 단점: 토큰 비용이 크고, **좌표 기반 클릭은 부정확**하다. 요소를 정확히 지목하기 어렵다

**방식 2: 접근성 트리 (구조화 텍스트)** ← 권장

```yaml
- banner:
  - link "홈"
  - navigation:
    - link "상품"
    - link "장바구니" [ref=e12]
- main:
  - heading "무선 이어폰" [level=1]
  - text "45,000원"
  - spinbutton "수량" [ref=e18] [value=1]
  - button "장바구니 담기" [ref=e19]
  - button "바로 구매" [ref=e20]
```

**이 형태가 에이전트에게 압도적으로 유리하다.**

- 각 요소에 **참조 ID**가 붙어 있어 정확히 지목할 수 있다
- 역할(button, link, heading)이 명시돼 있어 **무엇을 할 수 있는지** 바로 안다
- 토큰이 훨씬 적게 든다
- **트랙 3의 `getByRole` 과 같은 정보**다 — 접근성이 좋은 앱일수록 에이전트가 잘 동작한다

Playwright MCP가 이 방식을 쓴다 (3편). 그래서 MCP를 붙이는 것이 자율 탐색의 출발점이다.

**부수 효과**: 접근성 트리가 빈약한 앱(div 버튼 투성이)은 에이전트가 탐색을 못 한다. 그 자체가 **접근성 결함 신호**다.

### 탐색 차터 — 목적 없는 탐색은 시간 낭비

트랙 1의 SBTM 차터를 그대로 에이전트에게 준다. **"아무거나 눌러봐"는 최악의 지시다.**

```text
너는 탐색적 테스트를 수행하는 QA 에이전트다.

## 차터
장바구니 화면을 "경계값과 잘못된 입력" 관점으로 탐색하고,
수량·금액이 어긋나거나 오류 처리가 없는 경로를 찾아라.

## 탐색 규칙
- 매 행동 전에 현재 화면 구조를 읽고, 무엇을 왜 할지 먼저 말하라.
- 한 번에 한 가지만 바꿔라. (무엇이 원인인지 알 수 있게)
- 이상한 것을 발견하면 즉시 기록하고, 재현 절차를 남겨라.
- 콘솔 에러와 실패한 네트워크 요청도 관찰 대상이다.
- 같은 화면에서 3번 이상 유사한 행동을 반복하지 마라.

## 발견 기록 형식
{
  "type": "finding | question | idea",
  "severity_guess": "high | medium | low",
  "what": "무엇을 발견했는가",
  "steps": ["재현 절차"],
  "expected": "기대한 동작",
  "actual": "실제 동작",
  "evidence": "콘솔 에러 / 네트워크 응답 / 화면 상태"
}

## 종료 조건
- 최대 30 스텝
- 또는 차터 관점에서 더 시도할 것이 없다고 판단되면 중단하고 요약하라.
```

**"매 행동 전에 무엇을 왜 할지 먼저 말하라"** 가 중요하다. 이유가 두 가지다.

1. 사람이 나중에 로그를 읽고 **탐색 경로를 이해**할 수 있다
2. 에이전트가 스스로 생각을 정리하면서 **무의미한 행동이 줄어든다**

### 가드레일 — 이게 없으면 사고가 난다

에이전트가 실제로 앱을 조작한다는 건 위험을 동반한다. **반드시 제한을 건다.**

```text
□ 환경 격리
  - 운영 환경 절대 금지. 스테이징 또는 로컬 전용
  - baseURL 을 화이트리스트로 강제

□ 계정 격리
  - 전용 테스트 계정. 실제 사용자 데이터에 접근 불가
  - 관리자 계정 금지

□ 행동 제한
  - 결제·송금·삭제 등 되돌릴 수 없는 액션은 차단하거나 사전 승인
  - 외부 도메인으로의 이동 차단
  - 파일 업로드는 지정된 테스트 파일만

□ 실행 제한
  - 최대 스텝 수 (예: 30)
  - 최대 실행 시간 (예: 10분)
  - 최대 토큰/비용

□ 데이터 제한
  - 생성한 데이터는 식별 접두어 (트랙 2의 ORD-TEST-)
  - 종료 시 정리

□ 관찰
  - 모든 행동을 로그로 남긴다
  - 트레이스/영상 기록
```

**결제 차단을 구체적으로 구현**하면 이렇다.

```javascript
// 위험한 요청을 아예 막는다
await page.route('**/*', route => {
  const url = route.request().url();
  const method = route.request().method();

  const BLOCKED = [
    /\/api\/.*\/payments?\b/,
    /\/api\/.*\/withdraw/,
    /\/api\/.*\/delete-account/,
  ];

  if (method !== 'GET' && BLOCKED.some(re => re.test(url))) {
    console.warn('[가드레일] 차단됨:', method, url);
    return route.fulfill({ status: 403, body: '{"blocked":"guardrail"}' });
  }
  // 외부 도메인 차단
  if (!url.startsWith(process.env.BASE_URL)) return route.abort();

  return route.continue();
});
```

**최대 스텝 제한이 없으면 에이전트가 무한 루프에 빠진다.** 같은 두 화면을 왕복하거나, 실패한 액션을 계속 재시도한다. 비용도 계속 나간다.

### 루프 구조

```text
반복 (최대 N 스텝):
  1. 현재 화면의 접근성 트리를 읽는다
  2. 콘솔 에러 / 실패한 네트워크 요청을 수집한다
  3. 차터와 지금까지의 기록을 보고 다음 행동을 결정한다
  4. 행동한다 (클릭, 입력, 이동)
  5. 결과를 관찰하고 이상이 있으면 기록한다
  6. 종료 조건 확인
```

**2번이 자주 빠진다.** 화면만 보면 정상인데 콘솔에 에러가 쏟아지는 경우가 흔하다. 트랙 2의 "에러율 0%인데 장애"와 같은 관점이다.

```javascript
// 매 스텝 수집
const consoleErrors = [];
page.on('console', m => { if (m.type() === 'error') consoleErrors.push(m.text()); });
page.on('pageerror', e => consoleErrors.push(String(e)));
page.on('requestfailed', r => consoleErrors.push(`FAILED ${r.method()} ${r.url()}`));
page.on('response', r => { if (r.status() >= 500) consoleErrors.push(`${r.status()} ${r.url()}`); });
```

### 무엇을 찾아내는가 — 현실적인 기대치

에이전트 탐색이 실제로 잘 찾는 것과 못 찾는 것이 있다.

| 잘 찾는다 | 못 찾는다 |
|---|---|
| 입력 검증 누락 (음수, 초과, 특수문자) | 비즈니스 규칙 위반 (기획 의도와 다름) |
| 콘솔 에러 / 500 응답 | 사용성 문제 ("헷갈린다") |
| 깨진 링크, 404 | 시각적 어긋남 (접근성 트리엔 안 나옴) |
| 빈 상태 처리 누락 | 도메인 특유의 미묘한 오류 |
| 중복 제출 시 오동작 | "이 금액이 맞는가" (정답을 모름) |

**마지막 항목이 근본적 한계다.** 에이전트는 화면에 9,000원이 떠도 그게 맞는지 모른다. **기대값을 알아야 검증인데, 명세 없이는 기대값이 없다.**

그래서 실전에서는 **명세를 함께 준다.**

```text
## 검증 기준 (이 규칙에 어긋나면 finding 으로 기록하라)
- 총액 = 상품가 합계 - 할인액 + 배송비
- 수량은 1~10 만 허용
- 3만원 이상 배송비 0원
```

이러면 계산 오류까지 잡아낸다. **1·2단계와 결합하면** 명세가 자동으로 흘러들어온다.

### 결과를 어떻게 다룰 것인가

에이전트가 30스텝 돌면 finding이 10개쯤 나온다. **그대로 티켓으로 만들면 안 된다.**

```text
에이전트 finding 10건
  ↓ 자동 필터
  중복 제거, 알려진 이슈 제외 (2편의 중복 탐지)
  ↓ 사람 검토
  진짜 결함 / 사양 / 오탐 분류
  ↓
  진짜 결함만 티켓 (트랙 1의 결함 리포트 형식으로)
```

**오탐율이 높다는 것을 전제로 설계한다.** 초기에는 절반 이상이 오탐일 수 있다. 그래도 가치가 있는 이유는 **사람이 30분 걸릴 탐색을 5분에 하고, 사람은 검토만 하면 되기 때문**이다.

오탐이 반복되면 **차터와 검증 기준을 다듬는다.** 이게 에이전트를 "훈련"시키는 방법이다.

### 사람의 탐색과 어떻게 조합하는가

```text
1. 에이전트가 먼저 훑는다 (무차별, 넓게)
     ↓
2. 사람이 결과를 보고 의심스러운 영역을 파악
     ↓
3. 사람이 그 영역을 깊게 탐색 (도메인 직관 활용)
     ↓
4. 사람이 발견한 패턴을 차터로 만들어 에이전트에 피드백
```

**4번이 선순환을 만든다.** 사람이 찾은 결함 유형을 차터로 정리하면 다음부터 에이전트가 그 관점으로 훑는다.

## 왜 채용시장이 요구하는가

- **자율 탐색은 Agentic Testing의 가장 화제성 있는 부분**이고, 동시에 가장 과장되기 쉬운 부분이다. **한계를 정확히 말할 수 있는 것**이 오히려 변별력이다.
- 면접 질문: **"AI가 탐색적 테스트를 대체할 수 있을까요?"** — "보완이지 대체가 아니다"와 그 근거(기대값을 모른다, 도메인 직관이 없다)를 말할 수 있어야 한다.
- **가드레일 설계**는 실제로 운영해 본 사람만 말한다. 결제 차단, 스텝 제한, 환경 격리를 구체적으로 설명하면 강하다.
- **접근성 트리 기반 탐색**과 **접근성이 나쁘면 에이전트도 못 쓴다**는 통찰은 매우 드물다.

## 실습 과제

### 과제 1 — 접근성 트리 직접 보기 (12분)

Playwright로 아무 페이지의 접근성 트리를 덤프한다.

```javascript
// snapshot.mjs
import { chromium } from 'playwright';
const b = await chromium.launch();
const p = await b.newPage();
await p.goto('https://demo.playwright.dev/todomvc');
console.log(JSON.stringify(await p.accessibility.snapshot(), null, 2));
await b.close();
```

1. 출력을 읽고 **에이전트가 무엇을 할 수 있다고 판단할지** 예상해 본다
2. 실습 랩의 샘플 앱으로도 해본다
3. **div로 만든 버튼**이 트리에 어떻게 나오는지 확인 → 에이전트가 못 찾는 것을 확인

3번이 이 과제의 핵심이다. 접근성과 에이전트 가용성의 관계를 체감한다.

### 과제 2 — 수동 탐색 루프 (18분)

**자동화하기 전에 사람이 에이전트 역할을 해본다.**

실습 랩의 결함 샘플 앱을 대상으로:

1. 차터를 하나 정한다 ("장바구니를 경계값 관점으로")
2. 매 스텝마다 아래를 기록하며 진행한다 (10스텝)

```text
스텝 N
  현재 화면: (무엇이 보이는가)
  왜: (이 행동을 하는 이유)
  행동: (무엇을 했는가)
  결과: (무엇이 일어났는가)
  발견: (있으면)
```

이 로그가 **에이전트에게 시킬 프롬프트의 설계도**가 된다. 사람이 무엇을 보고 판단했는지 알아야 에이전트에게 무엇을 줘야 할지 안다.

### 과제 3 — 가드레일 구현 (15분)

Playwright 스크립트에 가드레일을 넣는다.

1. 결제 관련 POST 요청 차단
2. 외부 도메인 이동 차단
3. 최대 스텝 카운터
4. 콘솔 에러 / 5xx 응답 수집

그리고 **일부러 차단 대상을 호출해 보고** 로그에 남는지 확인한다.

### 과제 4 — 에이전트 탐색 실행 (20분, MCP 사용 시)

Playwright MCP를 지원하는 도구(3편)에서:

1. 이 레슨의 차터 프롬프트를 준다
2. 대상: 실습 랩 샘플 앱 또는 로컬에 띄운 연습 앱
3. 최대 15스텝으로 제한
4. finding 을 JSON 으로 받는다

**MCP 환경이 없다면**: 접근성 트리 스냅샷을 수동으로 떠서 AI에게 주고 "다음에 무엇을 할지" 물은 뒤, 사람이 대신 실행하고 결과를 다시 주는 방식으로 3~5스텝 반복한다. 루프의 원리는 같다.

### 과제 6 — 명세 유무 비교 (12분)

- A: 차터만 제공
- B: 차터 + 검증 기준(계산 규칙, 허용 범위)

| 비교 | A | B |

**B에서만 잡히는 것이 무엇인지** 확인한다. 이게 "기대값을 알아야 검증"이라는 원리의 실증이다.

## 자가 체크리스트

- [ ] 3단계가 1·2단계와 근본적으로 다른 점을 설명할 수 있다
- [ ] 에이전트 탐색이 사람의 탐색적 테스트를 대체가 아니라 보완한다는 것을 안다
- [ ] 사람과 에이전트가 각각 잘하는 탐색 유형을 구분할 수 있다
- [ ] 스크린샷 방식과 접근성 트리 방식의 차이와 장단점을 안다
- [ ] 접근성 트리에 참조 ID와 역할이 있어 에이전트에 유리한 이유를 안다
- [ ] 접근성이 나쁜 앱은 에이전트도 탐색하지 못한다는 것을 안다
- [ ] SBTM 차터를 에이전트 프롬프트로 옮길 수 있다
- [ ] "행동 전에 이유를 말하라" 지시가 주는 두 가지 효과를 안다
- [ ] 가드레일 6가지 범주(환경·계정·행동·실행·데이터·관찰)를 설계할 수 있다
- [ ] `page.route` 로 위험한 요청을 차단하는 코드를 쓸 수 있다
- [ ] 최대 스텝 제한이 없으면 무한 루프와 비용 문제가 생긴다는 것을 안다
- [ ] 매 스텝 콘솔 에러와 5xx 응답을 수집해야 하는 이유를 안다
- [ ] 에이전트가 잘 찾는 것과 못 찾는 것을 각각 5가지 이상 말할 수 있다
- [ ] **명세 없이는 기대값이 없어 검증이 안 된다**는 근본 한계를 설명할 수 있다
- [ ] 오탐율이 높다는 전제로 검토 프로세스를 설계할 수 있다
- [ ] 사람 탐색과 에이전트 탐색을 조합하는 선순환 구조를 설계할 수 있다
