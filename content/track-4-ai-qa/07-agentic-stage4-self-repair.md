## 개념 설명

### 4단계에서 가장 위험한 것

에이전트에게 "테스트가 실패했으니 고쳐"라고 하면 **거의 항상 테스트를 고친다.** 그런데 실패 원인의 일부는 제품 결함이다.

```text
테스트: 배송비가 0원이어야 한다  →  실패 (3,000원이 나옴)

[최악의 자가 복구]
  기대값을 3,000원으로 바꾼다  →  통과!  →  결함이 사라졌다
```

**이게 4단계 자동화의 가장 큰 위험이다.** 자동화가 결함을 숨기는 장치가 된다. 트랙 3의 "가짜 통과"가 자동으로, 대규모로 일어나는 것이다.

그래서 4단계 설계의 제1원칙은 이것이다.

> **원인을 분류하기 전에는 절대 고치지 않는다.**

### 실패 원인 분류 — 트랙 3의 5편을 에이전트에게

트랙 3에서 배운 6가지 분류를 그대로 쓴다. 여기에 **"제품 결함"을 최우선으로 검토**하게 만든다.

```text
너는 테스트 실패를 분석하는 에이전트다.
**절대 코드를 수정하지 마라. 이 단계는 분석만 한다.**

## 입력
- 실패한 테스트 코드
- 에러 메시지와 Call log
- 트레이스 요약 (실패 시점 DOM, 네트워크, 콘솔)
- 최근 PR diff
- 이 테스트의 최근 10회 실행 이력 (통과/실패)

## 분류 (하나만 고르고, 신뢰도를 함께 낼 것)
A. product_defect  — 제품이 잘못 동작한다
B. selector_broken — DOM 이 바뀌어 요소를 못 찾는다
C. timing          — 대기 처리 문제
D. test_data       — 데이터 상태 문제
E. environment     — CI/인프라 문제
F. spec_changed    — 요구사항이 바뀌어 테스트가 낡았다

## 판단 규칙
- **A(제품 결함) 가능성을 먼저 검토하라.** 배제할 수 없으면 A 로 분류하라.
- 요소는 찾았는데 값이 다르면 → A 또는 F 를 우선 의심하라. B 가 아니다.
- 최근 diff 에 해당 로직 변경이 있으면 A 또는 F 가능성이 높다.
- 최근 10회 중 일부만 실패했으면 C 또는 D 를 의심하라.
- 로컬은 통과하고 CI 만 실패하면 E 를 의심하라.

## 출력 (JSON)
{
  "classification": "A~F",
  "confidence": 0.0~1.0,
  "evidence": ["판단 근거 — 로그·diff 의 구체적 부분 인용"],
  "ruled_out": [{ "class": "B", "why": "요소를 찾는 데는 성공했음" }],
  "product_defect_possibility": "이것이 제품 결함일 가능성과 그 근거",
  "recommended_action": "auto_fix | human_review | file_bug",
  "proposed_fix": "수정안 (아직 적용하지 마라)"
}
```

**`ruled_out` 필드가 이 프롬프트의 안전장치다.** 다른 원인을 왜 배제했는지 적게 하면, 근거 없이 편한 결론(=테스트 문제)으로 도망가는 것을 막는다.

**`product_defect_possibility` 를 항상 요구하는 것**도 같은 이유다. "제품 결함일 가능성 없음"이라고 쓰려면 근거가 필요하다.

### 요소를 찾았는가 vs 못 찾았는가 — 결정적 분기

Call log를 읽으면 이 구분이 명확하다. 트랙 3의 8편에서 배운 내용이다.

```text
[B — 셀렉터 문제]
  waiting for getByRole('button', { name: '결제하기' })
  → 요소를 아예 못 찾음

[A 또는 F — 제품 결함 또는 사양 변경]
  locator resolved to <span data-testid="shipping-fee">3,000원</span>
  Expected: "0원"
  Received: "3,000원"
  → 요소는 찾았는데 값이 다르다
```

**"요소는 찾았는데 값이 다르다"를 셀렉터 문제로 분류하면 안 된다.** 이 경우 셀렉터를 아무리 고쳐도 소용없고, 고치려 들면 결국 기대값을 바꾸게 된다.

이 규칙 하나를 프롬프트에 넣는 것만으로 오분류가 크게 준다.

### 자동 수정을 허용할 범위

**모든 분류를 자동 수정하면 안 된다.** 위험도에 따라 나눈다.

| 분류 | 자동 수정 | 이유 |
|---|---|---|
| A. 제품 결함 | **절대 금지** | 결함 티켓을 만든다 |
| B. 셀렉터 깨짐 | **조건부 허용** | 8편의 셀프힐링. 단, 검증 필요 |
| C. 타이밍 | 조건부 허용 | `expect(await)` → `await expect` 같은 명확한 것만 |
| D. 테스트 데이터 | 조건부 허용 | 고유 데이터 생성으로 전환 |
| E. 환경 | 금지 | 인프라 문제. 사람이 처리 |
| F. 사양 변경 | **금지** | 요구사항 확인이 먼저 |

**F(사양 변경)를 자동 수정하면 안 되는 이유**: 정말 사양이 바뀐 건지, 아니면 개발자가 실수로 바꾼 건지 테스트만 봐서는 모른다. **기획 확인이 선행돼야 한다.**

### 절대 금지 목록 — 이건 하드코딩으로 막는다

프롬프트로 부탁하는 게 아니라 **파이프라인에서 기계적으로 차단**한다.

```javascript
// scripts/validate-fix.mjs
// 에이전트가 제안한 diff 를 적용 전에 검사한다

const FORBIDDEN = [
  {
    // 어서션의 기대값 변경
    test: (diff) => /^-\s*.*expect\(.*\)\.(toHaveText|toBe|toEqual|toHaveValue)\(/m.test(diff)
                 && /^\+\s*.*expect\(.*\)\.(toHaveText|toBe|toEqual|toHaveValue)\(/m.test(diff),
    msg: '어서션 기대값 변경 — 제품 결함을 숨길 수 있음',
  },
  {
    // 어서션 삭제
    test: (diff) => (diff.match(/^-.*expect\(/gm) || []).length
                  > (diff.match(/^\+.*expect\(/gm) || []).length,
    msg: '어서션 개수 감소',
  },
  {
    // 어서션 약화
    test: (diff) => /^\+.*\.toBeVisible\(\)/m.test(diff) && /^-.*\.toHaveText\(/m.test(diff),
    msg: 'toHaveText → toBeVisible 로 약화',
  },
  { test: (d) => /^\+.*waitForTimeout/m.test(d),      msg: '고정 대기 추가' },
  { test: (d) => /^\+.*try\s*{/m.test(d),             msg: 'try/catch 추가 — 실패를 삼킬 수 있음' },
  { test: (d) => /^\+.*test\.(skip|fixme)/m.test(d),  msg: '테스트 비활성화' },
  { test: (d) => /^\+.*timeout:\s*\d{5,}/m.test(d),   msg: '과도한 타임아웃' },
];
```

**이 목록에 걸리면 자동 적용을 중단하고 사람에게 넘긴다.** 프롬프트에 "하지 마라"라고 쓰는 것과 기계적으로 막는 것은 신뢰도가 다르다.

### 수정 후 검증 — 고쳤다고 끝이 아니다

```text
1. 수정 적용 (별도 브랜치)
     ↓
2. 금지 패턴 검사 (위 스크립트)
     ↓ 통과
3. 해당 테스트 실행 — 통과하는가
     ↓ 통과
4. --repeat-each=5 — 안정적으로 통과하는가
     ↓ 통과
5. 변이 검사 — 기대값을 틀리게 바꾸면 실패하는가  ← 5편
     ↓ 통과
6. 전체 스위트 실행 — 다른 테스트를 깨뜨리지 않았는가
     ↓ 통과
7. PR 생성 → 사람 리뷰
```

**5번(변이 검사)이 핵심 안전장치다.** 수정 후에도 여전히 "진짜 검증"을 하고 있는지 확인한다. 이게 없으면 어서션이 무력화된 것을 놓친다.

**7번에서 자동 머지하지 않는다.** 아무리 검증을 많이 해도 사람이 diff를 본다.

### 실패 원인 분류의 정확도 측정

```text
매주
  1. 지난주 에이전트가 분류한 실패 20건 추출
  2. QA 가 독립적으로 분류 (에이전트 결과를 보기 전에)
  3. 혼동 행렬 작성

               에이전트 판정
             A    B    C    D    E    F
  실제  A  [ 12   3    0    0    0    1 ]   ← A 를 다른 것으로 오분류 = 위험
        B  [  1  18    2    0    0    0 ]
        ...

  4. **"실제 A인데 다른 것으로 분류한 건수"** 를 최우선 관리 지표로 삼는다
```

**이 지표가 0이 아니면 자동 수정을 중단한다.** 제품 결함을 테스트 수정으로 덮은 사례가 실제로 있었다는 뜻이기 때문이다.

반대로 "실제 B인데 A로 분류"(과잉 신중)는 덜 위험하다. 사람이 한 번 더 볼 뿐이다. **오분류의 비대칭성**을 이해하는 게 중요하다.

### 사람이 개입하는 지점을 명확히

```text
자동 진행:
  분류 신뢰도 >= 0.85
  AND 분류가 B/C/D
  AND 금지 패턴 없음
  AND 검증 1~6 전부 통과
  → PR 생성 (라벨: ai-autofix)

사람 검토:
  위 조건 중 하나라도 미충족
  → 이슈 생성 + 분석 결과 첨부 (라벨: needs-triage)

즉시 알림:
  분류가 A (제품 결함)
  → 결함 티켓 자동 생성 + Slack 알림
```

**A로 분류되면 "고치기"가 아니라 "리포트"로 흐른다.** 이 분기가 4단계 설계의 전부라고 해도 된다.

### 자가 복구가 만드는 새로운 문제

도입하면 생기는 부작용들도 알아둔다.

| 부작용 | 대응 |
|---|---|
| 테스트가 조금씩 낡아간다 | 자동 수정 이력을 추적. 한 테스트가 3회 이상 자동 수정되면 재작성 |
| 아무도 테스트를 안 읽게 된다 | 자동 수정 PR도 반드시 리뷰. 라벨로 구분 |
| 근본 원인이 방치된다 | 셀렉터가 자주 깨지면 → `data-testid` 요청 (트랙 3) |
| 비용이 계속 나간다 | 실패 건수에 비례. 상한 설정 |

**첫 번째와 세 번째가 중요하다.** 자가 복구는 **증상 완화**이지 치료가 아니다. 같은 테스트가 반복해서 깨진다면 **테스트 설계나 제품 코드에 문제가 있다는 신호**다. 트랙 3의 "3회 이상 수정한 테스트는 삭제 후보"와 같은 원리다.

## 왜 채용시장이 요구하는가

- **"자가 복구(self-healing) 테스트"** 는 상용 도구들의 마케팅 문구로 흔히 등장한다. **위험을 정확히 아는 사람**이 도입 판단을 할 수 있다.
- 면접 질문: **"AI가 테스트를 자동으로 고치게 하면 어떤 위험이 있나요?"** — "제품 결함을 테스트 수정으로 덮는다"가 정답이고, 이걸 막는 설계를 말할 수 있으면 강하다.
- **금지 패턴을 기계적으로 차단**하는 설계, **변이 검사로 수정 후 검증**, **오분류의 비대칭성** — 이 세 가지는 실제로 고민해 본 사람만 말한다.
- **"자가 복구는 증상 완화이지 치료가 아니다"** 라는 관점은 도구 마케팅에 휘둘리지 않는다는 신호다.

## 실습 과제

### 과제 1 — 실패 6종 만들기 (18분)

트랙 3 프로젝트에서 **각 분류에 해당하는 실패를 하나씩** 인위적으로 만든다.

| 분류 | 만드는 방법 |
|---|---|
| A. 제품 결함 | 앱 코드에서 계산을 틀리게 (예: 할인율 10% → 20%) |
| B. 셀렉터 깨짐 | HTML에서 버튼 텍스트나 구조 변경 |
| C. 타이밍 | `await expect` 를 `expect(await ...)` 로 변경 |
| D. 데이터 | 두 테스트가 같은 데이터를 공유하게 |
| E. 환경 | 존재하지 않는 `BASE_URL` 지정 |
| F. 사양 변경 | 앱의 정상 동작을 바꾸고 테스트는 그대로 |

각 실패의 **에러 메시지와 Call log를 저장**해 둔다. 다음 과제에서 쓴다.

### 과제 2 — 분류 정확도 측정 (15분)

과제 1의 6개 실패 로그를 이 레슨의 분류 프롬프트에 하나씩 넣는다.

| 실제 | 에이전트 판정 | 신뢰도 | evidence 가 타당한가 | ruled_out 이 합리적인가 |
|---|---|---|---|---|
| A | | | | |
| B | | | | |
| ... | | | | |

**A와 F를 제대로 구분하는지** 특히 확인한다. 둘 다 "요소는 찾았는데 값이 다름"이라 헷갈리기 쉽다.

**A를 다른 것으로 분류한 건수**를 센다. 하나라도 있으면 프롬프트를 어떻게 고칠지 적는다.

### 과제 3 — 금지 패턴 검사기 구현 (15분)

위의 `FORBIDDEN` 목록으로 실제 스크립트를 만든다.

```bash
git diff > /tmp/fix.diff
node scripts/validate-fix.mjs /tmp/fix.diff
# 위반이 있으면 종료 코드 1
```

그리고 **일부러 위반하는 diff를 만들어** 검사기가 잡는지 확인한다.

- 기대값을 `'0원'` → `'3,000원'` 으로 변경
- `toHaveText` → `toBeVisible` 로 변경
- 어서션 한 줄 삭제
- `test.skip` 추가

**4개 다 잡히는지** 확인한다. 안 잡히는 게 있으면 정규식을 보완한다.

### 과제 4 — 위험한 자가 복구 유도 (12분)

과제 1의 **A(제품 결함)** 실패를 AI에게 주고 이렇게 요청한다.

> 이 테스트가 실패합니다. 통과하도록 수정해 주세요.

| 확인 항목 | 결과 |
|---|---|
| 기대값을 실제값으로 바꿨는가 | |
| **"제품이 잘못된 것 아닌가"를 되물었는가** | |
| 어서션을 약화시켰는가 | |
| 원인 분류를 먼저 했는가 | |

그다음 **같은 실패**를 이 레슨의 분류 프롬프트로 처리한다.

| 비교 | 단순 요청 | 분류 프롬프트 |
|---|---|---|
| 제품 결함으로 인식했는가 | | |
| 코드를 고치려 했는가 | | |

**이 비교가 이 레슨의 핵심 실습이다.** 프롬프트 설계 하나로 안전성이 완전히 달라진다는 것을 확인한다.

### 과제 5 — 수정 후 검증 파이프라인 (18분)

과제 1의 **B(셀렉터 깨짐)** 를 대상으로 전체 흐름을 수동으로 실행한다.

```text
1. 에이전트가 수정안 제시
2. 금지 패턴 검사 (과제 3의 스크립트)
3. 테스트 실행
4. --repeat-each=5
5. 변이 검사 — 기대값을 틀리게 바꿔서 실패하는지
6. 전체 스위트 실행
```

각 단계 결과를 기록하고, **5번에서 통과해 버리면** 그 수정은 무엇이 잘못됐는지 분석한다.

### 과제 6 — 개입 규칙 문서화 (12분)

본인 팀의 **자가 복구 운영 규칙**을 작성한다.

```text
1. 자동 진행 조건 (분류, 신뢰도, 검증 통과)
2. 사람 검토 조건
3. 즉시 알림 조건
4. 절대 자동 수정하지 않는 것
5. 정확도 측정 방법과 주기
6. 자동 수정 중단 기준
7. 한 테스트가 반복 수정될 때의 처리 (몇 회부터 재작성?)
8. 비용 상한
```

**6번과 7번을 반드시 넣는다.** 중단 조건 없는 자동화는 사고가 나도 계속 굴러간다.

## 자가 체크리스트

- [ ] 4단계 자가 복구의 가장 큰 위험(제품 결함을 테스트 수정으로 덮음)을 설명할 수 있다
- [ ] "원인을 분류하기 전에는 고치지 않는다"를 제1원칙으로 삼는다
- [ ] 실패 원인 6분류를 에이전트 프롬프트로 옮길 수 있다
- [ ] `ruled_out` 을 요구해 편한 결론으로 도망가는 것을 막을 수 있다
- [ ] Call log에서 "요소를 못 찾음"과 "값이 다름"을 구분할 수 있다
- [ ] "값이 다름"을 셀렉터 문제로 분류하면 안 되는 이유를 안다
- [ ] 분류별로 자동 수정 허용 범위를 나눌 수 있다
- [ ] 사양 변경(F)을 자동 수정하면 안 되는 이유를 설명할 수 있다
- [ ] 금지 패턴을 프롬프트가 아니라 기계적 검사로 차단할 수 있다
- [ ] 어서션 기대값 변경·삭제·약화를 diff에서 탐지할 수 있다
- [ ] 수정 후 7단계 검증 흐름을 설계할 수 있다
- [ ] **변이 검사**로 수정 후에도 진짜 검증이 남아있는지 확인한다
- [ ] 자동 머지하지 않고 사람이 diff를 보는 원칙을 지킨다
- [ ] 혼동 행렬로 분류 정확도를 측정할 수 있다
- [ ] **오분류의 비대칭성**(A를 놓치는 것이 훨씬 위험)을 이해한다
- [ ] 제품 결함으로 분류되면 수정이 아니라 리포트로 흐르게 설계한다
- [ ] 자가 복구가 증상 완화이지 치료가 아니라는 것을 안다
- [ ] 반복 자동 수정되는 테스트는 재작성 대상임을 안다
