## 개념 설명

### 나쁜 프롬프트와 좋은 프롬프트

```text
[나쁨] 로그인 기능 테스트 케이스 만들어줘
```

이렇게 하면 대체로 이런 게 나온다.

```text
1. 올바른 아이디와 비밀번호로 로그인 → 성공
2. 잘못된 비밀번호로 로그인 → 실패
3. 빈 값으로 로그인 → 오류 메시지
...
```

**틀린 건 없는데 쓸모가 없다.** 이 정도는 누구나 5분이면 쓴다. 경계값이 없고, 우선순위가 없고, 무엇보다 **모호한 부분을 물어보지 않는다.** 트랙 1에서 배운 기법이 하나도 적용되지 않았다.

AI에게 TC를 시킬 때 결과 품질을 결정하는 건 모델이 아니라 **프롬프트에 무엇을 넣었는가**다.

### 좋은 프롬프트의 5요소

```text
1. 역할과 기준     — 누구처럼 생각할 것인가
2. 입력 컨텍스트   — 요구사항, 화면 구조, 도메인 제약
3. 적용할 기법     — 동등분할, 경계값, 상태전이, 결정테이블, 페어와이즈
4. 출력 형식       — 표 컬럼까지 지정
5. 검증 지시       — 모르는 것은 질문으로, 추측 금지
```

**5번이 가장 중요하고 대부분이 빠뜨린다.** 이걸 넣지 않으면 AI는 명세에 없는 규칙을 지어내서 채워 넣는다.

### 실제로 쓰는 프롬프트 템플릿

```text
너는 15년 경력의 시니어 QA 엔지니어다.

## 대상
[요구사항 명세 또는 화면 설명을 여기에]

## 설계 규칙
- 동등분할과 경계값 분석을 반드시 적용하고, 각 TC에 사용한 기법을 표시하라.
- 조건이 2개 이상 얽히면 결정테이블로 전체 조합을 먼저 나열한 뒤 압축하라.
- 상태가 있는 기능이면 불가 전이(일어나면 안 되는 전이)를 반드시 포함하라.
- 비유효 케이스는 한 번에 하나씩만 위반시켜라. (결함 마스킹 방지)
- 우선순위는 High/Medium/Low 로 매기고, High 는 전체의 30% 이내로 제한하라.

## 금지
- 요구사항에 없는 규칙을 만들어내지 마라.
- 확인할 수 없는 것은 "확인 필요"로 표시하라.

## 출력
1) 테스트 케이스 표
   | TC ID | 구분 | 적용 기법 | 사전조건 | 절차 | 입력 | 기대 결과 | 우선순위 |
2) "커버하지 못한 영역"
3) "요구사항에서 판단할 수 없어 확인이 필요한 질문" (최소 3개)
```

**"High 는 전체의 30% 이내"** 같은 제약이 실전에서 큰 차이를 만든다. 제약이 없으면 AI는 모든 걸 High로 매긴다. 우선순위가 전부 높으면 우선순위가 없는 것이다.

### 컨텍스트를 무엇으로 줄 것인가

같은 프롬프트라도 입력이 무엇이냐에 따라 결과가 다르다. **좋은 순서**가 있다.

| 입력 | 품질 | 비고 |
|---|---|---|
| **OpenAPI 명세** | 최상 | 필드·타입·제약·응답코드가 구조화돼 있다 (트랙 2) |
| DB 스키마 | 상 | 제약조건, NOT NULL, 관계에서 경계가 나온다 |
| 기획서 + 화면 캡처 | 중상 | 멀티모달 모델이면 화면을 읽는다 |
| PR diff | 상 | **무엇이 바뀌었는지** — 회귀 범위 판단에 직접 쓰인다 (4편) |
| 기존 TC 몇 건 | 중 | 팀의 작성 스타일을 학습시킨다 (few-shot) |
| 한 줄 설명 | 하 | 일반론만 나온다 |

**여러 개를 함께 주는 게 가장 좋다.** OpenAPI 명세 + 기존 TC 3건 + 도메인 제약을 함께 넣으면 결과가 크게 달라진다.

### Few-shot — 우리 팀 스타일을 학습시키기

가장 효과가 큰데 잘 안 쓰는 기법이다. **기존 TC 2~3건을 예시로 넣는다.**

```text
## 우리 팀의 TC 작성 예시 (이 형식과 상세도를 따르라)

| TC-PAY-001 | 정상 | 경계값 | 로그인 상태, 장바구니 1건 | 1. 장바구니 진입 2. 쿠폰 "WELCOME10" 적용 3. 결제 버튼 클릭 | 상품 10,000원 | 결제금액 9,000원, 주문상태 PENDING, DB orders.total_amount = 9000 | High |

이제 아래 요구사항에 대해 같은 형식으로 작성하라.
```

이렇게 하면 **"DB 값까지 기대 결과에 적는다"** 같은 팀 관행이 그대로 따라온다. 형식을 말로 설명하는 것보다 예시 하나가 훨씬 정확하다.

### AI가 잘하는 것과 못하는 것

이걸 알아야 어디를 검증할지 안다.

| 잘한다 | 못한다 |
|---|---|
| 빠짐없이 나열하기 (조합, 필드별 케이스) | **범위를 좁히는 판단** |
| 형식 맞추기 | 우선순위의 근거 있는 차등 |
| 놓치기 쉬운 관점 상기 (보안, 접근성) | 도메인 특유의 암묵적 규칙 |
| 기존 TC를 다른 형식으로 변환 | 명세에 없는 것을 질문으로 만들기 |
| 반복 작업 (100개 상품에 대한 데이터셋) | 비즈니스 임팩트 판단 |

**"범위를 좁히는 판단"을 못 한다는 게 핵심이다.** AI는 200건을 만들어 준다. 그중 이번 릴리즈에 필요한 30건을 고르는 게 사람의 일이고, 그 판단 근거가 트랙 1의 리스크 기반 계획이다.

### 검증 체크리스트 — AI가 만든 TC를 채점하는 법

받은 결과를 **반드시** 이 순서로 검토한다.

```text
□ 1. 요구사항에 없는 규칙을 지어냈는가        ← 가장 위험
□ 2. 경계값이 실제로 경계인가 (0, 1, max, max+1)
□ 3. 비유효 케이스가 한 번에 하나씩인가
□ 4. 조합이 빠진 곳은 없는가 (결정테이블과 대조)
□ 5. 불가 전이가 포함됐는가
□ 6. 기대 결과가 검증 가능한 형태인가 ("정상 동작한다" 금지)
□ 7. 우선순위에 근거가 있는가
□ 8. 중복 케이스가 없는가
□ 9. "확인 필요" 질문이 실제로 모호한 지점을 짚었는가
□ 10. 우리 도메인에서 불가능한 케이스가 섞이지 않았는가
```

**1번이 가장 위험한 이유**: 지어낸 규칙으로 만든 TC를 실행하면 "실패"가 나온다. 그걸 결함으로 리포트하면 개발자가 "그런 요구사항 없는데요"라고 답한다. **QA의 신뢰가 깎인다.**

전형적인 환각 예시:

```text
요구사항: "비밀번호는 8자 이상"

AI 생성 TC:
  - 비밀번호 5회 실패 시 계정 잠금 확인      ← 요구사항에 없음
  - 비밀번호 90일마다 변경 요구 확인          ← 요구사항에 없음
  - 이전 3개 비밀번호 재사용 금지 확인        ← 요구사항에 없음
```

**틀린 건 아니다. 일반적인 보안 관행이다.** 하지만 이 제품의 요구사항이 아니다. AI는 "일반적으로 이럴 것이다"를 채워 넣는다.

**올바른 처리**: 이런 항목을 발견하면 지우는 게 아니라 **"확인 필요 질문"으로 옮긴다.**

> "비밀번호 실패 횟수 제한 정책이 있나요? 명세에 없어 TC에서 제외했습니다."

이러면 AI의 환각이 **오히려 명세 결함을 발견하는 도구**가 된다. 이게 AI를 제대로 쓰는 방식이다.

### 반복 개선 — 한 번에 끝내지 않는다

```text
1차: 전체 TC 초안 생성
2차: "경계값이 빠진 곳을 찾아 추가하라"
3차: "이 TC 목록에서 중복되거나 가치가 낮은 것을 골라내라"
4차: "우선순위 High 를 5건 이내로 줄이고, 각각 근거를 적어라"
5차: "이 TC들이 커버하지 못하는 리스크를 3가지 지적하라"
```

**3차와 5차가 특히 유용하다.** AI에게 자기 결과물을 비판하게 시키면 의외로 잘 찾는다. 다만 **그 비판도 검증 대상**이다.

### 비용을 0원으로 유지하기

이 플랫폼의 AI 실습 도우미는 BYOK 방식이라 **내 키를 넣어야 동작**한다. 무료로 쓰려면:

- **Google Gemini 무료 티어** — 분당·일일 호출 제한 내에서 무과금
- **Ollama 로컬 모델** — 완전 무료, 오프라인. 품질은 낮지만 형식 변환 작업엔 충분
- **키 없이 프롬프트만 복사** — AI 패널의 "프롬프트 복사" 버튼으로 만들어 평소 쓰는 도구에 붙여넣기

**프롬프트 설계 능력 자체가 학습 목표**이므로, 어느 도구에 붙여넣든 상관없다.

## 왜 채용시장이 요구하는가

- 2026년 QA 채용공고에 **"AI 활용 테스트 설계"** 가 명시적으로 등장한다. 이제 "AI를 써봤다"는 변별력이 없고, **"어떻게 검증하며 쓰는가"** 가 변별력이다.
- 면접 질문: **"AI로 TC를 생성해 보셨나요? 결과를 어떻게 검증하셨나요?"** — 두 번째 질문에 답할 수 있어야 한다. 위 10개 체크리스트가 그 답이다.
- **환각을 명세 결함 발견으로 전환하는 관점**은 흔치 않아서 강한 인상을 준다.
- **프롬프트를 자산으로 관리하는 팀**이 늘고 있다. 잘 만든 프롬프트를 Confluence에 정리해 팀이 공유하는 것 자체가 QA의 산출물이 된다.

## 실습 과제

### 과제 1 — 나쁜 프롬프트 vs 좋은 프롬프트 (15분)

같은 요구사항으로 **두 번** 생성해 비교한다.

```text
요구사항: 쿠폰은 주문당 1장만 사용할 수 있다. 정액 쿠폰(5,000원 할인)과
정률 쿠폰(10% 할인, 최대 20,000원)이 있다. 최소 주문금액 10,000원 이상부터
사용 가능하다. 휴면 회원은 쿠폰을 사용할 수 없다.
```

- **A**: "위 요구사항의 테스트 케이스를 만들어줘"
- **B**: 이 레슨의 5요소 템플릿을 적용

| 비교 항목 | A | B |
|---|---|---|
| TC 건수 | | |
| 경계값 포함 (9,999 / 10,000) | | |
| 정률 쿠폰 상한(20,000원) 경계 | | |
| 조합 커버리지 | | |
| 우선순위 차등 | | |
| 확인 필요 질문 | | |
| 지어낸 규칙 | | |

**정률 쿠폰 상한 경계**를 A가 잡는지 꼭 확인한다. 20만원 주문에 10%면 2만원인데, 상한이 2만원이므로 **정확히 20만원이 경계**다.

### 과제 2 — Few-shot 효과 측정 (12분)

과제 1의 B 프롬프트에 **본인이 트랙 1에서 작성한 TC 2건을 예시로 추가**하고 다시 생성한다.

- 형식이 예시를 따라갔는가
- 상세도(DB 검증 포함 여부 등)가 달라졌는가
- 예시에 없던 컬럼을 임의로 추가했는가

### 과제 3 — 환각 찾아내기 (12분)

일부러 **정보가 부족한 요구사항**을 준다.

```text
요구사항: 사용자는 프로필 사진을 업로드할 수 있다.
```

AI가 생성한 TC에서 **요구사항에 없는데 등장한 항목**을 전부 찾아 표로 만든다.

| AI가 만든 TC | 근거가 요구사항에 있는가 | 확인 필요 질문으로 전환 |
|---|---|---|
| 5MB 초과 파일 업로드 시 오류 | 없음 (크기 제한 미명시) | "파일 크기 제한이 있나요?" |
| JPG/PNG 외 형식 거부 | | |
| | | |

**최소 8개는 나온다.** 그 8개가 곧 기획자에게 보낼 질문 목록이다. 이게 이 과제의 진짜 산출물이다.

### 과제 4 — 반복 개선 5단계 (15분)

과제 1의 결과에 5단계 개선 프롬프트를 순서대로 적용하고, 각 단계에서 **무엇이 좋아졌고 무엇이 나빠졌는지** 기록한다.

특히 3차("가치가 낮은 것 골라내기")에서 **AI가 지우자고 한 TC 중 실제로는 남겨야 할 것**이 있는지 확인한다. 있다면 왜 AI가 그걸 저평가했는지 분석한다.

### 과제 5 — 팀 프롬프트 자산 만들기 (12분)

본인 도메인에 맞춘 **재사용 가능한 TC 생성 프롬프트**를 완성해 저장한다.

포함할 것:
- 도메인 특유의 제약 (예: 금융이면 원 단위 절사 규칙, 커머스면 재고·배송 정책)
- 팀의 TC 형식 예시 2건
- 우선순위 기준
- 절대 지어내면 안 되는 항목 목록

이 프롬프트를 이 레슨의 **내 메모**에 저장해 두고, 앞으로 실무에서 계속 다듬는다.

## 자가 체크리스트

- [ ] "TC 만들어줘" 수준의 프롬프트가 왜 쓸모없는지 설명할 수 있다
- [ ] 좋은 프롬프트의 5요소를 나열할 수 있다
- [ ] "추측 금지, 모르면 확인 필요로 표시" 지시가 왜 가장 중요한지 안다
- [ ] 우선순위에 비율 제약을 걸지 않으면 전부 High가 되는 문제를 안다
- [ ] 입력 컨텍스트의 품질 순서(OpenAPI > 스키마 > 기획서 > 한 줄)를 안다
- [ ] Few-shot으로 팀의 TC 형식과 상세도를 학습시킬 수 있다
- [ ] AI가 잘하는 것과 못하는 것을 각각 5가지 이상 구분할 수 있다
- [ ] AI가 "범위를 좁히는 판단"을 못 한다는 것과 그 의미를 안다
- [ ] AI 생성 TC 검증 체크리스트 10개를 적용할 수 있다
- [ ] 환각으로 지어낸 규칙을 삭제하지 않고 **확인 필요 질문으로 전환**할 수 있다
- [ ] 반복 개선 5단계를 적용하고, AI의 자기 비판도 검증 대상으로 본다
- [ ] 무료로 AI 기능을 쓰는 방법(Gemini 무료 티어, Ollama, 프롬프트 복사)을 안다
- [ ] 잘 만든 프롬프트를 팀 자산으로 관리할 수 있다
