## 개념 설명

### 왜 이 체크리스트가 필요한가

AI가 만든 산출물의 위험은 **틀렸다는 것이 아니라 그럴듯하다는 것**이다.

```text
사람이 만든 실수    → 대체로 어색해서 눈에 띈다
AI 가 만든 실수     → 문법 완벽, 형식 완벽, 자신감 넘침. 검증 없이는 안 보인다
```

그리고 AI 산출물은 **양이 많다.** 100건을 하나씩 정독할 수 없다. **체계적인 체크리스트와 자동 검사가 필요한 이유**다.

이 레슨은 트랙 4에서 흩어져 나온 검증 지침을 하나로 모으고, 트랙 6의 1~7편에서 얻은 판단력을 적용하는 곳이다.

### 6가지 결함 유형

```text
① 환각 (hallucination)      — 존재하지 않는 것을 있다고 함
② 가짜 통과                  — 실행은 되지만 아무것도 검증 안 함
③ 엣지 케이스 누락           — 정상 경로만 다룸
④ 잘못된 대기 처리           — 타이밍을 시간으로 때움
⑤ 하드코딩·격리 실패         — 재실행·병렬 실행이 안 됨
⑥ 맥락 무시                  — 우리 도메인·팀 규칙과 안 맞음
```

**위험도 순서는 ② > ① > ③ > ⑥ > ⑤ > ④** 다. 가짜 통과가 가장 위험한 이유는 **초록불이 뜨기 때문에 아무도 안 보기 때문**이다.

### ① 환각 — 존재하지 않는 것

```javascript
// 존재하지 않는 API
await page.waitForElementVisible('.btn');        // Playwright 에 없다
await page.getByRole('button').waitForClickable(); // 없다
expect(res).toHaveStatusCode(200);                // toHaveStatus 다

// 존재하지 않는 옵션
await page.click('.btn', { waitForNavigation: true });   // 없는 옵션

// 존재하지 않는 컬럼·테이블 (SQL)
SELECT o.customer_name FROM orders o;   -- users 에 있는 컬럼

// 존재하지 않는 라이브러리 함수
import { retryUntil } from '@playwright/test';   // 없다
```

**검증 방법**

```text
□ 공식 문서에서 이름 검색 (Playwright, k6, pytest 등)
□ 타입 체크 실행: npx tsc --noEmit          ← 가장 빠르고 확실
□ 린트 실행: npx eslint
□ IDE 자동완성에 뜨는가
□ SQL 이면 스키마와 대조
□ 실제로 실행
```

**`npx tsc --noEmit` 한 줄이 환각의 대부분을 잡는다.** TypeScript를 쓰는 이유 중 하나다 (트랙 3의 8편).

**교묘한 환각**도 있다. 존재하는 API를 **잘못된 맥락**에서 쓰는 경우다.

```javascript
// 존재하지만 여기 쓰면 안 되는 것
await page.$eval('.btn', el => el.click());   // 존재하지만 자동 대기가 없다
await page.evaluate(() => location.reload()); // 존재하지만 waitForLoadState 없이는 불안정
```

**이건 타입 체크로 안 잡힌다.** 사람이 판단해야 한다.

### ② 가짜 통과 — 가장 위험한 유형

**"테스트가 통과한다"와 "테스트가 검증한다"는 다르다.**

```javascript
// 유형 1: 어서션이 없다
test('주문 생성', async ({ page }) => {
  await page.goto('/order');
  await page.getByRole('button', { name: '주문' }).click();
  // 끝. 클릭만 하고 아무것도 확인 안 함
});

// 유형 2: 항상 참인 어서션
expect(res.status).toBeGreaterThan(0);
expect(body).toBeDefined();
expect(items.length).toBeGreaterThanOrEqual(0);   // 항상 참
expect([200, 400, 404]).toContain(res.status());  // 뭐가 와도 통과

// 유형 3: 존재만 확인
await expect(page.getByTestId('total')).toBeVisible();
// 금액이 맞는지는 확인 안 함

// 유형 4: try/catch 로 삼킴
try {
  await expect(page.getByText('완료')).toBeVisible();
} catch (e) { console.log('없음'); }

// 유형 5: 조건 분기로 회피
if (await page.getByText('쿠폰 적용됨').isVisible()) {
  await expect(total).toHaveText('9,000원');
}

// 유형 6: 기대값이 실제값에서 나옴
const actual = await page.getByTestId('total').textContent();
expect(actual).toBe(actual);   // 극단적이지만 변형이 실제로 나온다

// 유형 7: mock 이 전부 (Python/유닛)
mocker.patch('app.db.save', return_value=True)
mocker.patch('app.payment.charge', return_value=True)
assert create_order(data).success is True
```

**자동으로 잡는 방법 — 변이 검사 (트랙 4의 5편)**

```text
기대값을 일부러 틀리게 바꾼다 → 테스트가 실패해야 정상
여전히 통과하면 → 그 테스트는 가짜다
```

```bash
# 개념: 기대 문자열을 무작위로 치환하고 실행
sed -i "s/toHaveText('9,000원')/toHaveText('__MUTANT__')/" test.spec.ts
npx playwright test test.spec.ts
# 통과하면 문제. 실패해야 정상.
```

**정규식으로 잡는 방법**

```javascript
const FAKE_PASS = [
  { re: /toBeGreaterThanOrEqual\(0\)/,      msg: '항상 참인 어서션' },
  { re: /toBeDefined\(\)\s*;?\s*$/m,        msg: '존재만 확인' },
  { re: /toContain\(\[?\s*200[^)]*40\d/,    msg: '여러 상태코드 허용 = 검증 없음' },
  { re: /catch\s*\([^)]*\)\s*\{[^}]*\}/s,   msg: 'try/catch 로 어서션 감쌈' },
  { re: /if\s*\(await[^)]*isVisible\(\)\)/, msg: '조건 분기로 어서션 회피' },
  { re: /test\([^)]*\)[^{]*\{(?![\s\S]*expect)[\s\S]*?\n\}\)/, msg: '어서션 없는 테스트' },
];
```

**세는 방법도 있다.** 테스트 함수 하나당 `expect` 개수를 세서 0이면 경고.

### ③ 엣지 케이스 누락

AI는 **정상 경로를 잘 만들고 경계를 빠뜨린다.** 트랙 1의 기법으로 점검한다.

```text
□ 경계값 — 0, 1, 최대, 최대+1, 음수, 빈 값
□ null / undefined / 빈 배열 / 빈 문자열
□ 타입 오류 — 숫자 자리에 문자열
□ 권한 — 남의 리소스, 비로그인, 권한 없는 역할
□ 상태 — 불가 전이 (트랙 1)
□ 동시성 — 중복 클릭, 두 탭, 경쟁 조건 (트랙 6의 2편)
□ 실패 경로 — API 500, 타임아웃, 네트워크 끊김
□ 대용량 — 목록 0건 / 1건 / 1000건
□ 특수 문자 — 이모지, 개행, 따옴표, HTML 태그
□ 시간 — 자정 경계, 월말, 윤년, 타임존
```

**빠른 판정법**: 생성된 TC 목록에서 **"실패해야 정상인 케이스"의 비율**을 센다.

```text
정상 경로 12건 / 실패·경계 3건  →  20%. 너무 낮다.
실무에서는 40~60% 가 실패·경계 케이스여야 한다.
```

**요청에 명시하지 않으면 AI는 실패 경로를 거의 안 만든다.** 트랙 4의 1편에서 프롬프트에 기법을 명시한 이유다.

### ④ 잘못된 대기 처리

트랙 3의 3편 내용이 그대로 검증 항목이 된다.

```javascript
// ✗ 고정 대기
await page.waitForTimeout(3000);

// ✗ networkidle (트랙 6의 2편에서 이유를 다뤘다)
await page.waitForLoadState('networkidle');

// ✗ 재시도 안 되는 어서션
expect(await locator.textContent()).toBe('완료');

// ✗ 타임아웃만 늘리기
await expect(locator).toBeVisible({ timeout: 120000 });

// ✗ 대기 없이 바로 확인
await page.goto('/products');
expect(await page.getByTestId('card').count()).toBe(20);   // CSR 이면 0
```

**정규식으로 전부 잡힌다.** 트랙 4의 5편에서 만든 안티패턴 검사기를 쓴다.

**AI가 "안정적으로 만들어줘"라고 하면 오히려 나빠진다**는 것을 기억한다. sleep을 넣거나 try/catch로 감싼다.

### ⑤ 하드코딩·격리 실패

```javascript
// ✗ 환경 하드코딩
await page.goto('https://staging-3.internal.example.com/login');

// ✗ 계정 하드코딩 (게다가 커밋되면 유출)
await page.getByLabel('비밀번호').fill('Test1234!');

// ✗ 고정 테스트 데이터 — 병렬 실행 시 충돌 (트랙 3의 4편)
const email = 'qa@test.com';

// ✗ 순서 의존
await page.getByRole('row').nth(0).click();

// ✗ 날짜 하드코딩 — 내일이면 깨진다
await expect(page.getByTestId('date')).toHaveText('2026-08-15');

// ✗ 정리 없음 — 실행할수록 데이터가 쌓인다

// ✗ 실행 순서 의존
test('A: 생성'); test('B: A가 만든 것을 조회');
```

**검증 방법**

```text
□ 두 번 연속 실행 → 두 번째도 통과하는가
□ --repeat-each=3 → 전부 통과하는가
□ 병렬 실행 (fullyParallel) → 통과하는가
□ 테스트 순서를 섞어서 → 통과하는가
□ 다른 환경(BASE_URL 변경) → 동작하는가
□ 하드코딩된 비밀값이 없는가 (커밋 전 스캔)
```

**"두 번 연속 실행"이 가장 값싸고 효과적인 검사다.**

### ⑥ 맥락 무시

**문법도 맞고 검증도 하는데, 우리 팀에 안 맞는 경우다.**

```text
□ 프로젝트 규칙 파일의 컨벤션을 안 따름 (트랙 4의 3편)
□ 기존 페이지 오브젝트를 안 쓰고 새로 만듦
□ 우리 도메인 규칙 위반 (원 단위 절사 vs 반올림)
□ 존재하지 않는 기능을 전제 (요구사항에 없는 규칙)
□ 우리 환경에서 불가능한 것 (외부 결제를 실제 호출)
□ 과거 장애 이력을 반영 안 함 (트랙 4의 10편)
```

**이건 자동 검사로 못 잡는다.** 사람이 도메인 지식으로 판단한다. 그래서 트랙 4의 10편에서 컨텍스트 주입을 다뤘다.

### 검증 파이프라인 — 3단계

100건을 하나씩 정독할 수 없으므로 **깔때기 구조**로 만든다.

```text
[1단계] 자동 검사 — 기계가 전부 처리 (비용 0, 수초)
   □ 컴파일/타입 체크        → 환각 ①
   □ 린트                    → 스타일·명백한 오류
   □ 안티패턴 정규식          → 대기 ④, 가짜 통과 ② 일부
   □ 하드코딩·시크릿 스캔     → ⑤
   □ 실행 (--repeat-each=3)  → ⑤ 격리
   □ 변이 검사               → ② 가짜 통과  ★핵심

   → 여기서 걸린 것은 사람이 안 봐도 된다. 반려.

[2단계] 구조 검토 — 사람이 빠르게 훑음 (건당 1분)
   □ 실패·경계 케이스 비율    → ③
   □ 어서션이 실질적인가       → ②
   □ 계층 선택이 적절한가      → 트랙 3의 10편
   □ 기존 자산을 재사용했는가  → ⑥

[3단계] 도메인 검토 — 사람이 정독 (건당 5분, 소수만)
   □ 도메인 규칙 위반          → ⑥
   □ 과거 장애 영역 커버       → ⑥
   □ 비즈니스 임팩트 판단      → 우선순위
```

**1단계에서 절반 이상이 걸러진다.** 그리고 1단계는 CI에서 자동으로 돌아간다.

**3단계에 도달하는 것은 전체의 10~20%** 정도가 되도록 설계한다. 그래야 사람이 감당한다.

### 한 장 체크리스트

실무에서 옆에 두고 쓰는 형태로 압축한다.

```text
[실행 전 — 눈으로]
 □ 존재하는 API·컬럼·함수만 쓰는가
 □ 어서션이 있는가, 실질적인가
 □ 기대값이 실제 계산과 비교되는가
 □ 실패·경계 케이스가 40% 이상인가
 □ 고정 대기·networkidle·try/catch 가 없는가
 □ 환경·계정·데이터가 하드코딩되지 않았는가
 □ 우리 규칙과 도메인에 맞는가
 □ AI 가 "가정"한 것이 무엇인지 명시됐는가

[실행 — 기계로]
 □ tsc --noEmit / lint 통과
 □ 안티패턴 검사 통과
 □ 테스트 통과
 □ --repeat-each=3 통과
 □ 병렬 실행 통과
 □ 변이 검사에서 실패하는가  ★ (실패해야 정상)

[실행 후 — 판단]
 □ 이 테스트가 잡을 수 있는 결함이 무엇인지 한 문장으로 말할 수 있는가
 □ 유지보수 비용을 감당할 가치가 있는가 (트랙 3의 10편)
 □ 정식 스위트에 편입할 것인가, 버릴 것인가
```

**마지막 그룹의 첫 항목이 최종 관문이다.** *"이 테스트는 무엇을 잡는가?"* 에 답할 수 없으면 그 테스트는 필요 없다.

### 검증 비용을 줄이는 방법 — 애초에 잘 시키기

검증도 비용이므로, **생성 단계에서 결함을 줄이는 게 이득**이다.

```text
□ 프로젝트 규칙 파일 (트랙 4의 3편)
□ 기존 코드 2~3개를 예시로 (few-shot, 트랙 4의 1편)
□ 실제 DOM 스냅샷 제공 (트랙 4의 5편)
□ 도메인 규칙·장애 이력 주입 (트랙 4의 10편)
□ 출력에 assumptions 를 요구
□ "추측 금지, 모르면 확인 필요로 표시"
□ 계층·기법·우선순위를 명시적으로 요구
```

**이 7가지를 적용하면 1단계 반려율이 크게 준다.** 검증 체크리스트와 프롬프트 설계는 한 쌍이다.

### 검증하지 말아야 할 것 — 과잉 검증 경계

**모든 것을 정독하면 AI를 쓰는 의미가 없다.**

```text
자동 검사만: 형식 변환, 반복 작업, 문서 초안, 로그 요약
빠른 훑기:   TC 초안, 테스트 코드, 리팩터링
정독:        인증·결제·권한 관련, 데이터 마이그레이션, 삭제 로직
```

**리스크 기반으로 검증 깊이를 나눈다.** 트랙 1의 리스크 기반 계획이 여기서도 적용된다.

## 왜 채용시장이 요구하는가

- **"AI 산출물 검증"** 은 2026년 QA의 새로운 핵심 업무다. AI가 만들 수 있게 된 만큼 **검증이 병목**이 됐다.
- 면접 질문: **"AI가 만든 코드를 어떻게 신뢰하세요?"** — 6가지 유형과 3단계 파이프라인으로 답할 수 있으면 압도적이다.
- **변이 검사**를 아는 사람은 드물다. "테스트를 테스트한다"는 발상 자체가 QA다운 것이다.
- **자동 검사와 사람 검토를 깔때기로 나누는 설계**는 실제로 운영해 본 사람의 것이다.
- **과잉 검증을 경계한다**는 관점도 중요하다. 전부 정독하면 AI 도입 효과가 0이 된다.


포함할 검사:

### 과제 3 — 변이 검사 구현 (18분)

```bash
node scripts/mutation-check.mjs tests/generated/
```

동작:
1. 각 테스트 파일에서 `toHaveText('...')`, `toBe(...)` 의 기대값을 찾는다
2. 값을 무작위 문자열로 치환한 사본을 만든다
3. 그 사본으로 테스트 실행
4. **여전히 통과하면 "의심" 목록에 추가**
5. 원본 복구

트랙 3에서 만든 테스트들에 돌려본다. **의심으로 잡히는 게 있는지** 확인한다.

### 과제 4 — 3단계 파이프라인 (20분)

AI에게 테스트 10건을 생성시키고 3단계 파이프라인을 실제로 돌린다.

| **최종 채택** | | | |

**각 단계에 걸린 시간도 기록**한다. 1단계가 자동이라 거의 0에 수렴하는지 확인한다.

**최종 채택률이 10~30%면 정상이다.** 너무 높으면 검증이 느슨한 것이고, 너무 낮으면 프롬프트를 개선해야 한다.

### 과제 6 — 한 장 체크리스트 개인화 (12분)

레슨의 체크리스트를 **본인 환경에 맞게** 고친다.

- 우리 도메인 특유의 확인 항목 추가
- 우리 팀이 쓰는 도구에 맞게 명령어 수정
- 우선순위 재배치 (가장 자주 걸리는 것을 위로)

완성한 체크리스트를 이 레슨의 **내 메모**에 저장한다. 실무에서 계속 쓸 것이다.

## 자가 체크리스트

- [ ] AI 산출물의 위험이 "틀림"이 아니라 "그럴듯함"임을 안다
- [ ] 6가지 결함 유형을 나열하고 위험도 순서를 말할 수 있다
- [ ] **가짜 통과가 가장 위험한 이유**(초록불이라 아무도 안 봄)를 안다
- [ ] 환각을 `tsc --noEmit`, 문서 대조, 실행으로 검증할 수 있다
- [ ] 존재하지만 잘못된 맥락에서 쓰인 API는 타입 체크로 안 잡힘을 안다
- [ ] 가짜 통과 7가지 유형을 알아볼 수 있다
- [ ] **변이 검사**로 가짜 통과를 자동 탐지할 수 있다
- [ ] 엣지 케이스 점검 10가지 항목을 적용할 수 있다
- [ ] 실패·경계 케이스 비율로 TC 품질을 빠르게 판정할 수 있다
- [ ] 잘못된 대기 5가지 패턴을 정규식으로 잡을 수 있다
- [ ] 하드코딩·격리 실패를 "두 번 연속 실행"으로 검증할 수 있다
- [ ] 맥락 무시는 자동 검사로 못 잡고 도메인 지식이 필요함을 안다
- [ ] 3단계 깔때기 파이프라인을 설계할 수 있다
- [ ] 1단계 자동 검사로 절반 이상을 걸러낼 수 있다
- [ ] **"이 테스트가 무엇을 잡는가"에 답할 수 없으면 버린다**
- [ ] 프롬프트 개선으로 검증 비용을 줄일 수 있다 (7가지 방법)
- [ ] 리스크에 따라 검증 깊이를 나누고 과잉 검증을 경계한다
