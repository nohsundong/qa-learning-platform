## 개념 설명

### 여기까지 온 것

```text
트랙 1  QA 기본기        무엇을 테스트할지 정하는 판단
트랙 2  도구 실무        API·SQL·로그로 스스로 확인하는 능력
트랙 3  테스트 자동화     반복 검증을 기계에 넘기는 능력
트랙 4  AI 활용 QA       생성을 AI 에 넘기고 검증을 설계하는 능력
트랙 5  성능 테스트       기능 테스트로 안 잡히는 것을 잡는 능력
트랙 6  개발 교차검증     AI 와 남의 산출물을 판단하는 능력
```

**여섯 트랙은 독립된 주제가 아니라 하나의 흐름이다.** 이 레슨은 그 흐름을 실제 업무 순서로 재배열한다.

### 하나의 릴리즈를 처음부터 끝까지

실제 업무 흐름에 각 트랙이 어디서 쓰이는지 배치해 본다.

```text
【기획 단계】
  요구사항 리뷰
    → 결정테이블로 조합을 채우다 빈칸 발견        (트랙 1)
    → OpenAPI 명세에서 정의 안 된 응답 코드 발견   (트랙 2)
    → 명세 결함으로 제기 — 개발 전에 잡는 게 가장 싸다

【계획 단계】
  리스크 기반 테스트 계획 작성                      (트랙 1)
    → 과거 장애 이력 반영                          (트랙 4의 10편)
    → 자동화 대상/수동 대상 분리                    (트랙 3의 10편)
    → 성능 테스트 필요 여부 판단                    (트랙 5)

【개발 중】
  PR 이 올라옴
    → diff 를 읽고 회귀 범위 산정                   (트랙 6의 6편)
    → 부등호 변경 발견 → 경계값 TC 추가             (트랙 1 + 6의 4편)
    → 호출처 역추적으로 간접 영향 확인               (트랙 6의 6편)
    → 에이전트가 1차 분석, 내가 검토                (트랙 4의 4편)
    → PR 코멘트: null 처리 질문, data-testid 요청   (트랙 6의 4편 + 3편)

【TC 작성】
  AI 로 초안 생성                                   (트랙 4의 1편)
    → 기법 지정, 출력 형식 강제, 추측 금지
    → 환각을 명세 질문으로 전환
    → 검증 체크리스트 적용                          (트랙 6의 8편)
    → 계층 선택: Unit / API / E2E                   (트랙 3의 10편)

【테스트 실행】
  자동화 스위트 실행                                (트랙 3)
    → 실패 → 원인 6분류                            (트랙 3의 5편)
    → 제품 결함이면 리포트, 아니면 수정              (트랙 4의 7편)
  수동 탐색적 테스트                                (트랙 1의 5편)
    → 에이전트가 먼저 훑고 내가 깊게                 (트랙 4의 6편)
  API 로 서버 검증 뚫기                             (트랙 2의 2편)
    → UI 로 막힌 것을 직접 호출
  DB 정합성 검증                                    (트랙 2의 5편)
    → 화면은 정상인데 데이터가 어긋난 것

【결함 발견】
  리포트 작성                                       (트랙 1의 6편)
    → trace_id, curl, 로그 첨부                    (트랙 2의 3·6편)
    → 심각도/우선순위 구분
    → AI 로 다듬되 지어낸 정보 제거                 (트랙 6의 8편)

【성능】
  부하·스파이크 테스트                              (트랙 5)
    → 에러율 먼저 확인 후 p95/p99
    → 대시보드와 대조해 병목 특정                    (트랙 2의 6편)

【릴리즈 판단】
  Go/No-Go 근거 제시                                (트랙 1의 7편)
    → 실행률·통과율·잔여 결함·롤백 가능 여부
    → 성능 결과 포함
    → 선택지와 권고안 제시

【배포 후】
  스모크 + 지표 관찰                                (트랙 1의 7편 + 2의 6편)
    → 에러율, p95, 전환율
    → 정합성 쿼리 실행                              (트랙 2의 5편)

【회고】
  탈출 결함 원인 분류                               (트랙 1의 8편)
    → 장애 이력 파일에 기록                         (트랙 4의 10편)
    → 에이전트 프롬프트에 반영
    → 다음 릴리즈에 자동으로 반영된다
```

**마지막 회고에서 트랙 4로 되돌아가는 것**이 이 체계의 핵심이다. 학습이 조직에 축적된다.

### 교차검증의 4가지 축

AI 산출물이든 사람 산출물이든, **같은 것을 다른 방법으로 확인**하는 것이 검증의 본질이다.

```text
축 1. 계층 교차
   화면에서 9,000원  →  API 응답에서 9,000원  →  DB 에 9,000원
   하나라도 다르면 그 사이에 문제가 있다

축 2. 방법 교차
   같은 집계를 JOIN 으로, 서브쿼리로, 손으로 계산해 대조   (트랙 6의 7편)
   같은 검증을 UI 로, API 로 각각                        (트랙 2)

축 3. 관점 교차
   개발자 관점(구현) vs QA 관점(깨뜨리기) vs 사용자 관점(사용성)
   AI 에게도 다른 역할을 주고 서로 검증시킨다

축 4. 시간 교차
   지금 값 vs 이전 릴리즈 값 vs 추세                     (트랙 5의 3편)
   절대값만 보면 서서히 나빠지는 것을 놓친다
```

**축 1이 가장 자주 쓰인다.** "화면만 보는 테스트는 절반짜리"라는 말이 이것이다.

### AI 시대에 사람이 쥐고 있어야 할 것

트랙 4의 10편에서 정리한 것을 다시 본다. 이제는 각 항목의 근거를 댈 수 있어야 한다.

| 사람의 몫 | 왜 AI 가 못 하는가 | 근거 트랙 |
|---|---|---|
| **무엇을 테스트하지 않을지** | 비즈니스 임팩트·리스크 감수 수준을 모른다 | 1, 3의 10편 |
| 기대값 정의 | 명세 없이는 무엇이 옳은지 모른다 | 4의 6편 |
| 제품 결함 판단 | 테스트를 고치는 쉬운 길을 택한다 | 4의 7편 |
| 도메인 판단 | 암묵적 규칙을 모른다 | 4의 10편 |
| 과거 이력 반영 | 주지 않으면 모른다 | 4의 10편 |
| 릴리즈 Go/No-Go | 책임 소재 | 1의 7편 |
| **검증의 설계** | 자기 출력을 객관적으로 못 본다 | 6의 8편 |

**마지막 항목이 이 트랙의 결론이다.** AI에게 "네 답을 검증해줘"라고 해도 제한적이다. **검증 체계를 설계하는 것은 사람의 일이고, 그것이 QA의 정체성**이다.

### 역설: AI 시대에 기본기가 더 중요해졌다

```text
AI 가 TC 를 만들어준다
  → 무엇이 빠졌는지 알려면 설계 기법을 알아야 한다      (트랙 1)

AI 가 테스트 코드를 짜준다
  → 가짜 통과를 알아보려면 코드를 읽어야 한다          (트랙 6)

AI 가 SQL 을 만들어준다
  → JOIN 중복을 알아보려면 SQL 을 알아야 한다          (트랙 2, 6)

AI 가 성능 스크립트를 만들어준다
  → sleep 누락을 알아보려면 VU 개념을 알아야 한다      (트랙 5)

AI 가 원인을 분석해준다
  → 지어낸 인과관계를 걸러내려면 로그를 읽어야 한다     (트랙 2)
```

**"AI가 해주니까 안 배워도 된다"의 정반대다.** 생성은 싸졌고 검증은 비싸졌다. 그리고 검증에 필요한 것이 기본기다.

**면접에서 이 이야기를 할 수 있으면** AI 시대의 QA를 제대로 이해하는 사람으로 보인다.

### 실전 워크플로 — PR 하나를 검증하는 30분

가장 자주 하게 될 작업을 시간과 함께 정리한다.

```text
[0~5분] 맥락 파악
  gh pr view <번호>                          PR 제목·설명
  gh pr diff <번호> --name-status            바뀐 파일
  git log --oneline -5                       최근 커밋 맥락
  → 변경 유형 분류 (기능/수정/리팩터링/설정)

[5~12분] 코드 읽기
  diff 를 순서대로 읽으며 표시                (트랙 6의 6편)
    조건문·경계 → ★
    null 처리 → ★
    외부 호출·에러 처리 → ★
    테스트 파일 변경 → ★
  git grep <함수명>                          호출처 역추적
  → 직접 영향 / 간접 영향 정리

[12~18분] AI 1차 분석
  diff + 호출처를 에이전트에 투입             (트랙 4의 4편)
  → 내가 찾은 것과 대조
  → AI 만 찾은 것 / 내가만 찾은 것 분석
  → evidence 가 실제 존재하는지 확인

[18~25분] TC 설계
  경계값·조합·불가 전이 도출                  (트랙 1)
  계층 선택 (Unit/API/E2E)                   (트랙 3의 10편)
  기존 TC 와 중복 확인
  → 실행할 것 / 안 할 것 결정

[25~30분] 코멘트와 실행
  PR 코멘트 작성                             (트랙 6의 6편)
    [질문] 사양 확인
    [제안] null 처리
    [테스트] 추가할 TC
    [요청] data-testid 유지
  회귀 스위트 실행 범위 지정
```

**이 30분이 QA의 하루에서 가장 가치 있는 시간**이다. 여기서 잡은 결함이 가장 싸다.

### 도구 스택 — 전부 무료

이 커리큘럼에서 다룬 것을 정리한다. **유료 의존성이 하나도 없다.**

| 영역 | 도구 | 비용 |
|---|---|---|
| 이슈 관리 | Jira Cloud (10명), Notion 개인 | 무료 |
| API 테스트 | Postman 개인, Bruno, httpbin, Petstore | 무료 |
| DB | DBeaver CE, DB Fiddle, SQLite | 무료 |
| 모니터링 학습 | Grafana Play, Grafana OSS | 무료 |
| 웹 자동화 | Playwright | 오픈소스 |
| 모바일 자동화 | Appium, Maestro, Android Studio AVD | 무료 |
| 성능 | k6 | 오픈소스 |
| CI | GitHub Actions (public 무제한) | 무료 |
| 호스팅 | GitHub Pages | 무료 |
| AI | Gemini 무료 티어, Ollama 로컬 | 무료 |
| 조합 테스트 | Microsoft PICT | 무료 |
| Git 학습 | Learn Git Branching | 무료 |

**학습에 돈이 들지 않는다.** 이 플랫폼 자체도 같은 원칙으로 만들어졌다.

### 지속하는 방법

커리큘럼을 한 번 훑는 것으로는 안 된다.

```text
매일 (10~20분)
  □ 이 플랫폼의 복습 큐 — 약점 항목 간격 반복
  □ 아침 브리핑 메일의 오늘의 실습 미션

매주
  □ 실제 PR 하나를 30분 워크플로로 검증
  □ 플래키 목록 점검                          (트랙 3의 5편)
  □ 자동화 안정성 지표 확인

매월
  □ AI 산출물 검증 체크리스트 개인화 갱신      (트랙 6의 8편)
  □ 프롬프트 자산 정리                        (트랙 4의 1편)
  □ 학습 데이터 export 백업

분기
  □ 장애 이력 파일 갱신                       (트랙 4의 10편)
  □ escaped_because 집계 → 우리 팀 약점 도출
  □ 자동화 스위트 정리 (삭제 후보)             (트랙 3의 10편)
  □ 커리큘럼 재점검 — 채용시장 변화 반영
```

**`escaped_because` 집계가 개인 학습에도 적용된다.** 내가 놓친 결함의 원인을 분류하면 내 약점이 보인다.

### 포트폴리오로 만들기

학습한 것을 증명할 수 있어야 채용에 쓰인다.

```text
공개 저장소 하나에 담을 것
  □ 자동화 프레임워크 (Playwright + POM + fixture)   트랙 3
  □ CI 워크플로 (병렬, 리포트, 알림)                  트랙 3의 9편
  □ API 테스트 컬렉션 + Newman CI                    트랙 2의 3편
  □ k6 성능 스크립트 + 회귀 감지                      트랙 5
  □ AI 검증 스크립트 (안티패턴, 변이 검사)             트랙 6의 8편
  □ PR 회귀 범위 분석 에이전트                        트랙 4의 4편
  □ 테스트 전략 문서 / TC 설계 예시                   트랙 1
  □ README 에 "무엇을 왜 이렇게 만들었는가"

면접에서 말할 수 있는 것
  □ "자동화율" 이 아니라 "회귀 시간 8시간 → 25분"     트랙 1의 8편
  □ "AI 를 썼다" 가 아니라 "검증 파이프라인을 만들었다"  트랙 6의 8편
  □ "테스트를 많이 만들었다" 가 아니라
    "무엇을 자동화하지 않기로 했는지와 그 근거"        트랙 3의 10편
```

**세 번째가 가장 강력하다.** 대부분의 지원자가 "무엇을 했는가"를 말할 때, "무엇을 하지 않기로 했는가"와 그 근거를 말하면 판단력이 드러난다.

### 마지막으로 — QA의 정체성

```text
과거:  테스트 케이스를 실행하는 사람
현재:  무엇을 테스트할지 정하고, 자동화하고, 판단하는 사람
가까운 미래: AI 가 만든 것을 검증하고, 검증 체계를 설계하는 사람
```

**변하지 않는 것이 하나 있다.**

> **"이게 정말 맞는가?"를 묻는 사람.**

도구가 바뀌고, AI가 코드를 쓰고, 에이전트가 탐색해도 이 질문은 사람의 것이다. 그리고 이 질문을 **근거를 갖고** 던지려면 여섯 트랙의 기본기가 필요하다.

## 왜 채용시장이 요구하는가

- **개별 스킬이 아니라 흐름으로 설명할 수 있는 사람**이 시니어로 평가된다. "Playwright 할 줄 압니다"와 "PR diff를 읽고 회귀 범위를 정해 자동화 범위를 결정합니다"는 다른 답이다.
- 면접 질문: **"QA 업무 프로세스를 설명해 주세요"** — 이 레슨의 릴리즈 흐름이 그대로 답이다.
- **"AI가 QA를 대체할까요?"** 에 역설(기본기가 더 중요해졌다)로 답하면 깊이가 드러난다.
- **포트폴리오 저장소**는 서류 단계에서 결정적이다. 특히 README에 판단 근거를 적으면 강하다.
- **"무엇을 하지 않기로 했는가"** 를 말할 수 있는 지원자는 드물다.

## 실습 과제

### 과제 1 — 나만의 릴리즈 워크플로 작성 (20분)

레슨의 릴리즈 흐름을 **본인 팀 상황에 맞게** 재작성한다.

각 단계에:
- 실제로 하는 활동
- 쓰는 도구
- 산출물
- 걸리는 시간
- **아직 못 하고 있는 것과 그 이유**

**마지막 항목이 다음 학습 목표가 된다.**

### 과제 2 — 30분 PR 검증 실전 (30분)

**실제 오픈소스 PR 하나로 타이머를 켜고 수행한다.**

| 구간 | 시간 | 산출물 |
|---|---|---|
| 맥락 파악 | 0~5분 | 변경 유형 |
| 코드 읽기 | 5~12분 | ★ 표시 목록, 영향 범위 |
| AI 1차 분석 | 12~18분 | 대조 결과 |
| TC 설계 | 18~25분 | TC 목록 + 계층 |
| 코멘트 작성 | 25~30분 | 4가지 유형 코멘트 |

**시간을 지키는 것이 이 과제의 목적이다.** 완벽하게 하려 하지 말고 30분에 끝낸다. 실무에서는 이 시간밖에 없다.

끝나고 **어느 구간에서 시간이 부족했는지** 기록한다. 그게 약한 부분이다.

### 과제 3 — 4가지 교차검증 축 적용 (20분)

기능 하나를 골라 **네 축으로 모두 검증**한다.

| 축 | 방법 | 결과 | 불일치 |
|---|---|---|---|
| 계층 | 화면 / API / DB | | |
| 방법 | 두 가지 쿼리, UI+API | | |
| 관점 | 개발/QA/사용자 | | |
| 시간 | 이전 릴리즈 대비 | | |

**불일치가 하나라도 나오면 그게 결함 후보다.**

### 과제 4 — 종합 감사 (25분)

트랙 6의 8편 과제 7(복합 AI 산출물 감사)을 아직 안 했다면 여기서 한다.

했다면, **본인이 실제로 쓰는 코드베이스**에 대해 같은 감사를 수행한다.

- 기존 자동화 테스트 5개를 골라 변이 검사
- 기존 검증 쿼리 3개를 교차 검증
- 결과를 표로 정리

**"우리 테스트가 진짜 검증하고 있는가"** 에 답한다.

### 과제 5 — 학습 회고와 다음 계획 (20분)

메모에 정리한다.

**1) 트랙별 자기 평가**

| 트랙 | 자신 있음 (1~5) | 가장 유용했던 것 | 더 필요한 것 |
|---|---|---|---|
| 1 QA 기본기 | | | |
| 2 도구 실무 | | | |
| 3 자동화 | | | |
| 4 AI 활용 | | | |
| 5 성능 | | | |
| 6 교차검증 | | | |

**2) 지금 당장 실무에 적용할 3가지**
근거와 예상 효과를 함께.

**3) 적용하지 않기로 한 것 2가지**
왜 우리 상황에 안 맞는지.

**4) 다음 3개월 학습 계획**
복습 큐에 쌓인 약점 항목을 근거로.

### 과제 7 — 면접 답변 준비 (20분)

아래 질문에 **각 200자 내외**로 답을 작성한다. 근거로 어느 트랙 내용을 쓸지 표시한다.

```text
1. 회귀 범위를 어떻게 정하시나요?
2. 플래키 테스트를 어떻게 관리하셨나요?
3. 모든 테스트를 자동화해야 할까요?
4. AI가 만든 코드를 어떻게 검증하세요?
5. 릴리즈 직전 Critical 결함을 발견했습니다. 어떻게 하시겠어요?
6. 평균 대신 p95를 보는 이유는?
7. QA 업무 성과를 어떻게 측정하셨나요?
8. AI가 QA를 대체할까요?
```

**작성한 답을 소리 내어 읽어본다.** 막히는 곳이 실제로 약한 부분이다. 그 트랙을 복습 큐에 넣는다.

## 자가 체크리스트

- [ ] 여섯 트랙이 하나의 흐름임을 설명할 수 있다
- [ ] 릴리즈 전 과정에서 각 트랙 지식이 어디에 쓰이는지 배치할 수 있다
- [ ] 회고에서 트랙 4로 되돌아가는 피드백 루프를 이해한다
- [ ] 교차검증 4가지 축(계층·방법·관점·시간)을 적용할 수 있다
- [ ] 계층 교차(화면-API-DB)가 가장 자주 쓰이는 이유를 안다
- [ ] AI 시대에 사람이 쥐어야 할 7가지와 각각의 근거를 댈 수 있다
- [ ] **검증 체계를 설계하는 것이 QA의 정체성**임을 설명할 수 있다
- [ ] "AI가 해주니 안 배워도 된다"의 정반대인 이유를 5가지 예로 설명할 수 있다
- [ ] PR 하나를 30분 워크플로로 검증할 수 있다
- [ ] 30분 중 어느 구간이 본인의 약점인지 안다
- [ ] 이 커리큘럼의 도구 스택이 전부 무료임을 안다
- [ ] 매일·매주·매월·분기 지속 루틴을 설계했다
- [ ] 개인 학습에도 `escaped_because` 집계를 적용할 수 있다
- [ ] 포트폴리오에 담을 8가지 항목을 안다
- [ ] 성과를 "자동화율"이 아니라 지표로 말할 수 있다
- [ ] **"무엇을 하지 않기로 했는가"와 근거**를 말할 수 있다
- [ ] 면접 단골 질문 8개에 근거를 갖고 답할 수 있다
- [ ] 변하지 않는 QA의 질문이 무엇인지 말할 수 있다
