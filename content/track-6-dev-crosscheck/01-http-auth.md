## 개념 설명

### 이 트랙의 목표를 먼저 정한다

트랙 6은 **개발자가 되기 위한 것이 아니다.** AI가 만든 코드와 분석이 맞는지 **내가 직접 판단**하기 위한 최소한의 지식이다.

```text
목표 아님: 인증 시스템을 구현할 수 있다
목표:     인증 테스트 코드를 읽고 "이건 실제로 인증을 검증하지 않는다"고 말할 수 있다
```

각 편에서 **"이걸 알면 무엇을 판단할 수 있게 되는가"** 를 기준으로 읽으면 된다.

### 요청 헤더 — QA가 실제로 보는 것들

트랙 2에서 상태코드를 다뤘다. 여기서는 **헤더**를 본다. 인증은 대부분 헤더에서 일어난다.

```http
GET /api/v1/orders/1001 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NSIsInJvbGUiOiJVU0VSIiwiZXhwIjoxNzY3MjI1NjAwfQ.abc123
Cookie: session_id=a1b2c3; theme=dark
Content-Type: application/json
Accept: application/json
X-Request-Id: 7f3a9b2c
```

| 헤더 | QA가 보는 이유 |
|---|---|
| `Authorization` | 누구로 요청하는가. **바꿔치기 테스트의 대상** |
| `Cookie` | 세션 방식일 때의 인증 정보 |
| `Content-Type` | 서버가 바디를 어떻게 파싱하는가 |
| `X-Request-Id` | 로그 추적 (트랙 2의 trace_id) |
| `User-Agent` | 기기별 분기 로직이 있으면 |
| `Referer` / `Origin` | CSRF 방어, 리다이렉트 검증 |

**응답 헤더**에서도 볼 것이 있다.

```http
HTTP/1.1 200 OK
Set-Cookie: session_id=a1b2c3; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=1800
Cache-Control: no-store
X-Frame-Options: DENY
```

`Set-Cookie` 의 플래그가 **보안 검증 항목**이다. 뒤에서 다룬다.

### 세션 방식 — 서버가 기억한다

```text
① 로그인 요청 (id/pw)
      ↓
② 서버가 세션을 저장하고 세션 ID 발급
   Set-Cookie: session_id=a1b2c3; HttpOnly; Secure
      ↓
③ 이후 요청마다 브라우저가 쿠키를 자동으로 붙인다
   Cookie: session_id=a1b2c3
      ↓
④ 서버가 세션 저장소에서 조회해 사용자를 식별
```

**특징과 검증 포인트**

| 특징 | QA가 확인할 것 |
|---|---|
| 서버가 상태를 갖는다 | 서버 재시작·스케일아웃 시 세션이 유지되는가 |
| 즉시 무효화 가능 | **로그아웃 후 이전 세션으로 접근하면 막히는가** |
| 쿠키에 의존 | 쿠키 차단 시 어떻게 되는가 |
| 만료 시간 | 30분 뒤 실제로 만료되는가, 활동 시 연장되는가 |

**"로그아웃 후 이전 세션 재사용"** 은 반드시 테스트해야 한다. 로그아웃이 클라이언트 쿠키만 지우고 서버 세션을 안 지우는 구현이 실제로 흔하다. **UI로는 절대 안 보이고, API로 찔러야 드러난다** (트랙 2).

### 쿠키 보안 플래그 — 외워둘 만한 것

```http
Set-Cookie: session_id=a1b2c3; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=1800
```

| 플래그 | 없으면 무슨 일이 | 검증 |
|---|---|---|
| `HttpOnly` | JS로 쿠키를 읽을 수 있다 → XSS로 세션 탈취 | `document.cookie` 에 안 보여야 정상 |
| `Secure` | HTTP로도 쿠키가 전송된다 → 도청 | https 전용인지 |
| `SameSite` | 다른 사이트에서 요청 시 쿠키가 붙는다 → CSRF | `Lax` 또는 `Strict` |
| `Max-Age`/`Expires` | 세션 쿠키(브라우저 닫으면 삭제) | 의도한 수명인가 |

**브라우저 콘솔에서 바로 확인하는 방법**

```javascript
document.cookie
// HttpOnly 쿠키는 여기 안 나온다 — 안 나오는 게 정상이다
```

개발자도구 → Application → Cookies 에서 플래그를 눈으로 볼 수 있다. **로그인 직후 이 화면을 확인하는 것이 5초짜리 보안 점검**이다.

### JWT — 서버가 기억하지 않는다

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiIxMjM0NSIsInJvbGUiOiJVU0VSIn0 . abc123
└──────── 헤더 ────────┘   └──────── 페이로드 ────────┘   └ 서명 ┘
```

점(`.`)으로 구분된 세 부분이고, **앞 두 개는 그냥 Base64URL 인코딩**이다. 암호화가 아니다.

```javascript
// 브라우저 콘솔에서 페이로드 읽기
JSON.parse(atob(token.split('.')[1]))
// { sub: "12345", role: "USER", exp: 1767225600, iat: 1767223800 }
```

**이게 QA에게 중요한 이유 두 가지.**

1. **토큰 내용을 직접 확인할 수 있다.** 만료 시각(`exp`), 권한(`role`), 사용자 ID(`sub`)를 눈으로 본다
2. **누구나 읽을 수 있다는 것이 검증 항목이다.** 페이로드에 개인정보(주민번호, 전화번호, 이메일)가 들어있으면 **결함**이다

`exp` 는 Unix 타임스탬프다.

```javascript
new Date(1767225600 * 1000)   // 만료 시각 확인
```

**JWT 검증 항목**

```text
□ 페이로드에 민감정보가 없는가
□ exp 가 적절한가 (액세스 토큰이 30일이면 과하다)
□ 만료된 토큰으로 요청하면 401 인가
□ 서명을 조작한 토큰이 거부되는가
□ 페이로드의 role 을 ADMIN 으로 바꾸면 거부되는가  ← 중요
□ 로그아웃 후에도 토큰이 유효한가 (JWT 의 구조적 한계)
□ 리프레시 토큰이 있다면 갱신 흐름이 동작하는가
```

**"role 을 바꿔서 보내기"** 가 핵심 테스트다. 페이로드를 수정하면 서명이 깨지므로 서버가 거부해야 정상이다. 서명 검증을 안 하는 구현이 실제로 존재한다.

```text
원본 페이로드: { "sub": "12345", "role": "USER" }
조작:         { "sub": "12345", "role": "ADMIN" }
→ Base64 로 다시 인코딩해서 보낸다
→ 401 또는 403 이 와야 정상. 200 이 오면 심각한 보안 결함
```

**JWT의 구조적 한계**: 서버가 상태를 안 가지므로 **발급된 토큰을 즉시 무효화할 수 없다.** 로그아웃해도 토큰 자체는 만료 시각까지 유효하다. 그래서 블랙리스트나 짧은 만료 + 리프레시 토큰 조합을 쓴다. **"로그아웃 후 토큰이 여전히 동작한다"를 결함으로 볼지 사양으로 볼지는 팀의 설계에 달렸다** — 물어봐야 한다.

### 세션 vs JWT 비교

| | 세션 | JWT |
|---|---|---|
| 상태 저장 | 서버 | 없음 (토큰 자체에) |
| 즉시 무효화 | 가능 | **어렵다** |
| 스케일아웃 | 세션 공유 필요 | 쉽다 |
| 토큰 크기 | 작음 (ID만) | 큼 (모든 클레임) |
| 저장 위치 | 쿠키 (HttpOnly) | 쿠키 또는 localStorage |

**JWT를 localStorage에 저장하면 XSS에 취약하다.** `HttpOnly` 쿠키에 못 담기 때문이다. 이건 트레이드오프이고, 어느 쪽인지 확인하는 게 QA의 일이다.

```javascript
// 콘솔에서 확인
localStorage.getItem('accessToken')   // 값이 나오면 XSS 노출 위험
```

### OAuth 2.0 — "다른 서비스로 로그인"

카카오·구글 로그인의 흐름이다. **전체를 이해할 필요는 없고, 어디가 깨지는지만 알면 된다.**

```text
① 사용자가 "구글로 로그인" 클릭
② 우리 서비스 → 구글 인증 페이지로 리다이렉트
   (client_id, redirect_uri, scope, state 를 쿼리로 전달)
③ 사용자가 구글에서 로그인·동의
④ 구글 → 우리 서비스의 redirect_uri 로 리다이렉트 (code 전달)
⑤ 우리 서버가 code + client_secret 으로 구글에 토큰 요청
⑥ 구글이 액세스 토큰 발급
⑦ 우리 서버가 사용자 정보 조회 후 우리 세션/JWT 발급
```

**QA가 테스트할 지점**

```text
□ ③에서 사용자가 "취소"하면 어떻게 되는가
□ ③에서 뒤로가기를 누르면
□ ④의 code 를 두 번 사용하면 (재사용 방지가 되는가)
□ state 파라미터가 있는가 — 없으면 CSRF 취약  ← 확인 필요
□ 이미 같은 이메일로 가입된 계정이 있으면 (계정 연동? 오류?)
□ 구글 계정에서 우리 앱 권한을 해제하면
□ 구글 서버가 응답하지 않으면 (타임아웃 처리)
□ 신규 사용자와 기존 사용자의 흐름이 다른가
```

**`state` 파라미터 확인**은 개발자도구 Network 탭에서 리다이렉트 URL을 보면 된다. 없으면 CSRF 위험이 있으므로 개발팀에 확인한다.

**5번(이메일 중복)이 실무에서 가장 자주 터진다.** 이메일로 가입한 사용자가 나중에 같은 이메일로 구글 로그인을 하면? 계정이 두 개가 되는지, 합쳐지는지, 오류가 나는지 — 명세에 없으면 명세 결함이다 (트랙 1).

### 권한 검증 — 인증과 인가는 다르다

트랙 2에서 401(인증 안 됨)과 403(권한 없음)을 구분했다. **테스트도 나눠서 한다.**

```text
인증(Authentication): 너 누구야?
  □ 토큰 없이 요청 → 401
  □ 만료된 토큰 → 401
  □ 잘못된 서명 → 401

인가(Authorization): 너인 건 알겠는데 이거 해도 돼?
  □ 다른 사용자의 주문 조회 → 403 또는 404
  □ 일반 사용자가 관리자 API 호출 → 403
  □ 본인 주문이지만 이미 배송 완료된 것 취소 → 409
```

**인가 테스트는 자동화 1순위다** (트랙 3). 사람이 매번 "남의 데이터 조회해 보기"를 손으로 하지 않게 되고, 그러면 언젠가 뚫린다.

가장 흔한 결함이 **IDOR(Insecure Direct Object Reference)** 이다.

```text
GET /api/v1/orders/1001   ← 내 주문
GET /api/v1/orders/1002   ← 숫자만 바꿨는데 남의 주문이 보인다
```

**URL의 숫자를 하나 바꿔보는 것**이 가장 값싸고 효과적인 보안 테스트다.

### 이 지식으로 무엇을 판단할 수 있게 되는가

AI가 만든 인증 테스트를 예로 본다.

```javascript
test('로그인이 필요한 페이지는 보호된다', async ({ page }) => {
  await page.goto('/dashboard');
  await expect(page).toHaveURL(/\/login/);
});
```

**이 테스트의 문제를 지적할 수 있어야 한다.**

- **프론트엔드 라우팅 가드만 검증한다.** 서버가 보호하는지는 확인하지 않았다
- **API를 직접 호출하면 데이터가 나올 수 있다.** UI만 막고 API는 열려 있는 구현이 흔하다
- 만료된 토큰, 다른 사용자의 토큰 케이스가 없다

**보완한 버전**

```javascript
test('인증 없이 API 호출 시 401', async ({ request }) => {
  const res = await request.get('/api/v1/dashboard');
  expect(res.status()).toBe(401);
});

test('만료된 토큰은 거부된다', async ({ request }) => {
  const res = await request.get('/api/v1/dashboard', {
    headers: { Authorization: `Bearer ${EXPIRED_TOKEN}` },
  });
  expect(res.status()).toBe(401);
});

test('다른 사용자의 주문은 조회할 수 없다', async ({ request }) => {
  const res = await request.get(`/api/v1/orders/${OTHER_USER_ORDER_ID}`, {
    headers: { Authorization: `Bearer ${MY_TOKEN}` },
  });
  expect([403, 404]).toContain(res.status());
});
```

**"UI 테스트만으로는 인증을 검증할 수 없다"** — 이게 이 레슨의 핵심 결론이다.

## 왜 채용시장이 요구하는가

- 채용공고의 **"HTTP/REST 이해"**, **"인증 방식 이해"** 는 API 테스트의 전제 조건이다.
- 면접 질문: **"세션과 JWT의 차이가 뭔가요?"** 는 매우 흔하다. 즉시 무효화 가능 여부로 답하면 좋다.
- **"UI에서 막혀 있는데 API로는 되는" 결함**을 찾아본 경험은 강한 신호다. 트랙 2·3과 이어진다.
- **JWT 페이로드를 직접 디코딩해서 확인한다**는 습관은 실무자의 것이다.
- **AI가 만든 인증 테스트는 대부분 프론트엔드 가드만 검증한다.** 이걸 지적할 수 있으면 AI 검증 능력이 있는 것이다.

## 실습 과제

### 과제 1 — 실제 서비스의 인증 관찰 (15분)

로그인이 있는 아무 웹서비스에서 개발자도구를 열고:

1. **Network 탭**에서 로그인 요청을 찾아 요청·응답 헤더 전체 확인
2. **Application → Cookies** 에서 쿠키 플래그 확인

| 쿠키 이름 | HttpOnly | Secure | SameSite | Max-Age |
|---|---|---|---|---|
| | | | | |

3. 콘솔에서 `document.cookie` 실행 → **어떤 쿠키가 안 보이는가** (HttpOnly)
4. `localStorage` 를 확인 → 토큰이 있는가

4번에서 토큰이 나오면, **왜 그게 트레이드오프인지** 메모에 적는다.

### 과제 2 — JWT 디코딩 (12분)

JWT를 쓰는 서비스를 찾거나, [jwt.io](https://jwt.io) 의 샘플 토큰을 쓴다.

```javascript
const t = 'eyJ...';
JSON.parse(atob(t.split('.')[1]))
```

1. 페이로드에 어떤 클레임이 있는가
2. `exp` 를 사람이 읽는 시각으로 변환 → 토큰 수명은?
3. **민감정보가 들어있지 않은가**
4. 페이로드의 값을 하나 바꿔 다시 인코딩하고, 서명 부분은 그대로 둔 토큰을 만들어 본다
   (실제 서비스에 보내지 말고, 로컬 연습 서버나 `httpbin` 으로)

**4번의 목적은 "서명이 깨진다"를 이해하는 것**이다. 실제 공격이 아니라 원리 확인이다.

### 과제 3 — 인증/인가 TC 설계 (15분)

본인이 아는 서비스로 **인증 5건 + 인가 5건** TC를 설계한다.

| # | 구분 | 시나리오 | 기대 상태코드 | UI로 가능? API 필요? |
|---|---|---|---|---|
| 1 | 인증 | 토큰 없이 API 호출 | 401 | API |
| ... | | | | |

**마지막 열이 중요하다.** UI로 불가능한 것이 몇 개인지 세어본다. 그게 API 테스트가 필요한 이유다.

### 과제 4 — IDOR 점검 (10분)

**본인이 권한을 가진 환경에서만** 수행한다. (자기 계정, 테스트 환경)

1. 리소스 상세 페이지의 URL에서 ID를 찾는다
2. ID를 ±1 해서 접근해 본다
3. 결과 기록

| 시도 | 결과 상태코드 | 데이터가 보이는가 | 판정 |
|---|---|---|---|
| | | | |

**403과 404 중 무엇이 왔는지**도 기록한다. 트랙 2에서 다룬 대로, 민감 리소스는 404가 나은 경우가 있다.

> 주의: 타인 소유 서비스에 대한 무단 점검은 하지 않는다. 학습은 본인 계정·테스트 환경에서만.

### 과제 5 — OAuth 흐름 관찰 (12분)

## 자가 체크리스트

- [ ] 트랙 6의 목표가 "구현"이 아니라 "판단"임을 이해한다
- [ ] 요청·응답 헤더에서 QA가 봐야 할 항목을 5가지 이상 안다
- [ ] 세션 방식의 흐름 4단계를 설명할 수 있다
- [ ] 로그아웃 후 이전 세션 재사용 테스트가 왜 필요한지 안다
- [ ] 쿠키 4가지 플래그(HttpOnly/Secure/SameSite/Max-Age)의 역할을 안다
- [ ] `document.cookie` 에 안 보이는 것이 정상임을 안다
- [ ] JWT의 세 부분 구조와 앞 두 개가 암호화가 아님을 안다
- [ ] 브라우저에서 JWT 페이로드를 디코딩해 확인할 수 있다
- [ ] JWT 페이로드에 민감정보가 있으면 결함임을 판단할 수 있다
- [ ] `role` 조작 토큰이 거부되는지 확인하는 테스트를 설계할 수 있다
- [ ] JWT를 즉시 무효화하기 어렵다는 구조적 한계를 설명할 수 있다
- [ ] JWT를 localStorage에 두는 것의 트레이드오프를 안다
- [ ] OAuth 흐름 7단계의 개요와 테스트 지점 8가지를 안다
- [ ] `state` 파라미터가 CSRF 방어용임을 알고 존재를 확인한다
- [ ] 이메일 중복 시 계정 연동 정책이 명세에 있는지 확인한다
- [ ] 인증(401)과 인가(403) 테스트를 나눠 설계할 수 있다
- [ ] IDOR을 URL의 ID를 바꿔보는 것으로 점검할 수 있다
- [ ] **UI 테스트만으로는 인증을 검증할 수 없다**는 것을 설명할 수 있다
- [ ] AI가 만든 인증 테스트가 프론트엔드 가드만 검증하는 것을 지적할 수 있다
