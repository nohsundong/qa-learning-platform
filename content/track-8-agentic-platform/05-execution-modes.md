## 개념 설명

### 세 가지 모드 — 레시피 비유

웨비나는 요리에 빗대 설명했다.

| 모드 | 사람이 주는 것 | 비유 | 실행 주체 |
|---|---|---|---|
| **자동화 테스트** | 스크립트 | 사람이 **레시피**를 쓰면 도구가 그대로 따른다 | 사람 (도구는 실행만) |
| **증강 테스트** | 프롬프트 | 사람이 **요리 이름**을 정하면 AI가 방법을 안내한다 | 사람 + 옆에서 돕는 AI |
| **자율 테스트** | 의도 | 사람은 **"배고프다"** 고 말할 뿐 | 주로 에이전트 |

그리고 결론: **"세 영역 모두 가져가야 이긴다."** 모든 테스트를 자율로 돌릴 수는 없기 때문이다.

### 사라지는 단계

```text
전통적 자동화   ① 수동 TC 정의 → ② 스크립트로 변환 → ③ 실행
자율 실행       ① 수동 TC 정의 ─────────────────→ ③ 에이전트가 읽고 바로 실행
자율 탐색       (의도·요구사항) ──────────────────→ 에이전트가 시나리오까지 만들어 실행
```

자율 실행은 **②를 없앤다.** 자율 탐색(8-06)은 **①까지 없앤다.**
사라진 단계의 일은 없어진 것이 아니라 **실행 시점으로 옮겨간다.** 매번 화면을 읽고 판단하므로 느리고, 비용이 들고, 결과가 매번 조금씩 다를 수 있다.

### 자율 실행 — 문서로 확인한 Run with Autopilot

UiPath Test Manager의 **Autonomous Test Execution** 문서 기준이다.

```text
시작      수동 테스트 케이스 → Manual Steps 탭 → 오른쪽의 Run with Autopilot
필수      대상 애플리케이션 URL (비어 있으면 실행 버튼 비활성)
매개변수   {{ 로 매개변수 자동완성, 자격증명은 {{credential:이름}}
모델      AI 모델 선택
실행 대상  Orchestrator에 연결된 런타임 — Testing, App Testing, Production(Unattended),
          Cloud–VM Testing, Cloud–VM  (서버리스 제외)
브라우저   Chromium 계열, Firefox
실행 중    라이브 스트리밍 시청 · 원격 제어 넘겨받기 · 취소
```

문서에 적힌 경고가 이 레슨의 핵심이다.

> 사람 테스터를 위해 쓴 수동 단계는 에이전트에게 **충분히 모호하지 않을 수** 있다.

웨비나 데모 정리:

- 대출 신청 화면의 수동 TC (자동화 스크립트 연결 없음, 단계만 정의)
- 실행하면 에이전트가 화면을 탐색하며 단계별로 스스로 스크립트를 만들고 값을 입력
- 결과: 일부 단계 실패, **성공한 단계는 스크립트와 단계별 스크린샷으로 남음**
- 실제 속도는 녹화보다 **훨씬 느림** — 컴퓨터 사용(computer use) 방식이라 화면을 탐색하며 판단하기 때문
- 현재는 사람이 옆에서 지켜보는 **Assisted** 방식, 사람 없이 도는 **Unassisted** 는 곧 제공 예정(웨비나 발표)

### 에이전트가 실행할 수 있는 수동 단계 쓰기

사람은 맥락으로 채우는 빈칸을 에이전트는 **추측**으로 채운다. 추측은 매번 달라진다.

**Before — 사람용**

```text
1. 대출 신청 페이지로 이동한다
2. 적절한 대출 상품을 선택한다
3. 필수 정보를 입력한다
4. 신청한다
5. 정상 접수되는지 확인한다
```

**After — 에이전트용**

```text
사전 조건: 테스트 계정 {{credential:loan-tester}} 로그인 상태

1. 상단 메뉴에서 "대출 신청"을 클릭한다
   기대: 제목 "기업 대출 신청" 화면이 보인다
2. "대출 상품" 드롭다운에서 "운전자금 대출"을 선택한다
   기대: "신청 금액" 입력란이 활성화된다
3. "신청 금액"에 {{amount}} (기본 50000000) 을 입력한다
4. "자금 용도"에 "원자재 구매"를 입력한다
5. "연 매출"에 1200000000 을 입력한다
6. "신청하기" 버튼을 클릭한다
   기대: "접수가 완료되었습니다" 문구와 "접수번호 LN-" 로 시작하는 번호가 보인다
   기대: 입력 폼이 초기 상태로 비워진다
```

| 규칙 | 이유 |
|---|---|
| **한 단계에 한 동작** | 실패 지점을 특정할 수 있다 |
| **보이는 이름으로 요소 지목** ("신청하기" 버튼) | 접근성 트리의 이름과 일치 → 찾기 쉽다 (트랙 4-06) |
| **값을 명시하거나 매개변수화** | "적절한" 은 매번 다른 값이 된다 |
| **기대 결과를 관찰 가능한 문장으로** | "정상 접수" 는 판정 기준이 아니다 |
| **사전 조건을 분리** | 로그인 같은 준비가 단계에 섞이면 실패 원인이 흐려진다 |

마지막 기대 "폼이 비워진다"를 보라. **명세에 없던 기대를 사람이 적는 순간 결함 판정이 가능해진다.** 8-06의 자율 탐색 데모에서 바로 이 지점이 문제가 된다.

### 모드 선택 기준

| 기준 | 스크립트 자동화 쪽 | 자율 실행 쪽 |
|---|---|---|
| 실행 빈도 | 하루 여러 번 (CI) | 분기·릴리즈 1회 |
| UI 변경 빈도 | 안정 | 자주 바뀜 (스크립트 유지보수가 더 비쌈) |
| 결과 재현성 요구 | 감사 증거·규제 | 탐색·확인 성격 |
| 실행 시간 허용 | 분 단위 필요 | 느려도 됨 |
| 실행당 비용 | 거의 0 | 모델 호출 비용 |
| 되돌릴 수 없는 액션 | 통제된 스크립트로 | 자율 실행 제외 |
| 테스트 수명 | 길다 (몇 년) | 짧다 (신규·임시) |

```text
판단 순서 (빠른 버전)
1. 되돌릴 수 없는 액션이 있나?          → 있으면 스크립트 + 사람 확인
2. 규제·감사 재현성이 필요한가?          → 필요하면 스크립트 (자율 실행 결과는 스크립트로 고정)
3. 하루 1회 이상 도는가?                → 그렇다면 스크립트 (AI 증강으로 생성·유지)
4. UI가 자주 바뀌고 실행은 드문가?        → 자율 실행
5. 무엇을 테스트할지 아직 모르는가?        → 자율 탐색 (8-06)
```

### 규제 산업은 어디서 시작하나

웨비나의 권고: 금융·의료·공공처럼 규제가 엄격한 곳은 **자동화와 AI 증강부터**, 클라우드를 바로 쓸 수 있는 조직은 **자율까지 확장**.

이유를 풀면 이렇다.

- 감사관은 "그날 무엇을 어떻게 테스트했나"를 **재현 가능하게** 요구한다
- 자율 실행은 같은 수동 단계로도 **실행마다 경로가 다를 수 있다**
- 그래서 실무 패턴은 **자율 실행으로 초안을 얻고 → 성공한 실행을 스크립트로 고정 → 고정된 스크립트를 증거로 쓴다**

### 비결정성을 측정한다

자율 실행을 도입하기 전에 같은 TC를 **3~5회** 돌려 본다.

| 지표 | 의미 |
|---|---|
| 결과 일치율 | 5회 중 같은 판정 비율. 낮으면 단계가 모호하거나 에이전트가 불안정 |
| 경로 일치율 | 같은 요소를 같은 순서로 조작했나 |
| 평균 실행 시간 | 스크립트 대비 몇 배인가 |
| 사람 개입 횟수 | Assisted 모드에서 원격 제어를 넘겨받은 횟수 |

**결과 일치율이 낮은 TC를 자율 실행에 넣으면 플래키 테스트를 대량 생산**하는 것과 같다(트랙 3-05).

### 포트폴리오 예시

| 테스트 묶음 | 모드 | 이유 |
|---|---|---|
| 결제·정산 회귀 | 스크립트 (AI 증강 생성) | 고빈도, 되돌릴 수 없음, 감사 |
| 로그인·핵심 여정 Sanity | 스크립트 | 게이트, 분 단위 |
| 신규 기능 수동 TC (출시 전 2주) | 자율 실행 | 화면이 매일 바뀜 |
| 백오피스 드문 메뉴 | 자율 실행 | 연 몇 회, 스크립트 유지 비용이 더 큼 |
| 출시 전 요구사항별 탐색 | 자율 탐색 + 사람 탐색 | 모르는 문제 찾기 |

비율은 조직마다 다르다. 중요한 것은 **모드를 테스트마다 의식적으로 고르는 것**이다.

## 왜 채용시장이 요구하는가

- "자율 테스트 도입" 을 말하는 조직이 늘면서 **어디에 쓰지 말아야 하는지 아는 사람**이 필요해졌다. 과대 적용은 비용·플래키·감사 리스크로 돌아온다.
- 수동 TC를 **에이전트가 실행 가능한 형태로 쓰는 능력**은 이제 TC 작성 역량의 일부다. 트랙 1의 TC 설계와 바로 이어진다.
- 면접 질문: **"자율 테스트가 스크립트 자동화를 대체할까요?"** — 빈도·재현성·비용·되돌릴 수 없는 액션 기준으로 포트폴리오를 설명하면 된다.

## 실습 과제

### 과제 1 — 수동 TC 재작성 (15분)

우리 서비스(또는 실습 랩 결함 샘플 앱)의 수동 TC 2개를 위 After 형식으로 다시 쓴다.
재작성 전후로 **모호한 표현**("적절히", "정상", "확인한다")의 개수를 센다.

### 과제 2 — 모드 배정표 (15분)

테스트 묶음 10개를 나열하고 모드를 배정한다.

| 테스트 묶음 | 빈도 | 되돌릴 수 없는 액션 | 감사 필요 | UI 변경 | 배정 모드 | 이유 |
|---|---|---|---|---|---|---|
| | | | | | | |

### 과제 3 — 자율 실행 재현과 비결정성 측정 (25분, AI 도구 사용 시)

Claude Code·Cursor 등에서 Playwright MCP를 연결하고, 과제 1의 After TC를 그대로 준다.

```text
너는 수동 테스트 케이스를 실행하는 에이전트다.
- 단계를 순서대로 수행하고, 각 단계의 기대 결과를 확인해 PASS/FAIL 을 기록하라.
- 단계에 없는 행동은 하지 마라. 막히면 멈추고 이유를 적어라.
- 결과는 [{ step, action, expected, actual, result }] JSON 으로 출력하라.
```

**같은 TC를 3회** 실행하고 결과 일치율·경로 차이·실행 시간을 기록한다.
MCP 환경이 없으면 AI 실습 도우미에 TC와 화면 설명을 주고 "다음 행동"을 묻는 방식으로 1회만 해본다.

### 과제 4 — 스크립트로 고정 (15분)

과제 3에서 성공한 실행을 Playwright 테스트 코드로 옮긴다(에이전트에게 요청해도 된다).
옮긴 코드에 **기대 결과마다 어서션이 있는지** 8-02 과제 3 방식으로 감사한다.

### 과제 5 — 판단 훈련 (10분)

실습 랩 **🧭 에이전틱 테스트 운영 판단 훈련**의 시나리오 1·2를 푼다.

## 자가 체크리스트

- [ ] 자동화·증강·자율 테스트를 사람이 주는 것과 실행 주체로 구분할 수 있다
- [ ] 자율 실행이 없애는 단계와 자율 탐색이 없애는 단계를 구분할 수 있다
- [ ] 사라진 스크립트 작성 비용이 실행 시점의 속도·비용·비결정성으로 옮겨감을 안다
- [ ] Run with Autopilot의 필수 입력(대상 URL)과 실행 대상 런타임 조건을 안다
- [ ] 사람용 수동 단계가 에이전트에게는 모호할 수 있다는 문서 경고의 의미를 설명할 수 있다
- [ ] 한 단계 한 동작, 보이는 이름, 명시 값, 관찰 가능한 기대 결과로 TC를 쓸 수 있다
- [ ] 자격증명과 매개변수를 TC 본문에서 분리할 수 있다
- [ ] 실행 빈도·재현성·비용·되돌릴 수 없는 액션으로 실행 모드를 고를 수 있다
- [ ] 규제 산업에서 자율 실행 결과를 스크립트로 고정해 증거로 쓰는 패턴을 설명할 수 있다
- [ ] 자율 실행 도입 전 결과 일치율을 측정해야 하는 이유를 안다
- [ ] 결과 일치율이 낮은 TC를 자율 실행에 넣으면 플래키를 양산함을 설명할 수 있다
- [ ] 테스트 묶음별로 모드를 배정한 포트폴리오를 만들 수 있다
