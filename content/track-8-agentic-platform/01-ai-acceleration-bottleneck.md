> **이 트랙에 대하여** — UiPath Test Cloud 소개 웨비나(2026년 9월)를 출발점으로 삼고, 공개 문서·보도자료·조사 보고서로 내용을 확인하고 보강했다.
> 본문에서 **웨비나 주장**과 **공개 자료로 확인한 사실**을 구분해 표시한다. 특정 제품 사용법이 아니라 **어떤 플랫폼을 쓰든 통하는 설계·검증 능력**이 목표다.

## 개념 설명

### 두 개의 데이터 — 빨라졌는데 불안정해졌다

| 조사 | 규모·방법 | 핵심 발견 |
|---|---|---|
| **DORA 2025** — State of AI-assisted Software Development | 기술 실무자 약 5,000명 | AI 도입이 늘수록 **배포 처리량과 배포 불안정성이 함께** 올라간다. AI는 만능 해결책이 아니라 **증폭기**다 |
| **Faros AI Engineering Report 2026** — "Acceleration Whiplash" | 개발자 22,000명·4,000여 팀의 2년치 텔레메트리 (조직별 AI 도입 최저기 vs 최고기 비교) | 개발자당 완료 에픽 **+66%** · 개발자당 버그 **+54%** · PR당 인시던트 **+242.7%** · 리뷰 없이 머지된 PR **+31.3%** · 리뷰 시간 중앙값 **+441.5%** |

두 조사는 같은 곳을 가리킨다. **코드 생산은 사람 속도를 넘어섰는데, 검증은 여전히 사람 속도다.** 그 격차가 결함과 인시던트로 새어 나간다.

웨비나의 문제의식도 정확히 이것이다. "테스트가 느리다"가 아니라 **"테스트가 개발 속도를 흡수하지 못한다"** 가 문제다.

### 테스트 라이프사이클 지도 — 대부분이 회색이다

웨비나는 가로축에 라이프사이클 4단계, 세로축에 세부 활동을 놓고 **누가 하는지**로 칠했다. 회색은 사람, 빨간색은 규칙 기반 자동화다.

```text
            설계                자동화               실행                관리
          ───────────────   ───────────────   ───────────────   ───────────────
사람      요구사항 동기화      자동화 대상 선정      환경 구성            결과 검토
(회색)    테스트 케이스 생성   자동화 스크립트 작성  데이터 준비          실패 원인 분석
          우선순위 지정        검토·리팩터링         실행 트리거          커버리지 개선
                                                  케이스 안정화        알림·보고서 생성

규칙 기반                                         ▶ 테스트 실행
자동화
(빨강)
```

전통적 자동화가 맡아 온 것은 **맨 뒤 "실행" 칸 하나**뿐이다. 나머지는 사람 손이고, 단계 사이마다 **대기 시간**이 쌓인다.

에이전트가 들어오면 그림이 바뀐다. 요구사항 평가, 테스트 설계 검토, 자동화 대상 선정, 데이터 프로비저닝, 결과 검토, 실행 모니터링, 커버리지 개선이 에이전트 쪽으로 넘어간다. 사람은 **승인·예외 처리·리스크 판단**에 집중한다. **대체가 아니라 증폭**이다.

### 리드타임 분해 — 무엇이 느린지부터 잰다

"테스트가 느리다"는 측정 전에는 의미 없는 말이다. 회귀 사이클 한 번을 쪼갠다.

```text
테스트 리드타임 = 작업 시간 + 대기 시간 + 재작업 시간

예) 릴리즈 회귀 1회 (AS-IS)
  요구사항 변경 확인          3h 작업  +  8h 대기 (기획 답변)
  테스트 케이스 갱신          6h 작업
  자동화 스크립트 수정        8h 작업  +  4h 대기 (코드 리뷰)
  환경·데이터 준비            2h 작업  +  6h 대기 (인프라 요청)
  실행                        3h 작업
  실패 분석·재실행            6h 작업                +  4h 재작업
  리포트                      2h 작업  +  8h 대기 (다음 날 회의)
  ─────────────────────────────────────────────────────────
  합계                       30h 작업  + 26h 대기  +  4h 재작업  = 60h
```

이 예에서 **실행은 60시간 중 3시간, 5%** 에 불과하다.

### 암달의 법칙 — 실행만 빠르게 해서는 안 된다

전체 중 비율 **p** 인 구간을 아무리 빠르게 만들어도, 전체 속도 향상은 최대 **1 / (1 − p)** 다.

| 빠르게 만든 구간 | 비율 p | 최대 배속 |
|---|---|---|
| 실행만 | 5% (3h/60h) | 1.05배 |
| 실행 + 실패 분석 | 20% (12h/60h) | 1.25배 |
| 대기 시간 전부 | 43% (26h/60h) | 1.76배 |
| 작업·대기의 90% | 90% | 10배 |

**6배·12배는 실행 속도로는 절대 나오지 않는다.** 설계·분석·대기를 함께 줄여야 가능한 숫자다. 벤더가 배속을 말하면 **"어느 구간을 줄였나"** 를 물어야 하는 이유다.

역산도 해둔다. 6배가 되려면 `1/(1−p) = 6` → **p ≈ 83%**. 리드타임의 83%를 사실상 없애야 한다는 뜻이다.

### 웨비나의 "6배 → 9배 → 12배" 읽기

| 시점 | 배속 | 웨비나가 설명한 원천 |
|---|---|---|
| 현재 | 6배 | 에이전트가 설계와 자동화 일부를 대체 |
| 6개월 후 | 9배 | Maestro 오케스트레이션으로 단계 사이 대기 시간 축소 |
| 12개월 후 | 12배 | 자율 실행 비중 확대, 사람 개입은 예외 처리로 한정 |

웨비나의 측정 정의: **동일한 회귀 테스트 세트를 한 번 돌려 결과 리포트가 나올 때까지 걸린 총 소요 시간을 AS-IS와 TO-BE로 비교한 값.**

정의를 밝힌 것은 좋은 신호다. 원천 설명도 암달의 법칙과 맞는다(실행이 아니라 설계·대기를 줄인다). 그래도 **우리 조직에 옮기려면** 아래를 확인한다.

```text
□ AS-IS 기준선은 몇 번 측정했나 (1회인가, 평균인가)
□ 테스트 세트 규모·앱 유형이 우리와 비슷한가 (웹? SAP? 모바일?)
□ 초기 구축·학습 시간이 TO-BE에 포함됐나
□ 유지보수(깨진 테스트 수정) 시간이 포함됐나
□ 사람의 검토·승인 시간이 포함됐나
□ 6·12개월 수치는 측정값인가, 로드맵 목표인가   ← 발표 맥락상 목표치로 읽는 것이 맞다
```

### 사람의 자리는 어디에 남는가

| 에이전트에게 넘기는 것 | 사람에게 남기는 것 |
|---|---|
| 반복 작업 — TC 초안, 스크립트 변환, 결과 요약 | **승인** — 이 결과로 배포해도 되는가 |
| 판단의 1차 초안 — 실패 분류, 우선순위 제안 | **예외 처리** — 규칙이 없는 상황 |
| 대기를 만드는 전달·취합·알림 | **리스크 수용** — 무엇을 테스트하지 않고 갈 것인가 |

트랙 4가 "에이전트는 무엇을 할 수 있나"였다면, 트랙 8은 **"조직은 에이전트를 어떻게 운영하나"** 다.

## 왜 채용시장이 요구하는가

- QA 리드·매니저 공고에 **"AI 기반 테스트 체계 도입", "릴리즈 리드타임 단축"** 이 성과 목표로 적히기 시작했다. 병목을 **숫자로** 보여줄 수 있는 사람이 도입을 이끈다.
- 면접 질문: **"AI로 개발이 빨라졌는데 QA는 어떻게 따라가야 하나요?"** — DORA·Faros 데이터와 리드타임 분해로 답하면 인상 비평과 격이 다르다.
- 벤더 데모를 본 경영진이 "12배"를 기대할 때, **암달의 법칙으로 기대치를 조정**하는 사람이 프로젝트를 살린다. 과대 기대는 도입 실패의 가장 흔한 원인이다.

## 실습 과제

### 과제 1 — 우리 팀 리드타임 분해 (15분)

최근 회귀 사이클 1회를 위 형식으로 적는다. 기억이 흐리면 Jira 티켓 상태 변경 시각, CI 실행 로그, 메신저 대화 시각을 근거로 쓴다.

| 활동 | 작업 h | 대기 h | 재작업 h | 담당(사람/도구) | 대기 원인 |
|---|---|---|---|---|---|
| | | | | | |

**대기 시간이 작업 시간보다 긴 활동**에 표시한다. 그곳이 오케스트레이션(8-04)의 첫 대상이다.

### 과제 2 — 암달 계산 (10분)

과제 1의 숫자로 계산한다.

1. 실행만 0으로 만들면 최대 몇 배인가
2. 실행 + 실패 분석을 0으로 만들면 몇 배인가
3. 대기 시간을 절반으로 줄이면 몇 배인가
4. **3배**가 되려면 리드타임의 몇 %를 없애야 하나 (정답: 약 67%)

### 과제 3 — 라이프사이클 지도 색칠 (10분)

위 4단계 지도를 우리 팀 버전으로 다시 그린다. 각 활동에 **사람 / 규칙 자동화 / 에이전트 후보** 중 하나를 표시한다.
에이전트 후보로 표시한 것마다 **"사람이 여전히 승인해야 하나?"** 를 한 줄로 적는다.

### 과제 4 — 배속 주장 질문지 (10분)

위 체크리스트 6개에 **우리 조직에만 해당하는 질문 2개**를 더해 벤더 미팅용 질문지를 만든다.
예: "SAP 트랜잭션 테스트도 같은 배속이 나왔나요?", "온프레미스 모델로도 같은 결과인가요?"

### 과제 5 — CTO에게 보내는 한 문단 (10분)

트랙 7-07의 원칙(결론 먼저·사실과 추정 구분·필요한 결정)으로 쓴다.

```text
[결론] 우리 회귀 리드타임의 ○%는 실행이 아니라 대기입니다. 실행 자동화 확대만으로는 최대 ○배입니다.
[근거] 과제 1 측정값 + DORA 2025 / Faros 2026 요약 1줄
[요청] ○○ 구간을 대상으로 한 2주 PoC 승인
```

## 자가 체크리스트

- [ ] DORA 2025가 말하는 "AI는 증폭기"의 의미를 처리량·불안정성으로 설명할 수 있다
- [ ] Faros 2026 보고서의 핵심 수치(버그·인시던트·무리뷰 머지) 중 3개 이상을 말할 수 있다
- [ ] 전통적 규칙 기반 자동화가 라이프사이클에서 "실행" 칸만 맡아 왔다는 것을 설명할 수 있다
- [ ] 에이전트 도입 후 사람에게 남는 세 가지(승인·예외 처리·리스크 판단)를 말할 수 있다
- [ ] 테스트 리드타임을 작업·대기·재작업으로 분해할 수 있다
- [ ] 암달의 법칙 1/(1−p)로 최대 배속을 계산할 수 있다
- [ ] 목표 배속에서 줄여야 할 비율 p를 역산할 수 있다
- [ ] "실행 속도만으로는 6배가 나오지 않는다"를 숫자로 설명할 수 있다
- [ ] 웨비나의 6·9·12배 측정 정의(동일 회귀 세트, 리포트까지 총 소요 시간)를 안다
- [ ] 배속 주장을 우리 조직에 옮기기 전에 확인할 질문 6가지를 말할 수 있다
- [ ] 로드맵 목표치와 측정값을 구분해 보고할 수 있다
- [ ] 우리 팀 라이프사이클 지도에서 에이전트 후보와 사람 승인 지점을 표시할 수 있다
