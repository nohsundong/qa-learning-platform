## 개념 설명

### 트랙 4-06과 무엇이 다른가

| 트랙 4-06 | 이 레슨 |
|---|---|
| 에이전트 탐색 **루프의 원리** — 접근성 트리, 차터, 스텝 제한, 가드레일 코드 | 탐색을 **팀 운영 절차로** — 요구사항 연결, 시나리오 검토, 타임박스, 분류, 자산화, 지표 |
| "에이전트가 어떻게 돌아다니나" | "탐색 세션을 어떻게 계획하고, 결과를 무엇으로 바꾸나" |

### 자율 탐색이란

웨비나 정의: **단계별 지시조차 없다.** 수동 테스트 단계도, 스크립트도 없이 **무엇을 테스트할지만** 알려주면 에이전트가 애플리케이션을 스스로 돌아다니며 시나리오를 만들고 실행한다.

과거의 몽키 테스트와 다른 점은 **의도가 있다**는 것이다. 요구사항을 읽고, 핵심 여정과 경계 조건을 추론하고, 그 추론을 시나리오로 남긴다. 웨비나는 이것을 "사람이 미처 예상하지 못한 시나리오를 발견하는 능력, AI가 진정 능력을 발휘하는 지점"이라고 했다.

### 웨비나 데모 해부 — 대출 신청 자율 탐색

> 자율 탐색은 공개 문서에서 기능 설명을 찾지 못했다. 아래는 **웨비나 데모에서 보여준 흐름**이다. 도입 시 제공 상태(프리뷰/GA)를 확인한다.

```text
대상       바이브 코딩으로 만든 테스트용 사이트 (탭 6~7개, 탭마다 별도 기능)
요구사항   "운전자금 대출을 신청할 수 있어야 한다" (등록된 요구사항 7개 중 1개)
시작       요구사항 화면 → 자율 탐색
추가 지시   핵심 사용자 여정, 경계 조건, 엣지 케이스를 식별하고 스스로 추론해 여정을 탐색하라
          + "생성된 시나리오는 한글로 설명해 주세요"  (기본 출력이 영어였음)
설정       테스트 URL · 타임박스 30분(최대 60분) · 모델 · 라이브 스트리밍 · 테스트 로봇 연결
진행       로봇 로그 + 시나리오 탭에 생성된 시나리오 목록
결과       시나리오 6건 — 완료 2 · 사람이 스킵 3 · 실패 발견
```

데모에서 소개된 발견 두 가지를 **QA 눈으로** 다시 본다.

**발견 A — 신청 후 입력 폼이 초기화되지 않는다**

발표자는 "사이트를 만들 때 제출 후 초기화를 넣지 않았다"고 설명했다. 그럼 이것은 결함인가?

```text
요구사항 원문: "운전자금 대출을 신청할 수 있어야 한다"
→ 제출 후 폼 상태에 대한 기준이 없다
```

**기대값이 명세에 없으면 결함이 아니라 사양 질문이다.** 초기화하지 않는 것이 의도일 수도 있다(연속 신청 편의). 올바른 처리:

```text
유형: 사양 질문
질문: 신청 완료 후 입력 폼을 비워야 합니까, 유지해야 합니까?
근거: 제출 후에도 이전 입력값이 남아 있음 (스크린샷)
위험: 유지할 경우 중복 신청 가능성 → 중복 제출 방지 여부도 확인 필요
요청: 수용 기준에 제출 후 폼 상태를 명시
```

**발견 B — 숫자만 받아야 할 필드에 문자를 넣어도 접수된다**

에이전트가 스스로 "숫자 입력 데이터 형식 유효성 검증" 시나리오를 만들어 연 매출에 `abc!`, 금액에 `deff` 같은 문자를 넣었고, **접수 완료** 화면이 떴다(스크린샷 첨부).

이것은 사양 질문이 아니다. 금액 필드가 문자를 받는 것을 의도하는 명세는 없다. **결함**이다. 다만 결함 리포트를 쓰기 전에 한 걸음 더 간다.

```text
□ 화면 검증만 빠졌나, 서버도 받아들였나?     → API로 같은 값 전송 (트랙 2-02)
□ 저장된 값은 무엇인가?                     → DB 조회 (트랙 2-04)
□ 다른 숫자 필드도 같은가?                   → 동등 분할로 확장 (트랙 1-02)
```

서버까지 받아들였다면 **데이터 정합성 결함**으로 심각도가 올라간다. 에이전트는 화면 결과까지 봤고, **층을 가르는 것은 QA의 몫**이다.

### 미션 프롬프트 — 요구사항에 닻을 내린다

```text
[자율 탐색 미션]
요구사항   REQ-LOAN-003 "운전자금 대출을 신청할 수 있어야 한다"
수용 기준  - 신청 금액 1천만~10억 원
           - 연 매출·금액은 숫자만
           - 신청 완료 시 LN- 접수번호 표시
관점       핵심 여정 / 경계값 / 입력 형식 / 중복 제출 / 새로고침·뒤로가기
제외       다른 탭(세금계산서, 지원사업), 관리자 화면
금지       실제 외부 발송, 운영 URL 접근, 계정 설정 변경
데이터     금액·매출은 테스트용 값만. 개인정보처럼 보이는 실제 값 입력 금지
시나리오    최대 8개. 실행 전에 목록을 먼저 제시하라
출력       시나리오·발견은 한국어. 발견마다 유형(결함/사양 질문/관찰), 재현 절차, 기대, 실제, 증거
타임박스    20분
```

수용 기준이 있으면 발견 A 같은 애매함이 줄고, 발견 B는 명확한 결함이 된다. **요구사항의 품질이 탐색의 품질을 정한다.** 8-02에서 본 "요구사항 품질 평가"가 먼저인 이유다.

### 타임박스 정하기

탐색적 테스트의 세션 기반 관리(SBTM)에서 한 세션은 보통 45~90분이다. 에이전트 탐색은 이렇게 시작한다.

| 상황 | 타임박스 | 이유 |
|---|---|---|
| 처음 도입, 미션 다듬는 중 | 10~15분 | 오탐 원인을 빨리 보고 미션을 고친다 |
| 요구사항 1개, 화면 1~2개 | 20~30분 | 데모 수준 |
| 기능 영역 전체 | 30~60분 (여러 세션으로 쪼갬) | 한 세션에 요구사항 하나 |

**긴 타임박스 하나보다 짧은 세션 여러 개**가 낫다. 세션마다 결과를 보고 다음 미션을 고칠 수 있다.

### 시나리오 검토 — 사람은 편집자다

데모에서 발표자는 시나리오 3개를 **스킵**했다. 이것이 사람의 역할이다.

| 스킵 기준 | 예 |
|---|---|
| 이미 회귀 자동화가 커버 | 정상 신청 기본 흐름 |
| 범위 밖 | 다른 탭 기능 |
| 위험 행동 | 대량 반복 제출 (운영 알림 발생) |
| 가치 대비 비용 과다 | 브라우저 크기 전체 조합 |
| 다른 시나리오와 중복 | 금액 상한·하한이 따로 두 개 |

실행 전에 시나리오를 받는 설정이 없다면, **미션 프롬프트에 "실행 전 목록 제시"를 넣는다.**

### 발견 분류 — 네 칸

| 유형 | 판정 기준 | 다음 행동 |
|---|---|---|
| **결함** | 명세·수용 기준에 어긋남, 또는 명백한 오류(500, 데이터 손상) | 층 확인 후 결함 리포트 |
| **사양 질문** | 기대값이 명세에 없음 | 기획에 질문, 수용 기준 보강 |
| **오탐** | 에이전트의 오해 (잘못된 요소, 타이밍, 기대 착오) | 미션·데이터 규칙 수정 |
| **환경** | 테스트 환경 문제 (데이터 없음, 외부 연동 막힘) | 환경 담당 전달, 결과에서 제외 |

**"에이전트에게 결함인지 다시 물어보기"는 분류가 아니다.** 명세에 없는 기대값은 에이전트도 모른다(트랙 4-06의 근본 한계).

### 발견의 자산화 — 탐색은 한 번 쓰고 버리는 것이 아니다

```text
자율 탐색 세션
   │
   ├─ 결함 ──────────▶ 결함 리포트 ──▶ 수정 후 회귀 테스트로 고정 (스크립트)
   │
   ├─ 사양 질문 ──────▶ 수용 기준 보강 ──▶ 다음 미션의 검증 기준으로
   │
   └─ 오탐 ──────────▶ 미션·데이터 규칙 수정
                            │
다음 세션: 이미 회귀로 고정된 영역은 제외, 새 관점으로 이동
```

탐색이 찾은 것이 **회귀 자산**과 **더 나은 요구사항**으로 남아야 다음 탐색이 새 영역으로 간다. 그렇지 않으면 매번 같은 발견을 비용 내고 다시 찾는다.

### 운영 지표

| 지표 | 계산 | 해석 |
|---|---|---|
| 세션당 유효 발견 | (결함 + 사양 질문) / 세션 | 가치의 크기 |
| 오탐률 | 오탐 / 전체 발견 | 높으면 미션·데이터 규칙 개선 |
| 사양 질문 비율 | 사양 질문 / 전체 발견 | 높으면 요구사항 품질 문제 |
| 자산화율 | 회귀로 고정된 결함 / 결함 | 낮으면 같은 결함이 돌아온다 |
| 세션 비용 | 분 + 모델 비용 | 사람 탐색 시간과 비교 |
| 요구사항 탐색 커버리지 | 탐색한 요구사항 / 출시 대상 요구사항 | 빈 곳을 보여준다 |

## 왜 채용시장이 요구하는가

- 자율 탐색은 데모 효과가 가장 크고, **실제 운영에서 오탐과 사양 질문이 가장 많이 나오는** 기능이다. 발견을 분류하고 자산화하는 운영 능력이 차별점이다.
- 면접 질문: **"AI가 찾은 결함을 그대로 믿나요?"** — 결함/사양 질문/오탐/환경 분류와 층 확인(화면→API→DB)을 말하면 된다.
- "사양 질문"을 잘 쓰는 QA는 기획·개발과의 협업 병목을 줄인다. 웨비나 Q&A에서도 **요구사항 관리팀·개발팀과의 협업 병목**이 주요 질문이었다.

## 실습 과제

### 과제 1 — 미션 프롬프트 작성 (15분)

실습 랩 **🐞 결함이 숨겨진 샘플 앱**의 장바구니 또는 결제 기능으로 위 미션 양식을 모두 채운다.
수용 기준은 화면을 보고 **본인이 가정해서** 3개 이상 쓴다(가정이라고 표시).

### 과제 2 — 시나리오 먼저 받고 편집 (10분)

AI 도구(또는 AI 실습 도우미)에 미션을 주고 **시나리오 목록만** 받는다. 위 스킵 기준으로 편집한다.

| 시나리오 | 유지/스킵 | 스킵 기준 또는 유지 이유 |
|---|---|---|
| | | |

### 과제 3 — 15분 타임박스 탐색 (15분)

두 방법 중 하나.

- **MCP 사용**: Claude Code 등에 Playwright MCP를 연결하고 편집된 시나리오로 탐색 (최대 스텝 30)
- **수동 대행**: 본인이 에이전트 역할을 해 편집된 시나리오를 15분 동안 수행하며 트랙 4-06의 스텝 로그 형식으로 기록

타이머를 정확히 15분에 맞춘다. 끝나지 않은 시나리오는 "미완료"로 남긴다.

### 과제 4 — 발견 분류와 층 확인 (15분)

발견을 네 칸으로 분류한다. **결함 1건**은 화면·API(개발자 도구 네트워크 탭)·저장 결과 중 어디까지 영향이 있는지 확인한다.
**사양 질문 1건**은 위 양식(질문·근거·위험·요청)으로 쓴다.

### 과제 5 — 회귀로 고정 (15분)

결함 1건을 Playwright 테스트로 만든다. 샘플 앱 결함 목록의 정답과 대조한다.

### 과제 6 — 세션 리포트 (5분)

```text
세션: REQ-○○ / 15분 / 시나리오 편집 전 ○ → 후 ○
발견: 결함 ○ · 사양 질문 ○ · 오탐 ○ · 환경 ○
자산화: 회귀 테스트 ○건 추가, 수용 기준 ○건 보강 요청
다음 세션: (제외할 영역) / (새 관점)
```

## 자가 체크리스트

- [ ] 자율 실행과 자율 탐색이 사람에게서 받는 입력의 차이를 설명할 수 있다
- [ ] 자율 탐색이 몽키 테스트와 다른 점(의도·추론·시나리오)을 말할 수 있다
- [ ] 웨비나 데모의 설정 항목(URL·타임박스·모델·스트리밍·로봇)을 말할 수 있다
- [ ] "제출 후 폼 초기화 안 됨"이 명세에 따라 결함이 아니라 사양 질문일 수 있음을 설명할 수 있다
- [ ] 숫자 필드 문자 입력 발견을 화면·API·DB 층으로 확인하는 이유를 안다
- [ ] 요구사항·수용 기준·관점·제외·금지·출력 형식을 갖춘 미션 프롬프트를 쓸 수 있다
- [ ] 요구사항 품질이 탐색 품질을 좌우하는 이유를 설명할 수 있다
- [ ] 상황에 맞는 타임박스를 정하고 짧은 세션 여러 개가 나은 이유를 안다
- [ ] 실행 전 시나리오를 스킵 기준으로 편집할 수 있다
- [ ] 발견을 결함·사양 질문·오탐·환경으로 분류할 수 있다
- [ ] 사양 질문을 질문·근거·위험·요청 형식으로 쓸 수 있다
- [ ] 발견을 회귀 테스트·수용 기준·미션 개선으로 자산화하는 흐름을 그릴 수 있다
- [ ] 자율 탐색 운영 지표(유효 발견·오탐률·자산화율 등)를 계산할 수 있다
