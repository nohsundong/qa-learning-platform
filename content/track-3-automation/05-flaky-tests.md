## 개념 설명

### 플래키 테스트가 진짜 위험한 이유

플래키(flaky) 테스트는 **코드 변경 없이 통과와 실패를 오가는 테스트**다. 이게 왜 심각한가.

```text
1주차   빨간불이 뜬다 → 원인을 조사한다 → 재실행하니 통과 → "아 플래키였네"
3주차   빨간불이 뜬다 → 일단 재실행한다 → 통과 → 넘어간다
6주차   빨간불이 떠도 아무도 안 본다
8주차   진짜 결함으로 빨간불이 떴는데 그냥 재실행하고 배포한다   ← 사고
```

**플래키의 진짜 피해는 시간 낭비가 아니라 신뢰 붕괴다.** 통과율 92%인 자동화 스위트는 0%인 것과 크게 다르지 않다. 아무도 결과를 믿지 않기 때문이다.

그래서 원칙은 명확하다. **플래키를 발견하면 고치거나 격리한다. 방치하지 않는다.**

### 원인 6가지 분류

플래키를 만나면 먼저 분류부터 한다. 원인마다 해법이 완전히 다르다.

#### 1. 타이밍 / 경쟁 조건 (가장 흔하다, ~40%)

```typescript
// 목록이 갱신되기 전에 개수를 센다
await page.getByRole('button', { name: '삭제' }).click();
await expect(page.getByTestId('item')).toHaveCount(2);   // 가끔 3이 잡힌다
```

원인은 3편에서 다룬 것들이다. 고정 대기, `expect(await ...)`, 자동 대기가 커버 못 하는 내용 변경.

**해법**: 웹 우선 어서션으로 전환. 애니메이션이 있으면 `toBeVisible()` 로 안정 상태를 먼저 확인.

#### 2. 테스트 간 데이터 오염 (~20%)

앞 레슨에서 다룬 것. 병렬 실행 시 순서가 매번 달라서 **어떤 순서로 실행되느냐에 따라 결과가 바뀐다.**

진단 방법이 명확하다.

```bash
npx playwright test --workers=1        # 순차 실행하면 통과하는가?
npx playwright test --repeat-each=10   # 10번 반복하면 몇 번 깨지는가?
npx playwright test cart.spec.ts       # 이 파일만 돌리면 통과하는가?
```

**"단독 실행하면 통과, 전체 실행하면 실패"** 이면 100% 데이터 오염이다.

**해법**: fixture 로 데이터 격리, 고유 식별자 사용.

#### 3. 환경 / 인프라 (~15%)

CI 머신이 로컬보다 느리거나, 리소스가 부족하거나, 네트워크가 불안정한 경우.

```text
증상: 로컬은 항상 통과, CI에서만 간헐적 실패
      실패 시각이 특정 시간대에 몰림 (다른 빌드와 리소스 경합)
```

**해법**: CI의 워커 수를 줄인다(`workers: 2`), 타임아웃을 CI에서만 늘린다, CI 머신 사양을 올린다. **무작정 전역 타임아웃을 늘리는 건 마지막 수단이다.**

#### 4. 외부 의존성 (~10%)

외부 API, 결제 샌드박스, 이메일 서버, 서드파티 스크립트(광고·분석 태그).

```typescript
// 광고 스크립트가 늦게 로드되면서 레이아웃이 밀려 클릭이 빗나간다
```

**해법**: 외부 요청을 차단하거나 목킹한다.

```typescript
// 광고·분석 스크립트 차단 — 안정성과 속도가 함께 올라간다
await page.route(/(googletagmanager|doubleclick|facebook)\.(com|net)/,
  route => route.abort());

// 외부 API 응답 고정
await page.route('**/api/external/exchange-rate', route =>
  route.fulfill({ json: { rate: 1350 } })
);
```

**단, 목킹은 트레이드오프가 있다.** 외부 연동이 실제로 깨진 것을 못 잡게 된다. 그래서 **핵심 흐름은 실제 연동으로 하루 1회, 나머지는 목킹으로 매 PR** 같은 이중 구성을 쓴다.

#### 5. 테스트 코드 자체의 결함 (~10%)

```typescript
// 오늘이 말일이면 실패한다
const tomorrow = new Date();
tomorrow.setDate(tomorrow.getDate() + 1);
await expect(page.getByTestId('date')).toHaveText(`${tomorrow.getMonth() + 1}월 ${tomorrow.getDate()}일`);

// 자정을 넘기면 실패한다
// 월요일에만 실패한다 (주말 배치가 도는 서비스)
// 랜덤 데이터를 쓰는데 특정 값에서만 실패한다
```

**해법**: 시간을 고정한다.

```typescript
await page.clock.setFixedTime(new Date('2026-08-15T10:00:00+09:00'));
```

#### 6. 진짜 제품 결함 (~5%)

**가장 중요한 분류다.** 간헐적으로 실패하는 게 실제로 제품이 간헐적으로 잘못 동작하기 때문일 수 있다.

```text
동시성 버그 — 빠르게 두 번 클릭하면 중복 주문
경쟁 조건 — 재고 차감과 주문 생성의 순서가 보장되지 않음
캐시 불일치 — 가끔 옛 데이터가 보임
```

**"플래키니까 재시도"로 처리하면 이걸 영원히 놓친다.** 그래서 분류 없이 재시도부터 하는 습관이 위험하다.

판단 기준: **테스트 코드를 아무리 봐도 타이밍/데이터 문제가 아니면, 제품을 의심한다.** 그리고 트랙 2에서 배운 대로 로그와 DB를 확인한다.

### 진단 절차

```text
1. 재현시킨다
   npx playwright test <파일> --repeat-each=20
   → 실패율을 숫자로 만든다 (20회 중 3회 = 15%)

2. 격리해서 실행
   --workers=1 로 통과하면 → 데이터 오염 (분류 2)
   단독 파일만 돌려 통과하면 → 데이터 오염

3. 트레이스를 본다
   실패한 실행의 트레이스에서
   - 어느 단계에서 실패했나
   - 그 시점 화면에 무엇이 있었나
   - 네트워크 요청이 지연됐나
   - 콘솔에 에러가 있었나

4. 성공한 실행과 비교
   Trace Viewer 로 성공/실패 트레이스를 나란히 열고 차이를 찾는다

5. 분류하고 조치
```

4번이 실무에서 가장 효과적이다. **차이가 곧 원인이다.**

### 재시도 — 도구이지 해결책이 아니다

```typescript
export default defineConfig({
  retries: process.env.CI ? 2 : 0,
});
```

재시도의 올바른 용도는 **"CI를 계속 굴러가게 하면서, 플래키 목록을 수집하는 것"** 이다.

Playwright는 재시도로 통과한 테스트를 **`flaky` 로 별도 표시**한다. HTML 리포트와 JSON 리포트에 남는다. 이 목록을 주기적으로 봐야 한다.

**로컬은 `retries: 0` 으로 둔다.** 개발 중에 재시도로 가려지면 플래키를 만들고도 모른 채 커밋하게 된다.

### 격리 — 고칠 수 없을 때의 임시 조치

당장 고칠 수 없다면 **격리하되 기록을 남긴다.** 조용히 지우거나 skip 하면 영영 잊힌다.

```typescript
// 방법 1: 태그로 분리 — CI 메인 파이프라인에서 제외하고 별도 잡에서 실행
test('결제 완료 후 이메일이 도착한다 @flaky @issue-1423', async () => { ... });
```

```bash
npx playwright test --grep-invert @flaky      # 메인 파이프라인
npx playwright test --grep @flaky             # 격리 잡 (실패해도 빌드는 통과)
```

```typescript
// 방법 2: fixme — 실행하지 않고 리포트에 남긴다
test.fixme('재고 동시 차감 시 중복 주문 @issue-1500', async () => { ... });

// 방법 3: 조건부 skip — 원인이 명확할 때
test.skip(({ browserName }) => browserName === 'webkit',
          'WebKit 의 clipboard API 미지원 — issue-1502');
```

**격리할 때 지켜야 할 규칙 3가지**

1. **반드시 이슈 티켓을 만들고 번호를 태그에 남긴다.** 티켓 없는 격리는 삭제와 같다
2. **기한을 정한다.** "다음 스프린트까지" 같은 것. 격리 목록에 3개월 넘게 있는 테스트는 삭제 대상이다
3. **격리 개수를 지표로 관리한다.** 늘어나면 자동화가 병들고 있다는 신호다

### 안정성을 지표로 관리하기

```text
테스트 안정성 = 1 - (플래키 실행 수 / 전체 실행 수)

목표: 99% 이상
     (100번 실행에 1번 미만으로 흔들림)
```

**주간 점검 루틴**

```text
□ 이번 주 flaky 로 표시된 테스트 목록 확인
□ 3회 이상 반복된 것은 티켓 생성
□ 격리 목록 검토 — 기한 넘긴 것 처리
□ 전체 실행 시간 추이 (느려지고 있으면 원인 파악)
□ 안정성 지표 추이
```

이 루틴을 **QA가 주도하면 자동화가 살아있고, 아무도 안 하면 6개월 뒤에 죽는다.** 트랙 1의 품질 지표 레슨과 같은 원리다 — 측정하지 않으면 관리되지 않는다.

### 플래키를 애초에 덜 만드는 습관

| 습관 | 효과 |
|---|---|
| 고정 대기를 절대 쓰지 않는다 | 분류 1의 대부분 제거 |
| 테스트마다 고유 데이터 생성 | 분류 2 제거 |
| 외부 스크립트(광고·분석) 차단 | 분류 4 감소 + 속도 향상 |
| 시간 의존 로직에 clock 고정 | 분류 5 제거 |
| 새 테스트는 `--repeat-each=5` 로 검증 후 머지 | **사전 차단** |
| PR 리뷰에서 안티패턴 체크 | 팀 차원 예방 |

**마지막 두 개가 가장 효과가 크다.** 플래키는 만들어진 뒤 고치는 것보다 들어오지 못하게 막는 게 훨씬 싸다.

## 왜 채용시장이 요구하는가

- **"플래키 테스트를 어떻게 관리하셨나요?"** 는 자동화 경력자 면접의 핵심 질문이다. 이 질문 하나로 실제 운영 경험 유무가 드러난다.
- 좋은 답의 구조: **재현 → 분류 → 조치 → 격리 절차 → 지표 관리.** "재시도를 켰습니다"만 말하면 얕은 답이다.
- **"플래키인 줄 알았는데 진짜 결함이었던 경험"** 을 말할 수 있으면 강하다. 분류 6번을 아는 사람은 많지 않다.
- **AI에게 "이 테스트가 불안정한데 고쳐줘"라고 하면 대체로 대기를 늘리거나 재시도를 추가한다.** 원인을 분류하지 않고 증상을 덮는다. 심하면 `try/catch` 로 감싸서 "이제 실패하지 않습니다"라고 답한다. 원인 분류는 사람이 해야 한다.

## 실습 과제

### 과제 1 — 플래키 테스트 직접 만들기 (15분)

원인별로 **의도적으로 불안정한 테스트**를 3개 만든다. 각각 `--repeat-each=20` 으로 실패율을 측정한다.

| # | 만들 것 | 실패율 |
|---|---|---|
| 1 | `expect(await ...)` 를 써서 타이밍에 의존하게 | |
| 2 | 두 테스트가 같은 데이터를 공유하게 (병렬 실행) | |
| 3 | 현재 시각에 의존하게 (예: 초 단위 값 비교) | |

**직접 만들어 봐야 코드 리뷰에서 알아본다.**

### 과제 2 — 진단 절차 연습 (15분)

과제 1의 2번 테스트로 진단 절차를 그대로 따라간다.

1. `--repeat-each=20` 으로 실패율 측정
2. `--workers=1` 로 실행 → 통과하는가?
3. 단독 파일만 실행 → 통과하는가?
4. 실패 트레이스와 성공 트레이스를 **나란히 열고 차이 찾기**
5. 원인 분류와 조치 방법을 메모에 기록

### 과제 3 — 외부 스크립트 차단 효과 측정 (12분)

외부 스크립트가 많은 실제 사이트(뉴스 사이트 등)를 대상으로:

1. 페이지 로드 후 특정 요소를 확인하는 테스트 작성, 실행 시간 측정
2. `page.route` 로 광고·분석 도메인 차단 후 다시 측정
3. **시간 차이와 안정성 차이**를 기록
4. 차단으로 인해 **놓칠 수 있는 결함**은 무엇인지 적기

4번을 빼먹지 않는 게 중요하다. 트레이드오프를 인식하는 훈련이다.

### 과제 4 — 격리 절차 설계 (10분)

본인 팀(또는 가상의 팀)의 **플래키 관리 절차 문서**를 작성한다.

```text
1. 발견 기준: 무엇을 플래키로 판정하는가 (예: 최근 20회 중 2회 이상 실패)
2. 분류 기준: 6가지 중 어디에 속하는지 판단하는 질문들
3. 조치 기한: 분류별로 며칠 안에 처리하는가
4. 격리 규칙: 태그 형식, 티켓 필수 여부, 최대 격리 기간
5. 지표: 무엇을 주간으로 확인하는가
6. 삭제 기준: 언제 테스트를 지우는가
```

**6번이 어렵다.** 고칠 수 없고 가치도 낮은 테스트는 지우는 게 맞다. 그 판단 기준을 정한다.

### 과제 5 — AI의 플래키 처방 검증 (12분)

AI 실습 도우미에 과제 1에서 만든 불안정한 테스트 코드를 붙여넣고 요청한다.

> 이 테스트가 간헐적으로 실패합니다. 안정적으로 만들어 주세요.

| 확인 항목 | 결과 |
|---|---|
| 원인을 분류하고 설명했는가, 아니면 바로 코드를 고쳤는가 | |
| `waitForTimeout` 을 추가했는가 | |
| 타임아웃을 늘리는 것으로 때웠는가 | |
| `retries` 추가를 제안했는가 (원인 분석 없이) | |
| `try/catch` 로 감쌌는가 | |
| **근본 원인(어서션 방식, 데이터 공유)을 짚었는가** | |
| "제품 결함일 가능성"을 언급했는가 | |

마지막 두 항목이 핵심이다. **AI는 거의 항상 테스트 코드만 고치려 하고, 제품을 의심하지 않는다.**

- [ ] 플래키 원인 6가지를 나열하고 각각의 해법을 안다
- [ ] "단독 실행 통과, 전체 실행 실패"가 데이터 오염 신호임을 안다
- [ ] `--repeat-each`, `--workers=1` 로 플래키를 진단할 수 있다
- [ ] 실패 트레이스와 성공 트레이스를 비교해 원인을 찾을 수 있다
- [ ] `page.route` 로 외부 스크립트를 차단할 수 있고, 그 트레이드오프를 안다
- [ ] `page.clock` 으로 시간 의존 테스트를 고정할 수 있다
- [ ] **간헐적 실패가 진짜 제품 결함일 수 있다**는 가능성을 항상 검토한다
- [ ] 재시도는 플래키 수집 도구이지 해결책이 아니라는 것을 안다
- [ ] 로컬에서 `retries: 0` 을 유지하는 이유를 설명할 수 있다
- [ ] 격리 시 티켓 번호·기한·개수 관리 3원칙을 지킨다
- [ ] 테스트 안정성을 지표로 만들고 주간으로 점검할 수 있다
- [ ] 새 테스트를 머지 전에 반복 실행으로 검증하는 습관이 있다
- [ ] AI가 원인 분류 없이 대기·재시도로 덮는 처방을 걸러낼 수 있다
