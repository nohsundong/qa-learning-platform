## 개념 설명

### 이 레슨이 트랙 3의 결론이다

앞의 9편은 **어떻게** 자동화하는가였다. 이번 편은 **무엇을** 자동화할 것인가다. 그리고 실무에서 더 중요한 건 이쪽이다.

자동화 프로젝트가 실패하는 가장 흔한 경로는 이렇다.

```text
1. "우리도 자동화하자" → 목표: 자동화율 80%
2. 기존 수동 TC 500건을 그대로 자동화 시작
3. 3개월 뒤 300건 완성. 실행에 2시간. 통과율 85%
4. 매주 20건씩 깨짐. 고치는 데 QA 한 명이 붙음
5. 6개월 뒤: 아무도 결과를 안 봄. 자동화 담당자 번아웃
6. "자동화는 우리한테 안 맞는 것 같다"
```

문제는 도구도 실력도 아니었다. **무엇을 자동화할지 정하지 않고 시작한 것**이다.

### 자동화의 비용은 만드는 게 아니라 유지하는 것

이걸 숫자로 보면 판단이 쉬워진다.

```text
테스트 1건의 총비용 = 최초 작성 + (유지보수 × 기간)

수동 실행 비용   = 1회 실행 시간 × 실행 횟수
```

| 항목 | 대략치 |
|---|---|
| E2E 테스트 1건 최초 작성 | 2~4시간 |
| 연간 유지보수 (셀렉터 변경, 흐름 변경) | 작성 시간의 **50~100%** |
| 수동 실행 1회 | 5~15분 |

**손익분기 계산 예시**

```text
어떤 시나리오를 자동화한다고 하자.
  작성 4시간 + 연 유지보수 3시간 = 첫해 7시간
  수동 실행 10분

  7시간 ÷ 10분 = 42회

→ 1년에 42번 이상 실행할 시나리오면 이득이다.
  매주 배포 = 연 50회 → 자동화 이득
  분기 1회 기능 = 연 4회 → 자동화 손해
```

이 계산이 **"자동화율 80%"라는 목표가 왜 잘못됐는지** 설명해 준다. 자동화율은 목표가 아니라 결과여야 한다. (트랙 1의 굿하트의 법칙이 여기서도 적용된다)

### 자동화 우선순위 판단표

실무에서 쓰는 점수표다. 각 항목 1~5점.

| 기준 | 질문 | 점수가 높을 때 |
|---|---|---|
| **실행 빈도** | 얼마나 자주 실행하는가 | 매 배포마다 확인해야 함 |
| **비즈니스 임팩트** | 깨지면 얼마나 큰일인가 | 결제·로그인·주문 |
| **안정성** | 화면·흐름이 자주 바뀌는가 | 6개월 이상 안 바뀔 예정 |
| **판단 난이도** | 결과가 명확히 판정 가능한가 | 금액·상태 등 기계적 판정 |
| **수동 비용** | 손으로 하면 얼마나 걸리는가 | 오래 걸리고 지루함 |

```text
자동화 점수 = 실행빈도 + 임팩트 + 안정성 + 판단난이도 + 수동비용

20점 이상  →  최우선 자동화
15~19점    →  자동화
10~14점    →  검토 (수동 유지도 합리적)
10점 미만  →  자동화하지 않음
```

**예시 적용**

| 시나리오 | 빈도 | 임팩트 | 안정성 | 판단 | 수동비용 | 합계 | 결정 |
|---|---|---|---|---|---|---|---|
| 로그인 → 주문 → 결제 | 5 | 5 | 4 | 5 | 4 | **23** | 최우선 |
| 상품 검색 결과 정확성 | 5 | 3 | 4 | 4 | 3 | 19 | 자동화 |
| 권한별 메뉴 노출 | 4 | 4 | 4 | 5 | 4 | 21 | 최우선 |
| 신규 프로모션 배너 | 2 | 2 | 1 | 3 | 1 | 9 | 하지 않음 |
| 이메일 디자인 확인 | 2 | 2 | 2 | 1 | 2 | 9 | 하지 않음 |
| 접근성 스크린리더 체험 | 2 | 3 | 3 | 1 | 4 | 13 | 검토 |

**"판단 난이도" 항목이 중요하다.** "보기 좋은가", "자연스러운가"는 기계가 판정할 수 없다. 낮은 점수를 받는다.

### 자동화하지 말아야 할 것들

명확히 정리해 두면 논쟁이 줄어든다.

| 대상 | 이유 | 대안 |
|---|---|---|
| **탐색적 테스트** | 자동화는 예상한 것만 확인한다. 예상 못 한 것을 찾는 게 목적 | 사람이 SBTM 세션 (트랙 1) |
| **1회성 검증** | 손익분기를 못 넘는다 | 수동 |
| **자주 바뀌는 신규 기능** | 만드는 족족 깨진다 | 안정화 후 자동화 |
| **주관적 판단** | 디자인 미감, 문구 자연스러움, UX 흐름 | 사람 리뷰 |
| **재현이 매우 어려운 것** | 특정 기기·네트워크 조건 | 수동 or 모니터링 |
| **곧 없어질 기능** | 투자 회수 불가 | 수동 |

**첫 번째가 가장 중요하다.** 자동화가 늘어날수록 사람의 시간이 남는데, **그 시간을 탐색적 테스트에 써야 한다.** 자동화의 목적은 사람을 대체하는 게 아니라 **사람이 기계가 못 하는 일에 집중하게 하는 것**이다.

### 테스트 피라미드 — 어느 계층에서 자동화할 것인가

같은 검증을 어느 계층에서 하느냐로 비용이 10배 차이 난다.

```text
        /\
       /E2E\        느림·비쌈·불안정        10%   사용자 핵심 여정만
      /------\
     /  API   \     빠름·안정적            30%   비즈니스 로직, 권한, 계약
    /----------\
   /   Unit     \   매우 빠름·매우 안정적   60%   계산, 검증, 분기
  /--------------\
```

**QA가 흔히 만드는 실수: 모든 것을 E2E로 검증하려는 것.**

```text
할인 금액 계산 로직에 조합이 20가지 있다
  → E2E 20건: 실행 20분, 매우 불안정, 유지보수 지옥
  → API 20건: 실행 30초, 안정적
  → Unit 20건: 실행 1초, 개발자가 관리

  E2E 는 "할인이 적용된 화면이 보인다" 1건이면 충분하다.
```

**"이 검증을 더 낮은 계층에서 할 수 있는가?"** 를 항상 먼저 묻는다. 이 질문 하나로 E2E 스위트가 절반으로 준다.

그리고 낮은 계층은 대체로 개발자가 만든다. **QA가 "이건 유닛 테스트로 커버해 주세요"라고 요청**하는 것이 좋은 협업이다. 트랙 6의 코드 읽기 능력이 여기서 쓰인다.

**안티패턴: 아이스크림 콘**

```text
  \--------------/
   \    E2E     /     ← 대부분이 여기
    \----------/
     \  API   /
      \------/
       \Unit/
        \--/
```

유닛 테스트가 없어서 모든 걸 E2E로 검증하는 상태. 실행이 느리고 불안정하며 결함 위치를 특정하기 어렵다. **많은 조직이 실제로 이 모양이다.**

### 시작하는 순서

자동화를 처음 도입한다면 이 순서가 안전하다.

```text
1단계 (1개월)  스모크 5~10건
   로그인, 메인 로드, 핵심 트랜잭션 1건
   → CI에 붙이고 매 PR 실행. 10분 이내.
   → 여기서 팀이 "CI 빨간불 = 진짜 문제"라는 신뢰를 얻는다

2단계 (2~3개월)  핵심 여정 20~30건
   자동화 점수 20점 이상인 것들
   → 매일 야간 전체 실행

3단계  API 계층으로 확장
   E2E로 하던 조합 검증을 API로 내린다
   → 실행 시간이 줄고 안정성이 오른다

4단계  범위 확장
   브라우저 3종, 모바일 뷰포트, 접근성 자동 검사
```

**1단계에서 신뢰를 얻는 게 전부다.** 처음부터 100건을 만들면 그중 20건이 플래키이고, 팀은 첫 달에 자동화를 불신하게 된다. **적게, 확실하게 시작한다.**

### 자동화를 줄여야 할 때

늘리는 것만 생각하기 쉬운데, **정리도 정기적으로 해야 한다.**

```text
삭제 후보
  □ 6개월간 한 번도 실패한 적 없는 테스트
     → 결함을 못 잡고 있다는 뜻일 수 있다. 정말 의미 있는 검증인가?
  □ 지난 1년간 3회 이상 "테스트 수정"만 한 테스트
     → 유지보수 비용이 가치를 넘었다
  □ 격리된 채 3개월 넘은 테스트 (5편)
  □ 다른 테스트와 검증 내용이 겹치는 것
  □ 없어진 기능의 테스트
```

**첫 번째 항목은 논쟁적이다.** 한 번도 실패 안 한 테스트가 "안정성을 지켜주고 있는" 것일 수도 있다. 판단 기준은 **그 영역의 코드가 실제로 바뀌고 있는가**다. 코드가 계속 바뀌는데 테스트가 한 번도 안 깨졌다면 좋은 신호이고, 코드가 1년째 그대로면 그 테스트는 아무 일도 안 하고 있다.

### 자동화 성과를 어떻게 보고할 것인가

"자동화 300건 달성"은 성과가 아니다. **트랙 1의 지표 언어로 말한다.**

| 나쁜 보고 | 좋은 보고 |
|---|---|
| 자동화 300건 완료 | 회귀 테스트 소요 시간 8시간 → 25분 |
| 자동화율 65% 달성 | 결함 탈출률 18% → 9% |
| 매일 실행 중 | PR 단계에서 결함 12건 사전 차단 (지난 분기) |
| 커버리지 확대 | QA 수동 시간의 30%를 탐색적 테스트로 재배치 |

**마지막 행이 가장 강력한 논거다.** 자동화의 목적이 사람을 없애는 게 아니라 **사람의 시간을 더 가치 있는 곳으로 옮기는 것**임을 보여준다.

## 왜 채용시장이 요구하는가

- 채용공고에 명시적으로 **"자동화 대상 선정 기준 수립"**, **"자동화 전략 수립"** 이 들어가는 경우가 늘고 있다. 실행자가 아니라 설계자를 찾는다는 뜻이다.
- 면접 단골: **"모든 테스트를 자동화해야 할까요?"** — "아니오"와 그 근거를 조리 있게 말할 수 있어야 한다. 손익분기와 유지보수 비용을 숫자로 말하면 강하다.
- **"자동화 도입 후 무엇이 좋아졌나요?"** 에 건수가 아닌 지표로 답할 수 있는지가 시니어 판별 기준이다.
- **AI 시대에 이 판단의 가치가 오히려 올라갔다.** AI가 테스트 코드를 대량 생성할 수 있게 되면서, **"만드는 비용"은 싸졌지만 "유지하는 비용"은 그대로**다. 오히려 쉽게 만들 수 있으니 무분별하게 늘어나기 쉽다. **무엇을 만들지 않을 것인가가 더 중요해졌다.**

## 실습 과제

### 과제 1 — 손익분기 계산 (12분)

본인이 아는 서비스의 시나리오 5개를 골라 손익분기를 계산한다.

| 시나리오 | 작성(h) | 연 유지(h) | 수동 1회(분) | 손익분기 횟수 | 연 실행 예상 | 결정 |
|---|---|---|---|---|---|---|
| | | | | | | |

**"연 실행 예상"이 손익분기를 못 넘는 것이 반드시 1개 이상 나오게** 시나리오를 골라본다.

### 과제 2 — 우선순위 점수표 작성 (15분)

같은 서비스에서 시나리오 **10개**를 뽑아 5개 기준으로 점수를 매기고 정렬한다.

그리고 **아래 세 가지를 명시적으로 적는다.**

1. 최우선 자동화 3건과 그 이유
2. **자동화하지 않기로 한 3건과 그 이유** ← 이게 이 과제의 핵심
3. "지금은 아니지만 6개월 뒤 재검토" 2건과 재검토 조건

### 과제 3 — 계층 내리기 (12분)

E2E로 검증하려던 것을 **더 낮은 계층으로 내려본다.**

```text
검증 대상: 할인 정책
  - VIP 10%, 일반 5%
  - 쿠폰 중복 불가
  - 3만원 이상 무료배송
  - 도서산간 추가 3천원
  → 조합 12가지
```

| 검증 항목 | 원래 계층 | 내릴 수 있는 계층 | 남길 E2E |
|---|---|---|---|
| 등급별 할인율 계산 | E2E 6건 | | |
| 쿠폰 중복 차단 | E2E 2건 | | |
| 배송비 계산 | E2E 4건 | | |

**최종적으로 E2E 몇 건이 남는지** 세어보고, 원래 12건과 비교한다.

### 과제 4 — 정리 대상 선정 (10분)

가상의 자동화 스위트 현황이다. **삭제/유지/수정을 결정하고 근거를 적는다.**

| 테스트 | 최근 1년 실패 | 수정 횟수 | 비고 |
|---|---|---|---|
| A. 로그인 성공 | 3회 (전부 진짜 결함) | 1 | |
| B. 푸터 링크 검증 | 0회 | 0 | 푸터는 2년째 그대로 |
| C. 결제 흐름 | 8회 (5회 플래키) | 6 | |
| D. 프로모션 배너 | 15회 | 12 | 배너가 매달 바뀜 |
| E. 회원가입 | 0회 | 0 | 가입 로직이 최근 3번 리팩터링됨 |

**B와 E가 둘 다 "0회 실패"인데 판단이 달라야 한다.** 왜인지 설명한다.

### 과제 5 — 자동화 도입 제안서 (15분)

트랙 3 전체를 종합해 **1페이지 제안서**를 작성한다.

```text
1. 현황과 문제
   - 지금 무엇이 문제인가 (숫자로)
2. 목표
   - 자동화율이 아닌 지표로 (회귀 시간, 결함 탈출률)
3. 범위
   - 1단계에서 자동화할 시나리오 목록과 선정 근거
   - 자동화하지 않을 것과 그 이유
4. 도구와 근거 (7편)
5. 실행 계획
   - 1~4단계 일정
6. 유지보수 계획
   - 누가, 주 몇 시간, 플래키 관리 절차 (5편)
7. 리스크
   - 실패할 수 있는 시나리오와 대응
```

**6번이 대부분의 제안서에서 빠지고, 그래서 대부분의 자동화가 실패한다.** 유지보수 인력이 배정되지 않은 자동화는 도입하지 않는 게 낫다.

### 과제 6 — AI 자동화 전략 검증 (12분)

AI 실습 도우미에 요청한다.

> 쇼핑몰 웹서비스의 QA 자동화 전략을 수립하라. 현재 수동 테스트 케이스 400건을 운영 중이고, QA는 2명이다.

| 확인 항목 | 결과 |
|---|---|
| **자동화하지 않을 항목**을 명시했는가 | |
| 자동화율 같은 숫자 목표를 제시했는가 (나쁜 신호) | |
| 유지보수 비용과 인력 배정을 언급했는가 | |
| 테스트 피라미드 관점에서 계층을 나눴는가 | |
| 400건을 다 자동화하라고 했는가 | |
| 단계적 도입(스모크부터)을 제안했는가 | |
| 성과 측정을 건수가 아닌 지표로 제시했는가 | |
| QA 2명이라는 인력 제약을 반영했는가 | |

**AI는 대체로 "1단계: 400건 분석, 2단계: 우선순위 높은 것부터 자동화"처럼 그럴듯하지만 구체성 없는 답을 준다.** 그리고 **자동화하지 않을 것**을 거의 말하지 않는다. 그게 사람의 판단이다.

## 자가 체크리스트

- [ ] 자동화 프로젝트가 실패하는 전형적 경로를 설명할 수 있다
- [ ] 자동화 비용이 작성이 아니라 유지보수에 있다는 것을 숫자로 설명할 수 있다
- [ ] 손익분기 실행 횟수를 계산할 수 있다
- [ ] "자동화율 80%" 같은 목표가 왜 잘못됐는지 설명할 수 있다
- [ ] 5가지 기준(빈도·임팩트·안정성·판단난이도·수동비용)으로 점수를 매길 수 있다
- [ ] 자동화하지 말아야 할 6가지 대상을 근거와 함께 나열할 수 있다
- [ ] 탐색적 테스트를 자동화하지 않는 이유를 설명할 수 있다
- [ ] 자동화의 목적이 사람의 시간을 재배치하는 것임을 설명할 수 있다
- [ ] 테스트 피라미드의 계층별 비율과 각 계층의 특성을 안다
- [ ] "이 검증을 더 낮은 계층에서 할 수 있는가"를 먼저 묻는다
- [ ] 아이스크림 콘 안티패턴을 알아보고 개선 방향을 제시할 수 있다
- [ ] 개발팀에 유닛 테스트 커버를 요청하는 협업을 할 수 있다
- [ ] 1단계에서 스모크 5~10건으로 신뢰를 먼저 확보하는 이유를 안다
- [ ] 자동화 삭제 후보 5가지 기준을 알고 있다
- [ ] "0회 실패" 테스트를 코드 변경 여부로 판단할 수 있다
- [ ] 자동화 성과를 건수가 아닌 지표(회귀 시간, 탈출률)로 보고할 수 있다
- [ ] 유지보수 인력이 배정되지 않은 자동화는 도입하지 않는 게 낫다는 것을 안다
- [ ] AI 시대에 "무엇을 만들지 않을 것인가"가 더 중요해진 이유를 설명할 수 있다
