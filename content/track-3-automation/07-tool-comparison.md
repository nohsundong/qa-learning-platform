## 개념 설명

### 이 레슨의 목적

면접에서 **"왜 Playwright를 선택하셨나요?"** 라고 물으면, "요즘 많이 쓰니까요"는 약한 답이다. 반대로 **"이미 Selenium으로 500개를 운영 중인데 Playwright로 갈아탈까요?"** 에 무조건 "네"라고 답하는 것도 위험하다.

도구 선택은 기술 비교가 아니라 **팀 상황과 마이그레이션 비용을 포함한 판단**이다.

### 아키텍처 차이가 모든 것을 결정한다

세 도구가 브라우저를 제어하는 방식이 근본적으로 다르다. 장단점이 전부 여기서 나온다.

```text
Selenium
  테스트 코드 → WebDriver 프로토콜(HTTP) → 브라우저 드라이버 → 브라우저
  W3C 표준. 어떤 언어·어떤 브라우저든 붙는다. 대신 매 명령이 HTTP 왕복.

Playwright
  테스트 코드 → WebSocket(CDP 등) → 브라우저
  단일 연결로 양방향 통신. 브라우저 내부 이벤트를 구독할 수 있어
  자동 대기·네트워크 가로채기가 자연스럽다.

Cypress
  테스트 코드가 브라우저 안에서 실행된다
  앱과 같은 실행 컨텍스트. 디버깅이 편하지만 브라우저 밖의 일에 제약.
```

**Cypress의 "브라우저 안에서 실행"이 양날의 검이다.**

- 좋은 점: 앱의 내부 상태에 직접 접근, 타임 트래블 디버깅, 즉각적인 피드백
- 나쁜 점: 브라우저 보안 정책의 제약을 그대로 받는다. 탭 여러 개, 여러 도메인 이동, 파일 시스템 접근 등이 어렵거나 우회가 필요하다

### 비교표

| 항목 | Playwright | Cypress | Selenium |
|---|---|---|---|
| 언어 | JS/TS, Python, Java, .NET | **JS/TS 만** | 거의 모든 언어 |
| 브라우저 | Chromium, Firefox, WebKit | Chromium 계열, Firefox, WebKit(실험적) | 모든 주요 브라우저 |
| 자동 대기 | 강력 (actionability 6종) | 있음 | **없음** (직접 구현) |
| 병렬 실행 | 무료, 기본 제공 | 무료 티어는 제한적 (대시보드는 유료) | Grid 직접 구축 |
| 멀티 탭/도메인 | 자유롭게 | 제약 있음 (우회 API 존재) | 자유롭게 |
| 디버깅 | Trace Viewer, UI 모드 | 타임 트래블, 실시간 리로드 | 별도 구성 필요 |
| 모바일 웹 | 에뮬레이션 내장 | 뷰포트 변경 수준 | 드라이버에 따라 |
| API 테스트 | `request` 내장 | `cy.request()` | 별도 라이브러리 |
| 학습 곡선 | 중간 | **낮음** | 높음 |
| 생태계 성숙도 | 성장 중, 빠름 | 큼 | **가장 큼** (10년+) |
| 실행 속도 | 빠름 | 빠름 | 느림 |

### 언제 무엇을 고르는가

**Playwright를 고르는 경우** (신규 프로젝트의 기본값)
- 새로 자동화를 시작한다
- 브라우저 3종 크로스 검증이 필요하다
- 멀티 탭·멀티 도메인·파일 다운로드 등 복잡한 흐름이 있다
- CI에서 병렬로 빠르게 돌려야 한다
- 팀에 JS/TS 또는 Python 역량이 있다

**Cypress를 고르는 경우**
- **프론트엔드 개발자가 직접 테스트를 작성한다** (개발 워크플로에 자연스럽게 붙는다)
- 컴포넌트 테스트도 함께 하고 싶다
- 단일 도메인 SPA 위주다
- 팀에 이미 Cypress 자산과 노하우가 있다

**Selenium을 유지하는 경우**
- **이미 대규모 자산이 있다** ← 가장 흔한 이유이고, 정당한 이유다
- Java/C# 등 JS가 아닌 언어로 통일해야 한다
- IE·레거시 브라우저 등 특수 브라우저 지원이 필요하다
- 사내 Grid 인프라와 노하우가 이미 있다

**Detox를 고르는 경우**
- React Native 앱이다 (6편 참조)

### "갈아타야 하나요?" — 마이그레이션 판단

이 질문에 즉답하지 않는 게 좋은 QA다. 먼저 물어볼 것들이 있다.

```text
□ 지금 무엇이 문제인가?
   - 느리다 → 병렬화·불필요한 UI 테스트 정리로 해결될 수도 있다
   - 자주 깨진다 → 도구 문제가 아니라 로케이터·대기 전략 문제일 수 있다  ← 대부분 이쪽
   - 못 하는 게 있다 (멀티탭, WebKit) → 도구 교체가 정당하다

□ 기존 자산이 얼마나 되나? 500개면 전환 비용이 몇 개월이다
□ 팀이 새 도구를 배울 여력이 있나?
□ 전환 기간에 두 시스템을 병행 운영할 수 있나?
```

**핵심 통찰**: 자동화가 불안정한 이유의 대부분은 도구가 아니라 **로케이터 전략과 대기 처리**다 (2편, 3편). 도구를 바꿔도 같은 습관으로 짜면 똑같이 깨진다.

**현실적인 전환 전략**

```text
1. 새로 만드는 테스트만 새 도구로 (병행)
2. 기존 테스트는 손댈 일이 생길 때 하나씩 전환
3. 6개월 뒤 남은 것 중 가치 낮은 것은 삭제, 나머지만 마저 전환
```

**한 번에 전부 전환하는 프로젝트는 대체로 중간에 멈춘다.** 그리고 두 시스템을 다 방치하게 된다.

### 도구 선택 시 진짜 봐야 할 것

기능 비교표보다 중요한 것들이다.

| 기준 | 왜 중요한가 |
|---|---|
| **누가 테스트를 작성할 것인가** | QA만? 개발자도? 답에 따라 언어와 도구가 정해진다 |
| **팀의 기존 언어 역량** | 배우는 비용이 가장 큰 비용이다 |
| **CI 인프라** | 병렬 실행 비용, 컨테이너 지원 |
| **디버깅 경험** | 6개월 뒤 실패 원인을 얼마나 빨리 찾는가 = 유지보수 비용 |
| **채용 시장** | 그 도구를 아는 사람을 뽑을 수 있는가 |
| **문서와 커뮤니티** | 막혔을 때 답을 찾을 수 있는가 |

**첫 번째가 가장 중요하다.** 개발자가 함께 쓸 도구라면 개발자의 워크플로에 맞는 것을 골라야 한다. QA만 쓰는 도구는 QA가 병목이 되고, 결국 자동화가 개발 속도를 못 따라간다.

### 벤치마크 수치를 조심할 것

"Playwright가 Cypress보다 3배 빠르다" 같은 비교 글이 많다. 읽을 때 확인할 것.

- 어떤 테스트로 측정했나 (단순 페이지 로드 vs 실제 시나리오)
- 병렬 워커 수는 같았나
- 도구 버전은 언제인가 (6개월 전 벤치마크는 무의미할 수 있다)
- 측정자가 특정 도구 진영인가

**QA라면 벤치마크도 검증 대상으로 봐야 한다.** 그리고 가장 믿을 만한 수치는 **본인 프로젝트에서 직접 측정한 것**이다.

### 도구는 문제의 20%다

마지막으로 냉정하게 볼 것. 자동화가 실패하는 원인은 대부분 도구가 아니다.

```text
자동화 실패 원인
  전략 부재 (무엇을 자동화할지 안 정함)   ← 10편
  유지보수 인력 미배정                    ← 조직 문제
  로케이터·대기 전략 미숙                 ← 2·3편
  테스트 데이터 관리 실패                 ← 4편
  플래키 방치로 신뢰 붕괴                 ← 5편
  ────────────────────────────
  도구 선택 실패                          ← 실제로는 작은 비중
```

**면접에서 이 통찰을 말할 수 있으면 도구 이름을 나열하는 것보다 훨씬 강하다.**

## 왜 채용시장이 요구하는가

- **"도구를 왜 선택했는가"** 는 판단력을 보는 질문이다. 기술 비교만 하면 주니어, **팀 상황·비용·마이그레이션까지** 말하면 시니어로 읽힌다.
- 회사가 Selenium을 쓰고 있는데 지원자가 "Selenium은 낡았습니다"라고 하면 감점이다. **기존 자산을 존중하면서 개선안을 제시**할 수 있어야 한다.
- **"도구는 문제의 일부일 뿐"** 이라는 관점은 자동화를 실제로 운영해 본 사람만 갖는다.
- **AI에게 "어떤 도구가 좋아?"라고 물으면 항상 최신 인기 도구를 추천한다.** 기존 자산, 팀 역량, 전환 비용 같은 맥락을 묻지 않는다. **컨텍스트를 제공하고 트레이드오프를 요구하는 게 사람의 일**이다.

## 실습 과제

### 과제 1 — 같은 테스트를 두 도구로 (20분)

TodoMVC 시나리오 하나를 **Playwright와 Cypress 양쪽으로** 작성한다.

```bash
npm install -D cypress
npx cypress open
```

비교할 것:

| 항목 | Playwright | Cypress |
|---|---|---|
| 코드 줄 수 | | |
| 첫 실행까지 걸린 시간 | | |
| 실패했을 때 원인 파악 난이도 | | |
| 자동 대기 체감 | | |
| 문법이 직관적인가 | | |

**직접 써보지 않고 비교표를 외우는 것과는 완전히 다르다.**

### 과제 2 — 선택 근거 문서 작성 (15분)

아래 세 상황 각각에 대해 **도구 선택 제안서**를 작성한다. (각 200자 내외)

**상황 A**
> 스타트업. 프론트엔드 개발자 3명, QA 1명(본인). React SPA. 자동화 경험 없음. 개발자도 테스트를 작성했으면 함.

**상황 B**
> 대기업. Selenium + Java로 800개 테스트를 3년째 운영 중. 실행에 4시간 걸리고 통과율 87%. 팀은 Java만 씀.

**상황 C**
> 이커머스. 웹 + iOS/Android 앱. QA 4명. 결제 흐름을 브라우저 3종에서 검증해야 하고, 앱은 매주 배포.

각 제안서에 반드시 포함할 것: **선택한 도구 / 근거 3가지 / 예상 리스크 / 첫 3개월 계획**

**상황 B의 정답은 "Playwright로 전환"이 아닐 가능성이 높다.** 통과율 87%의 원인부터 물어야 한다.

### 과제 3 — 벤치마크 비판적으로 읽기 (10분)

"Playwright vs Cypress" 비교 글을 하나 찾아 읽고 다음을 평가한다.

| 확인 항목 | 결과 |
|---|---|
| 측정 방법이 공개돼 있는가 | |
| 도구 버전과 작성 시점은 | |
| 병렬 워커 수 등 조건이 동일했는가 | |
| 작성자가 특정 도구 관계자인가 | |
| **내 프로젝트에 적용 가능한 결론인가** | |

### 과제 4 — AI 도구 추천 검증 (12분)

AI 실습 도우미에 **과제 2의 상황 B**를 그대로 주고 도구 추천을 요청한다.

| 확인 항목 | 결과 |
|---|---|
| 통과율 87%의 **원인을 먼저 물었는가** | |
| 기존 800개 자산의 전환 비용을 언급했는가 | |
| 팀이 Java만 쓴다는 제약을 반영했는가 | |
| 무조건 Playwright를 추천하지 않았는가 | |
| 병행 운영·점진 전환을 제안했는가 | |
| **도구 교체 외의 대안**(병렬화, 테스트 정리, 로케이터 개선)을 제시했는가 | |

**첫 항목과 마지막 항목이 핵심이다.** AI는 대체로 원인을 묻지 않고 바로 도구를 추천하며, "도구를 바꾸지 않는 선택지"를 잘 제시하지 않는다.

## 자가 체크리스트

- [ ] Selenium·Playwright·Cypress의 아키텍처 차이를 그림으로 설명할 수 있다
- [ ] Cypress가 브라우저 안에서 실행되는 것의 장점과 제약을 함께 말할 수 있다
- [ ] 세 도구의 언어·브라우저·병렬·디버깅 지원 차이를 비교할 수 있다
- [ ] 신규 프로젝트에서 Playwright가 기본값이 되는 이유를 설명할 수 있다
- [ ] Cypress가 유리한 상황(개발자가 작성, 컴포넌트 테스트)을 안다
- [ ] Selenium을 유지하는 것이 정당한 이유 4가지를 댈 수 있다
- [ ] "갈아타야 하나요"에 즉답하지 않고 먼저 물어볼 질문 4가지를 안다
- [ ] 자동화 불안정의 원인이 대부분 도구가 아니라 로케이터·대기 전략임을 안다
- [ ] 점진적 전환 전략(신규만 새 도구 → 손댈 때 전환 → 나머지 정리)을 설명할 수 있다
- [ ] 도구 선택에서 "누가 테스트를 작성하는가"가 왜 1순위 기준인지 설명할 수 있다
- [ ] 벤치마크 수치를 검증 대상으로 보고 조건을 확인한다
- [ ] 자동화 실패 원인 중 도구 선택의 비중이 작다는 것을 설명할 수 있다
- [ ] 기존 도구를 폄하하지 않으면서 개선안을 제시할 수 있다
- [ ] AI의 도구 추천에서 맥락 무시와 대안 부재를 짚어낼 수 있다
