## 개념 설명

### COO — 일상적인 사업 운영과 생산 관리를 총괄

CEO가 **어디로 갈지** 정한다면, COO는 **매일 굴러가게** 만든다. 회사마다 범위 편차가 가장 큰 직함이기도 하다 — 생산·물류·CS 운영을 모두 갖기도 하고, 사업부 몇 개만 맡기도 한다.

| 하는 일 | 대표 숫자 | QA 접점 |
|---|---|---|
| 운영 프로세스 설계·개선 | 처리 리드타임, 운영 비용 | 운영 절차 변경의 검증 |
| 서비스 수준 관리 | SLA·SLO, 가용성 | 장애 기준, 성능 기준 (트랙 5) |
| 장애·위기 대응 | 장애 횟수, 복구 시간(MTTR) | 장애 재현, 사후 분석(포스트모템) |
| CS·물류·생산 운영 | 처리량, 오류율 | 운영 도구(백오피스) 테스트 |

### SLO를 숫자로 감각하기

COO와 대화하려면 **가용성 퍼센트가 시간으로 얼마인지** 알아야 한다. (30일 기준)

| 가용성 목표 | 한 달 허용 중단 시간 |
|---|---|
| 99% | 약 7시간 12분 |
| 99.9% | 약 43분 |
| 99.95% | 약 22분 |
| 99.99% | 약 4분 19초 |

**에러 버짓**(Error budget)은 "허용 중단 시간 중 남은 양" 이다. 이번 달 버짓을 다 썼다면 새 기능 배포보다 안정화가 먼저라는 합의를 만드는 도구다. QA는 **배포가 버짓을 얼마나 쓰게 했는지** 데이터를 줄 수 있다.

**운영 매뉴얼(런북)도 테스트 대상이다.** "결제 장애 시 수동 전환 절차" 가 문서대로 실제로 되는지, 장애가 나기 전에 확인한다.

### CHRO — 채용, 평가, 복지 등 인사 업무 총괄

| 하는 일 | QA와의 관계 |
|---|---|
| 채용 | QA 직무 기술서(JD), 면접 과제 설계 |
| 평가·보상 | QA 성과를 **무엇으로** 평가할지 (결함 수만 세면 왜곡된다) |
| 교육·경력 개발 | QA 역량 모델, 경력 사다리 |
| 조직문화 | 결함을 보고한 사람이 비난받지 않는 문화 |
| 인사 시스템 | 급여·근태·평가 시스템의 품질 |

**QA가 CHRO와 만나는 두 방향.**

1. **내 커리어** — 경력 사다리가 없으면 QA는 "시니어 다음" 이 안 보인다. 역량 모델 초안을 QA 리드가 먼저 제안하는 경우가 많다.
2. **HR 시스템 테스트** — 급여 계산은 **결정테이블과 경계값의 교과서**다(트랙 1-02, 1-03). 입사일·퇴사일 경계, 수습 기간, 휴직, 연장근로 조건이 얽힌다. 그리고 가장 민감한 개인정보를 다룬다.

**AI 도입에 따른 역할 재정의**도 CHRO 의제다. "테스트 실행" 비중이 줄고 "AI 산출물 검증·판단" 비중이 커지는 변화(트랙 4, 6)를 **직무 기술서와 교육 계획으로 옮기는 일**에 QA가 근거를 줄 수 있다.

평가 지표 설계 예:

| 나쁜 지표 | 왜 나쁜가 | 나은 지표 |
|---|---|---|
| 개인별 결함 발견 수 | 사소한 결함 쪼개기, 개발자와 대립 | 결함 탈출률, 치명 결함 사전 발견 비율 |
| 자동화 스크립트 개수 | 쓸모없는 스크립트 양산 | 자동화로 대체한 회귀 시간, 플래키율 |

(지표 자체는 트랙 1-08에서 다뤘다)

### CTO — 제품 기술과 개발 조직

| | CTO | CIO (7-04) |
|---|---|---|
| 대상 | **고객에게 파는 제품**의 기술 | **사내**에서 쓰는 IT 시스템 |
| 관심 | 아키텍처, 개발 생산성, 기술 부채 | 업무 시스템, 인프라 안정성, IT 비용 |

CTO가 자주 보는 개발 성과 지표로 **DORA 4대 지표**가 있다.

| 지표 | QA가 영향을 주는 방식 |
|---|---|
| 배포 빈도 | 느린 수동 회귀는 배포 빈도를 떨어뜨린다 |
| 변경 리드타임 | 테스트 대기 시간이 리드타임에 포함된다 |
| **변경 실패율** | 배포 후 장애·롤백 비율 — **QA 품질이 직접 드러나는 숫자** |
| 복구 시간 | 재현·원인 분석 속도 |

**속도(앞의 둘)와 안정성(뒤의 둘)을 함께 보는 지표**라서, QA가 "속도를 늦추는 조직" 이 아니라는 것을 보여주기 좋다.

### CPO — 제품 비전과 로드맵

Chief **Product** Officer. PM 조직을 이끌고 **무엇을 만들지, 무엇을 먼저 할지** 정한다.

| QA 접점 | 설명 |
|---|---|
| 요구사항 품질 | 명세 결함은 CPO 조직의 산출물에서 나온다 (트랙 1) |
| 인수 기준 | "완료" 의 정의를 PM과 함께 쓴다 |
| 기능 출시 판단 | 기능 플래그, 단계적 출시 범위 |

> **약어 주의** — CPO가 Chief **Privacy** Officer(개인정보 보호책임자)일 수도 있다. 한국 법에서 CPO라고 하면 보통 이쪽이다. (7-04)

### CAIO — AI 전략과 거버넌스

Chief AI Officer. **AI를 어디에 쓸지, 어떻게 안전하게 쓸지**를 책임진다. 최근 빠르게 늘어난 직함이다.

| 하는 일 | 예 |
|---|---|
| AI 활용 전략 | 어떤 업무·기능에 AI를 넣을지 |
| 거버넌스 | 사용 가이드, 승인 절차, 고위험 AI 관리 |
| 리스크 관리 | 환각, 편향, 개인정보·저작권, 보안 |
| 규제 대응 | 국내외 AI 규제 준수 |

**규제 흐름 두 가지**

- **미국** — 연방정부 관리예산처(OMB)가 2024년 각 연방기관에 CAIO 지정을 요구했고(M-24-10), 2025년 4월 이를 대체한 **M-25-21** 에서도 기관별 CAIO 지정과 고영향 AI 관리 절차를 유지했다.
- **한국** — **「인공지능 발전과 신뢰 기반 조성 등에 관한 기본법」(AI 기본법)** 이 **2026년 1월 22일 시행**됐다. 고영향 인공지능의 안전성·신뢰성 확보 조치, 생성형 AI 결과물 표시 등이 핵심이고, 정부는 시행 초기 최소 1년 이상의 계도기간을 두겠다고 밝혔다.

이 법들이 **민간 기업에 CAIO라는 직함을 두라고 강제하는 것은 아니다.** 하지만 이런 의무에 대응하는 일이 CAIO나 AI 거버넌스 조직의 몫이 된다.

**QA 접점 — AI 기능은 QA가 가장 필요한 영역이다**

| 검증 | 설명 |
|---|---|
| 품질 평가 | 정확도, 환각률 — **평가 데이터셋**을 누가 만들고 관리하는가 |
| 편향·안전 | 민감 주제, 차별적 응답, 레드팀 |
| 표시 의무 | AI 생성 결과물임이 표시되는가 (법 해석은 법무 확인) |
| 회귀 | 모델·프롬프트를 바꿨을 때 품질이 떨어지지 않는가 (트랙 4) |
| 사람 검토 | 사람이 개입·수정할 수 있는 경로가 동작하는가 |

### CQO — 전사 품질 책임자

Chief Quality Officer. **품질경영 체계, 규제 준수, 지속적 개선, 품질 문화**를 책임지고, 보통 CEO에게 보고한다.

| 업종 | 모습 |
|---|---|
| 제조·제약·의료기기·병원 | **흔하다.** 품질 규제와 인증이 사업의 전제다 |
| 소프트웨어·IT 서비스 | **드물다.** 대신 VP of Quality, QA 본부장, Head of QA 같은 직함 |

QA 커리어의 최상단이 어떤 모습인지 보여주는 역할이다. 소프트웨어 회사에서 **품질이 C레벨 의제가 되는 순간**은 대개 대형 장애·보안 사고 직후다. 그 전에 지표와 체계를 준비해 둔 QA 리드가 그 자리를 맡는다.

### 트랙 7 C레벨 지도 완성

```text
방향     CEO · CSO · (CEO Japan: 지역)
돈       CFO
매출·고객 CRO · CMO · CCO
운영     COO
사람     CHRO
기술     CTO · CIO · CDO
제품     CPO(Product)
위험     CISO · CPO(Privacy) · CLO
AI       CAIO
품질     CQO / Head of QA
```

## 왜 채용시장이 요구하는가

- **장애 대응·포스트모템 경험**은 운영 성숙도가 높은 회사일수록 필수로 본다. COO·CTO와 같은 테이블에 앉는 일이다.
- AI 기능을 가진 서비스가 늘면서 **"AI 품질 평가", "LLM 평가", "AI 레드팀"** 이 QA 공고에 등장했다. CAIO 조직과 협업하는 자리다.
- 리드 공고의 **"QA 조직 구축, 역량 모델·온보딩 설계"** 는 CHRO와 함께 하는 일이다.
- DORA 지표로 품질을 말할 수 있으면 **"QA가 속도를 늦춘다"** 는 편견에 숫자로 답할 수 있다.

## 실습 과제

### 과제 1 — SLO 감각 익히기 (10분)

1. 본인 서비스(또는 가상 서비스)의 가용성 목표를 정한다
2. 한 달 허용 중단 시간을 계산한다
3. 지난 한 달 장애 기록(또는 가상 기록)으로 **남은 에러 버짓**을 구한다
4. 버짓이 20% 남았을 때 QA가 제안할 배포 정책을 한 문단으로 쓴다

### 과제 2 — COO용 포스트모템 초안 (15분)

기억나는 장애 하나(또는 가상 장애)로 작성한다. **비난하지 않는(blameless) 형식**이다.

```text
[요약]        무엇이, 언제부터 언제까지, 누구에게 영향
[영향]        중단 시간, 영향 사용자, 매출·CS 영향
[타임라인]    감지 → 판단 → 조치 → 복구
[근본 원인]   왜 발생했나 / 왜 사전에 못 잡았나
[재발 방지]   테스트·모니터링·프로세스 (담당, 기한)
```

**"왜 사전에 못 잡았나"** 칸이 QA의 몫이다.

### 과제 3 — QA 경력 사다리 초안 (15분)

CHRO에게 제안한다고 가정하고 4단계를 설계한다.

| 단계 | 기대 역할 | 핵심 역량 | 성과 증거 |
|---|---|---|---|
| 주니어 | | | |
| 시니어 | | | |
| 리드/스태프 | | | |
| 매니저/헤드 | | | |

트랙 7의 내용(비즈니스 영향 보고, 예산 설득)이 **어느 단계부터 요구되는지** 표시한다.

### 과제 4 — AI 기능 출시 체크리스트 (15분)

사내 챗봇(고객 문의 응답)을 출시한다고 가정하고, CAIO에게 가져갈 체크리스트 10개를 만든다.

- 품질 평가(데이터셋, 합격 기준)
- 편향·안전 (민감 질문 목록)
- AI 생성 결과물 표시
- 사람 상담원 전환 경로
- 모델 교체 시 회귀

법 조항 해당 여부는 **"법무 확인 필요"** 로 표시한다. QA가 단정하지 않는다.

### 과제 5 — AI 결과 검증 (10분)

AI 실습 도우미에 요청한다.

> 한국 AI 기본법에 따라 고객 상담 챗봇을 운영하는 기업이 해야 할 일을 정리하라.

| 확인 항목 | 결과 |
|---|---|
| 시행일(2026-01-22)을 정확히 썼는가 | |
| 고영향 AI 해당 여부를 **근거 없이 단정**하지 않았는가 | |
| 존재하지 않는 조항 번호·과태료 금액을 만들어내지 않았는가 | |
| 원문(국가법령정보센터)을 확인하라고 안내했는가 | |
| 계도기간 등 최신 정부 방침을 반영했는가 (학습 시점 이후 변경 가능성) | |

## 자가 체크리스트

- [ ] COO가 하는 일과 대표 숫자(SLA, MTTR 등)를 말할 수 있다
- [ ] 99.9%·99.99% 가용성이 한 달에 몇 분인지 계산할 수 있다
- [ ] 에러 버짓이 배포 정책 합의 도구임을 설명할 수 있다
- [ ] 런북도 테스트 대상임을 안다
- [ ] CHRO와 QA가 만나는 두 방향(커리어, HR 시스템)을 안다
- [ ] 결함 발견 수가 나쁜 평가 지표인 이유를 설명할 수 있다
- [ ] CTO와 CIO의 차이를 제품/사내 시스템으로 구분할 수 있다
- [ ] DORA 4대 지표와 QA의 연결을 설명할 수 있다
- [ ] CPO가 Product와 Privacy 두 뜻임을 알고 문맥으로 구분한다
- [ ] CAIO의 역할과 AI 기능 QA 검증 항목을 5개 이상 안다
- [ ] 한국 AI 기본법 시행일과 핵심 의무의 방향을 안다
- [ ] 법이 CAIO 직함을 강제하는 것은 아님을 안다
- [ ] CQO가 흔한 업종과 소프트웨어 업계의 대응 직함을 안다
