## 개념 설명

### 전략(Strategy)과 계획(Plan)은 다른 문서다

면접에서 자주 걸러지는 지점이다. 두 단어를 섞어 쓰면 "문서 작성 경험이 없다"고 읽힌다.

| | 테스트 전략 | 테스트 계획 |
|---|---|---|
| 범위 | 조직·제품 전반 | 특정 릴리즈·프로젝트 |
| 수명 | 오래 유지 (분기~연 단위) | 릴리즈마다 새로 씀 |
| 답하는 질문 | **어떻게** 테스트하는가 | **이번에 무엇을** 언제 누가 |
| 예시 내용 | 자동화 대상 기준, 환경 정책, 결함 등급 정의, 릴리즈 기준 | 이번 스프린트 대상 기능, 일정, 담당자, 리스크, 진입/종료 조건 |

전략은 "우리 팀은 결제 도메인은 항상 회귀 자동화를 돌린다"이고,
계획은 "이번 3.2.0 릴리즈에서는 쿠폰 기능이 추가되므로 결제 회귀 + 쿠폰 신규 TC 42건을 4/8까지 수행한다"이다.

### 계획의 핵심은 '리스크 기반'이다

시간은 항상 부족하다. 그래서 계획의 본질은 **무엇을 테스트할지가 아니라, 무엇을 테스트하지 않을지 정하고 그 근거를 남기는 것**이다.

리스크 점수를 이렇게 매긴다.

```
리스크 = 발생 가능성(1~5) × 영향도(1~5)
```

- **발생 가능성**을 올리는 요인: 이번에 코드가 많이 바뀐 영역, 과거 결함이 잦았던 영역, 복잡한 조건 분기, 새로 합류한 개발자가 만진 영역, 외부 연동
- **영향도**를 올리는 요인: 돈이 오가는가, 데이터가 유실되는가, 전체 사용자가 막히는가, 법·규제 이슈인가, 되돌릴 수 있는가

점수가 높은 순으로 테스트 깊이를 차등 배분한다. 결제 실패(5×5=25)와 프로필 사진 썸네일 깨짐(3×1=3)에 같은 시간을 쓰면 안 된다.

### 진입 조건과 종료 조건

이 두 가지가 없는 계획서는 "언제 끝나는지 아무도 모르는 계획"이다.

**진입 조건 (Entry Criteria)** — 이게 충족돼야 테스트를 시작한다
- 빌드가 테스트 환경에 배포되어 있고 스모크 테스트를 통과했다
- 기능 명세가 확정되었다 (또는 변경분이 공유되었다)
- 테스트 데이터와 계정이 준비되었다

**종료 조건 (Exit Criteria)** — 이게 충족되면 테스트를 끝낸다
- 계획한 TC 실행률 100%, 통과율 95% 이상
- Blocker/Critical 결함 0건, Major 결함은 모두 원인 파악 및 릴리즈 판단 완료
- 회귀 자동화 스위트 통과

숫자를 적는 것이 중요하다. "충분히 테스트되면"은 조건이 아니다.

### 테스트 계획서 최소 목차

실무에서 A4 2~3장이면 충분하다. 길면 아무도 안 읽는다.

```text
1. 대상과 범위        - 이번 릴리즈에 포함되는 기능 / 명시적으로 제외하는 기능
2. 리스크 분석        - 영역별 리스크 점수와 그에 따른 테스트 깊이
3. 테스트 유형과 수준  - 기능/통합/회귀/탐색적/성능 중 무엇을 어디까지
4. 환경과 데이터      - 서버 환경, 단말, 계정, 테스트 데이터 준비 방법
5. 일정과 담당        - 누가 언제 무엇을
6. 진입/종료 조건     - 숫자로
7. 리스크와 대응      - 일정 지연 시 무엇을 먼저 버릴 것인가
```

7번이 실제로 가장 유용하다. 일정이 밀렸을 때 즉흥적으로 자르지 않고, 미리 합의된 우선순위대로 자를 수 있게 해준다.

## 왜 채용시장이 요구하는가

QA 채용공고의 "테스트 계획 수립 및 테스트 전략 문서 작성 경험"은 사실상
**"당신은 시키는 대로 TC를 실행하는 사람인가, 아니면 무엇을 테스트할지 스스로 결정하는 사람인가"**를 묻는 항목이다.

- **주니어와 시니어를 가르는 기준**이라서 묻는다. TC 실행은 신입도 하고 이제는 AI도 한다. 범위를 정하고 근거를 대는 판단은 대체되지 않는다.
- **AI 시대에 오히려 비중이 커졌다.** AI가 TC를 100건 뽑아주는 상황에서 QA의 일은 "그중 어떤 30건이 이번 릴리즈에 진짜 필요한가"를 고르는 것이다. 이 판단의 근거가 리스크 기반 계획이다.
- **개발·기획과 협상하는 언어**다. "시간이 부족합니다" 대신 "결제 회귀를 빼면 25점짜리 리스크가 열립니다. 대신 프로필 영역 3점짜리를 빼겠습니다"라고 말할 수 있어야 한다.

면접에서는 보통 이렇게 나온다. *"릴리즈 3일 전인데 큰 기능이 하나 추가됐습니다. 어떻게 하시겠어요?"*
정답은 야근이 아니라 **리스크 재평가 + 범위 재조정 + 판단 근거 공유**다.

## 실습 과제

### 과제 1 — 실제 서비스로 테스트 계획서 쓰기 (15분)

본인이 자주 쓰는 앱이나 웹서비스를 하나 고른다 (배달앱, 은행앱, 쇼핑몰 등).
그 서비스에 **"쿠폰 자동 적용"** 기능이 새로 추가된다고 가정하고, 위 7항목 목차로 A4 1장짜리 계획서를 작성한다.

반드시 포함할 것:
- 리스크 표에 최소 5개 영역, 각각 점수와 근거
- **명시적으로 테스트하지 않을 항목 3개와 그 이유**
- 종료 조건을 숫자로

### 과제 2 — 종료 조건 뒤집어 보기 (5분)

작성한 종료 조건을 보고 스스로 물어본다.

> "이 조건을 다 만족했는데도 운영에서 큰 장애가 났다면, 무엇이 빠져 있었던 걸까?"

떠오른 항목을 종료 조건에 한 줄 추가한다. 이 사고 훈련이 결함 탈출률을 줄인다.

### 과제 3 — AI에게 시키고 검증하기 (선택, 10분)

이 페이지 하단의 **AI 실습 도우미**에서 `요구사항 → 테스트 케이스 초안`을 열고, 과제 1의 쿠폰 기능 요구사항을 입력한다.
결과를 받은 뒤 **직접 채점**한다.

- AI가 리스크 우선순위를 매겼는가, 아니면 모든 항목을 평평하게 나열했는가?
- "확인이 필요한 질문"에 실제로 애매한 부분이 들어갔는가?
- 내가 쓴 계획서에는 있는데 AI가 놓친 항목은 무엇인가?

대체로 AI는 **범위를 좁히는 판단**을 못 한다. 그게 지금 당신이 학습하는 이유다.

## 자가 체크리스트

- [ ] 테스트 전략과 테스트 계획의 차이를 한 문장씩으로 설명할 수 있다
- [ ] 리스크 = 발생 가능성 × 영향도 로 영역별 점수를 매길 수 있다
- [ ] 발생 가능성을 높이는 요인 3가지, 영향도를 높이는 요인 3가지를 댈 수 있다
- [ ] 진입 조건과 종료 조건을 각각 숫자가 들어간 형태로 쓸 수 있다
- [ ] 테스트하지 않을 항목을 근거와 함께 명시할 수 있다
- [ ] 일정이 축소됐을 때 무엇부터 자를지 미리 정해둘 수 있다
- [ ] "3일 남았는데 기능이 추가됐다" 질문에 리스크 언어로 답할 수 있다
- [ ] 테스트 계획서 7개 항목을 보지 않고 나열할 수 있다
