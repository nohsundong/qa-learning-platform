## 개념 설명

앞 레슨에서 "숫자 근거로 말하라"고 했다. 이번 레슨은 그 숫자들의 정의와, **그 숫자를 어떻게 오해하지 않을 것인가**를 다룬다.

지표를 다루는 QA가 반드시 알아야 할 전제가 하나 있다.

> **모든 품질 지표는 조작 가능하다.** 그래서 지표는 "판단의 근거"로 쓰고, "달성해야 할 목표"로 걸어두면 반드시 망가진다.

### 1. 테스트 커버리지

커버리지에는 성격이 다른 두 가지가 있다. **면접에서 자주 섞어 쓰는데, 구분해야 한다.**

**요구사항 커버리지 (QA의 지표)**

```text
요구사항 커버리지 = (TC가 매핑된 요구사항 수 / 전체 요구사항 수) × 100
```

요구사항 명세의 각 항목에 최소 1개 이상의 TC가 연결돼 있는가를 본다. **이게 QA가 직접 관리하는 커버리지다.** 요구사항 추적 매트릭스(RTM)로 관리한다.

| 요구사항 ID | 내용 | TC ID | 실행 결과 |
|---|---|---|---|
| REQ-01 | 쿠폰은 주문당 1회 적용 | TC-011, TC-012, TC-013 | Pass |
| REQ-02 | 휴면 회원은 쿠폰 사용 불가 | TC-021 | Fail |
| REQ-03 | 도서산간 추가 배송비 | **없음** | ← 구멍 |

RTM의 진짜 가치는 마지막 행이다. **TC가 하나도 없는 요구사항을 발견하는 것**이 목적이다.

**코드 커버리지 (개발의 지표)**

```text
라인 커버리지   : 실행된 코드 라인 / 전체 라인
브랜치 커버리지 : 실행된 분기 / 전체 분기   ← 이쪽이 의미 있다
```

QA가 만드는 숫자는 아니지만 **읽을 줄은 알아야 한다.** 그리고 이 지표의 함정을 알아야 한다.

```javascript
function calcShipping(amount, isVip) {
  if (amount >= 30000 || isVip) return 0;
  return 3000;
}

// 이 테스트는 라인 커버리지 100% 를 만든다
test('배송비', () => {
  calcShipping(50000, false);   // 0 반환 경로
  calcShipping(10000, false);   // 3000 반환 경로
});
```

라인 커버리지 100%인데 **아무것도 검증하지 않았다.** `expect` 가 없다. 그리고 `isVip=true` 경로는 실행조차 안 됐는데 `||` 단축 평가 때문에 라인은 다 지나갔다.

> **커버리지는 "테스트되지 않은 곳"을 찾는 도구이지, "테스트가 잘 됐다"는 증거가 아니다.**

커버리지 80%가 목표로 걸리면 개발자는 assert 없는 테스트를 양산하게 된다. 이게 굿하트의 법칙이다. QA가 코드 커버리지 리포트를 볼 때는 **숫자가 아니라 "0%인 파일"** 을 본다. 그게 위험 지점이다.

### 2. 결함 밀도 (Defect Density)

```text
결함 밀도 = 발견된 결함 수 / 규모
```

규모 단위는 조직에 따라 다르다. KLOC(코드 1000줄), 기능 포인트, 화면 수, 스토리 포인트 등.

**절대값은 의미가 없고 비교할 때만 쓴다.**

| 모듈 | 결함 수 | 규모(KLOC) | 밀도 |
|---|---|---|---|
| 결제 | 24 | 8 | 3.0 |
| 상품목록 | 6 | 12 | 0.5 |
| 알림 | 15 | 3 | **5.0** |

알림 모듈이 눈에 띈다. 코드는 작은데 결함이 가장 많다. → **다음 릴리즈에서 이 모듈의 회귀 범위를 넓히고, 리팩터링을 제안할 근거**가 된다.

해석에 주의할 점: **결함 밀도가 낮은 게 항상 좋은 게 아니다.** 아예 테스트를 안 한 모듈도 밀도가 0이다. 실행한 TC 수와 함께 봐야 한다.

### 3. 테스트 실패율 / 통과율

```text
통과율 = Pass / (Pass + Fail) × 100
실행률 = 실행 / 계획 × 100
```

**Blocked(차단)를 분모에서 어떻게 다룰지 팀 규칙을 정해야 한다.** 환경 문제로 실행 못 한 TC를 Fail로 세면 품질이 나빠 보이고, 빼버리면 미검증 영역이 숨는다. 권장 방식은 **분모에서 제외하되 별도로 명시**하는 것이다.

```text
계획 96건 / 실행 89건 (실행률 92.7%) / 통과 86건 (통과율 96.6%) / Blocked 7건 ← 결제 영역
```

Blocked 건수를 감추지 않는 게 핵심이다. 앞 레슨의 Go/No-Go에서 이게 결정적 정보였다.

**자동화 스위트의 실패율은 별도로 관리한다.** 그리고 실패를 반드시 분류한다.

| 분류 | 의미 | 조치 |
|---|---|---|
| 진짜 결함 | 제품이 잘못됨 | 결함 리포트 |
| 플래키 | 재실행하면 통과 | 격리 후 원인 수정 (트랙 3) |
| 테스트 오류 | 테스트 코드가 잘못됨 | 테스트 수정 |
| 환경 문제 | 인프라·데이터 문제 | 환경 수정 |

이 분류를 안 하면 **"어차피 가끔 빨간불 뜨는 거"** 가 되고, 그 순간 자동화 스위트는 죽는다. 아무도 안 보게 된다.

### 4. 결함 탈출률 (Defect Escape Rate / DDP) ⭐

**QA 조직의 성과를 가장 잘 나타내는 단일 지표**다.

```text
결함 탈출률 = 운영에서 발견된 결함 / (QA가 발견한 결함 + 운영에서 발견된 결함) × 100

결함 제거 효율(DDP) = 100 - 결함 탈출률
```

예: QA가 45건 잡고 운영에서 5건 터졌다면 → 탈출률 10%, DDP 90%.

이 지표가 좋은 이유는 **"QA가 무엇을 놓쳤는가"를 직접 측정**하기 때문이다. 발견 건수만 세면 "많이 찾은 QA가 좋은 QA"가 되는데, 그건 개발 품질이 나쁘다는 뜻일 수도 있다. 탈출률은 그 왜곡이 없다.

**탈출한 결함은 반드시 원인을 분류한다.** 이게 실제 개선으로 이어지는 부분이다.

| 탈출 원인 | 개선 방향 |
|---|---|
| TC 자체가 없었다 | 설계 기법 적용 누락 → 해당 기법 재점검 |
| TC는 있었는데 실행 못 했다 | 시간·환경 문제 → 계획 또는 자동화 |
| 실행했는데 못 봤다 | 기대 결과가 모호했음 → TC 문장 개선 |
| 환경 차이 | 스테이징이 운영과 다름 → 환경 개선 요청 |
| 데이터 차이 | 실제 데이터 패턴 미반영 → 테스트 데이터 전략 |
| 명세에 없던 요구 | 요구사항 프로세스 문제 → 기획 단계 참여 확대 |

3~6번은 **QA 개인의 실수가 아니라 프로세스 문제**다. 이걸 구분해서 말할 수 있으면 회고가 비난이 아니라 개선이 된다.

### 5. 그 밖에 실무에서 쓰는 것

| 지표 | 정의 | 무엇을 보는가 |
|---|---|---|
| 결함 재발률 | 재오픈된 결함 / 전체 수정 결함 | 수정 품질, 회귀 테스트 부실 |
| 평균 수정 시간 (MTTR) | 리포트 → 수정 완료 평균 시간 | 대응 속도 |
| 자동화 비율 | 자동화 TC / 전체 TC | 단독으로는 무의미. 실행 시간·유지비와 함께 |
| 결함 유입 단계 | 요구사항/설계/구현 중 어디서 생긴 결함인가 | 앞단으로 갈수록 개선 효과가 크다 |

**자동화 비율을 목표로 거는 것은 특히 위험하다.** 유지비가 큰 UI 테스트를 무작정 늘리면 비율은 오르고 팀은 느려진다. 트랙 3에서 "무엇을 자동화하지 않을지"를 따로 배우는 이유다.

### 지표를 다룰 때의 원칙

1. **추세로 본다.** 이번 릴리즈 탈출률 10%는 단독으로는 좋은지 나쁜지 모른다. 지난 5회가 18 → 15 → 12 → 11 → 10 이면 좋은 것이다
2. **한 지표만 보지 않는다.** 통과율 100%인데 실행률이 40%면 아무 의미 없다
3. **목표로 걸지 않는다.** 특히 개인 평가에 연동하면 반드시 조작된다
4. **숫자 옆에 맥락을 쓴다.** "통과율 96.6% (Blocked 7건은 결제 스테이징 장애)"

## 왜 채용시장이 요구하는가

- 채용공고의 "품질 지표 관리 경험"은 **QA를 실행 인력이 아니라 관리자로 보는 조직**의 신호다. 리드·매니저 트랙으로 가려면 필수다.
- 면접에서 **"QA 업무 성과를 어떻게 측정하셨나요?"** 는 상당히 자주 나온다. "버그 몇 건 찾았습니다"는 약한 답이고, **결함 탈출률과 그 원인 분류**를 말하면 강한 답이 된다.
- **AI 도입 효과를 증명하는 언어도 지표다.** "AI로 TC를 생성했더니 좋았습니다"는 설득이 안 된다. "TC 작성 시간이 40% 줄고 결함 탈출률은 12% → 9%로 개선됐다"가 설득이다. 2026년에 AI 도구 도입을 주도하려면 이 언어가 필요하다.
- **AI가 만든 지표 리포트를 검증하는 것도 QA의 일이다.** AI에게 결함 데이터를 주고 리포트를 시키면 계산을 틀리거나, 분모를 마음대로 바꾸거나, 없는 추세를 읽어낸다. 정의를 정확히 알아야 검증할 수 있다.

## 실습 과제

### 과제 1 — 지표 계산과 해석 (12분)

아래 데이터로 지표를 계산하고, **회고 회의에서 발표할 3문장**을 작성한다.

```text
릴리즈 3.4.0
  계획 TC 120건 / 실행 108건 / Pass 99건 / Fail 9건 / Blocked 12건
  QA 발견 결함: Blocker 0, Critical 2, Major 11, Minor 23
  배포 후 2주간 운영 발견 결함: Critical 1, Major 3, Minor 4
  이전 3회 릴리즈 결함 탈출률: 21%, 17%, 14%
```

- 실행률 / 통과율 / 결함 탈출률 / DDP 계산
- 추세는 개선 중인가
- **Blocked 12건이 이 숫자들을 어떻게 왜곡하고 있는가**
- 발표 3문장 (좋아진 것 / 우려되는 것 / 다음에 할 것)

### 과제 2 — 탈출 결함 원인 분류 (10분)

과제 1에서 운영으로 탈출한 8건에 대해, 그럴듯한 원인을 지어내 6가지 분류에 배치한다.
그리고 **가장 많은 분류에 대한 개선안 1개**를 구체적으로 적는다. ("더 꼼꼼히 보겠다"는 개선안이 아니다)

### 과제 3 — 지표 조작 시나리오 (8분)

**"이 지표를 목표로 걸면 사람들이 어떻게 편법을 쓸까?"** 를 각 지표마다 하나씩 적어본다.

| 지표 | 목표로 걸었을 때의 편법 |
|---|---|
| 코드 커버리지 80% | |
| 자동화 비율 70% | |
| 결함 발견 건수 월 50건 | |
| 통과율 95% | |
| 결함 탈출률 5% 이하 | |

마지막 행이 어렵다. 탈출률조차 조작할 수 있다 — **운영 결함을 "사양 변경"으로 분류하면 분자가 줄어든다.** 이걸 아는 것이 지표를 제대로 쓰는 출발점이다.

### 과제 4 — AI에게 리포트 시키고 계산 검증 (10분)

AI 실습 도우미에 과제 1의 원본 데이터를 그대로 주고 품질 리포트를 만들게 한 뒤, **손으로 계산한 값과 대조**한다.

확인할 것:
- 실행률·통과율의 **분모를 무엇으로 잡았는가** (Blocked 처리 방식)
- 결함 탈출률 계산이 정의와 일치하는가
- 데이터에 없는 추세나 원인을 지어내지 않았는가
- "품질이 개선되고 있습니다" 같은 **근거 없는 총평**을 붙이지 않았는가

경험상 AI는 Blocked 처리에서 자주 틀리고, 요청하지 않은 낙관적 총평을 붙인다.

## 자가 체크리스트

- [ ] 요구사항 커버리지와 코드 커버리지를 구분하고 각각 누가 관리하는지 안다
- [ ] RTM의 목적이 "TC가 없는 요구사항 찾기"임을 설명할 수 있다
- [ ] 라인 커버리지 100%인데 아무것도 검증하지 않는 테스트의 예를 들 수 있다
- [ ] 커버리지 리포트에서 숫자가 아니라 "0%인 파일"을 봐야 하는 이유를 안다
- [ ] 결함 밀도를 계산하고, 밀도가 낮은 게 항상 좋은 게 아닌 이유를 설명할 수 있다
- [ ] 통과율·실행률을 계산하고 Blocked를 어떻게 처리할지 규칙으로 말할 수 있다
- [ ] 자동화 테스트 실패를 4가지(진짜 결함/플래키/테스트 오류/환경)로 분류할 수 있다
- [ ] 결함 탈출률과 DDP를 정의대로 계산할 수 있다
- [ ] 탈출한 결함의 원인을 6가지로 분류하고, 개인 실수와 프로세스 문제를 구분할 수 있다
- [ ] 지표를 목표로 걸었을 때 발생하는 조작 방식을 각 지표마다 예상할 수 있다
- [ ] 숫자를 보고할 때 추세와 맥락을 함께 제시할 수 있다
- [ ] AI가 만든 품질 리포트에서 분모 오류와 근거 없는 총평을 잡아낼 수 있다
