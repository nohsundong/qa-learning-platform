## 개념 설명

앞 레슨의 동등분할·경계값은 **입력 하나**를 보는 기법이다. 그런데 실무 결함의 상당수는 입력 하나만 봐서는 안 보인다.

- "로그아웃 상태에서 결제 버튼을 누르면?" → **이전에 무슨 일이 있었는가**가 중요하다 → 상태전이
- "VIP 회원이 쿠폰과 포인트를 동시에 쓰면서 5만원 미만을 주문하면?" → **조건들의 조합**이 중요하다 → 결정테이블

### 상태전이 테스트 (State Transition Testing)

시스템이 여러 **상태**를 오가고, 같은 동작이라도 현재 상태에 따라 결과가 달라질 때 쓴다.

주문 상태를 예로 들자.

```text
[결제대기] --결제완료--> [결제완료] --발송--> [배송중] --수령--> [배송완료]
     |                       |                                      |
   취소                     취소                                  반품신청
     v                       v                                      v
  [주문취소]              [결제취소]                            [반품접수]
```

여기서 만드는 표가 **상태전이표**다.

| 현재 상태 | 이벤트 | 다음 상태 | 비고 |
|---|---|---|---|
| 결제대기 | 결제완료 | 결제완료 | 정상 |
| 결제대기 | 취소 | 주문취소 | 정상 |
| 결제완료 | 발송 | 배송중 | 정상 |
| 결제완료 | 취소 | 결제취소 | 환불 처리 동반 |
| 배송중 | 취소 | **불가** | ← 여기가 핵심 |
| 배송완료 | 결제완료 | **불가** | ← 여기도 |

**이 기법의 진짜 가치는 "정상 경로"가 아니라 "불가 전이"에 있다.** 개발자는 정상 흐름은 반드시 구현한다. 버그는 항상 *"일어나면 안 되는 전이가 실제로는 막혀 있지 않은 곳"* 에서 나온다.

현실에서 이런 식으로 터진다.

- 배송중인데 취소 API를 직접 호출하면 취소가 된다 (UI 버튼만 숨겨놓고 서버 검증을 안 함)
- 결제 완료 응답이 늦어 사용자가 결제 버튼을 두 번 누르면 **두 번 결제된다** (같은 상태에서 같은 이벤트가 중복 발생)
- 뒤로가기로 이전 화면에 돌아가 다시 제출하면 이미 끝난 전이가 또 일어난다

그래서 상태전이 TC를 만들 때 최소한 이 세 가지는 반드시 넣는다.

1. **모든 정상 전이 1회씩** (0-switch 커버리지)
2. **불가 전이 시도** — UI로 막혀 있어도 **API를 직접 호출해서** 확인해야 진짜 검증이다
3. **중복 이벤트** — 같은 버튼 연타, 새로고침 후 재제출, 뒤로가기 후 재제출

### 결정테이블 (Decision Table)

여러 조건이 **동시에** 결과에 영향을 줄 때 쓴다. 조건과 결과를 표로 만들어 빠뜨리는 조합이 없게 한다.

> 요구사항: 배송비는 3,000원이다. 주문 금액이 30,000원 이상이면 무료. VIP 회원은 금액과 무관하게 무료. 단, 도서산간 지역은 무료 대상이라도 추가 배송비 3,000원을 받는다.

조건이 3개(금액, 등급, 지역)이므로 조합은 2×2×2 = 8가지다.

| 조건 \\ 규칙 | R1 | R2 | R3 | R4 | R5 | R6 | R7 | R8 |
|---|---|---|---|---|---|---|---|---|
| 30,000원 이상 | Y | Y | Y | Y | N | N | N | N |
| VIP 회원 | Y | Y | N | N | Y | Y | N | N |
| 도서산간 | Y | N | Y | N | Y | N | Y | N |
| **배송비** | 3,000 | 0 | 3,000 | 0 | 3,000 | 0 | 6,000 | 3,000 |

표를 다 채우고 나면 세 가지가 보인다.

1. **R7이 이상하다.** 일반 회원 + 3만원 미만 + 도서산간 = 기본 3,000 + 추가 3,000 = 6,000원이 맞는가? 요구사항에는 "무료 대상이라도 추가 3,000원"이라고만 적혀 있어 **유료 배송인 경우에 추가금이 붙는지가 명시돼 있지 않다.** → 이건 결함이 아니라 **명세 결함**이고, 개발 전에 물어봐야 한다.
2. **R1과 R3이 같은 결과다.** 도서산간이면 등급이 무의미해진다 → 로직 단순화 여지
3. 조합 8개를 다 적었기 때문에 **"이건 생각 못 했네"가 사라진다.** 이게 결정테이블의 목적이다.

조건이 늘면 조합은 2ⁿ으로 폭증한다. 조건 6개면 64가지다. 그럴 때는 다음 레슨의 **페어와이즈**로 줄이거나, 결과가 같은 규칙들을 묶어(`—` = 무관) 압축한다.

| 조건 | R1 | R2 | R3 |
|---|---|---|---|
| 도서산간 | Y | N | N |
| 무료 대상(30,000↑ 또는 VIP) | — | Y | N |
| **배송비** | 기본 + 3,000 | 0 | 3,000 |

8줄이 3줄이 됐다. 실무에서는 이렇게 압축한 표를 쓰되, **압축 전 전체 표를 한 번은 그려봐야** 빠진 조합을 발견할 수 있다.

### 두 기법을 언제 고르는가

| 상황 | 기법 |
|---|---|
| 순서·이력이 결과를 바꾼다 (주문, 결제, 로그인 세션, 승인 워크플로) | 상태전이 |
| 여러 조건이 동시에 결과를 정한다 (요금 계산, 권한, 할인, 노출 조건) | 결정테이블 |
| 둘 다 해당된다 (예: 등급별로 취소 가능 상태가 다름) | 상태전이표의 각 칸 안에 결정테이블 |

## 왜 채용시장이 요구하는가

- **면접 실기 단골**이다. "주문 취소 기능의 TC를 설계해 보세요"는 상태전이를 쓰는지 보는 문제고, "할인 정책 TC를 만들어 보세요"는 결정테이블을 쓰는지 보는 문제다. 기법 이름을 말하지 않고 나열식으로 답하면 바로 티가 난다.
- **명세 결함을 잡아내는 도구**라서 값이 크다. 위 R7처럼 표를 채우다 보면 "요구사항에 이 경우가 없는데요?"가 자동으로 나온다. **개발 전에 발견한 결함이 가장 싸다.** QA를 테스터가 아니라 품질 엔지니어로 보게 만드는 지점이다.
- **AI 생성 TC의 가장 큰 구멍이 여기다.** AI에게 할인 정책 TC를 시키면 대체로 조건을 하나씩 따로 테스트하는 케이스를 만들고, **조합을 빠뜨린다.** 상태전이는 더 심해서 "불가 전이"를 거의 만들지 않는다. 표를 그릴 줄 알아야 무엇이 빠졌는지 보인다.

## 실습 과제

### 과제 1 — 로그인 상태전이표 (12분)

아래 요구사항으로 상태전이표를 작성한다.

> 로그인은 이메일·비밀번호로 한다. 비밀번호를 5회 연속 틀리면 계정이 10분간 잠긴다. 잠금 중에는 올바른 비밀번호를 넣어도 로그인되지 않는다. 10분이 지나면 자동 해제된다. 로그인 성공 시 실패 횟수는 초기화된다.

상태: `미인증` / `실패누적(1~4회)` / `잠금` / `인증됨`

반드시 포함할 것:
- **불가 전이 3개 이상** (예: 잠금 상태에서 올바른 비밀번호)
- **경계**: 4회 실패 후 성공 / 5회째 실패 / 잠금 후 9분 59초 / 10분 1초
- **중복 이벤트**: 로그인 버튼 연타

### 과제 2 — 결정테이블 채우고 명세 결함 찾기 (12분)

> 무료 반품 조건: 수령 후 7일 이내이고, 상품을 개봉하지 않았으며, 단순 변심이 아닌 경우 무료. 단순 변심이면 반품비 5,000원. 상품 하자면 개봉했어도 무료.

조건 4개(7일 이내 / 개봉 여부 / 단순 변심 / 하자)로 전체 조합 표를 그린다.

목표는 TC를 만드는 게 아니라 **"요구사항만으로는 결과를 정할 수 없는 조합"을 찾아내는 것**이다. 최소 2개는 나온다. 찾았으면 기획자에게 보낼 질문 문장으로 정리해 메모에 적는다.

### 과제 3 — AI에게 시키고 표로 채점 (10분)

AI 실습 도우미에서 과제 1의 로그인 요구사항으로 TC를 생성시킨 뒤, **내 상태전이표와 대조**한다.

| 확인 항목 | AI |
|---|---|
| 불가 전이를 테스트했는가 | |
| API 직접 호출로 검증하라고 했는가 | |
| 잠금 시간 경계(9:59 / 10:01)를 넣었는가 | |
| 로그인 성공 시 카운터 초기화를 확인했는가 | |
| 요구사항에 없는 규칙을 지어냈는가 | |

경험상 마지막 두 항목에서 갈린다. AI는 "카운터 초기화"처럼 **명시돼 있지만 눈에 안 띄는 문장**을 자주 흘린다.

## 자가 체크리스트

- [ ] 상태전이 기법을 언제 쓰는지, 결정테이블을 언제 쓰는지 구분해 설명할 수 있다
- [ ] 상태전이표에서 가장 결함이 많이 나오는 칸이 "불가 전이"인 이유를 설명할 수 있다
- [ ] UI로 막힌 불가 전이를 API 직접 호출로 검증해야 하는 이유를 설명할 수 있다
- [ ] 중복 이벤트(연타·재제출·뒤로가기)를 상태전이 TC에 포함시킬 수 있다
- [ ] 조건 n개짜리 결정테이블의 전체 조합 수가 2ⁿ임을 알고 표를 끝까지 채울 수 있다
- [ ] 결정테이블을 채우다 발견한 빈칸을 명세 결함으로 제기할 수 있다
- [ ] `—`(무관) 표기로 규칙을 압축하되, 압축 전 전체 표를 먼저 그려야 하는 이유를 안다
- [ ] AI가 만든 TC에서 빠진 조합과 빠진 불가 전이를 찾아낼 수 있다
