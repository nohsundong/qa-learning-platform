## 개념 설명

결함 리포트는 QA가 가장 많이 쓰는 문서이고, **QA의 실력이 가장 빨리 드러나는 문서**다. 개발자는 리포트 제목만 보고도 그 QA의 수준을 안다.

### 나쁜 리포트와 좋은 리포트

```text
[나쁨] 결제가 안 됨
[나쁨] 장바구니 오류
[나쁨] 화면이 이상해요
```

이 제목들의 공통 문제는 **개발자가 무엇부터 봐야 할지 알 수 없다**는 것이다. 이슈 목록에서 이런 제목 20개가 나열되면 우선순위를 매길 수 없다.

```text
[좋음] [결제] 쿠폰 적용 후 수량을 변경하면 할인이 중복 적용되어 결제금액이 음수가 된다
[좋음] [로그인] 계정 잠금 10분 경과 후에도 잠금이 해제되지 않는다 (재로그인 시도 시에만 해제됨)
[좋음] [상품목록] iOS 앱에서 페이지 2 이후 스크롤 시 1페이지 상품이 중복 표시된다
```

좋은 제목의 공식은 이렇다.

```text
[영향 영역] {어떤 조건에서} {무엇이} {어떻게 잘못되는가}
```

### 필수 항목과 그 이유

| 항목 | 왜 필요한가 | 흔한 실수 |
|---|---|---|
| **제목** | 목록에서 우선순위를 판단하는 유일한 정보 | 증상만 적고 조건을 뺌 |
| **환경** | 재현 여부가 환경에 좌우된다 | "모바일"만 적음 → OS/버전/기기/앱버전/서버환경까지 |
| **재현 절차** | 개발자가 그대로 따라 할 수 있어야 한다 | 한 단계에 여러 동작을 뭉침 |
| **실제 결과** | 무엇이 일어났는가 | 기대 결과와 섞어서 서술 |
| **기대 결과** | 왜 그것이 결함인가의 근거 | 생략함 ← 가장 치명적 |
| **재현율** | 간헐적이면 접근이 완전히 달라진다 | "가끔"이라고만 적음 → "10회 중 3회"로 |
| **증거** | 스크린샷, 영상, 로그, 네트워크 응답 | 화면 캡처만 있고 로그가 없음 |
| **심각도/우선순위** | 처리 순서를 정하는 기준 | 둘을 같은 것으로 취급 |

**기대 결과를 빼는 것이 가장 흔하고 가장 나쁜 실수다.** 기대 결과가 없으면 개발자는 "이게 원래 그런 건데요?"라고 답할 수 있다. 기대 결과에는 **근거**를 붙이는 게 좋다.

```text
기대 결과: 할인은 1회만 적용되어 결제금액 9,000원
근거: 기획서 v2.3 4.2절 "쿠폰은 주문당 1회 적용"
```

기획서에 근거가 없다면 그렇게 적는다. `근거: 명세에 정의 없음 — 상식적으로 음수 결제는 불가능하다고 판단. 정책 확인 필요` 이렇게 쓰면 **결함 리포트인 동시에 명세 질문**이 된다.

### 재현 절차 쓰는 법

원칙은 하나다. **한 단계에 한 동작.** 그리고 **아무 정보 없는 사람이 따라 할 수 있어야 한다.**

```text
[나쁨]
1. 로그인해서 상품 담고 쿠폰 적용 후 결제한다

[좋음]
사전 조건: 테스트 계정 qa_user_01 / 장바구니 비어 있음 / 유효한 10% 쿠폰 1장 보유
1. qa_user_01 로 로그인한다
2. 상품 "무선 이어폰"(상품ID 10023) 상세 페이지로 이동한다
3. [장바구니 담기] 를 누른다
4. 장바구니로 이동한다
5. 쿠폰 [10% 할인] 을 적용한다   → 이 시점 결제예정금액 9,000원 확인
6. 수량을 1 → 2 로 변경한다
7. 결제예정금액을 확인한다
```

5번처럼 **중간 확인 지점**을 넣으면 개발자가 어디까지는 정상이고 어디서 틀어지는지 바로 안다. 디버깅 시간이 크게 줄어든다.

### 심각도(Severity)와 우선순위(Priority)는 다르다

이걸 구분 못 하면 면접에서 바로 걸러진다.

| | 심각도 (Severity) | 우선순위 (Priority) |
|---|---|---|
| 판단 주체 | QA (객관적) | PO/개발리드 (비즈니스 판단) |
| 기준 | 시스템에 미치는 영향의 크기 | 언제까지 고쳐야 하는가 |
| 바뀌는가 | 잘 안 바뀜 | 상황에 따라 자주 바뀜 |

**네 조합이 모두 실제로 존재한다.** 이걸 예시로 설명할 수 있어야 한다.

| 조합 | 예시 |
|---|---|
| 심각도 高 / 우선순위 高 | 결제가 전혀 안 된다 → 지금 당장 |
| 심각도 高 / 우선순위 低 | 관리자만 쓰는 통계 페이지에서 서버 오류. 데이터는 안전하고 월 1회만 사용 → 다음 스프린트 |
| 심각도 低 / 우선순위 高 | 메인 배너에 회사명 오타. 기능은 멀쩡하지만 **모든 사용자가 본다** → 지금 당장 |
| 심각도 低 / 우선순위 低 | 설정 화면 하단 아이콘이 2px 어긋남 → 백로그 |

세 번째 행이 핵심이다. **"기능에는 문제없으니 낮은 등급"이 아니다.** 브랜드·법무·보안 이슈는 심각도가 낮아도 우선순위가 최상이 된다.

심각도 등급의 일반적 기준.

```text
Blocker  : 테스트 진행 자체가 불가. 핵심 기능 완전 불가. 데이터 유실·금전 손실
Critical : 핵심 기능이 우회 방법 없이 실패. 보안 취약점
Major    : 주요 기능이 실패하지만 우회 방법이 있음
Minor    : 부가 기능 실패. 사용성 불편
Trivial  : 오타, 미세한 UI 어긋남
```

### 간헐적 결함을 다루는 법

"가끔 발생합니다"는 리포트로서 거의 쓸모가 없다. 개발자가 재현을 못 하면 **닫히거나 방치된다.** 간헐적 결함일수록 정보를 더 모아야 한다.

- **재현율을 숫자로**: "10회 시도 중 3회 발생"
- **발생/미발생 조건을 비교**: 성공한 7회와 실패한 3회의 차이는 무엇이었나 (시간대? 데이터? 순서? 네트워크?)
- **타임스탬프를 정확히**: 개발자가 서버 로그에서 그 시각을 찾을 수 있게. 초 단위까지
- **네트워크 탭 HAR 파일 첨부**: 요청/응답 원본이 있으면 재현 없이도 분석이 가능하다
- **영상 녹화**: 재현 절차로 표현 안 되는 타이밍 이슈는 화면 녹화가 가장 강력하다

### 리포트 전에 스스로 확인할 것

제출 전 30초만 쓰면 반려율이 크게 줄어든다.

1. **최신 빌드에서 재현되는가?** 이미 고쳐진 걸 올리면 신뢰를 잃는다
2. **중복 이슈가 아닌가?** 이슈 트래커에서 키워드로 먼저 검색
3. **환경 문제가 아닌가?** 다른 계정, 다른 브라우저, 캐시 삭제 후에도 발생하는가
4. **명세를 다시 읽었는가?** 의도된 동작을 결함으로 올리는 경우가 생각보다 많다
5. **제목만 읽고 무슨 일인지 알 수 있는가?**

## 왜 채용시장이 요구하는가

- 채용공고의 "결함 리포팅 및 이슈 트래킹 경험"은 기본 항목이지만, **면접 실기로 자주 나온다.** "이 화면에서 버그를 하나 찾아 리포트를 써 보세요"는 흔한 과제다.
- **심각도와 우선순위 구분은 단골 질문**이고, 네 조합의 예시를 즉석에서 못 대면 실무 경험이 얕다고 판단된다.
- **개발자와의 신뢰가 여기서 만들어진다.** 재현 잘 되는 리포트를 쓰는 QA는 "우리 팀 QA"가 되고, 애매한 리포트를 쓰는 QA는 티켓 발행기가 된다. 이 차이가 연봉과 직급에 반영된다.
- **AI로 리포트를 다듬는 것이 2026년의 기본**이 됐다. 다만 AI는 **없는 정보를 자연스럽게 지어낸다.** "Chrome 최신 버전에서 재현" 같은 문장을 만들어 넣는다. 확인하지 않은 것을 확인한 것처럼 쓰는 리포트는 신뢰를 통째로 깎아먹는다. AI를 쓰되 사실 여부는 반드시 본인이 검증해야 한다.

## 실습 과제

### 과제 1 — 나쁜 리포트 고쳐 쓰기 (10분)

아래 리포트를 완전한 형태로 다시 쓴다. 부족한 정보는 **"확인 필요"로 명시**하고, 무엇을 어떻게 확인할지 적는다.

> **제목**: 결제 오류
> **내용**: 장바구니에서 결제하려는데 가끔 실패함. 폰에서 봤음. 다시 하면 됨.

체크 포인트:
- 제목을 공식대로 다시 썼는가
- 실제 결과와 기대 결과를 분리했는가
- "가끔"을 숫자로 바꾸기 위해 무엇을 해야 하는지 적었는가
- 심각도와 우선순위를 각각 근거와 함께 매겼는가

### 과제 2 — 심각도/우선순위 4분면 채우기 (8분)

본인이 아는 서비스에서 **네 조합에 해당하는 결함을 각각 하나씩** 지어낸다. (실제 결함이 아니어도 된다)

| | 우선순위 高 | 우선순위 低 |
|---|---|---|
| **심각도 高** | | |
| **심각도 低** | | |

각 칸에 "왜 이 조합인가"를 한 줄로 붙인다. 면접에서 그대로 쓸 수 있는 답변이 된다.

### 과제 3 — 실습 랩에서 찾아 리포트 쓰기 (15분)

실습 랩의 **결함이 숨겨진 샘플 앱**에서 결함을 2개 찾아 완전한 리포트를 작성한다.
증거로 무엇을 첨부할지(스크린샷 / 콘솔 로그 / 네트워크 응답)도 함께 적는다.

### 과제 4 — AI로 다듬고 사실 검증하기 (10분)

AI 실습 도우미의 **결함 리포트 정리** 템플릿에 과제 3에서 찾은 결함을 두서없이 적어 넣고 정리시킨다.
그리고 **AI 출력물에서 다음을 찾아 표시한다.**

- 내가 말하지 않았는데 AI가 채워 넣은 정보 (환경, 버전, 재현율 등)
- 내가 확인하지 않은 것을 확인한 것처럼 단정한 문장
- "확인 필요"로 남겼어야 할 항목을 그냥 채워버린 곳

**이것들을 다 지우고 나서야 제출 가능한 리포트가 된다.** 이 검증 습관이 트랙 6의 핵심이다.

## 자가 체크리스트

- [ ] 결함 제목을 `[영역] {조건}에서 {무엇}이 {어떻게}` 공식으로 쓸 수 있다
- [ ] 실제 결과와 기대 결과를 분리해서 쓰고, 기대 결과에 근거를 붙일 수 있다
- [ ] 재현 절차를 한 단계 한 동작으로 쪼개고 중간 확인 지점을 넣을 수 있다
- [ ] 사전 조건(계정, 데이터 상태)을 명시할 수 있다
- [ ] 심각도와 우선순위의 차이를 판단 주체·기준으로 설명할 수 있다
- [ ] 심각도/우선순위 네 조합의 실제 예시를 각각 댈 수 있다
- [ ] 심각도 낮음 + 우선순위 높음의 대표 사례(오타·법무·브랜드)를 설명할 수 있다
- [ ] 간헐적 결함에서 재현율을 숫자로 만들고 발생/미발생 조건을 비교할 수 있다
- [ ] 제출 전 5가지 자가 확인(최신빌드·중복·환경·명세·제목)을 수행한다
- [ ] AI가 다듬은 리포트에서 지어낸 정보를 찾아 제거할 수 있다
