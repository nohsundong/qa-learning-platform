## 개념 설명

### 조합은 금방 폭발한다

쇼핑몰 결제 화면 하나를 생각해 보자.

| 변수 | 값 | 개수 |
|---|---|---|
| 결제수단 | 카드 / 계좌이체 / 간편결제 / 포인트전액 | 4 |
| 회원등급 | 일반 / VIP / 휴면 | 3 |
| 쿠폰 | 없음 / 정액 / 정률 | 3 |
| 배송지 | 국내 / 도서산간 | 2 |
| 기기 | PC / 모바일웹 / 앱 | 3 |

전체 조합은 4 × 3 × 3 × 2 × 3 = **216가지**다. 변수 하나만 더 늘어도 수백 개가 된다. 다 못 한다.

여기서 초보와 경력자가 갈린다.

- 초보: "다 못 하니까 적당히 20개쯤 골라서 하겠습니다" → **근거가 없다.** 무엇이 빠졌는지 설명할 수 없다
- 경력자: "페어와이즈로 줄이면 20개 남습니다. 대신 결제수단×쿠폰 3-way 조합은 리스크가 커서 별도로 9개 더 넣겠습니다" → **버린 것과 남긴 것에 근거가 있다**

### 페어와이즈의 근거

경험적으로 **결함의 대부분은 변수 1개 또는 2개의 조합에서 발생한다.** 변수 4개, 5개가 동시에 특정 값이어야만 터지는 결함은 훨씬 드물다.

그래서 이런 전략을 쓴다.

> **모든 조합**을 만들지 말고, **모든 "두 변수 값 쌍"이 최소 한 번씩 등장**하도록 케이스를 고른다.

위 예에서 `결제수단=간편결제 & 쿠폰=정률` 이라는 쌍이 어떤 케이스에든 한 번은 들어가면 된다. 그 케이스에 회원등급이 무엇이었는지는 상관하지 않는다.

이렇게 하면 216가지가 **20개 안팎**으로 줄어든다. 그러면서 모든 2개 조합은 다 덮는다.

```text
전체 조합 (all-combinations)  216개  — 커버리지 100%, 현실성 0%
페어와이즈 (2-way)             ~20개  — 2변수 조합 100%, 3변수 이상은 일부
단일 값만 훑기 (each-choice)    4개   — 각 값 1회씩만, 조합 결함 거의 못 잡음
```

### 손으로 만들지 말고 도구를 쓴다

페어와이즈 조합표를 손으로 짜는 것은 시간 낭비이고 실수가 난다. 무료 도구를 쓴다.

**Microsoft PICT** — 가장 널리 쓰이고 무료다. 입력 파일이 단순하다.

```text
결제수단: 카드, 계좌이체, 간편결제, 포인트전액
회원등급: 일반, VIP, 휴면
쿠폰: 없음, 정액, 정률
배송지: 국내, 도서산간
기기: PC, 모바일웹, 앱
```

```bash
pict model.txt > cases.tsv
```

**제약조건(constraint)이 진짜 실무 기능이다.** 현실에는 불가능한 조합이 있다.

```text
# 휴면 회원은 쿠폰을 쓸 수 없다
IF [회원등급] = "휴면" THEN [쿠폰] = "없음";

# 포인트 전액 결제에는 쿠폰을 중복 적용할 수 없다
IF [결제수단] = "포인트전액" THEN [쿠폰] = "없음";

# 앱에서는 계좌이체를 지원하지 않는다
IF [기기] = "앱" THEN [결제수단] <> "계좌이체";
```

제약을 넣지 않으면 **애초에 발생할 수 없는 케이스를 테스트하느라 시간을 버린다.** 실행해 보고 "이건 원래 안 되는 건데요"라는 답을 듣는 TC가 그것이다.

반대로 **제약조건을 적는 과정 자체가 요구사항 검증**이다. "휴면 회원이 쿠폰을 쓰면 어떻게 되나요?"를 기획자에게 물어야 제약을 적을 수 있기 때문이다.

### 페어와이즈로 부족한 경우

무조건 2-way가 정답은 아니다. 다음은 조합을 더 채워야 한다.

- **돈이 걸린 핵심 조합** — 결제수단 × 쿠폰 × 금액은 3-way로 올린다 (`pict model.txt /o:3`)
- **과거에 결함이 났던 조합** — 장애 이력에 있던 조합은 무조건 명시적으로 포함시킨다
- **비즈니스상 가장 흔한 경로** — 실제 사용자의 80%가 지나는 조합은 페어와이즈 결과에 없더라도 따로 넣는다

PICT는 특정 케이스를 반드시 포함시키는 시드(seed) 기능을 지원한다. 위 세 가지를 시드로 고정하고 나머지를 페어와이즈로 채우는 것이 실무적으로 가장 균형이 좋다.

### 자동화와의 관계

페어와이즈 결과표는 그대로 **자동화 테스트의 데이터셋**이 된다.

```javascript
// Playwright — 조합표를 그대로 파라미터라이즈 테스트로
const cases = [
  { 결제수단: '카드',     회원등급: '일반', 쿠폰: '정률', 배송지: '도서산간', 기기: 'PC' },
  { 결제수단: '간편결제', 회원등급: 'VIP',  쿠폰: '없음', 배송지: '국내',     기기: '앱' },
  // ... PICT 출력 20건
];

for (const c of cases) {
  test(`결제 ${c.결제수단}/${c.회원등급}/${c.쿠폰}/${c.배송지}/${c.기기}`, async ({ page }) => {
    // ...
  });
}
```

테스트 이름에 조합을 그대로 넣는 것이 중요하다. CI에서 실패했을 때 **어떤 조합이 깨졌는지 로그를 안 봐도 알 수 있다.**

## 왜 채용시장이 요구하는가

- 채용공고의 "테스트 케이스 설계 기법" 목록에 페어와이즈가 들어가 있으면, **조합 폭발을 겪어본 규모의 서비스**라는 뜻이다. 이 기법을 아는 것 자체가 필터를 통과하는 조건이 된다.
- **"시간이 없어서 못 했다"를 "이 근거로 줄였다"로 바꾸는 기술**이다. 앞선 레슨의 리스크 기반 계획과 짝을 이룬다. 조합을 줄인 근거를 문서로 남길 수 있는 사람은 릴리즈 회의에서 발언권이 생긴다.
- **AI 시대에 특히 중요해졌다.** AI에게 "가능한 모든 조합의 TC를 만들어줘"라고 하면 정말 200개를 만들어 준다. 그리고 그 200개는 아무도 실행하지 않는다. **줄이는 판단이 사람의 일**이고, 그 판단 기준이 페어와이즈와 리스크다.

## 실습 과제

### 과제 1 — PICT 모델 작성하고 돌려보기 (15분)

PICT는 무료다. macOS/Linux에서는 소스 빌드, Windows는 바이너리를 받는다.
설치가 번거로우면 웹 기반 페어와이즈 생성기를 써도 되고, 아래 과제는 **모델 파일을 작성하는 것 자체가 핵심**이라 도구 없이 표만 그려도 된다.

본인이 자주 쓰는 서비스의 **검색 필터 화면**을 하나 골라 모델을 만든다. (예: 숙소 예약의 지역·인원·날짜·가격대·편의시설·정렬)

반드시 포함할 것:
- 변수 5개 이상, 각 변수의 값 2~4개
- **제약조건 3개 이상** — 그리고 각 제약을 왜 넣었는지 한 줄 근거
- 전체 조합 수와 페어와이즈 후 케이스 수를 비교해 적기

### 과제 2 — 제약조건에서 질문 뽑기 (7분)

과제 1에서 제약조건을 적다 보면 **"이 조합은 되는 건가?"** 하고 확신이 안 서는 게 반드시 나온다.
그것들을 모아 기획자에게 보낼 질문 목록으로 정리한다.

> 예) "인원 10명 이상 + 원룸 타입" 조합이 검색 결과에 나와야 하나요, 아니면 결과 0건이 정상인가요?

이 목록이 **개발 전에 잡는 결함**이다.

### 과제 3 — AI에게 조합을 줄이게 시키기 (10분)

AI 실습 도우미에 과제 1의 변수 목록을 그대로 주고 이렇게 요청한다.

> 이 변수들로 페어와이즈(2-way) 조합표를 만들어라. 전체 조합 수와 줄인 후 케이스 수를 먼저 계산해서 밝히고, 모든 2변수 쌍이 커버되는지 검증 방법도 함께 제시하라.

그리고 **직접 검증한다.**

- AI가 만든 표에서 무작위로 2변수 쌍 5개를 골라 실제로 표에 존재하는지 확인
- 케이스 수가 이론값(가장 값이 많은 두 변수의 곱 이상)보다 적으면 **커버가 안 된 것이다**
- 제약조건을 위반하는 케이스가 섞여 있지 않은지 확인

**AI는 페어와이즈 조합표를 자주 틀린다.** 그럴듯한 표를 만들지만 실제로는 빠진 쌍이 있다. 이 검증 습관이 트랙 6의 핵심이다.

## 자가 체크리스트

- [ ] 변수와 값의 개수만 보고 전체 조합 수를 계산할 수 있다
- [ ] 페어와이즈가 성립하는 경험적 근거(결함 대부분이 1~2개 변수에서 발생)를 설명할 수 있다
- [ ] 페어와이즈로 덮이지 않는 것이 무엇인지(3-way 이상 조합) 명확히 말할 수 있다
- [ ] PICT 모델 파일 문법으로 변수와 제약조건을 작성할 수 있다
- [ ] 제약조건을 적는 과정에서 명세의 빈칸을 발견해 질문으로 만들 수 있다
- [ ] 페어와이즈 결과에 반드시 추가해야 할 3가지(핵심 3-way, 장애 이력 조합, 최다 사용 경로)를 안다
- [ ] 조합표를 자동화 테스트의 파라미터라이즈 데이터셋으로 전환할 수 있다
- [ ] AI가 만든 페어와이즈 표에서 빠진 쌍을 직접 검증할 수 있다
