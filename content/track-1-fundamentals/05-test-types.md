## 개념 설명

테스트 유형을 외우는 건 의미 없다. 실무에서 필요한 건 **"이번 릴리즈에 이 네 가지를 각각 어느 깊이로 돌릴 것인가"** 를 정하는 판단이다.

### 기능 테스트 (Functional Test)

이번에 만든 기능이 명세대로 동작하는지 본다. 앞 레슨들의 TC 설계 기법이 그대로 적용되는 영역이다.

주의할 점 하나. **기능 테스트는 "이 기능이 되는가"만 보는 게 아니라 "되면 안 되는 것이 안 되는가"도 본다.**

| 관점 | 예시 |
|---|---|
| 긍정 (positive) | 올바른 쿠폰 코드를 넣으면 할인이 적용된다 |
| 부정 (negative) | 만료된 쿠폰, 남의 쿠폰, 이미 쓴 쿠폰은 거부된다 |
| 권한 | 다른 사용자의 주문번호로 조회하면 막힌다 |
| 데이터 | 할인 적용 후 DB의 최종 결제금액이 화면과 일치한다 |

마지막 행이 자주 빠진다. 화면에 9,000원이라고 떠도 DB에 10,000원이 저장됐다면 결함이다. **화면만 보는 테스트는 절반짜리다.** (트랙 2의 SQL 검증으로 이어진다)

### 회귀 테스트 (Regression Test)

**"이번에 건드린 것 때문에, 원래 잘 되던 게 깨지지 않았는가"** 를 본다. QA 시간의 가장 큰 덩어리를 잡아먹는 영역이고, 그래서 자동화 1순위다.

가장 어려운 건 **범위 산정**이다. 전부 돌리면 시간이 없고, 적게 돌리면 사고가 난다. 판단 기준은 이렇다.

| 근거 | 방법 |
|---|---|
| **코드 변경 범위** | PR diff에서 어떤 모듈이 바뀌었는지 본다. 공통 모듈(인증, 결제, 공통 컴포넌트)이 바뀌었으면 범위를 크게 잡는다 |
| **의존 관계** | 바뀐 모듈을 호출하는 곳을 역추적한다. 개발자에게 "이거 어디서 쓰나요"를 묻는 게 가장 빠르다 |
| **과거 결함 이력** | 같은 영역에서 결함이 반복됐다면 그 영역은 항상 포함 |
| **비즈니스 임팩트** | 결제·로그인·주문은 변경이 없어도 매 릴리즈 스모크 수준으로는 돌린다 |

여기서 나오는 실무 개념 두 가지.

- **스모크 테스트(Smoke Test)** — 빌드가 테스트할 가치가 있는지 5~10분 만에 확인하는 최소 세트. 로그인 되나, 메인 뜨나, 주문 한 건 되나. **깨졌으면 QA를 시작하지 않고 빌드를 반려한다.** 이걸 안 하면 반나절 테스트하고 나서 "빌드가 잘못 올라갔었다"는 말을 듣게 된다
- **새니티 테스트(Sanity Test)** — 특정 결함을 수정한 뒤, 그 부분과 주변만 좁고 깊게 확인하는 것

**"PR diff를 읽고 회귀 범위를 정한다"** 는 2026년 QA 채용의 핵심 역량이고, 트랙 4의 Agentic Testing이 자동화하려는 바로 그 판단이다. 그래서 트랙 6에서 diff 읽는 법을 따로 배운다.

### 통합 테스트 (Integration Test)

각 부분은 되는데 **붙이면 안 되는** 문제를 찾는다. 실무 결함이 가장 많이 나오는 곳이 여기다.

| 통합 지점 | 자주 나오는 결함 |
|---|---|
| 프론트 ↔ 백엔드 | 필드명 불일치(`userName` vs `user_name`), 타입 불일치(숫자를 문자열로), null 처리 |
| 서비스 ↔ 외부 API | 타임아웃 시 동작, 응답 지연, 에러 코드 매핑, 재시도로 인한 중복 처리 |
| 앱 ↔ 서버 버전 | 구버전 앱이 신규 API를 호출할 때 (강제 업데이트 정책) |
| 서비스 ↔ DB | 트랜잭션 롤백, 동시 수정, 캐시와 DB 불일치 |

통합 테스트에서 **반드시 봐야 할 것은 "정상 응답"이 아니라 "비정상 응답"** 이다.

- 외부 결제사가 **타임아웃**되면 우리 주문은 어떤 상태로 남는가
- 외부 API가 **500**을 주면 사용자에게 뭐라고 보여주는가
- 응답이 **늦게 도착**해서 사용자가 이미 화면을 떠났다면?

이걸 테스트하려면 외부 응답을 인위적으로 만들어야 한다. Postman의 목 서버, 프록시 도구, 또는 개발팀에 스텁 환경을 요청한다. (트랙 2에서 다룬다)

### 탐색적 테스트 (Exploratory Test)

TC 없이 **설계·실행·학습을 동시에** 하는 테스트다. "그냥 막 눌러보는 것"이 아니다. 그건 애드혹(ad-hoc)이고, 탐색적 테스트는 **기록이 남는 구조화된 활동**이다.

실무에서 쓰는 방식이 **세션 기반 탐색적 테스트(SBTM)** 다.

```text
세션 시간: 60분 (타이머 켜고)
차터(Charter): 무엇을 어떤 관점으로 탐색할지 한 문장
  예) "쿠폰 적용 화면을 '동시성' 관점으로 탐색해, 중복 적용이 가능한 경로를 찾는다"

기록:
  - 발견 (finding): 결함 후보
  - 질문 (question): 기획/개발에 물어볼 것
  - 아이디어 (idea): 다음에 TC로 만들 것
  - 소요 (setup/test/bug 비율)
```

차터가 없으면 익숙한 경로만 반복하게 된다. **차터는 "어디를"이 아니라 "어떤 관점으로"를 정하는 것**이 핵심이다. 관점 예시:

| 관점 | 던지는 질문 |
|---|---|
| 동시성 | 두 탭에서 동시에 하면? 버튼 연타하면? |
| 중단 | 중간에 새로고침하면? 뒤로가기하면? 네트워크를 끊으면? |
| 극단값 | 아주 긴 문자열, 이모지, 0개, 999개 |
| 시간 | 세션 만료 직전에 제출하면? 자정을 넘기면? |
| 권한 | 로그아웃 상태로 URL 직접 접근하면? 남의 ID로 바꾸면? |
| 데이터 오염 | 이전 사용자의 데이터가 남아 보이는가? |

**탐색적 테스트는 자동화가 대체하지 못하는 유일한 영역**이다. 자동화는 "내가 예상한 것"만 확인한다. 예상하지 못한 것을 찾는 건 사람(과 트랙 4의 탐색형 에이전트)의 몫이다.

### 네 유형의 배분

리스크와 남은 시간에 따라 비율이 달라진다. 참고용 기준선.

| 상황 | 기능 | 회귀 | 통합 | 탐색적 |
|---|---|---|---|---|
| 신규 기능 큰 릴리즈 | 40% | 25% | 20% | 15% |
| 버그 픽스 위주 릴리즈 | 15% | 55% | 10% | 20% |
| 외부 연동 추가 | 25% | 20% | 40% | 15% |
| 리팩터링만 (기능 변경 없음) | 5% | 80% | 10% | 5% |

마지막 행이 중요하다. **"기능 변경이 없으니 테스트 안 해도 되죠?"에 대한 답은 "아니오, 오히려 회귀를 제일 크게 돌려야 합니다"** 다.

## 왜 채용시장이 요구하는가

- 채용공고에 "기능/회귀/통합 테스트 수행 경험"이 거의 빠지지 않는다. 하지만 진짜 평가 포인트는 수행 경험이 아니라 **범위를 정한 경험**이다. 면접에서 "회귀 범위는 어떻게 정하셨어요?"가 나오면 그 답으로 등급이 갈린다.
- **탐색적 테스트를 기록으로 남길 줄 아는 사람이 드물다.** SBTM 차터와 세션 노트를 쓸 줄 알면 "감으로 테스트하는 사람"이 아니라 "재현 가능한 방법론을 쓰는 사람"으로 보인다.
- **AI/자동화 시대에 인간 QA의 몫이 탐색적 테스트로 이동하고 있다.** 반복 확인은 자동화가 가져가고, 사람은 "무엇이 잘못될 수 있는가"를 상상하는 일을 한다. 이 능력이 채용에서 점점 더 비싸진다.

## 실습 과제

### 과제 1 — 회귀 범위 산정 (12분)

아래 상황에서 회귀 테스트 범위를 정하고 근거를 적는다.

> 이번 릴리즈 변경사항: (1) 로그인 세션 유지 시간을 30분 → 2시간으로 변경, (2) 상품 목록 API에 페이징 파라미터 추가, (3) 공통 날짜 포맷 유틸 함수 수정

각 변경에 대해:
- 직접 영향 영역 / 간접 영향 영역을 나눠 적기
- **(3)번이 가장 위험한 이유**를 설명하기
- 시간이 절반밖에 없다면 무엇부터 버릴지 순서 정하기

### 과제 2 — 탐색적 테스트 세션 실행 (20분)

실습 랩의 **결함이 숨겨진 샘플 앱**에서 30분 타이머를 켜고 SBTM 세션을 진행한다.

차터는 아래 중 하나를 고른다.
- "장바구니를 '동시성' 관점으로 탐색해, 수량·금액이 어긋나는 경로를 찾는다"
- "로그인을 '중단' 관점으로 탐색해, 중간에 끊었을 때 상태가 꼬이는 경로를 찾는다"

세션 노트를 이 레슨의 **내 메모**에 남긴다. 형식:

```text
차터:
발견:
  - F1) ...
질문:
  - Q1) ...
아이디어(다음에 TC로):
  - I1) ...
시간 배분: setup __분 / test __분 / bug 기록 __분
```

### 과제 3 — 통합 실패 시나리오 만들기 (10분)

본인이 아는 서비스 하나를 골라 **외부 연동 실패 시나리오 5개**를 적는다.

| # | 실패 상황 | 사용자에게 보여야 할 것 | 데이터는 어떻게 남아야 하나 |
|---|---|---|---|
| 1 | 결제사 타임아웃 (10초 초과) | | |
| 2 | 결제 성공했는데 우리 서버 저장 실패 | | |
| 3 | ... | | |

2번이 실무에서 가장 무서운 케이스다. **돈은 빠져나갔는데 주문이 없는 상태**를 어떻게 감지하고 복구할 것인가 — 이 질문을 던질 수 있으면 이미 시니어 관점이다.

## 자가 체크리스트

- [ ] 기능 테스트에서 긍정·부정·권한·데이터 4가지 관점을 모두 적용할 수 있다
- [ ] 화면 결과만이 아니라 저장된 데이터까지 확인해야 하는 이유를 설명할 수 있다
- [ ] 회귀 범위를 코드 변경·의존관계·결함이력·임팩트 4가지 근거로 산정할 수 있다
- [ ] 스모크 테스트와 새니티 테스트를 구분하고, 스모크 실패 시 빌드를 반려할 수 있다
- [ ] 통합 테스트에서 정상 응답보다 비정상 응답(타임아웃·5xx·지연)을 중시하는 이유를 안다
- [ ] "결제는 성공했는데 우리 DB 저장이 실패한" 상황의 위험을 설명할 수 있다
- [ ] 탐색적 테스트와 애드혹 테스트의 차이를 차터·기록 유무로 설명할 수 있다
- [ ] SBTM 차터를 "어떤 관점으로"의 형태로 쓸 수 있고, 관점 6가지 이상을 나열할 수 있다
- [ ] 리팩터링만 있는 릴리즈에서 회귀를 가장 크게 잡아야 하는 이유를 설명할 수 있다
