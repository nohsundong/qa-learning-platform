## 개념 설명

### Go/No-Go 는 "다 됐나요?"에 대한 답이 아니다

릴리즈 회의에서 QA에게 던져지는 질문은 대개 이렇다.

> "QA 다 끝났나요? 나가도 되죠?"

여기서 **"네, 다 됐습니다"** 라고 답하면 안 된다. 테스트는 결함이 없음을 증명할 수 없다. 실제로 해야 할 답은 이것이다.

> "계획한 TC 142건 중 140건 실행, 통과율 97%입니다. Blocker·Critical 0건이고, Major 2건이 남아 있습니다. 하나는 관리자 통계 화면 오류로 사용자 영향이 없고, 다른 하나는 쿠폰 중복 적용인데 해당 쿠폰을 발급 중지하는 조건으로 나갈 수 있습니다. **이 조건이면 Go 의견입니다.**"

**QA는 결정권자가 아니라 근거 제공자다.** 하지만 근거 없이 "느낌상 불안합니다"라고 말하면 아무도 듣지 않는다. 반대로 숫자와 조건을 제시하면 QA의 판단이 회의 결과를 좌우한다.

### 판단에 필요한 다섯 가지 근거

| 근거 | 구체적으로 |
|---|---|
| **실행 현황** | 계획 TC 수 / 실행 수 / 통과·실패·차단(Blocked) 수 |
| **미해결 결함** | 심각도별 잔여 건수, 각각의 사용자 영향과 우회 방법 |
| **미검증 영역** | 시간이 없어 못 본 영역과 그것을 감수하는 이유 |
| **회귀 결과** | 자동화 스위트 통과율, 실패한 테스트의 원인 분류 |
| **롤백 준비** | 되돌릴 수 있는가, 얼마나 걸리는가, 데이터는 어떻게 되는가 |

마지막 항목이 자주 빠진다. **되돌릴 수 있으면 리스크를 더 감수해도 되고, 되돌릴 수 없으면 훨씬 보수적으로 판단해야 한다.**

되돌릴 수 없는 변경의 예:
- DB 스키마 변경 (컬럼 삭제, 타입 변경)
- 데이터 마이그레이션 (기존 값을 덮어씀)
- 외부에 이미 발송된 것 (푸시 알림, 이메일)
- 앱 스토어 심사를 통과해 배포된 앱 (강제 롤백 불가, 새 버전 심사 필요)

이런 게 포함된 릴리즈는 **테스트 깊이를 한 단계 올려야 한다.** 앞 레슨의 리스크 계산에서 "되돌릴 수 있는가"가 영향도 항목에 들어갔던 이유다.

### No-Go 를 말해야 하는 순간

다음 중 하나라도 해당하면 개인 의견이 아니라 **원칙으로서** No-Go를 제시한다.

1. **Blocker/Critical 미해결** — 우회 방법이 없는 핵심 기능 실패
2. **데이터 유실 또는 금전 손실 가능성** — 재현율이 낮아도 마찬가지
3. **보안 취약점** — 인증 우회, 타인 데이터 노출, 권한 상승
4. **롤백 불가 + 검증 부족** — 되돌릴 수 없는데 핵심 영역을 못 봤다
5. **스모크 실패** — 애초에 테스트 가능한 빌드가 아니다

No-Go를 말할 때는 **대안을 함께 낸다.** "안 됩니다"만 말하는 QA는 협업 상대로 기피된다.

> "지금 상태로는 No-Go 의견입니다. 다만 세 가지 선택지가 있습니다.
> (1) 쿠폰 기능만 피처 플래그로 끄고 나머지를 배포한다 — 오늘 가능
> (2) 수정 후 회귀 3시간 → 내일 오전 배포
> (3) 발생 조건이 VIP 등급에만 해당하므로, 해당 등급을 임시 제외하고 배포 — 리스크 남음
> 저는 (1)을 권합니다."

### 배포 전 체크리스트 (Pre-release)

```text
□ 스모크 테스트 통과 (운영과 동일한 구성의 스테이징에서)
□ 계획 TC 실행 완료, 미실행 항목의 사유 기록
□ 회귀 자동화 스위트 통과 (실패 건은 원인 분류 완료)
□ 잔여 결함 목록과 각각의 처리 방침 합의 (수정 / 다음 릴리즈 / Won't fix)
□ 롤백 절차 확인 — 누가, 어떤 명령으로, 몇 분 안에
□ DB 마이그레이션이 있다면 롤백 스크립트 존재 여부 확인
□ 피처 플래그로 끌 수 있는 기능 목록 정리
□ 모니터링 대시보드와 알림 임계치 준비
□ 배포 후 확인할 항목(스모크) 목록을 미리 작성
□ 이해관계자 공지 (CS팀, 운영팀 — 무엇이 바뀌는지)
```

CS팀 공지가 빠지면 배포 직후 문의가 폭주할 때 아무도 답을 못 한다.

### 배포 후 검증 (Post-release)

배포는 끝이 아니라 **가장 위험한 순간의 시작**이다. 스테이징에서 안 나오던 게 운영에서 나온다. 실제 데이터, 실제 트래픽, 실제 외부 연동이 다르기 때문이다.

**1단계 — 배포 직후 (5~15분)**

미리 준비한 운영 스모크를 돌린다. 실제 계정으로 핵심 경로 하나씩.

```text
□ 메인 페이지 정상 로드
□ 로그인 / 로그아웃
□ 핵심 트랜잭션 1건 실제 수행 (주문 → 결제 → 취소까지 완주)
□ 변경된 기능 직접 확인
□ 에러 로그에 새로운 유형의 예외가 올라오는지
```

**2단계 — 지표 관찰 (1~24시간)**

여기서 보는 것은 기능이 아니라 **숫자의 변화**다. (트랙 2에서 도구 사용법을 배운다)

| 지표 | 무엇을 의미하나 |
|---|---|
| 에러율 (5xx, 4xx) | 배포 전 대비 급증하면 즉시 롤백 검토 |
| 응답시간 p95/p99 | 평균은 멀쩡해도 꼬리가 길어지면 특정 조건에서 문제 |
| 핵심 전환율 | 주문 완료율, 로그인 성공률 — **기능은 되는데 사람들이 못 쓰는** 경우를 잡는다 |
| 외부 API 실패율 | 연동 쪽 문제 |
| CS 문의 유입 | 지표보다 사람이 먼저 발견하는 경우가 많다 |

세 번째 행이 중요하다. **"에러는 안 나는데 주문 완료율이 20% 떨어졌다"** 는 최악의 상황이고, 기능 테스트로는 절대 안 잡힌다. 버튼이 화면 밖으로 밀려났거나, 문구가 헷갈리거나, 특정 기기에서만 안 눌리는 경우다.

**3단계 — 롤백 판단 기준을 미리 숫자로**

배포 후에 "롤백할까요 말까요"를 즉흥적으로 논의하면 늦는다. **배포 전에** 이런 기준을 합의해 둔다.

```text
즉시 롤백:
  - 5xx 에러율이 배포 전 대비 3배 이상, 5분 이상 지속
  - 결제 성공률이 95% 미만으로 하락
  - 데이터 정합성 오류가 1건이라도 확인됨

관찰 후 판단 (30분):
  - p95 응답시간이 1.5배 이상 증가
  - 특정 기능의 에러율만 상승 → 피처 플래그로 해당 기능만 차단
```

**단계적 배포(카나리)** 가 가능하다면 리스크가 크게 줄어든다. 5% 트래픽에만 먼저 배포하고 지표를 본 뒤 확대하는 방식이다. QA는 각 단계에서 무엇을 확인할지 정의한다.

### 릴리즈 회고

배포가 끝나면 15분만 써서 남긴다.

- 운영에서 발견된 결함이 있었다면 **왜 테스트에서 못 잡았는가** (환경 차이? 데이터 차이? TC 누락? 범위에서 뺐던 영역?)
- 다음 릴리즈에 추가할 TC 또는 자동화 항목
- 판단이 틀렸던 지점 (Go 했는데 문제가 났다면 어떤 근거가 부족했나)

이 기록이 쌓이면 **결함 탈출률**(다음 레슨)을 실제로 낮출 수 있다.

## 왜 채용시장이 요구하는가

- 채용공고의 "릴리즈 전후 품질 검증", "배포 판단 참여"는 **주니어에게는 잘 안 시키는 일**이다. 이걸 해봤다는 건 팀에서 신뢰받는 위치였다는 신호로 읽힌다.
- 면접 단골 질문: **"릴리즈 직전에 Critical 결함을 발견했습니다. 어떻게 하시겠어요?"**
  좋은 답의 구조 = 영향 범위 파악 → 우회 방법 확인 → 롤백 가능 여부 확인 → 선택지 2~3개와 권고안 제시. "무조건 막습니다"도 "일단 나가시죠"도 답이 아니다.
- **AI가 대체하기 가장 어려운 영역**이다. TC 생성과 실행은 자동화되지만, "지금 나가도 되는가"는 비즈니스 맥락·리스크 감수 수준·조직의 롤백 능력을 종합한 판단이다. QA 커리어의 상위 구간이 여기에 있다.

## 실습 과제

### 과제 1 — Go/No-Go 발언 작성 (12분)

아래 상황에서 릴리즈 회의에서 할 발언을 **그대로 읽을 수 있는 문장**으로 작성한다.

> - 계획 TC 96건 중 89건 실행 (7건은 결제 스테이징 환경 장애로 Blocked)
> - Critical 0건, Major 1건 (특정 안드로이드 12 기기에서 이미지 업로드 실패, 전체 사용자의 약 4%)
> - 회귀 자동화 통과율 94% — 실패 6건 중 5건은 플래키로 확인, 1건은 미분석
> - 이번 릴리즈에 DB 컬럼 타입 변경 포함 (롤백 스크립트 있음, 검증은 안 됨)
> - 마케팅 프로모션이 내일 오전 10시 시작 예정

포함할 것: 숫자 근거 / 미검증 영역과 그 리스크 / 선택지 2~3개 / 본인 권고안과 이유

**힌트**: 롤백 스크립트가 "있지만 검증 안 됨"인 것과 Blocked 7건이 하필 결제 영역인 것이 이 문제의 핵심이다.

### 과제 2 — 롤백 기준 숫자로 정하기 (8분)

본인이 아는 서비스 하나를 골라 배포 후 롤백 기준을 작성한다.

| 지표 | 정상 범위 | 관찰 임계치 | 즉시 롤백 임계치 |
|---|---|---|---|
| 5xx 에러율 | | | |
| 결제 성공률 | | | |
| p95 응답시간 | | | |
| 로그인 성공률 | | | |

숫자를 모르면 **"무엇을 알아야 이 숫자를 정할 수 있는가"** 를 적는다. (평상시 기준선을 모르면 이상을 판단할 수 없다는 것이 이 과제의 교훈이다)

### 과제 3 — 배포 후 스모크 스크립트 설계 (10분)

배포 직후 15분 안에 끝나야 하는 운영 스모크 체크리스트를 만든다.

제약: **10개 항목 이내**, 실제 운영 데이터를 오염시키지 않을 것.

마지막 제약이 실무에서 까다롭다. 운영에서 테스트 주문을 넣으면 매출 집계와 재고가 틀어진다. 어떻게 할 것인가를 함께 적는다. (테스트 계정 제외 처리, 즉시 취소, 별도 테스트 상품 등)

## 자가 체크리스트

- [ ] "QA 다 됐나요"에 숫자 근거로 답하는 문장을 만들 수 있다
- [ ] Go/No-Go 판단에 필요한 5가지 근거를 나열할 수 있다
- [ ] 롤백 가능 여부가 판단 기준을 어떻게 바꾸는지 설명할 수 있다
- [ ] 되돌릴 수 없는 변경의 예를 4가지 이상 댈 수 있다
- [ ] No-Go 조건 5가지를 원칙으로 제시할 수 있다
- [ ] No-Go를 말할 때 대안 선택지를 함께 제시할 수 있다
- [ ] 배포 전 체크리스트를 10개 항목 이상 작성할 수 있다
- [ ] 배포 후 1단계(스모크)와 2단계(지표 관찰)를 구분해 수행할 수 있다
- [ ] "에러는 없는데 전환율이 떨어진" 상황의 원인을 3가지 이상 추측할 수 있다
- [ ] 롤백 기준을 배포 전에 숫자로 합의해 두어야 하는 이유를 설명할 수 있다
- [ ] 릴리즈 회고에서 "왜 테스트에서 못 잡았는가"를 분류할 수 있다
