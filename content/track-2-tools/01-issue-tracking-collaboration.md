## 개념 설명

도구 사용법 자체는 반나절이면 익힌다. 채용에서 보는 건 **"이 사람이 팀의 일 흐름을 이해하고 있는가"** 다. 이 레슨은 버튼 위치가 아니라 흐름을 다룬다.

### Jira — 이슈 트래커

**이슈 타입의 계층**을 먼저 이해해야 한다. 팀마다 이름은 조금씩 다르지만 구조는 같다.

```text
Epic (큰 기능 덩어리)
 └─ Story / Task (개발 단위)
     └─ Sub-task (쪼갠 작업)
Bug (결함)          ← QA가 가장 많이 만드는 것
```

**결함 티켓의 표준 워크플로**는 대략 이렇게 흐른다.

```text
Open ──> In Progress ──> Resolved ──> [QA 확인] ──> Closed
  ^                          │
  └──── Reopened ◄───────────┘  (재현되면 되돌린다)

  └──> Won't Fix / Duplicate / Cannot Reproduce / Not a Bug  (닫히는 다른 경로)
```

**QA가 실제로 신경 쓰는 지점은 두 군데다.**

1. **Resolved → Closed 로 넘기는 판단** — 개발자가 "고쳤다"고 하면 QA가 확인하고 닫는다. 이때 원래 재현 절차 그대로 재현해 보고, **주변 회귀까지** 본다. 고치면서 다른 걸 깨뜨리는 일이 흔하다
2. **Cannot Reproduce 로 되돌아온 티켓** — 대부분 리포트에 정보가 부족했던 것이다. 앞 트랙의 결함 리포트 레슨이 여기서 값을 한다

**필드 중 실무에서 중요한 것들**

| 필드 | QA가 쓰는 이유 |
|---|---|
| Priority / Severity | 처리 순서. 두 필드를 다 쓰는 팀도, 하나만 쓰는 팀도 있다 |
| Affects Version | **어느 버전에서 발견됐는가** — 회귀인지 신규인지 판단 |
| Fix Version | 어느 릴리즈에 포함되는가 — 릴리즈 노트가 여기서 자동 생성된다 |
| Component | 담당 팀 자동 배정, 결함 밀도 집계의 단위 |
| Labels | `regression`, `flaky`, `escaped` 같은 분류. 나중에 통계를 낼 수 있다 |
| Linked Issues | `blocks`, `is caused by`, `relates to` — 원인 티켓 연결 |

**`escaped` 라벨을 습관화하면** 앞 트랙의 결함 탈출률을 JQL 한 줄로 계산할 수 있다. 지표를 만들려면 데이터를 남기는 습관이 먼저다.

### JQL — 이걸 쓸 줄 알아야 Jira를 쓰는 것이다

JQL(Jira Query Language)은 SQL과 비슷한 이슈 검색 문법이다. **JQL을 못 쓰면 매번 화면을 뒤지느라 시간을 버린다.**

```sql
-- 내가 리포트했는데 아직 안 닫힌 것
reporter = currentUser() AND status not in (Closed, Done) ORDER BY priority DESC

-- 이번 릴리즈에 포함되는 미해결 Critical 이상 (Go/No-Go 회의 준비용)
fixVersion = "3.4.0" AND priority in (Blocker, Critical) AND status != Closed

-- QA 확인 대기 중인 것 (내가 지금 해야 할 일)
status = Resolved AND reporter = currentUser()

-- 최근 30일간 운영에서 탈출한 결함 (탈출률 계산용)
labels = escaped AND created >= -30d

-- 결제 컴포넌트에서 재발한 결함
component = "Payment" AND status changed FROM Closed TO Reopened
```

마지막 쿼리의 `status changed FROM ... TO ...` 가 강력하다. **결함 재발률**을 이걸로 뽑는다.

이런 쿼리를 대시보드 위젯으로 저장해두면 매일 아침 확인할 화면이 만들어진다.

### Confluence / Notion — 문서

이슈 트래커는 "지금 처리 중인 일", 문서 도구는 "쌓여서 참조되는 것"을 담는다. QA가 이곳에 남기는 문서는 보통 다섯 가지다.

| 문서 | 갱신 주기 | 핵심 |
|---|---|---|
| 테스트 전략 | 분기~연 | 조직 차원. 자동화 기준, 환경 정책, 결함 등급 정의 |
| 릴리즈별 테스트 계획 | 릴리즈마다 | 트랙 1의 7항목 |
| 테스트 케이스 / RTM | 기능마다 | 요구사항 ↔ TC 매핑. 커버리지의 근거 |
| 릴리즈 리포트 | 릴리즈마다 | 실행 현황, 잔여 결함, Go/No-Go 근거, 회고 |
| 트러블슈팅 / 환경 가이드 | 상시 | 테스트 계정, 환경 접속법, 자주 겪는 문제 |

마지막 항목을 잘 관리하는 QA가 팀에서 신뢰를 받는다. **"그거 어떻게 하는 거였죠?"에 링크 하나로 답하는 사람**이 되기 때문이다.

문서 작성 원칙 하나만 기억하면 된다. **문서는 최신이 아니면 해롭다.** 틀린 문서는 없는 문서보다 나쁘다. 그래서 유지할 수 없는 문서는 아예 만들지 않는 게 낫고, 만든 문서에는 "최종 확인일"과 "담당"을 반드시 남긴다.

### Slack — QA의 실제 커뮤니케이션

여기서 실력 차이가 크게 난다. 같은 내용도 어떻게 쓰느냐에 따라 팀의 시간이 달라진다.

**나쁜 예**

> 결제가 안 되는데요?

**좋은 예**

> 🔴 **[스테이징] 결제 실패 — 확인 요청**
> - 증상: 카드 결제 시 "일시적 오류" 후 주문 미생성
> - 재현: 10회 중 10회 (계정 qa_user_01)
> - 발생 시각: 14:32 ~ 현재
> - 확인한 것: 다른 계정·다른 카드에서도 동일 / 어제 16시 배포 이후로 추정
> - 티켓: PROJ-1423
> - **필요한 것**: 결제 서버 로그 14:30~14:40 확인 부탁드립니다 (@개발자)

차이는 세 가지다. **(1) 이미 확인한 것을 명시**해서 중복 조사를 막고, **(2) 무엇이 필요한지 구체적으로 요청**하고, **(3) 티켓 링크로 맥락을 연결**한다.

실무 팁 몇 가지.

- **스레드를 쓴다.** 채널이 스크롤 지옥이 되면 아무도 안 읽는다
- **긴급도를 이모지나 접두어로 표시한다.** 🔴 차단 / 🟡 확인 필요 / 🟢 정보 공유
- **DM 대신 채널**을 쓴다. DM으로 해결한 문제는 팀의 자산이 되지 않고, 같은 질문이 반복된다
- **CI 실패, 배포 알림을 채널로 받는다.** (트랙 3에서 GitHub Actions → Slack 알림을 붙인다)

### 도구를 연결하면 손이 줄어든다

무료 범위에서 할 수 있는 자동화들이다.

```text
GitHub PR 머지  ──> Jira 티켓 자동 In Review 전환 (커밋 메시지에 PROJ-1423 포함)
CI 테스트 실패   ──> Slack 알림 + 실패 리포트 링크
Jira 티켓 생성   ──> Slack 채널 알림
Confluence 문서 ──> Jira 이슈 목록 매크로로 실시간 임베드
```

첫 줄이 특히 유용하다. **커밋 메시지에 티켓 번호를 넣는 습관**만으로 코드 변경과 결함이 자동 연결되고, 나중에 "이 결함은 어느 커밋에서 생겼나"를 추적할 수 있다.

## 왜 채용시장이 요구하는가

- 채용공고의 "Jira, Confluence 사용 경험"은 **거의 모든 공고에 있는 기본 항목**이라 없으면 서류에서 걸린다. 다만 이건 변별력이 없는 항목이기도 하다.
- **변별력은 JQL에서 난다.** 면접에서 "Jira에서 데이터를 어떻게 뽑으셨나요?"를 물었을 때 JQL 쿼리를 말할 수 있으면 "도구를 쓰는 사람"이 아니라 "도구로 관리하는 사람"으로 보인다.
- **비동기 커뮤니케이션 능력**이 원격·하이브리드 환경에서 크게 평가된다. Slack 메시지 한 통에서 그 사람이 남의 시간을 아껴주는 사람인지가 드러난다.
- AI 도구들이 티켓 초안을 대신 써주는 시대지만, **무엇을 이미 확인했고 무엇이 필요한지**는 사람만 안다. AI가 쓴 티켓을 그대로 올리면 "확인하지 않은 것을 확인한 것처럼" 적히는 사고가 난다.

## 실습 과제

### 과제 1 — 무료로 Jira 환경 만들기 (10분)

Jira Cloud는 **10명까지 무료**다. 개인 학습용으로 하나 만든다.

1. Jira Cloud 무료 플랜으로 사이트 생성, 스크럼 또는 칸반 프로젝트 하나 생성
2. Bug 이슈 타입의 워크플로를 확인 — 기본 상태가 무엇인지 본다
3. 트랙 1의 결함 리포트 과제에서 쓴 결함 2건을 실제 티켓으로 등록
4. 한 건을 Resolved → Closed 까지 직접 옮겨보고, 다른 한 건은 Reopened 시켜본다

### 과제 2 — JQL 5개 작성 (12분)

본인 프로젝트에서 아래를 뽑는 JQL을 직접 작성해 실행한다. (결과가 0건이어도 문법이 통과하면 성공)

| # | 뽑을 것 |
|---|---|
| 1 | 내가 만들었고 아직 안 닫힌 이슈, 우선순위 높은 순 |
| 2 | 최근 7일 내 생성된 Bug |
| 3 | Resolved 상태로 3일 이상 방치된 이슈 |
| 4 | 특정 라벨(`escaped`)이 붙은 이슈 |
| 5 | Closed 에서 Reopened 로 상태가 바뀐 적 있는 이슈 |

3번이 실무에서 특히 쓸모 있다. **QA 확인 대기 중인데 잊힌 티켓**을 잡아낸다.

### 과제 3 — Slack 메시지 다시 쓰기 (8분)

아래 메시지를 좋은 예의 형식으로 다시 쓴다. 부족한 정보는 **"이걸 먼저 확인하고 보내겠다"** 로 표시한다.

> 앱에서 로그인이 자꾸 풀리는데 이거 왜 이러죠? 아까부터 그러네요

### 과제 4 — AI로 티켓 초안 만들고 검증 (10분)

AI 실습 도우미의 **결함 리포트 정리** 템플릿으로 티켓 본문을 만든 뒤, 다음을 확인한다.

- 내가 말하지 않은 환경 정보(브라우저 버전, OS 버전)를 채워 넣었는가
- Affects Version / Component 를 임의로 지정했는가
- "재현율 100%" 처럼 내가 세어보지 않은 숫자를 단정했는가

**AI가 채운 필드 중 내가 실제로 확인한 것만 남기고 나머지는 지운다.** 그 상태가 제출 가능한 티켓이다.

## 자가 체크리스트

- [ ] Epic / Story / Task / Sub-task / Bug 의 계층을 설명할 수 있다
- [ ] 결함 티켓의 표준 워크플로와 Reopened 가 발생하는 이유를 설명할 수 있다
- [ ] Resolved → Closed 로 넘기기 전에 주변 회귀까지 확인해야 하는 이유를 안다
- [ ] Affects Version 과 Fix Version 의 차이와 각각의 용도를 안다
- [ ] JQL 로 "내가 확인해야 할 이슈"를 뽑는 쿼리를 쓸 수 있다
- [ ] `status changed FROM Closed TO Reopened` 로 결함 재발을 추적할 수 있다
- [ ] 라벨을 남겨두면 나중에 지표를 계산할 수 있다는 걸 이해하고 습관화한다
- [ ] QA가 문서 도구에 남기는 5가지 문서를 나열할 수 있다
- [ ] "틀린 문서는 없는 문서보다 나쁘다"의 의미를 설명하고 최종 확인일을 남긴다
- [ ] Slack 이슈 공유 메시지에 (이미 확인한 것 / 필요한 것 / 티켓 링크)를 포함시킨다
- [ ] 커밋 메시지에 티켓 번호를 넣으면 무엇이 가능해지는지 설명할 수 있다
- [ ] AI가 만든 티켓에서 확인하지 않은 정보를 걸러낼 수 있다
