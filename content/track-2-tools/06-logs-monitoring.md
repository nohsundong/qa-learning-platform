## 개념 설명

### QA가 로그를 봐야 하는 이유

같은 결함을 발견해도 리포트의 가치가 완전히 달라진다.

```text
[약함] 결제가 가끔 실패해요
[강함] 14:32:07 에 order-service 에서 PaymentGatewayTimeoutException 발생.
       trace_id=7f3a9b2c. 외부 결제사 응답이 5초 타임아웃을 넘겼고,
       재시도 없이 500 을 반환했습니다. 최근 1시간 동일 예외 23건.
```

두 번째 리포트는 **개발자가 재현할 필요조차 없다.** 원인이 이미 적혀 있다. 이런 리포트를 쓰는 QA는 팀에서 위치가 달라진다.

그리고 트랙 1에서 다룬 배포 후 검증, Go/No-Go 판단의 근거가 전부 이 도구들에서 나온다.

### 옵저버빌리티의 세 기둥

| 기둥 | 무엇인가 | QA가 쓰는 상황 |
|---|---|---|
| **로그 (Logs)** | 시점별 이벤트 기록. 텍스트 | "그때 무슨 일이 있었나" 개별 사건 추적 |
| **메트릭 (Metrics)** | 시간에 따른 숫자. 집계 | "지금 정상인가" 전체 상태 판단 |
| **트레이스 (Traces)** | 요청 하나가 거친 서비스들의 경로 | "어느 구간에서 느려졌나" 병목 특정 |

세 가지를 순서대로 쓴다. **메트릭으로 이상을 감지 → 트레이스로 구간 특정 → 로그로 원인 확인.**

### 로그 읽는 법

**로그 레벨**부터. 이걸 알아야 무엇을 무시하고 무엇을 봐야 하는지 판단한다.

| 레벨 | 의미 | QA의 반응 |
|---|---|---|
| `ERROR` | 처리 실패. 사용자 영향 있음 | **무조건 확인** |
| `WARN` | 이상하지만 처리는 됨 | 급증하면 확인 (재시도, 폴백 동작 중일 수 있음) |
| `INFO` | 정상 흐름 기록 | 재현 경로 추적용 |
| `DEBUG` | 개발용 상세 | 보통 운영엔 없음 |

**구조화 로그(JSON)** 를 쓰는 팀이 많다. 이런 형태다.

```json
{
  "timestamp": "2026-08-15T14:32:07.412+09:00",
  "level": "ERROR",
  "service": "order-service",
  "trace_id": "7f3a9b2c1d4e5f60",
  "user_id": 12345,
  "order_id": "ORD-20260815-0001",
  "message": "Payment gateway timeout",
  "exception": "PaymentGatewayTimeoutException",
  "duration_ms": 5031,
  "http_status": 500
}
```

QA가 여기서 뽑아 쓰는 필드는 정해져 있다.

- **`trace_id`** — 이게 가장 중요하다. 뒤에서 따로 다룬다
- `timestamp` — 결함 리포트에 초 단위까지 적는다
- `service` — 어느 팀에 티켓을 보낼지 결정된다
- `duration_ms` — 타임아웃인지 즉시 실패인지 구분
- `exception` — 그대로 검색하면 같은 유형의 다른 사례가 나온다

### trace_id — QA가 반드시 익혀야 할 개념

요즘 서비스는 요청 하나가 여러 서비스를 거친다.

```text
[사용자] → api-gateway → order-service → payment-service → 외부 결제사
                              ↓
                        inventory-service
```

이때 각 서비스가 남기는 로그를 **하나의 요청으로 묶어주는 식별자**가 trace_id다. 이게 없으면 서비스 5개의 로그를 시각으로 눈대중해서 맞춰야 한다.

**QA의 실전 활용법**

1. 테스트 중 오류가 나면 **화면이나 응답 헤더에서 trace_id를 먼저 찾는다** (`X-Trace-Id`, `X-Request-Id` 같은 헤더로 내려오는 경우가 많다)
2. 없으면 브라우저 개발자도구 Network 탭에서 실패한 요청의 응답 헤더 확인
3. 그 값으로 로그를 검색하면 **그 요청이 거친 전 구간의 로그가 한 번에** 나온다
4. 결함 리포트에 trace_id를 적는다

**결함 리포트에 trace_id 한 줄이 들어가면 개발자의 조사 시간이 몇십 분에서 몇 분으로 줄어든다.** 앞 레슨의 curl 명령과 함께, QA가 붙일 수 있는 가장 값싼 증거다.

### 로그 검색 문법

도구마다 문법은 다르지만 개념은 같다.

```text
# Datadog 로그 검색
service:order-service status:error @trace_id:7f3a9b2c1d4e5f60
service:payment-service @duration_ms:>3000
@http.status_code:5* -service:health-check

# Grafana Loki (LogQL)
{service="order-service"} |= "PaymentGatewayTimeout"
{service="order-service"} | json | duration_ms > 3000

# Kibana / OpenSearch (Lucene)
service:"order-service" AND level:ERROR AND NOT message:"health"
```

공통 패턴 네 가지만 알면 된다.

| 하고 싶은 것 | 방법 |
|---|---|
| 특정 서비스의 에러만 | `service:X level:ERROR` |
| 특정 요청 추적 | `trace_id:값` |
| 느린 요청 찾기 | `duration_ms:>3000` |
| 노이즈 제거 | `-service:health-check` (앞에 `-` 로 제외) |

마지막이 실무에서 중요하다. 헬스체크·봇 트래픽을 빼지 않으면 진짜 문제가 묻힌다.

### 메트릭 대시보드 — 무엇을 볼 것인가

Google SRE의 **4가지 골든 시그널**이 기준이다. 트랙 1의 배포 후 검증과 직결된다.

| 시그널 | 지표 | 이상 신호 |
|---|---|---|
| **Latency (지연)** | p50 / p95 / p99 응답시간 | p99만 튀면 특정 조건에서만 느림 |
| **Traffic (처리량)** | RPS, 요청 수 | 급감 = 사용자가 도달 못 하는 중 |
| **Errors (에러)** | 5xx 비율, 4xx 비율 | 배포 직후 급증 → 롤백 검토 |
| **Saturation (포화)** | CPU, 메모리, 커넥션 풀 | 포화 직전이면 곧 지연·에러로 번진다 |

**평균이 아니라 백분위수(percentile)를 봐야 하는 이유**를 이해하는 게 핵심이다.

```text
응답시간 100건: 95건이 100ms, 5건이 10초

평균 = 595ms   → "좀 느리네" (문제를 놓친다)
p95  = 100ms   → 정상 구간
p99  = 10초    → 100명 중 1명은 10초를 기다린다 ← 실제 문제
```

**평균은 소수의 심각한 사례를 숨긴다.** 트랙 5(성능 테스트)에서 이 개념을 본격적으로 다룬다.

또 하나 중요한 관점. **에러율이 0인데도 문제가 있을 수 있다.**

| 상황 | 에러율 | 실제 문제 |
|---|---|---|
| 버튼이 화면 밖으로 밀림 | 0% | 아무도 클릭을 못 함 → 주문 수 급감 |
| 검색 결과가 항상 0건 | 0% | 200 OK 로 빈 배열 반환 |
| 결제 성공했는데 주문 미생성 | 0% | 양쪽 다 200 |

그래서 **기술 지표만 보면 안 되고 비즈니스 지표를 함께 봐야 한다.** 주문 완료 수, 로그인 성공률, 검색 결과 0건 비율 같은 것들이다. QA가 대시보드에 이런 패널을 추가해달라고 요청할 수 있으면 좋다.

### Datadog 과 Grafana — 무엇이 다른가

| | Datadog | Grafana |
|---|---|---|
| 형태 | SaaS (호스팅형) | 오픈소스 + Grafana Cloud |
| 데이터 소스 | 자체 에이전트로 수집 | Prometheus, Loki, Elasticsearch 등 **연결해서 씀** |
| 강점 | 설치하면 바로 통합됨. APM·로그·메트릭 한 화면 | 무료, 커스터마이징 자유, 벤더 종속 없음 |
| 비용 | 유료 (호스트 단위 과금) | OSS 무료 / Cloud 무료 티어 있음 |
| 학습 | 개념 이해 위주 | **직접 만져볼 수 있다** |

**학습 목적으로는 Grafana를 권한다.** 무료이고, `play.grafana.org` 라는 공개 데모 사이트에서 실제 대시보드를 바로 만져볼 수 있다.

Datadog은 개인이 실습하기 어려우므로 **개념과 화면 구성을 아는 수준**으로 접근한다. 실무에서 Datadog을 쓰는 팀에 가더라도, Grafana에서 익힌 개념(패널, 쿼리, 시간 범위, 알림 임계치)이 그대로 통한다.

### 알림(Alert) — QA가 관여할 지점

알림 규칙은 보통 개발/SRE가 만들지만, **QA가 제안할 수 있는 알림**이 있다.

```text
□ 결제 실패율이 5분간 5% 초과
□ 주문 생성 수가 지난주 같은 시간대 대비 50% 이하
□ 특정 예외(PaymentGatewayTimeoutException)가 5분간 10건 초과
□ p99 응답시간이 3초 초과 상태로 10분 지속
```

두 번째가 QA다운 제안이다. **에러가 아니라 "일어나야 할 일이 안 일어나는 것"을 감지**한다.

알림 설계에서 조심할 것: **알림 피로(alert fatigue)**. 너무 많이 울리면 아무도 안 본다. 트랙 1의 "롤백 기준을 숫자로" 와 같은 원칙이다 — **행동할 수 있는 알림만 만든다.**

### 실전 흐름 — 결함을 만났을 때

```text
1. 화면/응답에서 trace_id 확보 (없으면 정확한 시각 초 단위로 기록)
2. 개발자도구 Network 탭 → 실패한 요청의 상태코드·응답 바디 확인
3. 로그 검색: trace_id 또는 (service + 시각 범위 + level:ERROR)
4. 예외 이름과 스택 확인 → 어느 서비스, 어느 구간인지 특정
5. 메트릭 대시보드에서 같은 시각대의 에러율·지연 확인
   → 나만의 문제인가, 전체 문제인가 판단
6. 같은 예외의 최근 발생 건수 조회 → 재현율과 영향 범위 추정
7. 결함 리포트 작성 (trace_id, 시각, 예외명, 발생 건수 포함)
```

5번이 중요하다. **"나만 안 되는 것"과 "전체가 안 되는 것"은 심각도가 완전히 다르다.**

## 왜 채용시장이 요구하는가

- 채용공고의 **"로그 분석을 통한 이슈 원인 파악"**, **"모니터링 도구 활용 경험"** 은 이제 흔한 항목이다. 특히 마이크로서비스 환경의 회사는 반드시 본다.
- **원인 분석까지 하는 QA와 현상만 보고하는 QA의 차이**가 연차 대비 평가를 가른다. 면접에서 "결함의 원인을 어떻게 파악하셨나요?"에 로그·트레이스 이야기를 할 수 있으면 강하다.
- **배포 후 검증을 실제로 수행하려면 대시보드를 읽을 줄 알아야 한다.** 트랙 1의 Go/No-Go와 롤백 판단이 여기에 의존한다.
- **AI가 로그 분석을 도와주는 시대**지만, AI에게 로그를 붙여넣고 "원인이 뭐야?"라고 물으면 **그럴듯한 원인을 지어낸다.** 실제로는 로그에 없는 인과관계를 만들어내고, 존재하지 않는 예외 클래스명을 언급하기도 한다. 로그를 직접 읽을 수 있어야 그 답을 검증할 수 있다.

## 실습 과제

### 과제 1 — Grafana 공개 데모 둘러보기 (15분)

`https://play.grafana.org` 는 로그인 없이 쓸 수 있는 Grafana 공식 데모다.

1. 아무 대시보드나 열어 **패널 하나를 골라** 무슨 지표인지 파악
2. **시간 범위를 바꿔본다** (최근 5분 / 6시간 / 7일) — 같은 데이터가 어떻게 다르게 보이는지
3. 패널 제목 → Edit 또는 Inspect → **쿼리를 직접 본다.** 무엇을 어떻게 집계하고 있는가
4. 그래프에서 **튀는 지점(spike)** 을 찾아 그 시각을 기록
5. 메모에 적기: 이 대시보드에서 "지금 서비스가 정상인가"를 판단하려면 어느 패널 3개를 봐야 하는가

### 과제 2 — 브라우저에서 trace_id 찾기 (10분)

아무 웹서비스나 열고 개발자도구 → Network 탭에서:

1. API 요청 하나를 골라 **응답 헤더 전체**를 본다
2. `X-Request-Id`, `X-Trace-Id`, `X-Correlation-Id`, `traceparent` 중 있는 것을 찾는다
3. 없다면: 이 서비스에서 결함을 발견했을 때 **개발자에게 무엇을 대신 줘야 하는가**를 적는다
4. 요청을 **Copy as cURL** 로 복사해 본다 (결함 리포트 재현 절차용)

### 과제 3 — 로그에서 원인 추론 (12분)

아래 로그를 읽고 질문에 답한다.

```json
{"ts":"2026-08-15T14:32:02.100+09:00","level":"INFO","service":"api-gateway","trace_id":"7f3a9b2c","msg":"POST /api/v1/orders","user_id":12345}
{"ts":"2026-08-15T14:32:02.180+09:00","level":"INFO","service":"order-service","trace_id":"7f3a9b2c","msg":"order created","order_id":"ORD-0001","status":"PENDING"}
{"ts":"2026-08-15T14:32:02.240+09:00","level":"INFO","service":"inventory-service","trace_id":"7f3a9b2c","msg":"stock reserved","product_id":501,"qty":2}
{"ts":"2026-08-15T14:32:07.271+09:00","level":"ERROR","service":"payment-service","trace_id":"7f3a9b2c","msg":"Payment gateway timeout","exception":"PaymentGatewayTimeoutException","duration_ms":5031}
{"ts":"2026-08-15T14:32:07.280+09:00","level":"ERROR","service":"order-service","trace_id":"7f3a9b2c","msg":"order creation failed","order_id":"ORD-0001","http_status":500}
```

1. 사용자가 본 화면은 무엇이었을까?
2. **주문 ORD-0001 은 지금 어떤 상태로 남아 있는가?** (로그에 명시되지 않았다 — 무엇을 확인해야 알 수 있는가)
3. **예약된 재고 2개는 어떻게 됐는가?** 이게 왜 문제인가
4. 이 로그에서 **가장 심각한 결함**은 타임아웃 자체인가, 아니면 다른 것인가
5. 추가로 확인해야 할 것 3가지 (앞 레슨의 SQL 정합성 쿼리를 떠올려 볼 것)

**힌트**: 3번이 트랙 2 전체를 관통하는 문제다. 보상 트랜잭션(compensating transaction)이 없으면 재고가 영원히 묶인다.

### 과제 4 — 알림 규칙 설계 (8분)

본인이 아는 서비스 하나를 골라 알림 규칙 5개를 설계한다.

| # | 조건 | 임계치 | 왜 이 숫자인가 | 울리면 누가 무엇을 하나 |
|---|---|---|---|---|
| 1 | | | | |

**마지막 열이 핵심이다.** 받고 나서 할 일이 없는 알림은 만들지 않는다. 5개 중 최소 1개는 "에러가 아니라 일어나야 할 일이 안 일어나는 것"을 감지하는 규칙으로 만든다.

### 과제 5 — AI 로그 분석 교차검증 (10분)

AI 실습 도우미에 과제 3의 로그를 그대로 붙여넣고 원인 분석을 요청한다.

받은 답변을 **다음 기준으로 검증**한다.

| 확인 항목 | 결과 |
|---|---|
| 로그에 **실제로 있는** 사실만 근거로 삼았는가 | |
| 로그에 없는 인과관계를 지어내지 않았는가 | |
| 재고 예약이 롤백되지 않은 문제를 짚었는가 | |
| 주문 상태가 불확실하다는 점을 "확인 필요"로 남겼는가 | |
| 존재하지 않는 예외 클래스나 서비스명을 언급하지 않았는가 | |

**AI는 대체로 타임아웃을 원인으로 잘 짚는다. 그런데 "예약된 재고가 어떻게 됐는지"는 잘 묻지 않는다.** 로그에 명시되지 않은 것을 의심하는 게 사람의 몫이다.

## 자가 체크리스트

- [ ] 옵저버빌리티의 세 기둥(로그·메트릭·트레이스)과 각각을 쓰는 상황을 구분할 수 있다
- [ ] 메트릭 → 트레이스 → 로그 순으로 좁혀가는 분석 흐름을 설명할 수 있다
- [ ] 로그 레벨별로 무엇을 확인하고 무엇을 무시할지 판단할 수 있다
- [ ] 구조화 로그에서 QA가 쓸 필드 5가지를 뽑아낼 수 있다
- [ ] trace_id 의 역할을 설명하고, 응답 헤더나 개발자도구에서 찾을 수 있다
- [ ] 결함 리포트에 trace_id·정확한 시각·예외명·발생 건수를 포함시킨다
- [ ] 로그 검색에서 서비스 필터, 시간 범위, 제외 조건(`-`)을 조합할 수 있다
- [ ] 4가지 골든 시그널(지연·처리량·에러·포화)을 나열하고 각각의 이상 신호를 안다
- [ ] 평균 대신 p95/p99 를 봐야 하는 이유를 예시로 설명할 수 있다
- [ ] 에러율 0%인데도 장애인 상황을 3가지 이상 들 수 있다
- [ ] 기술 지표 외에 비즈니스 지표(주문 수, 로그인 성공률)를 함께 봐야 하는 이유를 안다
- [ ] Datadog과 Grafana의 차이(SaaS/오픈소스, 수집/연결)를 설명할 수 있다
- [ ] "일어나야 할 일이 안 일어나는 것"을 감지하는 알림을 설계할 수 있다
- [ ] 알림 피로를 피하기 위해 행동 가능한 알림만 만든다는 원칙을 안다
- [ ] AI 로그 분석에서 지어낸 인과관계와 누락된 관점을 짚어낼 수 있다
