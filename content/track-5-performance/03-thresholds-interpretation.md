## 개념 설명

### 평균은 거짓말한다

트랙 2에서 잠깐 다뤘던 내용을 여기서 제대로 본다.

```text
응답시간 100건: 95건이 100ms, 5건이 10,000ms

평균  =  595ms   → "좀 느리네" 정도로 읽힌다
중앙값 = 100ms   → "빠른데?"
p95   =  100ms   → 정상 구간
p99   = 10,000ms → 100명 중 1명은 10초를 기다린다   ← 실제 문제
```

**평균과 중앙값은 소수의 심각한 사례를 완전히 숨긴다.** 그리고 그 소수가 실제로는 매일 수천 명이다.

```text
일 100만 요청 서비스에서 p99 가 10초라면
→ 하루 1만 건이 10초 이상 걸린다
→ 그 사용자들은 이탈한다
```

### 백분위수 읽는 법

```text
p95 = 500ms  →  전체 요청의 95%가 500ms 안에 끝났다
                (= 5%는 500ms 보다 오래 걸렸다)
p99 = 2,000ms → 1%가 2초 이상 걸렸다
```

**어느 백분위를 볼 것인가**는 상황에 따라 다르다.

| 지표 | 무엇을 보는가 | 언제 쓰나 |
|---|---|---|
| p50 (중앙값) | 전형적인 사용자 경험 | 참고용 |
| **p95** | 대부분의 사용자가 겪는 최악 | **일반적인 SLA 기준** |
| **p99** | 꼬리 지연(tail latency) | 트래픽이 크거나 중요한 서비스 |
| p99.9 | 극단적 이상치 | 대규모 서비스, 금융 |
| max | 최악의 한 건 | 이상치 탐지용. 기준으로는 부적합 |

**`max` 를 기준으로 삼으면 안 된다.** 네트워크 순간 장애 한 건 때문에 항상 실패한다.

### 꼬리 지연이 왜 생기는가

p50은 멀쩡한데 p99만 튀는 것에는 원인이 있다.

| 원인 | 특징 |
|---|---|
| **GC (가비지 컬렉션)** | 주기적으로 수백 ms~수 초 멈춤 |
| 커넥션 풀 대기 | 풀이 고갈되면 대기열이 생긴다 |
| 캐시 미스 | 캐시에 없는 요청만 DB까지 간다 |
| 콜드 스타트 | 서버리스, 새 인스턴스 |
| 락 경합 | 특정 데이터에 동시 접근 |
| 느린 쿼리 | 특정 조건에서만 인덱스를 못 탄다 |
| 재시도 | 첫 시도 실패 후 재시도한 요청 |

**p99만 나쁘다면 "일부 요청에만 해당하는 특수 조건"이 있다는 뜻이다.** 이걸 좁히는 게 성능 분석이다.

### 여러 사용자가 겹치면 더 나빠진다

이게 직관에 반하는 부분이다.

```text
한 페이지가 API 20개를 호출한다.
각 API 의 p99 가 1% 라면,
그 페이지에서 느린 응답을 한 번이라도 겪을 확률은?

1 - (0.99)^20 ≈ 18%
```

**개별 API의 p99가 1%여도, 페이지 단위로는 5명 중 1명이 느린 경험을 한다.** 그래서 마이크로서비스 환경에서 꼬리 지연 관리가 특히 중요하다.

### k6 threshold — 합격 기준을 코드로

```javascript
export const options = {
  thresholds: {
    // 응답시간
    http_req_duration: ['p(95)<500', 'p(99)<1500'],

    // 에러율 — 1% 미만
    http_req_failed: ['rate<0.01'],

    // 처리량 — 최소 초당 100건
    http_reqs: ['rate>100'],

    // check 통과율
    checks: ['rate>0.99'],

    // 특정 그룹만
    'http_req_duration{group:::결제}': ['p(95)<1000'],

    // 시나리오별
    'http_req_duration{scenario:buyers}': ['p(95)<1200'],

    // 커스텀 메트릭
    'order_creation_time': ['p(95)<800'],
  },
};
```

**threshold 를 넘으면 종료 코드 99** 로 끝나서 CI가 실패한다. 1편에서 확인한 내용이다.

**즉시 중단 옵션**도 있다. 스트레스로 서버를 죽이지 않으려면 유용하다.

```javascript
thresholds: {
  http_req_failed: [
    { threshold: 'rate<0.05', abortOnFail: true, delayAbortEval: '1m' },
  ],
},
```

`delayAbortEval` 은 초반 워밍업 구간의 오차 때문에 조기 중단되는 것을 막는다.

### 커스텀 메트릭 — 비즈니스 관점 측정

HTTP 응답시간만으로는 부족할 때가 있다.

```javascript
import { Trend, Rate, Counter } from 'k6/metrics';

const orderTime = new Trend('order_creation_time', true);   // true = 시간 단위
const orderFailRate = new Rate('order_fail_rate');
const ordersCreated = new Counter('orders_created');

export default function () {
  const start = Date.now();
  const res = http.post(`${BASE}/api/orders`, payload);
  const elapsed = Date.now() - start;

  // 비즈니스 성공 여부는 HTTP 200 과 다를 수 있다
  const body = res.json();
  const businessOk = res.status === 201 && body.status === 'PENDING';

  orderTime.add(elapsed);
  orderFailRate.add(!businessOk);
  if (businessOk) ordersCreated.add(1);
}
```

**`businessOk` 가 핵심이다.** 서버가 200을 주면서 실패를 알리는 경우가 흔하다.

```json
HTTP 200 OK
{ "success": false, "message": "재고가 부족합니다" }
```

**`http_req_failed` 는 이걸 실패로 세지 않는다.** 트랙 2에서 다룬 "에러율 0%인데 장애"가 성능 테스트에서도 그대로 일어난다. 커스텀 Rate 메트릭으로 잡아야 한다.

### 결과 해석 — 판단 흐름

```text
1. 에러율부터 본다
   0% 가 아니면 → 성능 수치는 신뢰할 수 없다
   실패한 요청은 대체로 빨리 끝나서 p95 를 좋게 만든다  ← 함정

2. 처리량이 목표에 도달했는가
   VU 를 올렸는데 RPS 가 안 오르면 → 이미 포화 상태

3. 응답시간 분포를 본다
   p50 과 p95 의 차이가 크면 → 일부 요청만 느림
   p95 와 p99 의 차이가 크면 → 꼬리 지연 문제

4. 구간별로 쪼갠다
   http_req_waiting 이 대부분 → 서버 처리
   http_req_blocked / connecting → 커넥션 문제
   특정 group / endpoint 만 느림 → 그 기능의 문제

5. 서버 리소스와 대조 (트랙 2)
   CPU 포화 → 스케일 아웃 또는 코드 최적화
   메모리 증가 → 누수 의심
   DB 커넥션 포화 → 풀 크기 또는 쿼리
   CPU 여유 있는데 느림 → I/O 대기, 락, 외부 API
```

**1번의 함정이 실전에서 자주 걸린다.**

```text
VU 500 결과
  http_req_duration p(95) = 210ms   ← 좋아 보인다
  http_req_failed = 43%              ← 그런데 절반이 실패

→ 실패한 요청은 커넥션 거부로 5ms 만에 끝났다.
  성공한 요청만 보면 p95 가 3초였을 수 있다.
→ 에러율이 높으면 응답시간 지표는 의미가 없다.
```

**5번이 QA 혼자 못 하는 부분이다.** 트랙 2의 대시보드를 인프라·개발팀과 함께 본다. 성능 테스트가 협업 활동인 이유다.

### 병목 판단 표

| 관찰 | 유력한 원인 | 확인 방법 |
|---|---|---|
| VU 늘려도 RPS 정체 + 응답시간 선형 증가 | 처리 용량 포화 | CPU, 스레드 풀 |
| 응답시간은 그대로인데 에러 급증 | 커넥션·큐 한계 | 커넥션 풀, 큐 길이 |
| p99만 주기적으로 튐 | GC 또는 배치 | GC 로그, 크론 |
| 특정 엔드포인트만 느림 | 쿼리 또는 외부 API | 슬로우 쿼리 로그, APM |
| 시간이 갈수록 느려짐 | 누수 | 메모리·커넥션 추이 |
| 첫 요청만 느림 | 콜드 스타트, 캐시 | 워밍업 여부 |
| DB CPU는 낮은데 쿼리가 느림 | 락 경합 | 락 대기 조회 |

### 리포팅 — 숫자를 결정으로 바꾸기

**"p95가 480ms입니다"로 끝나면 아무 일도 안 일어난다.** 트랙 1의 Go/No-Go 언어로 옮긴다.

```text
[나쁜 보고]
  부하 테스트 결과 p95 480ms, 에러율 0.3% 입니다.

[좋은 보고]
  목표 트래픽(동시 500명)에서 p95 480ms 로 기준(500ms)을 통과했습니다.
  다만 세 가지를 보고합니다.

  1. p99 가 2.4초입니다. 100명 중 1명이 2초 이상 기다립니다.
     원인은 결제 API 의 외부 PG 호출로 보이며, waiting 이 95% 를 차지합니다.
  2. 스트레스 테스트에서 700 VU 부터 에러율이 급증합니다.
     현재 오토스케일 임계치가 800 VU 라 늦습니다. 600 으로 낮출 것을 제안합니다.
  3. 부하를 걷어낸 뒤 정상 복구까지 4분 걸렸습니다.
     실제 장애 시 트래픽이 줄어도 즉시 회복되지 않습니다.

  릴리즈 가능 여부: 목표 트래픽 기준 Go.
  단, 프로모션 트래픽(예상 3배)에는 대응 불가하므로
  프로모션 전 오토스케일 조정이 선행되어야 합니다.
```

**세 가지가 좋은 보고의 요소다.** 기준 대비 판정 / 원인 추정과 근거 / **행동 가능한 제안**.

### 성능 회귀 감지 — 절대값보다 변화

한 번 측정하고 끝나면 의미가 절반이다. **이전 대비 나빠졌는가**를 봐야 한다.

```text
릴리즈    p95     p99    에러율   RPS
3.2.0    380ms  1.1s    0.02%    420
3.3.0    390ms  1.2s    0.02%    418
3.4.0    520ms  2.8s    0.05%    390   ← 여기서 무슨 일이?
```

**절대 기준(500ms)만 보면 3.4.0에서 처음 실패한다.** 하지만 추세를 보면 **3.4.0에서 뭔가 바뀌었다**는 게 명확하고, 그 릴리즈의 변경사항을 뒤지면 원인을 빨리 찾는다.

k6 결과를 파일로 남겨 추이를 관리한다.

```javascript
// handleSummary 로 커스텀 리포트 생성
export function handleSummary(data) {
  const p95 = data.metrics.http_req_duration.values['p(95)'];
  const p99 = data.metrics.http_req_duration.values['p(99)'];
  const errRate = data.metrics.http_req_failed.values.rate;

  return {
    'stdout': textSummary(data, { indent: ' ', enableColors: true }),
    'results/summary.json': JSON.stringify(data, null, 2),
    'results/trend.csv': `${__ENV.VERSION},${p95},${p99},${errRate}\n`,
  };
}
```

**`handleSummary` 가 CI 연동의 핵심**이다. 4편에서 파이프라인으로 엮는다.

## 왜 채용시장이 요구하는가

- 면접 단골: **"평균 대신 p95를 보는 이유가 뭔가요?"** — 예시 숫자로 설명할 수 있어야 한다.
- **"에러율이 높으면 응답시간 지표를 신뢰할 수 없다"** 는 함정을 아는 사람은 많지 않다. 실제로 측정해 본 사람의 통찰이다.
- **HTTP 200인데 비즈니스 실패**를 커스텀 메트릭으로 잡는 것은 트랙 2와 이어지는 관점이고, 강한 인상을 준다.
- **숫자를 Go/No-Go 언어로 옮기는 능력**이 QA와 성능 엔지니어를 가른다. 측정은 도구가 하고, 판단은 사람이 한다.
- **AI에게 결과 해석을 시키면 에러율을 먼저 확인하지 않고 응답시간부터 해석한다.** 그리고 근거 없이 "성능이 양호합니다"를 붙인다. 트랙 1의 품질 리포트에서와 같은 문제다.

## 실습 과제

### 과제 1 — 평균의 거짓말 실증 (12분)

k6로 응답시간이 크게 흩어지는 상황을 만든다.

```javascript
// test.k6.io 의 빠른 엔드포인트와 느린 엔드포인트를 섞는다
export default function () {
  if (Math.random() < 0.05) {
    http.get(`${BASE}/contacts.php`);      // 느린 쪽 (5%)
  } else {
    http.get(`${BASE}/`);                   // 빠른 쪽 (95%)
  }
}
```

결과에서 avg / med / p(90) / p(95) / p(99) / max 를 모두 기록하고 비교한다.

| 지표 | 값 | 이 숫자만 보면 어떤 판단을 하게 되는가 |
|---|---|---|
| avg | | |
| med | | |
| p(95) | | |
| p(99) | | |
| max | | |

### 과제 2 — threshold 설계 (15분)

본인 도메인 서비스를 가정하고 threshold 세트를 작성한다.

```javascript
thresholds: {
  // 전체
  // 화면별
  // 시나리오별
  // 비즈니스 메트릭
}
```

각 항목에 **왜 그 숫자인지 근거를 주석으로** 단다. 2편에서 배운 근거 출처를 쓴다.

그리고 **일부러 실패하는 값**으로 바꿔 실행해 종료 코드가 99인지 확인한다.

### 과제 3 — 비즈니스 성공률 메트릭 (15분)

**HTTP 200인데 실패인 상황**을 처리하는 스크립트를 작성한다.

1. 커스텀 `Rate` 메트릭으로 비즈니스 성공률 측정
2. `http_req_failed` 와 값이 다르게 나오는 상황 만들기
   (응답 바디에 `success: false` 가 오는 목 서버를 쓰거나, 조건부로 실패 판정)
3. 두 지표를 나란히 놓고 차이 확인
4. threshold 를 비즈니스 성공률에 걸기

**이 차이를 못 보면 "성능은 정상인데 아무도 주문을 못 하는" 상황을 놓친다.**

### 과제 4 — 에러율 함정 재현 (12분)

VU를 계속 올려 **에러율이 20% 이상 나오게** 만든다. (로컬에 띄운 작은 서버를 대상으로 — 공용 사이트에는 하지 않는다)

| VU | 에러율 | p(95) | 이 p95를 믿을 수 있는가 |
|---|---|---|---|
| | | | |

**에러율이 오르는데 p95가 오히려 좋아지는 구간**이 있는지 확인한다. 있다면 왜인지 설명한다.

### 과제 5 — 병목 판단 연습 (12분)

아래 결과를 읽고 병목을 추정한다.

```text
케이스 A
  VU 100 → RPS 95,  p95 =   210ms
  VU 200 → RPS 190, p95 =   230ms
  VU 400 → RPS 195, p95 = 1,980ms   ← RPS 정체, 응답 급증
  CPU 사용률 98%

케이스 B
  VU 100 → RPS 98,  p95 = 180ms, 에러 0%
  VU 200 → RPS 195, p95 = 190ms, 에러 12%
  CPU 사용률 35%

케이스 C
  1시간차 p95 = 200ms
  4시간차 p95 = 480ms
  7시간차 p95 = 1,100ms
  RPS 는 일정, CPU 는 일정, 메모리 우상향
```

각각에 대해: **원인 추정 / 확인 방법 / 개발팀에 할 질문**을 적는다.

### 과제 6 — 보고서 작성 (15분)

과제 2·4의 실제 결과로 **릴리즈 회의용 보고**를 작성한다.

포함할 것:
- 기준 대비 판정 (통과/미달)
- 우려사항 2~3개, 각각 원인 추정과 근거
- **행동 가능한 제안** (누가 무엇을 해야 하는가)
- Go/No-Go 의견과 조건

### 과제 7 — AI 결과 해석 검증 (12분)

과제 4의 결과(에러율 높은 케이스)를 AI에게 주고 해석을 요청한다.

| 확인 항목 | 결과 |
|---|---|
| **에러율을 먼저 확인했는가** | |
| 에러율이 높으면 응답시간을 신뢰할 수 없다고 지적했는가 | |
| 근거 없는 총평("성능 양호")을 붙였는가 | |
| p95와 p99를 구분해 해석했는가 | |
| 데이터에 없는 원인을 지어냈는가 | |
| 추가로 확인할 것을 제안했는가 | |

**첫 항목에서 대부분 걸린다.** AI는 주어진 숫자를 순서대로 해석하지, 신뢰성을 먼저 따지지 않는다.

## 자가 체크리스트

- [ ] 평균과 중앙값이 소수의 심각한 사례를 숨기는 과정을 예시로 설명할 수 있다
- [ ] p95, p99의 정확한 의미를 말할 수 있다
- [ ] 상황에 따라 어느 백분위를 볼지 선택할 수 있다
- [ ] `max` 를 기준으로 삼으면 안 되는 이유를 안다
- [ ] 꼬리 지연의 원인 7가지를 나열할 수 있다
- [ ] API 20개를 호출하는 페이지에서 p99 1%가 18%가 되는 계산을 이해한다
- [ ] k6 threshold 를 전체·그룹·시나리오·커스텀 메트릭별로 설정할 수 있다
- [ ] `abortOnFail` 과 `delayAbortEval` 의 용도를 안다
- [ ] 커스텀 Trend/Rate/Counter 메트릭을 만들 수 있다
- [ ] **HTTP 200인데 비즈니스 실패**인 경우를 별도 메트릭으로 잡는다
- [ ] 결과 해석 시 **에러율을 가장 먼저** 확인한다
- [ ] 에러율이 높으면 응답시간 지표를 신뢰할 수 없는 이유를 설명할 수 있다
- [ ] VU를 올려도 RPS가 안 오르면 포화 상태임을 안다
- [ ] p50/p95/p99 간 격차로 문제 유형을 추정할 수 있다
- [ ] `http_req_waiting` 비중으로 서버 처리 병목을 판단할 수 있다
- [ ] 병목 판단 표의 7가지 패턴을 원인과 연결할 수 있다
- [ ] 숫자를 Go/No-Go 언어와 행동 가능한 제안으로 옮길 수 있다
- [ ] 절대값뿐 아니라 릴리즈 간 추세로 성능 회귀를 감지한다
- [ ] `handleSummary` 로 결과를 파일로 남길 수 있다
- [ ] AI 결과 해석에서 에러율 미확인과 근거 없는 총평을 잡아낼 수 있다
