## 개념 설명

### 다섯 가지 유형과 각각이 답하는 질문

"성능 테스트를 돌린다"는 말은 너무 뭉뚱그린 표현이다. **무엇을 알고 싶은지**에 따라 완전히 다른 테스트를 설계해야 한다.

| 유형 | 답하는 질문 | 부하 패턴 |
|---|---|---|
| **스모크** | 스크립트가 제대로 동작하는가 | VU 1~2, 1분 |
| **부하 (Load)** | 예상 트래픽에서 목표 성능을 내는가 | 예상 최대치까지 올려 유지 |
| **스트레스 (Stress)** | 어디서 무너지는가, 어떻게 무너지는가 | 예상치를 넘어 계속 증가 |
| **스파이크 (Spike)** | 급증을 견디고 회복하는가 | 순간적으로 확 올렸다 내림 |
| **내구성 (Soak)** | 오래 돌리면 문제가 생기는가 | 보통 부하로 몇 시간~며칠 |

**가장 자주 빠뜨리는 것이 내구성 테스트다.** 그리고 메모리 누수·커넥션 누수는 이걸로만 잡힌다.

### 스모크 — 항상 먼저 한다

```javascript
export const options = {
  vus: 1,
  duration: '1m',
  thresholds: { http_req_failed: ['rate<0.01'] },
};
```

**부하가 목적이 아니다.** 스크립트가 올바른지, 엔드포인트가 살아있는지 확인하는 것이다.

트랙 3의 스모크 테스트와 같은 역할이다. **이걸 건너뛰고 500 VU를 걸면**, 스크립트 오타 때문에 30분을 날리고 서버에 의미 없는 부하만 준다.

### 부하 테스트 — 예상 트래픽에서의 성능

```javascript
export const options = {
  stages: [
    { duration: '5m',  target: 200 },   // 5분에 걸쳐 램프업
    { duration: '30m', target: 200 },   // 30분 유지  ← 여기가 측정 구간
    { duration: '5m',  target: 0 },     // 램프다운
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'],
    http_req_failed: ['rate<0.01'],
  },
};
```

**설계에서 중요한 것 세 가지**

1. **램프업을 급하게 하지 않는다.** 0에서 200으로 순간에 올리면 커넥션 풀·JIT 워밍업·캐시가 준비되지 않아 초반이 비정상적으로 느리다. 그 데이터가 p95를 오염시킨다
2. **유지 구간이 충분히 길어야 한다.** 최소 10분, 가능하면 30분. 짧으면 캐시 효과 때문에 실제보다 좋게 나온다
3. **측정은 유지 구간만 한다.** 램프업/다운 구간을 포함해 p95를 계산하면 왜곡된다

k6에서 특정 구간만 측정하려면 태그를 쓴다.

```javascript
// 유지 구간에만 태그를 붙여 나중에 필터링
import { Trend } from 'k6/metrics';
const steadyDuration = new Trend('steady_duration', true);

export default function () {
  const res = http.get(url);
  // __ENV.PHASE 를 스테이지별로 다르게 주거나, 시간 기준으로 판단
  if (isSteadyPhase()) steadyDuration.add(res.timings.duration);
}
```

간단하게는 **유지 구간만 따로 한 번 더 돌리는 것**도 방법이다.

### 목표 수치는 어디서 오는가

**"p95 500ms 미만"이라는 숫자를 QA가 마음대로 정하면 안 된다.** 근거가 필요하다.

```text
근거의 출처
  1. 명시적 요구사항 / SLA — 있으면 최고
  2. 현재 운영 지표 — 트랙 2의 모니터링에서 p95를 뽑는다
     → "지금보다 나빠지지 않을 것"이 최소 기준
  3. 비즈니스 임팩트 — 응답 1초 지연 시 전환율 하락 데이터
  4. 업계 관행 — 근거가 가장 약하다. 마지막 수단
```

**2번이 가장 실용적이다.** 운영 대시보드에서 현재 p95가 380ms라면, 목표를 500ms로 잡는 것에 근거가 생긴다.

**목표 트래픽도 마찬가지다.**

```text
동시 사용자 수 추정
  = 시간당 활성 사용자 × 평균 세션 시간(분) / 60

예) 시간당 12,000명, 평균 세션 5분
  = 12,000 × 5 / 60 = 1,000 동시 사용자
```

여기에 **피크 배수**를 곱한다. 프로모션·점심시간 같은 피크는 평상시의 3~10배가 흔하다.

### 스트레스 테스트 — 한계와 붕괴 방식

```javascript
export const options = {
  stages: [
    { duration: '3m', target: 200 },
    { duration: '3m', target: 400 },
    { duration: '3m', target: 600 },
    { duration: '3m', target: 800 },
    { duration: '3m', target: 1000 },
    { duration: '5m', target: 0 },
  ],
  thresholds: {
    // 스트레스에서는 threshold 를 실패 기준으로 쓰지 않는 경우가 많다
    // 어디서 깨지는지 보는 게 목적이므로 abortOnFail 을 끄거나 느슨하게
    http_req_failed: [{ threshold: 'rate<0.10', abortOnFail: false }],
  },
};
```

**스트레스 테스트에서 봐야 할 것은 통과/실패가 아니라 "무너지는 방식"이다.**

| 붕괴 방식 | 의미 |
|---|---|
| **응답이 서서히 느려짐** | 좋은 신호. 큐가 쌓이며 버티는 중 |
| 특정 지점에서 에러율 급증 | 한계점(knee point). 그 직전이 실제 수용량 |
| **완전히 응답 없음** | 나쁜 신호. 우아한 성능 저하(graceful degradation)가 없다 |
| 부하를 내려도 회복 안 됨 | **매우 나쁨.** 커넥션·스레드가 고갈된 상태 |

마지막 항목이 실무에서 가장 중요하다. **부하를 걷어냈는데 서비스가 안 돌아오면**, 실제 장애 시 트래픽이 줄어도 자동 복구가 안 된다는 뜻이다. 사람이 재시작해야 한다.

**한계점(knee point) 찾기**가 스트레스 테스트의 산출물이다.

```text
VU  200 → p95  180ms, 에러 0%
VU  400 → p95  240ms, 에러 0%
VU  600 → p95  420ms, 에러 0%      ← 여기까지 정상
VU  800 → p95 2,100ms, 에러 3%     ← 여기서 꺾인다
VU 1000 → p95 8,500ms, 에러 34%

→ 실제 수용 한계는 약 600~700 VU
→ 오토스케일 임계치를 500 VU 부근으로 잡는 근거가 된다
```

### 스파이크 테스트 — 급증과 회복

```javascript
export const options = {
  stages: [
    { duration: '1m',  target: 50 },    // 평상시
    { duration: '10s', target: 1000 },  // 급증! (프로모션 오픈)
    { duration: '3m',  target: 1000 },  // 유지
    { duration: '10s', target: 50 },    // 급감
    { duration: '3m',  target: 50 },    // ← 회복 관찰 구간. 절대 빼지 말 것
  ],
};
```

**마지막 구간이 이 테스트의 핵심이다.** 급증을 견디는 것보다 **끝나고 정상으로 돌아오는지**가 더 중요하다.

```text
확인할 것
  □ 급증 순간 에러율이 얼마나 튀는가
  □ 오토스케일이 작동한다면 몇 초 만에 반응하는가
  □ 급감 후 응답시간이 평상시 수준으로 돌아오는가
  □ 돌아오는 데 얼마나 걸리는가
  □ 큐에 쌓인 요청이 나중에 몰려 2차 부하를 만들지 않는가
```

**스파이크는 열린 모델로 하는 게 현실적이다.** 프로모션 오픈 순간엔 사용자가 응답을 기다려주지 않고 계속 새로고침한다.

### 내구성 테스트 — 시간이 드러내는 문제

```javascript
export const options = {
  stages: [
    { duration: '5m',  target: 100 },
    { duration: '8h',  target: 100 },   // 8시간 유지
    { duration: '5m',  target: 0 },
  ],
};
```

**여기서만 잡히는 문제들**

| 문제 | 증상 |
|---|---|
| 메모리 누수 | 시간에 따라 응답시간이 서서히 증가, 결국 OOM |
| 커넥션 누수 | DB 커넥션 풀 고갈, "too many connections" |
| 로그·임시파일 누적 | 디스크 가득 참 |
| 캐시 무한 증가 | 메모리 압박 |
| 세션·토큰 만료 처리 | 특정 시간 후 전부 401 |
| 배치와의 충돌 | 새벽 배치 시간에 성능 급락 |

**핵심은 "시간에 따른 추세"를 보는 것이다.** 평균값 하나로는 안 보인다.

```text
1시간차: p95 = 210ms,  메모리 1.2GB
3시간차: p95 = 280ms,  메모리 2.1GB
5시간차: p95 = 390ms,  메모리 3.4GB   ← 우상향 = 누수 의심
7시간차: p95 = 620ms,  메모리 4.8GB
```

k6 결과만으로는 부족하다. **트랙 2의 모니터링 대시보드를 함께 열어두고 서버 리소스를 관찰**해야 한다. 이게 성능 테스트에서 QA와 인프라 팀이 협업하는 지점이다.

**현실적 타협**: 8시간이 부담되면 2~3시간이라도 한다. 그것도 어려우면 부하를 올려 짧게 압축하는 방법이 있지만(가속 내구성 테스트), 시간 의존 문제는 재현되지 않는다.

### k6 시나리오 — 여러 워크로드를 한 번에

`stages` 는 하나의 패턴만 만든다. 실제 서비스는 여러 종류의 사용자가 동시에 있다.

```javascript
export const options = {
  scenarios: {
    // 대다수: 둘러보기만 하는 사용자
    browsers: {
      executor: 'ramping-vus',
      exec: 'browse',                    // 실행할 함수 지정
      startVUs: 0,
      stages: [
        { duration: '2m', target: 100 },
        { duration: '10m', target: 100 },
        { duration: '2m', target: 0 },
      ],
    },
    // 소수: 실제 구매하는 사용자
    buyers: {
      executor: 'ramping-vus',
      exec: 'purchase',
      startVUs: 0,
      stages: [
        { duration: '2m', target: 10 },
        { duration: '10m', target: 10 },
        { duration: '2m', target: 0 },
      ],
    },
    // 배치: 초당 고정 요청 (열린 모델)
    apiPolling: {
      executor: 'constant-arrival-rate',
      exec: 'pollStatus',
      rate: 50,                          // 초당 50건
      timeUnit: '1s',
      duration: '14m',
      preAllocatedVUs: 20,
      maxVUs: 100,
    },
  },
  thresholds: {
    'http_req_duration{scenario:buyers}': ['p(95)<1000'],   // 시나리오별 임계치
    'http_req_duration{scenario:browsers}': ['p(95)<500'],
  },
};

export function browse()     { /* 목록·상세 조회 */ }
export function purchase()   { /* 로그인 → 장바구니 → 결제 */ }
export function pollStatus() { /* 주문 상태 폴링 */ }
```

**이게 실전 워크로드 모델링이다.** 사용자 비율이 실제와 비슷해야 결과가 의미 있다.

**비율을 어디서 얻는가**: 트랙 2의 로그·분석 도구에서 **실제 엔드포인트별 호출 비율**을 뽑는다. 추측하지 않는다.

```text
운영 로그 분석 결과 (1시간)
  GET  /products         62%
  GET  /products/:id     23%
  POST /cart              8%
  POST /orders            4%
  기타                    3%
→ 이 비율대로 시나리오 가중치를 설정한다
```

### executor 선택

| executor | 모델 | 쓰는 곳 |
|---|---|---|
| `constant-vus` | 닫힘 | 고정 VU 유지 |
| `ramping-vus` | 닫힘 | **가장 많이 쓴다.** 램프업/다운 |
| `constant-arrival-rate` | 열림 | 초당 고정 요청. API·배치 |
| `ramping-arrival-rate` | 열림 | RPS를 점진적으로 올림. **스트레스에 적합** |
| `shared-iterations` | — | 총 N회를 VU들이 나눠 실행. 데이터 처리 |
| `per-vu-iterations` | — | VU마다 N회씩. 계정별 시나리오 |

**요구사항이 "초당 몇 건"이면 arrival-rate 계열을 쓴다.** VU 기반으로 초당 건수를 맞추려고 계산하는 건 잘못된 접근이다.

## 왜 채용시장이 요구하는가

- 면접 질문: **"부하 테스트와 스트레스 테스트의 차이가 뭔가요?"** — 기본 중의 기본이고, 목적 차이로 답해야 한다.
- **내구성 테스트를 언급할 수 있으면 차별화된다.** 대부분 부하·스트레스만 말한다. 메모리 누수 이야기까지 하면 실무 경험이 드러난다.
- **"부하를 걷어냈는데 회복이 안 되는 것"** 을 위험 신호로 아는 것은 실제로 장애를 겪어본 사람의 관점이다.
- **워크로드 모델링을 실제 로그 비율로 한다**는 접근은 "숫자를 추측하지 않는다"는 QA다운 태도를 보여준다.
- **AI에게 "부하 테스트 스크립트 짜줘"라고 하면 대부분 `ramping-vus` 로 뭉뚱그린 하나를 만든다.** 유형 구분도, 회복 관찰 구간도, 여러 사용자 유형도 없다.

### 과제 2 — 한계점 찾기 (18분)

스트레스 테스트를 실제로 실행해 한계점을 찾는다.

```javascript
stages: [
  { duration: '1m', target: 10 },
  { duration: '1m', target: 30 },
  { duration: '1m', target: 60 },
  { duration: '1m', target: 100 },
  { duration: '1m', target: 150 },
]
```

| VU | p(95) | 에러율 | RPS |
|---|---|---|---|
| 10 | | | |
| 30 | | | |
| ... | | | |

**꺾이는 지점**을 그래프로 그리고, 실제 수용 한계를 몇 VU로 판단할지 근거와 함께 적는다.

> 주의: `test.k6.io` 는 공용 연습 서버다. 과도한 부하는 자제하고 150 VU 이내로 한다.

### 과제 3 — 스파이크 회복 관찰 (15분)

스파이크 테스트를 실행하고 **급감 이후 구간**에 집중한다.

```text
□ 급증 순간 에러율 최고치
□ 급감 후 첫 정상 응답까지 걸린 시간
□ 평상시 수준으로 돌아오는 데 걸린 시간
□ 회복이 안 된 지표가 있는가
```

회복 구간을 **일부러 빼고** 다시 실행해 보고, 무엇을 못 보게 되는지 메모에 적는다.

### 과제 4 — 워크로드 모델링 (15분)

본인이 아는 서비스의 **실제 사용 비율**을 추정해 다중 시나리오를 설계한다.

1. 사용자 유형 3가지 이상 정의 (둘러보기 / 검색 / 구매 / 관리자 등)
2. 각 유형의 비율과 근거 (로그 데이터가 없으면 추정 근거를 명시)
3. `scenarios` 로 작성
4. 시나리오별 `thresholds` 설정 — **유형마다 기준이 달라야 한다**

**구매 흐름의 기준이 조회보다 느슨해야 하는 이유**를 적는다.

### 과제 5 — 목표 수치의 근거 만들기 (12분)

임의로 "p95 500ms"라고 쓰는 대신 **근거를 만드는 연습**을 한다.

| 항목 | 값 | 근거 출처 |
|---|---|---|
| 목표 동시 사용자 | | 시간당 활성 사용자 × 세션 시간 / 60 |
| 피크 배수 | | |
| p95 목표 | | 현재 운영 지표 or SLA |
| 에러율 허용치 | | |
| 처리량 목표 | | |

**"현재 운영 지표를 모른다"면 무엇을 누구에게 물어야 하는지** 적는다. 이것도 답이다.

### 과제 6 — AI 시나리오 설계 검증 (12분)

AI 실습 도우미에 요청한다.

> 이커머스 서비스의 성능 테스트 계획을 세우고 k6 스크립트를 작성하라.
> 블랙프라이데이 프로모션을 앞두고 있다.

| 확인 항목 | 결과 |
|---|---|
| 부하 유형을 구분해 여러 개 제안했는가 | |
| **스파이크 테스트를 제안했는가** (프로모션이므로 필수) | |
| 스파이크에 회복 관찰 구간이 있는가 | |
| 내구성 테스트를 언급했는가 | |
| 여러 사용자 유형을 모델링했는가 | |
| 목표 수치의 근거를 물었는가, 아니면 임의로 정했는가 | |
| 열린 모델(arrival-rate)을 적절히 썼는가 | |

**"목표 수치의 근거를 물었는가"** 가 핵심이다. AI는 대체로 "p95 500ms"를 근거 없이 제시한다.

## 자가 체크리스트

- [ ] 다섯 가지 부하 유형과 각각이 답하는 질문을 구분할 수 있다
- [ ] 큰 부하를 걸기 전에 스모크로 스크립트를 검증한다
- [ ] 램프업을 급하게 하면 초반 데이터가 p95를 오염시킨다는 것을 안다
- [ ] 유지 구간이 충분히 길어야 캐시 효과를 걷어낼 수 있음을 안다
- [ ] 목표 수치의 근거 출처 4가지를 알고 운영 지표를 우선 활용한다
- [ ] 동시 사용자 수를 활성 사용자와 세션 시간으로 추정할 수 있다
- [ ] 스트레스 테스트의 목적이 통과/실패가 아니라 붕괴 방식 관찰임을 안다
- [ ] 한계점(knee point)을 찾아 오토스케일 임계치 근거로 쓸 수 있다
- [ ] **부하를 걷어냈는데 회복 안 되는 것**이 가장 나쁜 신호임을 안다
- [ ] 스파이크 테스트에서 회복 관찰 구간이 핵심임을 알고 반드시 넣는다
- [ ] 내구성 테스트로만 잡히는 문제 6가지를 나열할 수 있다
- [ ] 내구성 테스트는 추세를 보는 것이고 서버 리소스 모니터링이 필요함을 안다
- [ ] `scenarios` 로 여러 사용자 유형을 동시에 모델링할 수 있다
- [ ] 사용자 비율을 추측하지 않고 실제 로그에서 뽑는다
- [ ] executor 6종의 특성과 열린/닫힌 모델 구분을 안다
- [ ] "초당 몇 건" 요구사항에는 arrival-rate 계열을 쓴다
- [ ] 시나리오별로 다른 threshold 를 설정할 수 있다
